# Core scheduling
#
# #1823: EXACT, and equal to `docker/backend/Dockerfile`'s `apscheduler==3.11.0`
# — the one deliberate exception to this file's floor convention. The backend
# validates a schedule by constructing the same `CronTrigger` this service will
# register ("reject exactly what the scheduler would", #1472), so a floor here
# lets the validator and the executor resolve DIFFERENT APScheduler versions and
# quietly re-opens the gap the contract exists to close. `astimezone()` — which
# re-resolves a pytz zone through `zoneinfo` — is the precise function whose
# behaviour caused #1823, so "same version both sides" is not a tidy-up.
#
# Nothing ties these two declarations together yet; keep them equal by hand when
# either moves.
APScheduler==3.11.0
croniter>=2.0.1

# Timezone handling
pytz>=2024.1

# #1823 portability floor for the tz database. APScheduler's `astimezone()`
# re-resolves a pytz zone through the stdlib `zoneinfo`, which reads the SYSTEM
# database first and falls back to this wheel only for keys the system lacks —
# so with `tzdata-legacy` installed in docker/scheduler/Dockerfile this is inert
# in production. It exists so the capability survives another silent base-tag
# migration (`python:3.13-slim` carries no codename pin) and holds on a
# non-Debian base. A FLOOR, matching this file's convention and the rationale in
# tests/requirements-test.txt (#1771): an exact pin freezes a stale IANA database.
tzdata>=2024.1
