### 16.5 System Manifest Deployment
- **Status**: ✅ Implemented (2025-12-18; resilient deploy 2026-07-23, trinity-enterprise#125)
- **Description**: Recipe-based multi-agent deployment via YAML manifest
- **Key Features**: Permission presets, shared folders, schedules, auto-start
- **Resilient deploy (trinity-enterprise#125)**: deploy is **best-effort by default** — a per-agent create failure is collected into `failed: [{name, short_name, template, reason, status_code}]` and the remaining agents still deploy; post-create configuration (folders/permissions/schedules/tags/view) is scoped to the created agents and each phase degrades to `warnings` instead of aborting. Response `status` is **five-valued**: `deployed` (all created) / `partial` (some failed, HTTP 200) / `failed` (none created, HTTP 500 with the full report as the body) / `valid` (dry-run, no blockers) / `invalid` (dry-run, blockers populated in `failed` — #1841). **`status` describes AGENT CREATION only**: a folder/permission/schedule/tag/start failure lands in `warnings[]` while `status` stays `deployed`, so a consumer that renders `status` without `warnings` can report a fleet as deployed when every schedule failed and nothing started. `strict: true` on the request restores abort-on-first-error, preserving the failing agent's original status code. Failure reasons are credential-sanitized + URL-userinfo-redacted + truncated at the exit point. A partial response warns that re-deploying the same manifest creates `_N`-suffixed duplicates (create mode never converges; reconciling a live system to its manifest is the separate apply verb, §16.5.4 — the first-run seeder §16.5.1 sidesteps the duplicates by never re-deploying: flag latch + existence backstop). The global `trinity_prompt` write only happens when at least one agent was created. Prerequisite for the fresh-install seed (§16.5.1, trinity-enterprise#124) and the UI manifest install (§16.5.2, trinity-enterprise#126).
- **Deploy orchestration home (trinity-enterprise#124)**: the full deploy pipeline (parse → validate → resolve → create loop → prompt → config phases → start) lives in `services/system_service.py::deploy_manifest(manifest_yaml, current_user, request=None, *, dry_run, strict, create_agent_fn=None)` — `routers/systems.py::deploy_system` is a thin HTTP wrapper (maps `status="failed"` → HTTP 500 JSONResponse; everything else passes through). `create_agent_fn=None` resolves lazily to the `routers/agents.create_agent_internal` **facade** (which injects `ws_manager`), so `agent_created` WS broadcasts are preserved on both the HTTP and seed paths.
- **Flow**: `docs/memory/feature-flows/system-manifest.md`

#### 16.5.1 First-Run Default System Seed (trinity-enterprise#124)
- **Status**: ✅ Implemented (2026-07-24)
- **Description**: On a genuinely fresh install, auto-deploy a bundled default system manifest so a new instance comes up with a running starter fleet — the multi-agent generalization of the Cornelius seeder (ent#107, §core-agent).
- **Seeder**: `services/system_seed_service.py`. `ensure_first_run_seeded()` is the single first-run pass both call sites use (`routers/setup.py` setup-completion background task; `main.py` lifespan safety-net gated on `setup_completed`, held via a module-level strong task reference): it resolves the **persisted first-run verdict** then runs the Cornelius seeder and the fleet seeder under that one decision. **#2215:** the whole pass runs under ONE cross-worker lock (`first_run_seed:provision`, TTL 900s, via the shared `SingleFlightLock` #1920 — unique per-acquire token + compare-and-delete release, fail-open) — the two inner seeder locks serialise each seeder only against itself, so one worker's slow Cornelius clone used to run concurrently with another's fleet deploy (the burst behind the SSH-port collision and any concurrent boot transient that latches `partial`); the loser skips the entire pass without touching any flag and retries on the next trigger.
- **Persisted freshness verdict (`first_run_fresh` system-setting)**: computed ONCE — `count_non_system_agents() == 0`, forced false when `cornelius_seeded=="true"` (an established ent#107-era install, including one whose agents were later deleted) — and stored durably. Both seeders consume it (`ensure_seeded(fresh=...)`; Cornelius falls back to its legacy internal count when `fresh=None`). Without this, the first seeder's own agents poison every later pass's count: a failed fleet deploy could never retry, and a failed Cornelius would self-mark seeded after the fleet lands.
- **Idempotency & safety**: durable `default_system_seeded` flag; Redis SETNX lock `system_seed:provision` (TTL 600s, fail-open) — acquired + released through the shared `redis_breaker_util.SingleFlightLock`, so release is **ownership-checked (unique per-acquire token + compare-and-delete)**, not the pre-#1920 constant-`"1"` + unconditional `delete` that could delete a *successor's* live lock (#1920); the lock/token is LOCAL to the seeding pass (never stored on the singleton), so two overlapping in-process passes can't clobber each other's ownership state; **existence backstop** inside the locked section — if any final `{system}-{short}` agent name is already reserved (`is_agent_name_reserved`, covers soft-deleted), the seeder converges the flag WITHOUT deploying (the deploy path has no 409 backstop: name collisions become `_N` suffixes, so a fail-open lock race would otherwise double-seed). Flag policy: `deployed`/`partial` → set (a partial fleet must never be re-deployed — that suffixes duplicates); `failed` (0 created) / exception / unreadable manifest → NOT set (retry next pass; nothing to duplicate). `default_system_seed_info` (JSON: manifest name, sha256, status, created/failed counts, seeded_at) is stored beside the flag for diagnostics and future curated-fleet upgrades (ent#137).
- **Manifest resolution**: `TRINITY_DEFAULT_SYSTEM_MANIFEST` env (read at call time, `strip()`ed; empty ⇒ unset) — a path to an operator manifest, or a disable sentinel (`disabled`/`none`/`off`/`0`/`false`); otherwise the bundled `config/manifests/default-system.yaml` (baked into the backend image AND bind-mounted via the `config/manifests` directory in both compose files — the dev compose `./src/backend:/app` mount shadows image COPYs, so the mount is load-bearing locally). An explicitly-set-but-unreadable override fails loudly (ERROR log + operator-queue alert) and does not fall back to the bundled manifest.
- **Bundled starter fleet**: the in-tree acme trio (`local:scout`/`local:sage`/`local:scribe`) deployed as the coherent team its CLAUDE.md content assumes — system name `acme`, shared folders, `permissions: preset: full-mesh`; **no schedules** (zero-credential installs must not accumulate failing cron executions), **no `prompt:`** (never mutates the platform-wide `trinity_prompt`). Content is data: ent#137's curated public fleet replaces the manifest without touching the mechanism. Footprint: a fresh install runs `trinity-system` + Cornelius + 3 starters (limits, not reservations); operators opt out via the disable sentinel.
- **Honest status**: partial/failed seeds, seed-path errors (e.g. a parse-broken override), unreadable overrides, crash-interrupted partial fleets detected by the converge backstop, and — #2215 — a failed **Cornelius** creation (`create_failed`/`create_blocked`, or the belt-except when the seeder raises despite never-raises; id `system-seed-cornelius-failed`, previously log-only) all emit a platform-path operator-queue alert (direct DB create on `trinity-system`, deterministic `system-seed-*` id — a #1632 reserved prefix so an agent cannot pre-create-and-silence it; best-effort) in addition to logs.
- **Fail-open**: the seeder never raises and never blocks boot or setup completion.
- **Flow**: `docs/memory/feature-flows/system-manifest.md` (seed section)

#### 16.5.1a First-Run Front Desk (trinity-enterprise#319)
- **Status**: ✅ Implemented (2026-08-18)
- **Problem**: seeding (§16.5.1) made the onboarding wizard's own freshness test permanently false. `Dashboard.vue::maybeAutoOpenOnboarding` fires only when there are **zero non-system agents**; since a fresh install now comes up with Cornelius plus the bundled fleet already running, the ent#52 "one question → a tailored agent" wizard stopped auto-opening on exactly the install it was written for. The user meets a running fleet they did not choose and no route into anything.
- **Surface**: `components/onboarding/FrontDeskPanel.vue` + `stores/firstRun.js` — a dismissible, non-gating card on the Dashboard offering the three doors: **Show me** (opens the seeded demonstrator's chat — zero commitment), **Make me one** (emits to the existing wizard), and **Bring mine**, deliberately a de-emphasised secondary link rather than a peer button (fleet migration is the strongest capability and the worst first impression). It is a **surface, not an agent** — the issue's original "seed nothing, ship a front-desk agent" premise was reversed when trinity-enterprise#322 was closed not-planned; what a fresh install contains belongs to trinity-enterprise#137.
- **Predicate** (`GET /api/onboarding/first-run` → `services/onboarding_service.py`): `first_run` is true while every agent the caller can see is one Trinity seeded. The seed is deployed **under the admin account**, so it is indistinguishable from a human admin's own work in `audit_log` — an actor-based test cannot answer this. The seeded set is instead derived at read time from the seeder's own naming contract: `system_seed_service.seeded_agent_names()` (`{system}-{short}` from the manifest actually in force, honoring `TRINITY_DEFAULT_SYSTEM_MANIFEST` and its disable sentinels) plus `CORNELIUS_AGENT_NAME`. Read-time derivation, so no new persisted state, no migration, and an operator seeding their own manifest gets their own names.
- **DB-only read**: visibility comes from `db.get_all_agent_metadata` (owner/shared/is_system), NOT the Docker-backed `get_accessible_agents` — the question is about ownership rows, so the card renders truthfully when a container is down.
- **Two surfaces never stack**: the card requires `seeded_agents` to be non-empty, so a genuinely empty install (seeding disabled) still gets the wizard's auto-open, unchanged. Dismissal is per-browser `localStorage` (`trinity_front_desk_dismissed`), matching the wizard's existing key.
- **Fails toward silence**: any read failure resolves to `first_run: false`. A missed nudge is a non-event; a first-run card over a mature fleet is noise no user can dismiss on the install's behalf.
- **Gating**: OSS-core, un-gated — this is the open install's front door.
- **Superseded as a surface (ent#581)**: the card is absorbed into the first-run overlay's `agent` step (§16.5.1b). The predicate, the endpoint and `stores/firstRun.js` survive; the card, its dismissal getter and the "two surfaces never stack" rule do not — there is one surface now.

#### 16.5.1b First-Run Overlay (trinity-enterprise#581, epic ent#54)
- **Status**: 🚧 In progress
- **Problem**: five first-run surfaces from five issues (hardening guide #2380, front desk ent#319, activation checklist ent#238, finish-setup card #2381/ent#437, onboarding wizard ent#52) rendered inline in the Dashboard flow. #2380 stopped them stacking, but each still reflowed the page and dismissing one revealed the next — four dismissals deep on a fresh droplet.
- **Surface**: ONE blocking overlay, `components/onboarding/FirstRunOverlay.vue`, teleported to `<body>` over a Dashboard that never reflows: a 940px two-pane card (rail + content), a fixed-height panel whose body scrolls. It absorbs `HardeningGuide` (step `secure`), `FinishSetupCard` §1 (`email`) and §2 (`sharing`), `FrontDeskPanel` + the wizard intro (`agent`), and the wizard's credential step (`claude`, content per ent#582), plus a new `keys` slot (ent#582). `ActivationChecklist` stays inline by design — it tracks first-value milestones over days, and a blocking sequence would turn a progress marker into a gate.
- **FR-1 — registry, not a list**: steps are a registry with predicates in the pure module `components/onboarding/firstRunSteps.js` (node-testable; no `.vue` imports). Each step has an **eligible** term (who it is for) and a **pending** term (is there still something to do); `applies = eligible && pending`. Order is fixed (secure · email · claude · keys · agent · sharing); membership is not. Welcome and done are chassis bookends, not registry steps.
- **FR-2 — auto-open**: only after the flags document (successfully fetched), `/api/users/me` and `/api/onboarding/first-run` have all landed. Then: opens when a **state-derived** step applies and is not skipped — `secure` (admin, provenance-eligible, no domain), `email` (admin, no email bound), `claude` (admin, no Claude credential), `sharing` (admin, undecided, not hard-disabled), `agent` (the server first-run flag). `keys` rides along and never opens the overlay on its own. An established fleet (Claude configured, email set, telemetry decided, a domain, an agent of one's own) never sees it. A failed flags fetch reads as "not ready", never as "Claude is not configured".
- **FR-3 — completion is derived, never stored**: a step reads done when its predicate goes false after a refresh (domain saved, email bound, credential configured, consent decided, first agent created), or when the step emitted `complete` this session (the only way `keys` reads done). Only "Finish later"/"Done" (`trinity_first_run_closed`) and per-step skips (`trinity_first_run_skipped`) persist, per browser. A dismissal given to a card this replaces is honoured as a skip of the step that absorbed it, so an upgrade does not re-ask.
- **FR-4 — blocking**: `claude` is the only required step; Continue stays disabled until it emits `complete` or no longer applies. Every optional step has a Skip that names where to find it later (the real Settings tab). "Finish later" is always reachable and closes behind an explicit confirm that states the consequence; `Esc` raises the same confirm; there is no close button and the backdrop does not close it.
- **FR-5 — no duplicate asks**: anything `/setup` already collected (admin email, product-updates consent) is never asked again — the `email` step's predicate is false once an email is bound, so it is absent from the sequence.
- **FR-6 — re-openable**: `?onboarding=1` and Settings → General → **Re-run setup** open the sequence over every step this user is *eligible* for, with completed steps still showing complete and skipped ones recoverable.
- **FR-7 — design**: semantic tokens only, `Base*` primitives, both themes, focus trapped with initial focus on the safe action, rail collapses to a progress strip under 640px, `prefers-reduced-motion` freezes the constellation. The only new compositions are the rail, the welcome manifest, the constellation and the step schematics (`schematics/Schematic.vue`, inline SVG on `currentColor`). `TrinityMark.vue` is the one copy of the logo, shared with `/setup`.
- **Gating**: OSS-core, un-gated — it replaces OSS surfaces (the ent#54 precedent).
- **Tests**: `src/frontend/tests/unit/firstRunSteps.spec.js`, `hardeningGuide.spec.js`, `telemetryConsent.spec.js`

#### 16.5.2 UI Manifest Install (trinity-enterprise#126)
- **Status**: ✅ Implemented (2026-07-30)
- **Description**: Install a whole multi-agent system from the web UI — pick a bundled manifest, upload a file, or paste YAML; preview it; deploy it. Exposes the already-shipped `POST /api/systems/deploy` capability, which was previously reachable only via curl or the MCP `deploy_system` tool.
- **Surface**: a third stacked `<section id="systems">` on the **Library** page (`views/Library.vue`), between Agent Templates and Skills — no new NavBar entry. Shipped first as a `?tab=` strip on `Templates.vue`; ent#263 then renamed that page to Library and deliberately chose stacked sections + in-page anchors over tabs/filter pills, so ent#126 adopts the page's own model instead of competing with it. Systems sits beside Agent Templates because both **install agents** (one template = one agent; one manifest = a fleet with its permissions, schedules and folders wired), with Skills last as the kind that configures agents that already exist. Hidden entirely below `creator` rather than shown-and-disabled. `/templates` still redirects to `/library` preserving query **and** hash. Components in `components/systems/` (`SystemInstallPanel` / `ManifestPreview` / `DeployResult`) over the new domain-scoped `stores/systems.js` (Invariant #6; NOT bolted onto `systemViews.js` — a System is a manifest-deployed name-prefix group, a System View is a saved tag filter).
- **Bundled-manifest catalog (read-only)**: `GET /api/systems/manifests` and `GET /api/systems/manifests/{manifest_id}` in `routers/systems.py`, both `require_role("creator")` mirroring `POST /deploy` (AC #6; also rejects connector principals). Served from `config/manifests/` (already bind-mounted `:ro` into the backend in both compose files) via `TRINITY_MANIFESTS_DIR`, read at call time. **Both routes are declared above the parameterized routes (Invariant #4) for TWO collisions**: `/manifests` vs `GET /{system_name}`, and `/manifests/manifest` vs `GET /{system_name}/manifest`. Naming adjacency: `/api/systems/manifests` (bundled catalog) and `/api/systems/{name}/manifest` (export a **deployed** system as YAML) read alike and are unrelated. Not exported over MCP (Invariant #13) — a UI affordance; `deploy_system` already exists there.
- **Catalog semantics**: `valid` means parse + validate + the same side-effect-free template/resource preflight the dry-run runs — `parse_manifest` alone accepts invalid names, unsupported template prefixes and bogus presets, so a parse-only check would mark an undeployable manifest valid. Listing is **fail-soft per file** (an unreadable/oversized/invalid manifest is listed with `valid: false` + a short `reason`, never a 500 for the whole catalog — one bad file must not hide the others; every `reason` exits through `_failure_reason`, the same credential-sanitizing, URL-userinfo-redacting, length-capping exit the deploy report's `failed[].reason` uses, because PyYAML parse errors **echo the offending source line** and a joined blocker list grows with the manifest), and reports `already_deployed`, `sets_prompt` and `schedule_count` so the UI can warn before the user commits. Path confinement on `{manifest_id}` is layered: character allowlist, **explicit** rejection of `""`/`.`/`..`/embedded `..` (the regex does NOT reject these — `.` is inside its character class), a length cap, a suffix that is ours by construction, `resolve()` + `is_relative_to` (a symlink escaping the directory), and an `is_symlink()` check on the **unresolved** entry (a symlink whose target stays *inside* it — `resolve()` has already erased the link, so this must precede it). That last layer is catalog/read **parity**: `list_bundled_manifests` skips symlinks outright, so without it a symlink is invisible in the catalog yet readable by id, and "not listed" stops meaning "not served". Reads open once with `O_NOFOLLOW` and `fstat` that descriptor, capping at `MANIFEST_MAX_BYTES + 1` — `config/manifests` is a host bind mount, so a stat-then-read sequence has a real swap window.
- **Extended dry-run preview (AC #2)**: the response gains `permission_edges` ({source: targets}), `schedules_preview` ([{agent, short_name, name, cron, message, enabled, timezone, description}]) and `system_view_requested`. Both preview blocks are computed by **pure resolvers shared with the writers** — `resolve_permission_edges` / `resolve_schedule_previews` in `system_service.py`, which `configure_permissions` / `create_schedules` now loop over — so the preview cannot drift from what deploy does. Only the backend knows the resolved `_N`-suffixed names, so this cannot be derived client-side. `permissions_configured` / `schedules_created` deliberately stay `0` on a dry run: they mean "written". Behaviour preservation for the two refactored writers is pinned by characterization tests captured green BEFORE the refactor (`tests/unit/test_ent126_{permission,schedule}_characterization.py`) — a resolver-vs-refactored-writer parity test would be tautological, and the ent#125 suite mocks both writers.
- **Resource preflight**: `_preflight_template` now validates **merged** resources through the create path's own `normalize_cpu`/`normalize_memory`, with the create path's own template-wins precedence. Previously it checked template shape only, so a manifest with an unusable resource value previewed `valid` and then failed 100% of its agents at create — a shipped bundled manifest carried `cpu: 1.0` and did exactly that. For a `github:` template the merge needs a network call the preview refuses to make, so the declared values are validated instead (can over-report if the remote template overrides them; documented, and the fix is harmless either way).
- **Honest reporting**: `status` is switched on, never the HTTP code (`partial`/`invalid` are 200; `failed` is 500 **with the full report as the body**, which a naive `catch` would discard along with the `failed[]` list AC #3 needs). Deploy result is headed "agents created", not "success", and `warnings[]` renders prominently. A manifest that sets `prompt:` (replacing the platform-wide `trinity_prompt` for **every** agent) or carries enabled schedules (starting recurring autonomous executions) is gated behind an **explicit acknowledgement**, not a banner. `_N`-duplicate warnings are confirm-grade. A timeout or bare 5xx reports **"outcome unknown — may still be running"** and deliberately offers no retry, since cancelling the request does not cancel the serial server-side deploy and re-running duplicates every agent that succeeded.
- **Preview binding**: `preview` is bound to `previewedText` and Deploy is gated on them matching, so a user cannot preview manifest A, edit to B, and deploy B under A's preview.
- **Other guards**: manifests are capped at `MANIFEST_MAX_BYTES` (256 KB) — previously unbounded. The constant is defined **once**, in `models.py`, and imported by `system_service`, because the same number bounds two things that must agree about the same file: `parse_manifest`'s cap and the bundled-catalog file read (the request-model validator ent#126 originally added is gone — #1884 moved the cap into the parser, so an oversized manifest is a 400, not a 422). It is **byte-denominated at every one of them** (`len(encode("utf-8"))` / `st.st_size` / the UI's `file.size`) — a character-counting cap admits a multibyte manifest at up to ~4× the stated limit. Enforcement lives in `parse_manifest` alongside the alias-budget and duplicate-key guards (trinity#1884, which landed on `dev` during this branch's review and supersedes the request-model cap ent#126 originally added — an oversized manifest is now a 400 parse failure, not a 422 request-model violation). `parse_manifest` now records unrecognised top-level keys and `validate_manifest` **warns** about them (never rejects — that would 400 manifests deploying today); this is the durable guard for the class that let `trinity_prompt:`/`auto_start:` sit in a shipped manifest doing nothing. Keys are coerced with `str()` before sorting: PyYAML is YAML **1.1**, so bare `on`/`off`/`yes`/`no` parse as **booleans** and `2:` as an int — a mixed-type key set made `sorted` raise `TypeError`, and the catch-all turned it into a raw 500 on a manifest that deployed fine before the check existed, i.e. the hygiene check became the unnamed 500 it was added to prevent (AC #4). A **requested** system view that fails to create now appends a warning, since `create_system_view` swallows its exception and returns `None`, which was previously indistinguishable from "no view requested".
- **AC #5 (no dead end)**: deploy always tags every created agent with the system name, so `/?tags=<system>` always works as the next action, with `/?view=<id>` preferred when the manifest declared a `system_view:` and it was created. `views/Dashboard.vue` gained a small additive reader for both, yielding to an active system view.
- **Editor**: plain `<textarea>`. The orphaned monaco-based `components/YamlEditor.vue` (zero consumers since the Process Engine was decommissioned) was NOT revived: prod CSP is `script-src 'self'` with no `unsafe-eval` and no `worker-src` while the dev CSP allows `unsafe-eval`, so `npm run dev` cannot prove prod. Every AC is satisfiable without it.
- **Out of scope / deferred**: async deploy with a job id + reconciliation (the real fix for the timeout window — deploy is fully synchronous AND serial, so a large `github:` manifest outlives any client timeout); `SystemDetail.vue` / a deployed-systems browser; remote/registry manifest sources (ent#14, ent#108); per-agent credential setup after deploy (ent#127); `convergent`/`on_conflict` re-deploy semantics (delivered as the separate apply verb, §16.5.4; create mode is unchanged).
- **Flow**: `docs/memory/feature-flows/system-manifest.md`

#### 16.5.3 System Teardown (trinity-enterprise#454)
- **Status**: ✅ Implemented (2026-09-13)
- **Gating**: the teardown control plane is an **entitlement-gated module in the private submodule** — the route is absent (404) on an OSS or unentitled build, and `system_teardown` surfaces in `enterprise_features` only on an entitled one. This entry documents **only the public half** (the edition-agnostic membership primitive, the license-blind MCP proxy, and the Vue gate); the paid module's surface and internals are not in this repo.
- **Description**: deploy (§16.5) had no inverse. Removing a manifest-deployed fleet meant `DELETE /api/agents/{name}` once per member by hand — eleven times for the bundled flagship manifest — which is also why the install UI warned *"there is no un-deploy"* and why the duplicate-deploy trap (`_N`-suffixed copies) had no recovery path. Teardown is that inverse: preview the removal set, confirm it, then remove each member through the **existing per-agent soft-delete** (§33.1) — never a bespoke hard-delete.
- **Membership primitive (public, edition-agnostic)**: `services/system_service.py` gains `system_membership(system_name, agent_names) -> SystemMembership` (`members` / `tags_readable` / `evidence`), and `system_member_names()` becomes a **thin wrapper** returning `.members`. One body, one rule, one tag read — #2373's "THE ONE membership predicate" is still the only one, and a destructive verb does not get a fourth. The structured sibling exists because the `List[str]` return discarded the two facts a **destructive** consumer needs and `restart`/`get`/`export` do not:
  - `tags_readable` — the shared predicate deliberately **degrades to the raw prefix** when the tag read fails, which is the right ranking for `restart` (idempotent, and refusing would leave a broken fleet with no fleet-wide remedy during a DB hiccup). It is the wrong ranking for a verb that deletes, where over-capture removes an innocent agent's container. A consumer can therefore **refuse** on unverified membership instead of degrading, and rank the two errors at its own call site rather than forking the predicate.
  - `evidence` (`tag` | `prefix` | `both`) — *why* each name is a member, so a caller can show "matched by name only, not tagged by a deploy" and let the operator opt that member out. The documented residual of the prefix fallback (`acme` may capture `acme-extra-worker`) becomes visible rather than silent.
- **Auto-view description is one constant**: nothing persists a system↔view link — `create_system_view` marks the auto-created view only by its description plus the system tag in `filter_tags`. That literal is now `SYSTEM_VIEW_AUTO_DESCRIPTION` in `system_service.py`, shared by the writer and by any reader that has to find the view again, so the two cannot drift into two vocabularies for one fact.
- **MCP proxy tool (license-blind, Invariant #13)**: `teardown_system` is a public MCP tool in `src/mcp-server/src/tools/systems.ts` that proxies the gated route and reports whatever it says — a 404 (route absent, an OSS-only build) and an unentitled 403 are different operator situations, so it **degrades** to a distinct honest message for each instead of throwing (the `fetch_credential` precedent, §credentials 3.6). `dry_run` defaults **`true`** here, unlike `deploy_system`'s `false`: a model-driven call to a destructive fleet-wide verb is preview-first unless it explicitly says otherwise.
- **Vue gating**: a "Remove a deployed system" block on **Library → Systems** renders only when `enterprise_features` carries the id, on top of the section's existing `creator` gate (`canInstallSystems`). Preview → per-member checklist → acknowledgement → remove, reusing §16.5.2's `:acknowledged` + `update:acknowledged` contract rather than a second pattern — under its own `data-testid="teardown-ack-checkbox"`, because install and remove can both be previewed on this one page and a shared address is two elements at one selector (strict-mode ambiguous for the existing spec's `getByTestId('ack-checkbox')`). The pattern is worth sharing; the address is not. Result tone switches on `status`, never the HTTP code (the §16.5.2 rule). System names are typed or arrive from the deploy result — **never** from `GET /api/systems`, which groups by last-hyphen prefix and so does not resolve through the predicate.
- **Honest install warning**: `ManifestPreview.vue`'s *"There is no un-deploy"* stays exactly true on an unentitled build and is reworded only when the id is present — the warning tracks the capability, rather than being retired on every edition because one edition gained the verb.
- **Roster completeness (review, 2026-09-13)**: the removal set is resolved over the caller's roster, and every sibling on this surface builds that roster from Docker containers — so an agent with a live `agent_ownership` row and no container (#1747: routine after a Phase 1c recovery, a prune, or a crash between the row write and container creation) was invisible to a verb that reports completion. Teardown supplements its roster from the ownership rows under the same access rule and shows such a member as `status: "no container"`. Safe only because of the #2196 tri-state reader: `agent_container_states()` distinguishes *Docker could not be asked* (`None`) from *asked, none there* (`{}`) — conflating them would make a denied socket soft-delete every row while its container kept running — so an unreadable Docker refuses (503, both paths) instead of answering the old, false `404 System not found`.
- **Recovery**: per-member semantics are the unchanged §33.1 soft-delete — 180-day window, name stays reserved, schedules frozen (the scheduler's due-query joins `deleted_at IS NULL`), recovery via `POST /api/admin/soft-deleted/agents/{name}/recover` (admin, metadata-only: the container is **not** rebuilt). Ephemeral ghosts route through their own hard-discard path and have **no** recovery window, which the preview states per member before anything is confirmed.
- **Out of scope**: converge / `on_conflict` re-deploy semantics (delivered as the separate apply verb, §16.5.4); capturing a system definition from the live fleet (trinity-enterprise#455); a deployed-systems browser (§16.5.2's deferral stands — names are typed or come from a deploy result).
- **Flow**: `docs/memory/feature-flows/system-manifest.md` (teardown section — public half; the gated module's own flow lives in the private tree)

#### 16.5.4 Apply mode: reconcile a live system to its manifest (trinity-enterprise#695)
- **Status**: ✅ Implemented (2026-10-27; the REST surface — the MCP surface is a separate requirement)
- **Description**: `POST /api/systems/deploy` (§16.5) can only create: re-sending a manifest whose agents exist builds a parallel fleet of `_N`-suffixed copies, so every caller that wants idempotence (the per-instance controller's `/apply`, CI provisioning) diffs against the live fleet by hand. `POST /api/systems/apply` is the reconcile verb: per declared member, **absent → create, present → update the declared fields in place, present but undeclared → report as drift**. It never suffixes (it never calls `get_next_agent_name`).
- **A sibling route, not a `mode` field on `/deploy`**: create mode keeps a zero-line diff (the route, `SystemDeployRequest`/`SystemDeployResponse`, `deploy_manifest`, `parse_manifest`, `validate_manifest`, the `resolve_*` resolvers, `_build_schedule_create`, `create_schedules`, the `configure_*` writers and the first-run seeder are untouched), and a build without apply answers **405** for the new path (it matches `GET /{system_name}` by path only) instead of silently running create, which is what an ignored `mode` field would do on an older server.
- **Gates**: `require_role("creator")` + `require_person` — persons only (a JWT session or the person's own `user`-scoped key). Agent keys are refused (403) before any read: on EXISTING agents apply reaches permission grants (human-only), another agent's schedules and the platform prompt, so deploy's agent-callable `capability_fence("agents.manage")` would be a back door to all three. Deploy keeps its own gates.
- **Request**: `{manifest: str, dry_run: bool = true}` with `extra="forbid"` — a stray `mode` or `strict` is a 422, never silently ignored. `dry_run` defaults **true** (the teardown precedent: a verb that mutates live agents previews unless told otherwise); `/deploy` keeps `false`.
- **Principles**:
  - **P-A** Apply never removes, disarms, recreates, restarts or stops an EXISTING member. The one container operation it can cause: a member it created in the same run is started through the platform's own start path, which may stop and recreate it once to take its declared resources — the same path create mode's start step already takes for a just-created member whose manifest `folders:` differ from its template's.
  - **P-B** A failed read is never "absent": any read or lock apply depends on that fails is a named, retryable blocker before any write (create's `create_schedules` fails open; apply fails closed).
  - **P-B2** "No writes" (dry run, refusals) means no write to fleet state: agents and containers, tags, permission edges, schedules, folder config, resource overrides, platform settings, system views, files, and the apply lock key. Request bookkeeping every authenticated request performs (the MCP key's `last_used_at`/`usage_count`) is outside it, as for create's dry run and every GET. A refusal found before the lock writes no lock key; one found under the lock wrote and released it.
  - **P-C** Plan blockers are all-or-nothing (any blocker refuses the whole run before a write); once writes start, a failed write is recorded per member and the run continues, counted from actual outcomes (the ent#125 honesty contract).
  - **P-D** One plan, two consumers: the dry run and the real run compute the plan with the same functions, and the real run executes the plan it re-computed under its lock. The one re-read: schedules of a member it has just created (the template materializes its own rows inside create), marked `pending_template_resolution` in the dry run.
  - **P-E** Create mode is not touched (above).
  - **P-F** Same manifest, same meaning where the modes overlap, with exactly three stated differences: (1) a template's same-named schedule on a member apply created is updated to the manifest's declared fields rather than skipped; (2) declared `resources` win over a template's as a per-agent override (create keeps template-wins); (3) only an admin may change the platform-wide `prompt:` (create lets any creator).
- **Order of a real run**: parse + validate (create's named 400s, `agents: {}` included) → lock-free snapshot + plan → blockers refuse with no lock key → `SingleFlightLock("system_apply:<name>", ttl=900)` (busy → `apply_in_progress`; Redis unreachable → `apply_lock_unavailable`; never fail-open) with a lease keeper from acquisition that renews every TTL/3 through **atomic, ownership-checked** compare-and-expire / compare-and-delete → snapshot + plan again under the lock (a blocker here refuses and releases) → ownership confirmed → execute → release. Any renewal result but owned raises a stop flag checked before every write and every start; later writes are `lock_lost`. Residual, stated: a concurrent create-mode `/deploy` of the same system is not under this lock.
- **Membership and evidence (AC5, literal)**: the roster is the tri-state container list UNION the live ownership rows, filtered by the manage predicate the name classification below uses (`can_user_share_agent` + `agent_may_reach(manage=True)`; never `get_accessible_agents`, which reads `[]` on a Docker fault), and goes through the one predicate `system_membership`. An agent merely shared with the caller is outside it: it can neither refuse the run with a remedy only its owner could follow nor appear as drift, and apply never writes to it. Unreadable tags → `membership_tags_unreadable` (503); unreadable Docker → `roster_unreadable` (503), and a declared name that then reads as free is `blocked`, never `create` (a name held only by a container cannot be seen); **any** member, declared or not, whose evidence is `prefix` (matched by name only, never tagged) → `membership_evidence_prefix_only` (409) naming each, with a remedy fitted to it — a declared member: add this system's tag with the additive `POST /api/agents/{name}/tags/{system}` (not `PUT`, which replaces the set); an undeclared one: tag it with this system's name if it belongs here, with its own system's name if it belongs to another (`acme-extra`), or rename it.
- **Each declared name is classified globally, never from the caller's roster**: taken (a container, `agent_name_is_taken`, or a reserved volume base) and a live agent the caller may manage (`can_user_share_agent` + `agent_may_reach(manage=True)`, the deploy-local predicate) → the specific checks (`member_is_system_agent`, `member_is_ephemeral`, `member_container_missing`, `member_claimed_by_another_system`) or reconcile; taken but not manageable (another user's agent, a soft-deleted name, a volume reservation) → one uniform `member_name_unavailable` with byte-identical detail, so the code never says anything about an agent the caller cannot manage, and no detail names an owner; not taken → create.
- **What is reconciled on an existing member**:
  - **Tags**: additive (`add_agent_tag`, compared lower/stripped as stored); extra tags are untouched and not reported. Never `set_agent_tags`.
  - **Permission edges**: desired = `resolve_permission_edges(full declared map)` minus self-edges, deduplicated (what `set_permissions` stores); each missing edge added with `add_agent_permission`; a live edge between two declared members that the desired set lacks (including all a `none` / `orchestrator-workers` preset would clear) is reported `permission_extra`, never removed. Never `set_agent_permissions` (it also drops peer skill grants, ent#662).
  - **Folders**: only the declared keys (`expose`, `consume`) are compared and written; `folders` must be a mapping of those keys to booleans, else `folders_invalid`. A member apply creates gets create's semantics (both keys, omitted → `false`).
  - **Resources**: a declared `cpu`/`memory` (validated by create's `normalize_cpu`/`normalize_memory`, else `resources_invalid`) whose value differs from the effective one (DB override → container label → default, the start path's order) is written as a per-agent override with `set_resource_limits`, passing the stored value for the key the manifest omits. Never restarted. `restart_required` is computed from the platform's own drift predicates (`check_resource_limits_match`, `check_shared_folder_mounts_match`), so a stored override not yet applied keeps reporting `restart_required: true` (verdict still `unchanged`) until the member restarts.
  - **Schedules** (see `requirements/scheduling.md` §10.16): matched by exact name; on a matched row only the declared keys that differ are written in place through `update_schedule` (`cron`, `message` always; `timezone`, `description` only when present), **never `enabled`** (a difference is reported `enabled_differs`); rows the manifest does not name are reported `schedule_undeclared` and untouched; nothing is ever deleted. A row apply creates goes through the shared `_build_schedule_create` (manifest `enabled` default true) as the agent's OWNER; an update runs as the invoker and is refused up front (`schedule_not_updatable_by_caller`) where `update_schedule`'s owner-or-admin gate would silently no-op. Every row apply creates or updates is validated with the scheduler's own cron/timezone parser.
  - **Template**: a different declared template is reported `template_differs` (never recreated). `kind` is create-only (nothing readable stores it).
- **Platform prompt**: written only when `prompt:` is non-empty, differs from the stored `trinity_prompt`, and the caller passes the settings route's admin gate; a non-admin creator gets `prompt: requires_admin` (a report, not a blocker); `prompt: ""` is `not_declared`. Running agents take a new prompt at their next start.
- **System view**: found among the views the caller can see (own or shared) by `SYSTEM_VIEW_AUTO_DESCRIPTION` + the system tag. None and requested → create; one → `unchanged` (name/icon/color/shared differences reported `view_differs`); more than one → `ambiguous`, a warning, no create.
- **Execution**: create absent members (the same `AgentConfig` create builds); tag each created member with the system tag first, so a later failure cannot leave it untagged-but-declared (if that tag write fails the report names it: the next apply would refuse it as prefix-only); every other write is filtered to members that exist, so nothing is ever written naming an agent whose create failed (`skipped_member_not_created`); then tags, edges, folders, resource overrides, schedules (a created member's against a fresh post-create read — if that read fails its schedules go to `failed[]`, never to an unfiltered create), prompt, view; then start each created member one at a time, never an existing one. After tags are written on any member the same thin `agent_tags_changed` broadcast the tags API emits fires (identifiers only). Residual, stated: a free name whose workspace volume is an unclaimed leftover (#1667) is invisible to the snapshot, so the dry run plans `create` and the real run's create refuses it (409), reported in `failed[]` — never suffixed.
- **Response** (`SystemApplyResponse`): `mode: "apply"`, `dry_run`, `system_name`, `status` — `valid` / `invalid` (dry run without / with blockers), `refused` (real run, blockers, nothing written), `applied` (every attempted write succeeded, including none planned), `partial`, `failed` (every attempted write failed); `members[]` (`verdict` create / update / unchanged / blocked; `changes[]` of `{field, action: write|report, code, current, desired, note}`; `restart_required`; `applied`) — a member whose only differences are reports is `unchanged`, because AC1 counts writes; `drift[]` (a `<declared>_<N>` name is noted as a suffixed copy from an earlier create-mode deploy that apply never removes — the recovery story); `blockers[]` (`{code, member, detail, remedy, retryable}`); `prompt` and `system_view` verdicts; `failed[]` (`{name, short_name, step, reason}`, reasons through `_failure_reason`; one `step` name per writer, whether the write was attempted or skipped: `create`, `tag`, `permissions`, `folders`, `resources`, `schedules`, `start`); `warnings[]`.
- **HTTP**: 400 parse/validate (create's detail text); 422 malformed body; 200 `valid`/`invalid`/`applied`/`partial`; 409 `refused` with any non-retryable blocker; 503 `refused` with only retryable ones; 500 `failed`. 409/503/500 carry the full report as the body. A run that reached execution writes one `CONFIGURATION`/`system_apply` platform audit row (an audit failure after writes is a warning, never a 500); a refused run writes none.
- **Codes**: blockers — `membership_tags_unreadable`, `roster_unreadable`, `member_reads_unavailable`, `apply_in_progress`, `apply_lock_unavailable` (retryable); `membership_evidence_prefix_only`, `member_name_unavailable`, `member_claimed_by_another_system`, `member_is_system_agent`, `member_is_ephemeral`, `member_container_missing`, `template_unresolvable`, `folders_invalid`, `resources_invalid`, `schedule_name_ambiguous`, `schedule_declared_twice`, `schedule_cron_invalid`, `schedule_timezone_invalid`, `schedule_definition_invalid`, `schedule_not_updatable_by_caller`. Reports (never blockers) — `enabled_differs`, `schedule_undeclared`, `template_differs`, `permission_extra`, `view_differs`, `prompt_requires_admin`, `pending_template_resolution`; in `failed[]` — `skipped_member_not_created`, `lock_lost`.
- **Field coverage**: every `SystemManifest` / `SystemAgentConfig` field and every schedule key `_build_schedule_create` reads is classified exactly once (reconciled / report-only / create-only / inert) in `system_service.APPLY_FIELD_CLASSIFICATION`; a new manifest key fails CI until it is classified.
- **Schedule identity seam**: matching lives only in `schedule_match_policy(declared_entry, live_rows) -> matched | missing | unlinked | ambiguous`, consumed by `resolve_declared_schedule_actions`; the executor consumes actions, never matches, so a declared-id policy (trinity-enterprise#694 / #1198) plugs in without touching a writer. Two live rows with one name refuse (`schedule_name_ambiguous`); a declared rename is a create plus the old row reported `schedule_undeclared`, still armed as it was.
- **Out of scope**: removal of anything (stays an explicit human act — §16.5.3); recreate on template drift; restarts; an `adopt` option that tags prefix-only members; a plan digest the real run checks; resolving `local:` template schedules inside the dry run; schedule identity (trinity-enterprise#694).
- **Flow**: `docs/memory/feature-flows/system-manifest.md` (Phase 4: Apply)

### 17.2a System-Emitted Task Completion Events (#1578)
- **Status**: ✅ Implemented (2026-07-17)
- **Priority**: Medium (P2) · `theme-reliability`
- **Description**: The **backend** deterministically emits `agent.task.completed` / `agent.task.failed` at **every CAS-won execution terminal**, delivered over the existing EVT-001 subscription-dispatch machinery, so a subscribed caller/orchestrator is **woken** when a long async task finishes instead of polling `get_execution_result`. Implements the missing half of `TARGET_ARCHITECTURE.md` §Async-First Communication and is a down-payment on Epic #1045 → #1081 (pull coordination).
- **System- vs agent-emitted**: EVT-001 (17.2) carries only **agent-emitted** events (an agent's LLM calls `emit_event`). These are the first **system-emitted** events — synthesized by the deterministic backend chokepoint with no LLM in the loop, `source_agent` = the executing agent, in the reserved `agent.task.*` namespace.
- **Key Features**:
  - Emitted from a single shared helper (`services/event_dispatch_service.py::emit_task_terminal_event`) fanned across **every** CAS-won terminal writer — `apply_result` (success + failure), `_write_terminal_and_gate` (timeout/budget/crash), the #1083 lease-reaper (`cleanup_service`), and the pull sink (`pull_coordination_service`, dark until a pilot). Bulk watchdog sweeps are a documented residual (no per-row context).
  - **Matching-subscription gated**: `find_matching_event_subscriptions` runs FIRST — zero matching subscriptions ⇒ **no** `agent_events` row and **no** dispatch (inert by default, no fleet-wide spam).
  - **CAS-won exactly-once**: emit runs strictly inside the `won` branch, so a replayed/late #1083 callback or a lease-expiry race fires nothing (no double-wake).
  - **Payload** `{execution_id, status, triggered_by, summary_or_error, duration_ms, cost, fan_out_id, loop_id}` — flat + `{{payload.field}}`-interpolable; `status` is the string value (`success`/`failed`/`cancelled`). `fan_out_id`/`loop_id` carried for the future pull fan-out join envelope.
  - **Reserved namespace + loop safety (3 layers)**: agents cannot `emit_event` into `agent.task.*` (400); self-subscription to `agent.task.*` is blocked at create + update (400); and a **recursion-break** — a task spawned by an `agent.task.*` dispatch is persisted with `triggered_by="event"` and the emit helper suppresses re-emission, breaking self / A↔B / A→B→C→A auto-emit cycles at the root.
  - **Delivery** = EVT-001 subscription dispatch (loopback async `/task`). Best-effort: wakes a **running** (incl. #1402 parked-but-running) subscriber; a stopped subscriber's 503 is swallowed (the `agent_events` row persists, the wake does not). Durable "lands in the caller's queue" is the pull migration's future queue.
  - **Fail-open**: the entire emit body is try/except-swallowed — a broken/slow emit never affects the billed terminal.
- **Additive & inert**: reuses `agent_events` / `agent_event_subscriptions` and the existing `triggered_by` TEXT column — no schema change, no migration, no feature flag, no new config.
- **GitHub Issue**: #1578 (Epic #1045 → #1081)
