## 2. Authentication & Authorization

### 2.1 Email-Based Authentication
- **Status**: ✅ Implemented (2025-12-26, security-hardened 2026-03-26)
- **Description**: Passwordless email login with 6-digit verification codes
- **Key Features**: 2-step verification, admin-managed whitelist, auto-whitelist on agent sharing, rate limiting (IP-based + per-email OTP lockout after 5 failures)
- **Security**: OTP brute-force prevented by dual rate limits — the per-IP bucket `login_attempts_ip:{ip}` (shared with admin login) and `otp_attempts:{email}` (max 5 failures → 10-min lockout). Both `POST /api/auth/email/verify` and `POST /api/public/verify/confirm` are protected. (pentest 3.1.5 / #176)
- **Client address (trinity-enterprise#873, #3047)**: every per-IP bucket and every request-derived audit address is keyed on ONE canonical client address, resolved once per HTTP/WebSocket request by `utils/client_ip.py` before any route runs. Forwarding headers count only when the TCP peer is an explicitly trusted proxy — the bundled nginx and cloudflared at their reserved addresses on the prod/hosted ingress network, or an operator's `TRUSTED_PROXIES` entry — and only their authenticated right-hand suffix is read; a direct caller to the published backend port, an agent and the development Vite proxy are keyed on their own socket address whatever they send. Requirements:
  - Two clients behind the bundled proxy (Caddy, Cloudflare Tunnel, nginx on :80, an operator proxy) get separate per-IP buckets; each bucket counts only its own client's attempts.
  - Thresholds, windows, key names (`login_attempts_ip:{ip}`, `login_attempts_acct:{account}`), success resets and the Redis-outage fail-open behaviour are unchanged (#591).
  - A trusted proxy that forwards no identity leaves the request keyed on that proxy's own address (shared bucket, logged once per interval); identity that is present but malformed, empty, duplicated or unresolvable is refused (HTTP 400 / WebSocket close 1008).
  - IPv6 clients are keyed by their full canonical address, as before; a client rotating addresses inside one prefix is bounded by the per-account bucket only. Prefix aggregation is a separate decision.
  - Covered consumers: `POST /api/token`, email request/verify, access request, the Workspace portal's sign-in requests, public-link lookups and verification, the `/setup` instance-ID claim, webhook/A2A/AAuth per-IP limits and audit `actor_ip`.
  - MCP inline sign-in (#848) keeps its account-only limits: requests the MCP server relays arrive from the MCP container and carry no end-user address.
- **Enumeration-safety (#186)**: `POST /api/auth/email/request` returns an **identical body + status** regardless of whitelist membership (`{"success": true, "message": "If your email is registered, you'll receive a code shortly"}` — no distinct message, no `expires_in_seconds`). The rate-limit path returns the **same generic 200** (never a 429 differential; suppression is WARN-logged server-side), and the verification email is dispatched **fire-and-forget** so the whitelisted path's latency matches the non-whitelisted/rate-limited paths — closing the body, status, and timing membership oracles (pentest 3.3.3).
- **Workspace hand-off (#4157)**: a platform account that signs in on the Workspace's code page (sent to `/login` by the #3922 ruling) enters ONE emailed code. After a correct portal code the 409 `platform_login_required` carries a one-time token — opaque, bound to the email, stored hashed in Redis, 5-minute TTL, single-use, never logged, never in a URL (the browser holds it in memory). `POST /api/auth/email/handoff` redeems it with exactly the checks of `POST /api/auth/email/verify` minus the code: door gates, login policy, per-account/per-IP and OTP buckets, allow-list re-check, audit, 2FA. A wrong portal code stays the uniform 401 and mints no token (#186); a reload falls back to a second code. Portal codes are not made redeemable at the platform door (#3983).
- **Flow**: `docs/memory/feature-flows/email-authentication.md`

### 2.2 Admin Password Login
- **Status**: ✅ Implemented
- **Description**: Password-based fallback for admin user
- **Key Features**: Bcrypt hashing, first-time setup wizard
- **Rate limiting (#591, client address per §2.1)**: per-account `login_attempts_acct:{account}` 5 fails / 15 min and per-IP `login_attempts_ip:{ip}` 30 fails / 5 min, the IP being the canonical client address described in §2.1. On an install with the bundled proxy that is the client the proxy saw; only when the proxy forwards no client identity (the `proxy_fallback` case, including a request that arrived on the legacy listener) does the bucket fall back to the proxy's own address.
- **Changing the password in the app** (#3825): `PUT /api/users/me/password` `{current_password, new_password}` — a signed-in session only (no MCP key), the current password required, the setup complexity rule, wrong current passwords capped at 5 per 15 minutes per account in their own bucket (not the login one), audited as `password_changed` / `password_change_failed` with no password material. Only an account that already has a password can change it; an email-only account gets 409 `no_password` and never gains one. A change signs every other session of the account out (per-user cutoff; the response carries the caller's fresh token), optionally revokes the MCP API keys the person created (keys are not sessions; the response says how many still work) and survives a restart: boot re-applies `ADMIN_PASSWORD` only when it differs from the value it last applied, so a NEW value in `.env` still rotates or recovers the password. Settings → General carries the form. Admin reset of another user's password is out of scope: no other account has a password.

### 2.4 Agent Sharing
- **Status**: ✅ Implemented
- **Description**: Share agents with team members
- **Key Features**: Share via email, access levels (Owner/Shared/Admin), sharing tab for owners
- **What a share grants (trinity-enterprise#820, operator ruling 2026-10-15)**: one flat grant, no tier column on `agent_sharing`. A share holder chats with the agent, sees their own conversations, and browses and edits the agent's files **except** credentials, runtime config and its instructions. On the Files surface that is ruled per verb by one policy (`services/file_path_policy.py`, vendored into the agent server):
  - **Owner tier** (the agent's owner or an admin, as a person): instruction files (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `GEMINI.md`, `.gemini/GEMINI.md`, `.claude/**` including skills), files that run code (`.gitconfig`, `.config/git/**`, `.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.local/bin/**`), reading credential/secret-class files (ent#819), listing hidden or credential directories.
  - **Refused for every caller**: writing or deleting credentials, runtime config, `.trinity`, git metadata at any depth (including bare-repo `hooks/` and `config`), system paths; deleting any `CLAUDE.md`.
  - **Agent keys** keep their capability path (`instructions.manage` ent#164, `skills.manage` ent#596) and are refused files that run code.
  - Below the owner tier the list withholds hidden files and flags each node with the verbs the caller cannot use; every write, delete and mkdir writes an audit row.
  - The Access tab states the grant in one sentence.
- **Suggesting people when adding one (trinity-enterprise#450, OSS-core)**: as an owner or admin types in the Access tab's add field, it suggests registered accounts that match by a prefix of the email or username, or a word of the name. It's a suggestion over the input: any address can still be typed and shared.
  - Never offered: people already on the roster, the agent's owner, the person typing, suspended accounts, accounts with no email. Channel clients can't appear, since the source is `users`.
  - Bounded, because the people offered are by definition not on the agent yet: at least 2 characters, at most 8 rows, 60 lookups a minute per person (`rate_limited`, 429). Signed-in session only (`require_interactive`): every key is refused. Each row is email and name; role only for an admin, so the list can't be used to find the admins.
  - **Known limit:** an owner can still find accounts on the instance by trying prefixes. The bounds slow that down and don't prevent it.
  - If the lookup fails or is limited, the field is the plain email input. A query with no match says so, and how to invite anyway.
- **Telling a pending person (trinity-enterprise#459, OSS-core)**: a share to an address with no account emails that person, and **Resend invite** on a Pending row sends it again. A share to someone with an account sends nothing.
  - The mail names who invited them and which agent, and points at the Workspace sign-in. It carries no code and no secret; they request their own code there.
  - Owner or admin, signed-in session only (`require_interactive`), matching share. Named refusals: `not_shared` (404), `not_pending` (409), `invalid_address` (422, anything but one plain address), `invite_unavailable` (409, no real provider or emailed codes are off for them), `invite_rate_limited` (429), `invite_not_sent` (502).
  - Limits, shared by both paths: 3 an hour per (agent, address) and 30 an hour per inviter, since sharing can now mail an address the owner typed. A refused call spends none.
  - A share always stands if the mail doesn't go: the response's `invitation` says `sent`, `not_needed`, `invalid_address`, `unavailable`, `rate_limited` or `failed`, and the panel says so. `console` counts as unavailable. Every attempt is audit-logged.

### 2.7 Shared Imperative Auth-Guard Family (INV-8, #1310)
- **Status**: ✅ Implemented (2026-07-17)
- **GitHub Issue**: #1310 (split from #654's architecture-invariant drift report; carved off from INV-14/#1308 **because it is security-sensitive**)
- **Requirement**: Architectural Invariant #8 ("Auth Pattern") — duplicated inline auth wiring (`db.can_user_access_agent` / `db.can_user_share_agent` → 403, and inline `role != "admin"` → 403) collapses behind shared helpers. Threshold: **≤5 bespoke in-scope non-exception sites**.
- **Description**: `dependencies.py` already carried the **path-dependency** factories (`AuthorizedAgent` / `OwnedAgent[ByName]`, uniform-404, #186) and the imperative fences (`_enforce_connector_scope`, `reject_agent_principal`). #1310 adds a small **imperative-guard family** — callable from any router body, for the sites where the agent name is *derived from a resolved resource* or the check is *composite* (a session/notification/execution row must be looked up before the agent name is known), where a path-dependency can't reach.

  | Helper | Wraps | Raises | Replaces |
  |---|---|---|---|
  | `assert_admin(user, *, detail="Admin access required")` | `_reject_connector_principal` + `role != "admin"` | 403 | inline admin checks + 4 router-local `require_admin` dupes |
  | `assert_agent_access(user, agent_name, *, detail="Access denied")` | `_enforce_connector_scope(owner_op=False)` + `db.can_user_access_agent` | 403 | inline `can_user_access_agent` → 403 |
  | `assert_agent_owner(user, agent_name, *, detail=…)` | `_enforce_connector_scope(owner_op=True)` + `db.can_user_share_agent` | 403 | inline `can_user_share_agent` → 403. **NOT delete-authorization** (see below) |
  | `assert_owns_or_admin(user, owner_id, *, detail="Not authorized")` | `user.id != owner_id AND role != "admin"` | 403 | strict-self-**or-admin** session gates (voice/chat) |
  | `assert_owns(user, owner_id, *, detail=…)` | `user.id != owner_id` (id-only, **no admin bypass**) | 403 | strict-self session gate (`public.py` public-link session detail) |
  | `assert_person(user)` / `Depends(require_person)` | `is_person_principal` (JWT or the person's own `user` key) + no `vouched_source_agent` | 403 `HUMAN_ONLY_DETAIL` | owner-tier grant routes (§2.8, #2996) |
  | `Depends(require_interactive)` | `reject_non_interactive_principal` (JWT only) + no `vouched_source_agent` | 403 | credential / sign-in identity mint, bind, rotate (§2.8) |
  | `assert_own_agent(user, agent_name, *, detail=…, refusal=None)` | the agent the key acts as — `agent_principal_name(user)`, or `trinity-system` for the system key — not in (None, `agent_name`) | 403 (or `refusal()`) | the hand-copied agent-key self-gates (§2.13, trinity-enterprise#840; the system key since trinity-enterprise#719) |

- **Preserve-403 (not 404).** All five raise **403** — access-first inline handlers are already *self-uniform* per INV-8 (they check access before any existence lookup, so there is no 404-then-403 enumeration oracle). The platform precedent is `schedules.py` `create_schedule` (#1445: "Access-check FIRST … no 404-vs-403 name-enumeration oracle"). The clean `{agent_name}`-path sites *could* have adopted the uniform-404 path-dependencies, but were consciously kept 403 to minimize frontend blast-radius and hold **one** imperative convention.
- **Imperative vs path-dependency (when to use which).** Agent name **in the path** → prefer the path-dependency (`AuthorizedAgent[ByName]`/`OwnedAgent[ByName]`, uniform-404). Agent name **derived from a resolved resource** (notification/session/subscription/execution row) or a **composite** gate (owner-or-initiator, resource-404-then-access) → use the imperative helper. Both fences run `_enforce_connector_scope` first, so the two conventions enforce the connector boundary identically.
- **`assert_agent_owner` ≠ delete authorization.** It wraps `can_user_share_agent` (owner-or-admin) but does **NOT** carry the `is_system` guard that `can_user_delete_agent` (`db/agents.py`) does. A delete path must keep using the delete predicate — never reuse `assert_agent_owner` for delete.
- **Documented exceptions (permanent, not deferred).** `nevermined._require_read_access`/`_require_write_access` and `reports.get_report` stay on their own **intentional-404** helpers (#186 designs, enumeration-safe by construction). `sessions._session_or_404` stays a **compound uniform-404** (existence + user + agent binding in one `if`) — migrating it to `assert_owns` would regress 404→403 **and** leak session-id existence, so it is left as its own already-consolidated helper. `internal.py` is the INV-8 no-auth exception.
- **`slack.py` retired (#1710).** The 11 inline-auth sites #1310 deferred were migrated onto `assert_agent_access` (3 read) / `assert_agent_owner` (8 owner) — behavior-preserving (same 403 + `detail`; site #10's ent#223 human-only `reject_agent_principal` kept; trinity-enterprise#719 later made that inline check the `assert_person` allowlist its route decorator applies). No `# noqa: inv8` marker remains in the tree; a re-introduced inline gate now trips the static guard unless it carries a freshly-added, individually-reviewed marker.
- **Static guard**: `tests/unit/test_1310_auth_wiring.py` — a precise AST matcher forbids `db.can_user_access_agent(` / `db.can_user_share_agent(` Call-nodes whose negation guards a `raise HTTPException`, and inline `role != "admin"` deny-`If`s, in `routers/` (per-function allowlist; `# noqa: inv8` line-exemption retained for a future, individually-reviewed exception — none in-tree after #1710). Filter/capability/allow-branch sites (assignments, `role == "admin"` selection, WS-`close(4003)` dict handlers) are **not** flagged.
- **Behavioral proof**: `tests/unit/test_1310_auth_consolidation.py` (real-DB `db_harness`) locks status + detail + admitted-principal set per migrated site; `test_186_enumeration_uniformity.py` extended for the five helpers.
- **Flow**: `docs/memory/feature-flows/role-model.md`

### 2.8 Human-Only Grant Surfaces (INV-8, #2996 / trinity-enterprise#711)
- **Status**: ✅ Implemented (2026-09-28)
- **GitHub Issues**: #2996 (autonomy toggle), trinity-enterprise#711 (sign-in email rebind), trinity-enterprise#717 (the manual whitelist grant)
- **Problem**: `get_current_user` resolves an agent-scoped or system-scoped MCP key to its **owner, carrying the owner's role**. #1890 made the admin gates refuse agent keys; the **owner** tier (`can_user_share_agent`, `assert_agent_owner`, `OwnedAgentByName`) and the self-service routes (`get_current_user` alone) kept admitting them. The owner gates cannot simply refuse agent keys the way the admin gates do, because agents legitimately use owner-gated routes (MCP schedule tools, file writes). So the rule is applied per route, and a route census makes the next route choose a side.
- **Two principal rules** — both **allowlists** over `User.mcp_scope`, fail-closed on a principal without the attribute (sentinel, never `getattr(..., None)`), and each treats a backend-minted event-loopback JWT (`mcp_scope=None`) differently: PERSON refuses every loopback token outright (`is_person_principal` checks `is_event_loopback`, ent#751), while INTERACTIVE refuses only one carrying `vouched_source_agent`. For INTERACTIVE that second layer is not the only one: the backend also mints loopback JWTs without a source agent, and `require_interactive` does not refuse those; the `get_current_user` entry fence refuses **every** loopback JWT on every route but the subscriber-task dispatch (ent#614):

  | Rule | Admits | Refuses | Primitive |
  |---|---|---|---|
  | **PERSON** | JWT session; the person's own `user`-scoped key | agent, system, connector, portal_delegate, ops, ops_write, any future scope, a missing `mcp_scope`, a `user` principal carrying an agent/connector/delegate identity | `assert_person` / `Depends(require_person)` (predicate `is_person_principal`, ent#611) |
  | **INTERACTIVE** | JWT session only | every key | `Depends(require_interactive)` (predicate `is_interactive_principal`, #1854) |

  They are **credential-class** rules, not proof of human origin: a `user` key is the person's delegated credential, and a JWT counts as interactive only because non-human JWTs are fenced at `get_current_user`.
- **Assignment rule**: a route that **grants or changes what an agent may do** takes PERSON; a route that **mints, binds or rotates a credential or sign-in identity** takes INTERACTIVE — a minter must be stricter than the principal class it produces, or the PERSON rule is circular. **One ruled exception (2026-10-28, trinity-enterprise#719)**: writing a credential the caller supplies in the request into the caller's own agent takes PERSON — `POST /api/agents/{name}/credentials/inject` and `PUT /api/agents/{name}/github-pat`. The key holder already holds what it writes, and the public abilities toolkit's `/trinity:onboard` does both on the person's own `user` key (Step 5e `inject_credentials`; the tier-1 `set_agent_github_pat`). Agent and system keys stay refused. A route where the platform mints the secret and hands it back, restores a whole credential archive, binds a paid account, or binds a stored token the request does not carry (`POST .../git/bind-to-own-repo`) stays INTERACTIVE.

  | Route | Rule |
  |---|---|
  | `PUT /api/agents/{name}/autonomy` (#2996 — decides whether **unattended cron** fires; a manual `trigger_schedule` is not gated by autonomy) | PERSON |
  | `PUT /api/agents/{name}/{api-key-setting, capabilities, capacity}` | PERSON |
  | `PUT /api/agents/{name}/{read-only, resources, timeout, public-channel-model, guardrails}` | PERSON **or** an agent holding `agents.manage` (§2.9) |
  | `PUT /api/users/me/email` (ent#711) | INTERACTIVE |
  | `PUT` / `DELETE /api/users/me/github-pat` (a credential future agent creations inherit, ent#162) | INTERACTIVE |
  | `POST /api/agents/{name}/credentials/inject`, `PUT /api/agents/{name}/github-pat` (a credential the caller supplies, into its own agent; the ruled exception above) | PERSON |
  | `POST /api/agents`, only its `fork_to_own` arm with no token in the body: the creator's saved personal token becomes the new agent's (#3164). Every other creation is unchanged (trinity-enterprise#719) | INTERACTIVE; the arm answers 400 `FORK_PAT_REQUIRED` |
  | `POST /api/mcp/keys` (every scope), `POST /api/mcp/keys/ensure-default` | INTERACTIVE (security.md §20.10) |
  | `GET /api/mcp/keys` (trinity-enterprise#712 — the key inventory; no machine consumer) | INTERACTIVE |
  | `POST /api/agents/{name}/voice/start` (trinity-enterprise#595 — mints the voice socket's single-use ticket) | INTERACTIVE; the Workspace start (`/api/enterprise/client-portal/agents/{name}/voice/start`) applies the same `require_interactive` predicate to the platform user it already resolves, and stays a `portal` route |

- **WebSocket tickets name their surface (trinity-enterprise#595)**: every consumer of a single-use WebSocket ticket passes the exact scope it accepts — `/ws` takes `user`, the VoIP media stream `voip:{call_id}`, the voice socket `voice:{voice_session_id}` — and `consume_ticket` refuses any other scope after consuming it, so a ticket minted for one socket can never open another. The voice ticket is minted only by the two voice start routes above, from an interactive session.
  | `POST /api/settings/email-whitelist` (trinity-enterprise#717 — every role, the default `user` included: each whitelist role yields an interactive session at first sign-in, and `operator` and above can mint keys) | admin **and** INTERACTIVE |

- **Whitelist grants (trinity-enterprise#717)**: `POST /api/settings/email-whitelist` takes `Depends(require_interactive)` and keeps the handler's `assert_admin`, both before the request body is read, so a refused caller gets 403, never a validation 422, and no row is written or replaced. An admin's own `user`-scoped key and the `system` key pass the shared admin gate (#2323, unchanged) but not this route. A loopback JWT carrying a vouched source agent is refused by the route gate; every loopback JWT is refused on this route by the entry fence. Signed-in admins keep the same success body, duplicate wording, existing-account note and validation reasons.
- **Refusal**: 403. PERSON routes return `HUMAN_ONLY_DETAIL` (`{"code": "person_required", ...}`, the same machine code as ent#611's ask endings, whose own detail is unchanged); INTERACTIVE routes return `reject_non_interactive_principal`'s existing detail. The refusal depends only on the principal, never on whether the addressed agent exists, so answering 403 before a path's 404 is not an enumeration oracle (#186). Each refusal is also recorded (next bullet); the answer does not change.
- **Audit (trinity-enterprise#719)**: a refusal by `assert_person` / `require_person`, `require_interactive`, `reject_non_interactive_principal` or ent#611's `reject_non_person_principal` is recorded once. They raise `HumanOnlyRefused`, an `HTTPException` subclass, and one app handler (`error_handlers.human_only_refused`) writes an `authorization` / `human_only_refused` audit row, then answers with the handler the app registers for `HTTPException`, so the status, body and headers are unchanged. The row is filed against who was refused: an agent key as its agent, the system key as `trinity-system`, a vouched loopback as the agent it vouches for, the person's own `user` key as the person, any other key by its scope and key id, and a principal that names no agent and no key as the audit resolver's platform actor (`actor_type` `system`; the system key's row is `actor_type` `agent`, and both carry `actor_id` `trinity-system`); the key's owner rides as `actor_email`. It carries the routed path (with the path's own values: an agent name, an ask id, a preference key), the method, the route template, the rule and the detail's code; the path, the agent name and the request id are cut to 256 characters. It never carries the body or the query string. The handler copies one header into the row, the request id, which the app takes from an incoming `X-Request-ID` for every audit row (#905); `actor_ip` is `request.client.host`, the client address the app resolves for every audit row (§2.1, trinity-enterprise#873): behind a trusted proxy that forwards the client's identity it comes from the entry that proxy appended (with none, it is the proxy's own address), and it is never a value the caller chose unless the caller is itself a trusted proxy. At most one row is written per principal, method and route every 60 seconds in each worker process; an entry is never forgotten inside its window, a write that fails does not use it, and if the window ever fills, nothing new is recorded until entries expire, which is logged. An audit failure never changes the 403. A site that writes its own row for the refusal (the owner-tier file read's `file_read_refused`) gets no second one, and a check that catches the refusal as a predicate (`except HTTPException`) records nothing. The Workspace doors' own person checks (`PortalPrincipal.is_person`) and the human-only refusals outside this family (ent#69's agent-key denylist `reject_agent_principal` / `Depends(human_only)`, the org-chart and person-mention tag guards) raise a plain 403 and are not recorded by this handler. Test: `tests/unit/test_ent719_human_only_refusal_audit.py`, through the real app.
- **Still working**: the owner's `user` key and ops tooling on a `user` key keep the PERSON routes; the UI and CLI use JWTs everywhere; heartbeat, the result callback, reports and notifications do not use these gates; `trinity-system` keeps `require_admin` (#2323) and has no caller of the routes above.
- **Route census (the inheritance mechanism)**: `tests/unit/test_2996_human_only_routes.py` walks every `*.py` under `src/backend/` (`rglob`, `enterprise/` excluded — the private tree carries its own), every HTTP method (GETs included), both `@<router>.<verb>(...)` and `add_api_route(...)`. Each route must resolve to exactly one policy class: `person` / `interactive` (the Depends form, or the imperative call as the handler's **first** statement on its principal argument, with the name imported from `dependencies`), `admin_tier` (`require_admin` / `assert_admin`, counted and printed), `admin_widened` (an `allow_scopes` opt-in, listed per route), `portal` (`get_portal_principal`), `agent_callable_self` (the `assert_own_agent` self-gate recognised **and** listed with a reason, §2.13), `agent_callable_any` / `own_auth` / `delegated` (listed per route with the `METHOD /path` pinned and a reason; `agent_callable_any` also answers why a sibling agent may reach it), or `unclassified_at_freeze` — the frozen baseline `tests/unit/fixtures/human_only_route_baseline.json`. The baseline is **shrink-only**: exact count literal, stale entries fail, an entry that becomes gated must be removed. #### 2.9a Template-source bound for agent-created agents (trinity-enterprise#591)
- **Status**: ✅ Implemented (2026-11-06). OSS-core, ungated.
- **Problem**: `agents.manage` (and the grant-free ghost spawn) said *whether* an agent may create agents, never *what from*: any `github:owner/repo` its token can reach, any bundled template, or an uploaded archive. ent#591's other asks (no inherited `creator`, a declared capability, a non-builder refused at `POST /api/agents`, spawn lifecycle unchanged) are delivered by §2.9 (trinity-enterprise#164).
- **Rule**: one instance-wide allowlist, `system_settings['agent_creation_allowlist']` (a JSON array; no migration). **Empty = unbounded = the pre-#591 behaviour.** While it has entries, every **machine** principal outside `{JWT, user key, system key}` (the `ADMIN_GATE_SCOPES` allowlist; an absent scope is bounded) must create from a listed source — an `agents.manage` holder creating a durable agent and any agent spawning an ephemeral one alike. People and `trinity-system` are never bounded.
- **Entries**: `local:<name>` (a **bundled** template — a same-named upload in the deploy-local store never matches), `github:<owner>/*` (every repo of an owner), `github:<owner>/<repo>` (every branch and tag), `github:<owner>/<repo>@<ref>` (exactly that branch or tag, judged on what the build will really clone: the template's `@ref`, else `source_branch`, else `main` — except that a `fork_to_own` create, a copy of `main`, and a working-branch create (`source_mode: false`, which clones the repo's default branch) clone the default branch and so match only an unpinned entry). **A create admitted only by a pinned entry is made a source-mode (pull-only) create** when it left `source_mode` unset, so ent#705 cannot turn it into a working branch cloned from the default branch; an unpinned entry, when one also matches, takes precedence and changes nothing. Owner/repo compare case-insensitively, `local:` names and refs exactly. At most 100 entries of ≤200 characters; an invalid entry refuses the whole save (422 `invalid_template_sources`, one reason per entry).
- **Refused while the list has entries**: an out-of-list source, a blank (template-less) create, and an unrecognised template — 403 `template_source_not_allowed`; any upload (`POST /api/agents/deploy-local`) — 403 `template_upload_not_allowed`. Both bodies carry `allowed_sources` and tell the agent to use one or ask a person. A system deploy with any refused member refuses as a whole before anything is created (403 with `members[]`); its dry run lists each refused member in `failed[]` (status `invalid`). Every refusal writes one `template_source_refused` audit row (the agent as actor, the canonical source, never the raw string). Every check runs before any side effect: before the idempotency claim, the ghost pre-gates (spawn-rate token), archive extraction and the first member create. `POST /api/systems/apply` is person-only, so no agent key reaches it.
- **A create-time limit, not containment**: it governs which source the platform builds from. What an agent does with the created agent afterwards is governed by the other grants (`instructions.manage`, `skills.manage`), and a repo entry, pinned or not, is only as strong as who can push to that repo: a pin is a NAME, so anyone with push access can move a pinned branch or create a branch named like a pinned tag (git and the create's validation resolve the branch first). Protect the pinned name on GitHub (branch protection or tag rulesets) for a pin to hold against an agent that can push.
- **Surfaces**: Settings → Agents → *Template sources for agent-created agents* (admin). `GET /api/settings/agent-creation-allowlist` (admin): `entries`, `bounded`, `stored_invalid`, `not_bundled`, `hidden` (listed bundled templates marked `hidden: true`: creatable, but absent from `GET /api/templates`, so no `allowed_for_agents` entry shows them), and `in_use` — the templates live agent-created agents use, each allowed or refused under the saved list. `PUT` (admin **and interactive**, audited `agent_creation_allowlist_change`); `[]` clears it. The generic `PUT`/`DELETE /api/settings/{key}` refuse the key. Agents read the bound through `GET /api/templates` (`allowed_for_agents` per entry, agent keys only, while a list is set) and the refusal body. A stored value that is not a list bounds agents to nothing; a list with bad entries keeps the valid ones (fail closed per entry), and the panel says so. A refusal against a damaged row says the saved list could not be read and that agents stay limited until an admin saves it again (`list_unreadable: true`), never "X is not on the list".
- **Upgrade effect**: none (no row = unbounded).
- **Tests**: `tests/unit/test_ent591_template_source_bound.py`; `src/frontend/tests/unit/agentCreationAllowlistPanel.mount.spec.js`.

### 2.10 Workspace-Only Rung (ROLE-002, trinity-enterprise#837)
- **Status**: ✅ Implemented. PR 1 is OSS core (the floor, sign-in routing, sharing); PR 2 adds the role on the Access-tab row, a platform account before the first sign-in, and assigning a `user` to a companion.
- **GitHub Issue**: trinity-enterprise#837 (ruled 2026-10-07: no new role)
- **Rule**: platform role `user` means *a member who works with agents through the Workspace*. The operator UI starts at `operator`. `ROLE_HIERARCHY` and `VALID_ROLES` are unchanged. A role that is not in the hierarchy ranks below `user` and is Workspace-only too (fail closed).
- **The floor**: `get_current_user` is the door every operator route authenticates through (`CurrentUser`, `AuthorizedAgent*`, `OwnedAgent*`, `require_role`, `require_admin`, `get_optional_user`, `get_user_or_anonymous` — OSS and enterprise). It refuses a Workspace-only principal with `403 {"code": "workspace_only", "message": "This account works in the Workspace. Open /workspace."}`, except:
  - an **interactive session** (the SPA's JWT) on a route marked `@workspace_route("<reason>")` — an operator-side route the Workspace itself calls (session identity, sign-out, the `/ws` ticket, preferences, loops, the voice canvas, an `authorized` canvas link, the public chat page's history). A key, even the person's own `user`-scoped one, does not pass: a key scripts the Workspace through its own doors;
  - an **agent** principal whose owner is Workspace-only, on its own runtime surface (reports, notifications, self-info, its own asks, the skill-gate check; heartbeat and result delivery authenticate elsewhere), with any `{name}` in the path equal to its own name. An agent never exceeds its owner; everything else it did is refused until an admin raises the owner's role (there is no ownership transfer; the agent's key also stays bound to the account that minted it).
  The refusal depends only on the principal and the route, never on whether an addressed agent exists (Invariant #8).
- **Workspace doors** resolve the credential through `resolve_platform_user_unfloored` (every scope fence, no floor): `get_portal_principal`, the rooms principal and the Workspace voice start. A guard pins that caller set. The rooms door still refuses an agent whose owner is Workspace-only (rooming with the owner's agents is agent-to-agent chat). A Workspace-only member's roster is unchanged: agents shared with them, plus any they own.
- **WebSocket doors**: `/ws/events` and the agent terminal refuse a Workspace-only principal. `/ws` needs a ticket from the marked `POST /api/ws/ticket` (browser session only); its events are scoped to accessible agents (ent#467) and, for a Workspace-only account, to the kinds the Workspace reads (`WORKSPACE_WS_EVENT_TYPES`), each cut to the fields it reads (`WORKSPACE_WS_EVENT_FIELDS`): the operator queue, notifications, reports, room triggers, the agent lifecycle and the sharing events never reach a member's socket, and neither do an activity's prompt or reply previews.
- **Account state on socket doors** (abilityai/trinity-enterprise#863): every socket door (`/ws`, `/ws/events`, the agent terminal and the system-agent terminal) applies the same account-state checks as an HTTP request, so a deactivated account (`users.suspended_at` set, #995) is refused at connect. The two terminals authenticate through the shared socket decoder `decode_token`, which applies the check itself, so a future socket door that uses it inherits the rule. Reactivating the account (clearing the column) admits it again.
- **Connector keys** of a Workspace-only owner pass the floor on the two routes the ent#46 fence already confines them to (the bound agent's chat and playbook list), so the agent's external consumers keep working.
- **An event-stream key's agent list follows access changes** (abilityai/trinity-enterprise#863): a non-admin `/ws/events` socket re-reads its agent list from the key owner's current account when access changes (an agent shared, unshared, created, deleted or renamed) and on the `refresh` command. An owner that is gone, deactivated or Workspace-only reads as an empty list. Every non-admin `/ws` and `/ws/events` agent list on a worker is also re-read about once a minute, so a live list follows the database within that interval. A change that lands while a list is being read is followed by one more read of it, and the earlier read is not applied. Admin sockets are never filtered and are not re-read automatically.
- **Live connections follow the account** (abilityai/trinity-enterprise#863): an open `/ws` event socket and an open `/ws/events` event stream close when the account's access changes, and the client reconnects at the new scope. The comparison is one rule: what the door read when the connection opened against the account's current row. A change of role (raised or lowered), email or password closes with `4000` (the browser reconnects with a fresh ticket); a deactivated or removed account, or an event stream whose key is revoked or deleted, closes with `4001` (no reconnect). A role change, a password change, and the revoke or delete of an MCP key close at once: on the worker that served the change, and on every other worker through a control event on the event bus that no client ever receives. Revoking or deleting a key closes only the event streams opened with that key, not the owner's other connections. Each worker also re-checks its own open connections every 15 seconds, so a change made anywhere, by any writer, reaches every worker within about that interval while the database is readable. A re-check that cannot read the database keeps the connections open and logs. A connection whose account changes while it is still opening is refused and reconnects.
- **Terminals follow the account too** (abilityai/trinity-enterprise#863): an open agent terminal and an open system-agent terminal close under the same rule and on the same schedule as the event socket: at once on the worker that served a role change, and within about 15 seconds on every worker for a change made anywhere. The browser gets an error frame naming the reason (access changed, or access ended) and the socket closes with `4003`; the terminal does not reopen by itself, and opening it again checks the account afresh. A terminal closed this way also ends, best effort, the shell session it started in the agent container and the processes started from that session. A terminal whose account changes while it is still opening is refused the same way, and its shell is ended.
- **Shared canvases**: an `authorized` link recognises a Workspace session (someone the agent is shared with signs in to the Workspace, not at `/login`), limited to an agent on their roster and a `roster`-audience canvas; its "Sign in" goes through the Workspace and back.
- **Whitelist grants**: a deliberate grant replaces a row that sharing or an access-request approval wrote, so an admin can add such an email as `operator`; the form names an existing account's role, which only User Management changes. Adding an entry takes an admin's signed-in session whatever role it selects, `user` included; an API key gets 403 (trinity-enterprise#717, §2.8).
- **Other surfaces**: `/m` sends a signed-in member to the Workspace; the MCP server and `trinity init` report the `workspace_only` refusal instead of reading it as "no permission" or reporting success.
- **Inside the Workspace** a `user` keeps the team view — every canvas audience, the agent's whole activity (loop runs included), voice and model choice — because the Workspace resolves the account as a platform principal (`is_platform`). The narrower client view (`roster` canvases, their own work) is for people without an account. Nothing new is exposed: a `user` saw all of it on Agent Detail before #837.
- **Known limit — loops**: the marked loop routes keep their pre-#837 reach: a member lists every loop on an agent they can reach and may stop any of them (the starter, the owner or a share), and `start` takes the request's model and tools. Narrowing the Workspace rail to the person's own runs is a follow-up.
- **Sign-in routing (SPA)**: `/login` lands a `user` in `/workspace`, honouring `?redirect=` only for Workspace, shared-canvas, public-chat and terms (`/terms`, §2.13) paths. The router guard sends a `user` on any operator URL to `/workspace` (`/agents/:name/*` → `/workspace?agent=:name`); `/terms` is the one signed-in page outside the Workspace it leaves alone. A `workspace_only` 403 on an operator page refreshes the profile and moves the tab to `/workspace`. A platform session stays a Workspace session (ent#357); sign-out ends whichever credential is live (#2258).
- **Sharing**: `POST /api/agents/{name}/share` and access-request approval no longer write the login whitelist. A person an agent is shared with signs in to the Workspace with the emailed code. Existing sharing-sourced whitelist rows stay and yield Workspace-only accounts. The manual whitelist (now with a role picker), CLI self-signup and SSO first sign-in keep writing.

- **The role on the Access tab (AC5)**: for an admin whose role the server has verified, each other Active person on Agent Detail › Access has a role select (its accessible name says the role applies to every agent; one fixed-width slot per row, so the controls line up); an admin's own row stays read-only (the route refuses a self-change). ### 2.12 A Turn Is Held to What Its Person May Do (trinity-enterprise#926)
- **Status**: ✅ Implemented (operator rulings 2026-10-16 and 2026-10-19)
- **Rule**: an agent acts for whoever chats with it, so its own tools are held to that person's tier, decided by the platform from the execution row (a turn handed over by another agent is the exception below):
  - **owner** — the owner, an admin, or something set up at owner tier (a schedule rates as its creator): everything, as before;
  - **shared person** — the Files API's paths, no shell, no Gemini/Codex turn, no standing work (schedules, loops, reminders, events), reads of executions narrowed to their own;
  - **visitor** (Slack, Telegram, WhatsApp, a public link, voice, a paid call) — the Files API's share paths; the shell, Gemini/Codex and standing work while the owner's **"Channel and public visitors may run commands"** switch is on.
- **A turn one agent hands another (trinity-enterprise#1148)**: a turn an agent dispatches carries the person it acts for, and the callee rates it again. If that person can open the callee, they keep their own tier there. If they cannot open it at all, the callee runs the turn at its own owner tier — the callee does the caller's work, and the person only drove the caller — but only when the calling agent's owner is the callee's owner or an admin; otherwise it stays at the person's tier. A turn an agent hands itself (a self-task, a self fan-out) is never such a hand-off: it keeps the person's own tier on that agent, never the delegated owner tier. Any lookup that cannot be answered keeps the person's tier (fail closed). The callee's row still records the person and the calling agent, and the caller, acting for that person, cannot read that row when the person cannot open the callee. This is a platform-wide rule, not a per-agent switch.
- **A platform turn that continues another turn stands as it (trinity-enterprise#1225)**: the wake when a delegated run ends, the resume when an ask is answered, the wake when an ask is cancelled or expires, and the notice that a gated request was decided are rated exactly as the turn they continue: same tier, same person. A continuation of a shared person's turn has no shell and reads that person's rows; a continuation of the owner's work reads at the full view; a continuation of a turn another agent handed over keeps that turn's owner tier. The platform records the turn being continued only while it runs on the same agent; an id the agent writes itself is never used. A continued turn that can no longer be read (pruned, or another agent's) is held to a shared person with nobody behind it: no shell, no reads. One ending for asks raised by different turns is held the same way.
- **An optional module may rate a person the owner of one agent** (a provider registered with the turn-tier service): only on that agent, only that person's turns; their sign-in, their routes and their reach on every other agent are unchanged. Without a provider, nothing changes.
- **Owner setting**: `visitor_shell` in Settings › Guardrails (default **on**, so channel agents behave as before; saved immediately, applies to the next message, no restart). The switch's text states the trade-off: the shell reaches everything the agent can.
- **Every new route that names an agent declares its tier**; the default is owner, and CI fails on an undeclared route (`src/backend/services/agent_route_tiers.json`, also read at runtime: an agent's key acting for a shared person is refused every owner-tier route). Routes still at accessor tier only by the old default are a shrink-only list, ruled per route.
- **What a shared person will notice**: the agent refuses to run commands or edit its own instructions for them and says so; on a Gemini or Codex agent their message is refused with a reason naming what the owner can do; asking the agent to set a reminder or a schedule is refused.
- **Tests**: `tests/unit/test_ent926_turn_tier.py`, `test_ent926_turn_tier_hook.py`, `test_ent926_runtime_turn_scope.py`, `test_ent926_agent_key_turn_scope.py`, `test_ent926_agent_route_census.py`, `test_ent1148_delegation_tier.py`, `test_ent1148_ledger_columns_guard.py`, `test_ent1148_caller_reads_stay_person.py`, `test_ent1148_fleet_reads_stay_person.py`, `test_ent1148_fan_out_source.py`, `test_ent1225_continuation_tier.py`; `src/mcp-server/src/turn-context.test.ts`; `src/frontend/tests/unit/guardrailsVisitorShell.spec.js`
- **Architecture**: `architecture/security.md` §5f, §5g

### 2.13 Agent-Key Self-Gate (INV-8, trinity-enterprise#840)
- **Status**: ✅ Implemented (2026-10-23)
- **GitHub Issues**: trinity-enterprise#840 (triggered by trinity-enterprise#839, the seat-decisions route that shipped without the gate)
- **Problem**: an agent-scoped key resolves to its owner carrying the owner's role, so `AuthorizedAgent` / `assert_agent_access` answer "may this key reach that agent" — since ent#629 the agent itself, its permission-edge targets and the agents it spawned — never "is this key acting on its own agent". Every route an agent key may call that reads or changes one agent's state therefore needed a second check, copied by hand into ten modules, invisible to CI.
- **Rule**: one helper, `dependencies.assert_own_agent(current_user, agent_name, *, detail=…, refusal=None)` — 403 with the route's own `detail` when the principal acts as an agent other than the path agent: an agent key acts as its own agent, and the system key as `trinity-system` (trinity-enterprise#719 — the rule `get_self_acting_agent` already applies; its `mcp_scope` is read with a sentinel, so a test double is not the system key). A no-op for every other principal (person, `user` / connector key, event loopback). `refusal` builds the exception instead, for a router whose access dependency answers a uniform 404 so the two refusals stay byte-identical. Called as the handler's **first** statement (after the docstring); on a route with an access dependency it runs after that dependency, so a nonexistent or out-of-reach agent gets the uniform 404 and only an agent the key already reaches gets the 403, and on a route without one it runs before any lookup — either way the refusal discloses nothing new (#186).
- **Census classes** (§2.8): `agent_callable` splits in two.
  - `agent_callable_self` — **recognised and listed**: the handler's first statement is `assert_own_agent(<principal>, <agent>, …)` with the name imported unaliased from `dependencies`, `<principal>` a `Depends(get_current_user)` / `CurrentUser` parameter and `<agent>` the `name` / `agent_name` path parameter of every route decorator; or the signature takes `Depends(get_self_acting_agent)`. Each such route also has an `AGENT_CALLABLE_SELF` entry naming why it is a **use, not a grant** — the review the census exists to force: the gate alone never classifies a route. The reviewed reason, not a code check, is the guard: a self-scoped grant (an agent changing what it may do itself) that someone lists passes every check, as entries in the old `AGENT_CALLABLE` table did. A self-gated route with no entry, and an entry whose route carries no recognised gate, both fail.
  - `agent_callable_any` — listed in `AGENT_CALLABLE_ANY` with the reason it is agent-callable AND a separate written answer to "why may an agent other than the one in the path reach this" (a capability grant bounds it, the key itself names the agent, the handler authenticates the agent's own key, or a read inside the agent's reach).
- **Hand copies are refused**: `tests/unit/test_1310_auth_wiring.py` fails any inline comparison of a principal's agent name (attribute, `getattr`, `agent_principal_name`, or a local bound from one, also as an operand of `or` / `and` / `… if … else …`; the principal annotated `User` / `CurrentUser` in any form, defaulted `Depends(...)`, or unannotated and named like one) against a `name` / `agent_name` parameter or a local alias of one — `!=`, `is not`, `not in`, a negated `==`, or an `==` whose `else` refuses — that guards any `raise` or a returned 401/403/404, anywhere under `src/backend/` (allowlist: `aauth_person.assert_own_key`, the stricter own-key-only AAuth gate). Stated limit: a comparison against a differently-named parameter is not matched, so header checks such as `x_source_agent != current_user.agent_name` stay legitimate.
- **Converted** (behaviour-preserving, each module keeps its message): reminders (×3), seat decisions (×2), user memory, metric points, reports, canvas writes and deletes (×4), canon roles, objectives, shared files, voice reply, outbound A2A call and poll, and the Nevermined delegation read (its uniform 404 kept through `refusal=`) — and `get_my_ask` joins the two ask routes as a `get_self_acting_agent` fence. Three refusals change only for a caller refused either way: user memory now refuses an out-of-reach agent key with its self message (was "Not authorized", both 403); outbound A2A checks its kill switch as a dependency, so with the switch off a schema-invalid or missing body answers 404 (was 422; JSON that does not parse is still 422); and a test double whose `agent_name` is not a string (or that has none) is no longer treated as an agent key.
- **An admin's user key acts on behalf of an agent (trinity-enterprise#1024; operator ruling 2026-10-30: "admin user key should be able to do whatever it wants")**: every self-acting MCP tool — `ask_operator`, `get_my_ask`, `withdraw_ask`, `report`, `record_metrics`, `get_objectives`, `refresh_metric_definitions`, the five canvas tools and the fourteen project tools — takes an optional `agent_name`. `ask_for_credential` and the credential vault do not: credentials stay out of act-as. A user-scoped key passing it acts for that agent: the MCP sends `X-Trinity-Act-As-Agent`, and `get_current_user` (`dependencies.admit_act_as`) admits it only for a `user`-scoped MCP key whose user is an admin. Every other principal that sends it gets **403 `act_as_not_permitted`** naming why (agent, system, connector, portal_delegate, ops, anonymous, a non-admin user key, a browser session); a blank or >128-character name is **400 `act_as_invalid`**. An admitted request writes one audit row (`authorization` / `acted_as_agent`) naming both the acting user and the agent, and is held to that agent: `get_self_acting_agent` (the ask routes) and `assert_own_agent` (report, metrics, canvas) admit it on that agent's path only. An on-behalf ask's own `raised` / `withdrawn` / `replaced` audit row carries `acted_by: user:<id>`. The door's row is written at admission, before the route decides, so a request the route then refuses still has one, and its target is the header's agent. The header is read at `get_current_user`: `get_optional_user` turns its 403 into anonymous, and the Workspace doors never read it. An addressed report published while acting places no Workspace card. A user key without `agent_name` is refused naming the parameter; an agent or system key keeps acting as itself, and naming another agent is refused. No default "hub" agent is inferred when `agent_name` is omitted — nothing binds a person to one today.
- **The system key on self-gated routes (trinity-enterprise#719)**: it acts as `trinity-system`, so on every self-gated route it may act on `trinity-system` and gets the route's own refusal for any other agent; `POST /api/agents/{name}/emit-event` joined the self-gate in the same change, because delivery authorises each subscriber against the recorded source (trinity-enterprise#739); after the self-gate it admits only an agent key, the system key and a person (an allowlist over `mcp_scope` that fails closed), so a connector, ops or portal-delegate key, an unknown scope, a principal with no `mcp_scope` and a loopback get 403. This rule covers self-gated routes; the system key's reach on other routes is set by those routes' own gates and is reviewed in a follow-up of trinity-enterprise#719. The event loopback passes the helper (it carries no agent name) and is confined by the `get_current_user` entry fence to the subscriber-task dispatch, which is no self-gated route (ent#614). Reads such as the canvas list and report list admit an agent inside its reach by design of the owner-breadth model; they stay in the baseline until ruled.
- **Tests**: `tests/unit/test_ent840_agent_self_gate.py` (the helper's truth table; one sibling refusal per `AGENT_CALLABLE_SELF` route, driven off the census; the converted routes keep their messages), `tests/unit/test_ent719_self_gate_identity.py` (through the real routers: emit-event acts as the caller, and every principal outside its allowlist is refused; the system key is `trinity-system` on every `assert_own_agent` route, derived from the census; the `get_self_acting_agent` routes unchanged; a fresh install), `tests/unit/test_2996_human_only_routes.py` (recognition and table rules, self-tests), `tests/unit/test_1310_auth_wiring.py` (no hand copy).
- **Flows**: `feature-flows/agent-self-reminders.md`, `feature-flows/workspace-seat-decisions.md`, `feature-flows/agent-canvas.md`

### 2.13 Terms of Use (trinity-enterprise#1054, trinity-enterprise#1107)
- **Status**: ✅ Implemented (2026-11-02, seam + invite door; **2026-11-04, per instance**: OSS owns the gate, the text and the record). The provider an optional module registers now adds only the *door* (an invitation that is no longer live).
- **Rule**: every signed-in **person** — admin included, on whichever door they arrive through (Workspace, admin panel, public sign-in) — who has not accepted the current terms version is refused on every route they call with `403 {"code": "terms_required", "version": "<v>", "message": …}`. When the invitation that opened the account is no longer live, the code is `invite_expired` or `invite_revoked` (a registered provider's reasons). Those three codes are the closed set (`terms_gate.REFUSAL_CODES`). A new version is asked again at the next visit.
- **The text is an instance setting with a shipped default**: `services/terms_defaults.py` carries the default title, Markdown body and version (`default-1`); `terms_title` / `terms_text` / `terms_version` / `terms_required` are `system_settings` rows resolved `system_settings → default`, so a fresh install shows the default terms with nothing configured. `PUT /api/terms` (admin, interactive session) saves title + body and stamps a new version (ISO-Z timestamp); empty text is refused `422 terms_text_empty`, text over `TERMS_TEXT_MAX_BYTES` `422 terms_text_too_large`, a title over 200 chars `422 terms_title_too_long`; `POST /api/terms/restore-default` is the one action that restores the shipped default; `required: false` on the PUT switches the gate off (default on). The four keys are blocked on the generic `PUT` and `DELETE /api/settings/{key}` so the validated route is the only writer; both fields are validated before either is written, and a save of the text and title already in force stamps no new version.
- **Where it sits**: `services/terms_gate.enforce` is called once, inside `dependencies.resolve_platform_user_unfloored`, after every scope fence and the suspension check; with no provider registered the OSS decision (`services/terms_service.decision`) applies, with one registered the provider answers (door first, then the OSS decision it delegates to). **A Workspace portal session** (ruling A(1): the emailed-code sign-in, a verified email with no `users` row) is consulted the same way from `client_portal/portal_auth.py::get_portal_principal`'s portal-token branch (`terms_gate.enforce_portal_session`, after the client-block check and before the session slides) as a `terms_service.PortalPerson` — the same provider consultation (fail-closed: it is the Workspace-only population), the same refusal. Channel bindings, public links and the shared-canvas viewer read carry no platform principal and are not consulted.
- **Who is gated**: every person on an **interactive session**, whatever the role — a session the SPA declared at sign-in (`client=web` on `POST /api/token`, `"client": "web"` on `POST /api/auth/email/verify` and the hand-off), minted with an `interactive: true` claim that the resolver reads into `User.interactive_session`. A JWT **without** the claim — the CLI, curl, a CI harness, a test fixture, a session minted before the claim existed — is never gated: the gate is a UX/record contract the client declares, not a security boundary (a headless caller never accepts, and nothing is authorized by accepting). The portal half follows the same line: the Workspace sends `"client": "web"` on `POST /api/enterprise/client-portal/auth/verify`, the session is minted with `interactive: true` (`dependencies.create_portal_session_token`, carried across rotation by `renew_portal_session`), and only that session is asked; a harness-minted or delegate-minted portal token is not a visit. A Workspace-only person's own `user`-scoped key is gated too (ent#1054). A machine credential of operator-and-above (a `user`-scoped key, the system key) is **not** gated: the gate is for visits, and an ops key failing at 03:00 because the admin has not signed in since an upgrade is an outage, not a terms screen. Agent, connector, portal-delegate and loopback credentials are never gated.
- **Fails closed** when the OSS decision cannot be read (a DB fault refuses, the same fault that would refuse the sign-in itself). A **provider** fault refuses a Workspace-only person (the invitees the door is for) and is **ignored for operator-and-above**, so a broken optional module cannot lock an administrator out of the instance that could fix it.
- **Setup**: `/api/setup/*` resolves no principal, so the first admin's claim always precedes their acceptance; the admin's own first authenticated request is what shows the terms. An install can never lock itself out.
- **Record**: `terms_acceptances` (OSS, both migration tracks): one row per (person, version) — user id, email, version, time, `door` (the invitation id a provider names, else null) and IP. A portal person's row carries `user_id` NULL and is keyed by (email, version) through a partial unique index (`uq_terms_acceptances_email_version … WHERE user_id IS NULL`; `UNIQUE(user_id, version)` alone treats two NULLs as distinct); the decision for such a person is by address — a row a platform account with the same email wrote counts, it is the same person. `GET /api/terms/acceptances` (admin) lists them; the Settings › Access panel shows them. Audit: `AUTHORIZATION/terms_accepted` (version, door), `CONFIGURATION/terms_updated` and `terms_restored` (version only, never the text).
- **Exempt routes** (`@terms_route("<reason>")`): sign-out, `GET /api/users/me`, `GET /api/terms/current`, `POST /api/terms/accept`. The two terms routes resolve their caller through `routers/terms.py::terms_caller` — a platform principal through `get_optional_user`, or the Workspace portal session the bearer token carries (client-block check applied), else the resolver's own refusal — and keep the person / interactive rule as the handler's first statement; the portal sign-out is client-side and needs no route.
- **Terms page (SPA)**: `/terms` (`views/TermsAcceptance.vue`, store `stores/terms.js`, routes `/api/terms/*`) shows the title, the text and its version, one accept action disabled until the box is ticked; a newer version answers 409 `version_stale` and the page reloads and asks for a fresh tick. Declining signs the person out and says how to come back (sign in again and accept). A closed invitation shows no accept action. The page leaves only after a successful accept, role-aware. **A portal session** holds no platform credential and cannot open `/terms`, so the Workspace shell (`views/Portal.vue`) renders the same screen in place of the roster (`components/portal/PortalTerms.vue`, `stores/clientPortal.js::loadTerms` / `acceptTerms` on the portal bearer) while the roster was refused; accepting re-bootstraps the Workspace, declining is the shell's own sign-out.
- **The interceptor**: unchanged from ent#1054 — every HTTP client reports the three codes to `utils/termsGate.js`, which opens `/terms?redirect=<page>` once per burst, never from `/terms` or a sign-in page. That one mechanism is every door.
- **Admin editor (Settings › Access)**: `components/settings/TermsPanel.vue` — title, Markdown body, Save (stamps a version), Restore default, the gate switch, and the acceptance list (bounded, total stated).
- **Acceptance hooks**: `terms_service.register_acceptance_hook(fn)` — called `fn(user_id, email, terms_version, accepted_at)` after a NEW row, scheduled by the accept route after the response; a hook that raises is logged and audited (`terms_hook_failed`). The invite door's binding and the member Regent boot are hooks.
- **Tests**: `tests/unit/test_ent1107_terms_per_instance.py`, `tests/unit/test_ent1054_terms_gate.py`; frontend `termsAcceptance.mount.spec.js`, `termsPanel.mount.spec.js`, `termsRoute.spec.js`, `apiTermsRequiredInterceptor.spec.js`, `portalTerms.mount.spec.js`, `portalTermsRefusal.spec.js`, `portalTermsRefusal.mount.spec.js`.
- **Flows**: `feature-flows/terms-of-use.md`, `feature-flows/workspace-only-role.md`, `feature-flows/role-model.md`
