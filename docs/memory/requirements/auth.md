## 2. Authentication & Authorization

### 2.1 Email-Based Authentication
- **Status**: ✅ Implemented (2025-12-26, security-hardened 2026-03-26)
- **Description**: Passwordless email login with 6-digit verification codes
- **Key Features**: 2-step verification, admin-managed whitelist, auto-whitelist on agent sharing, rate limiting (IP-based + per-email OTP lockout after 5 failures)
- **Security**: OTP brute-force prevented by dual rate limits — `login_attempts:{ip}` (shared with admin login) and `otp_attempts:{email}` (max 5 failures → 10-min lockout). Both `POST /api/auth/email/verify` and `POST /api/public/verify/confirm` are protected. (pentest 3.1.5 / #176)
- **Enumeration-safety (#186)**: `POST /api/auth/email/request` returns an **identical body + status** regardless of whitelist membership (`{"success": true, "message": "If your email is registered, you'll receive a code shortly"}` — no distinct message, no `expires_in_seconds`). The rate-limit path returns the **same generic 200** (never a 429 differential; suppression is WARN-logged server-side), and the verification email is dispatched **fire-and-forget** so the whitelisted path's latency matches the non-whitelisted/rate-limited paths — closing the body, status, and timing membership oracles (pentest 3.3.3).
- **Flow**: `docs/memory/feature-flows/email-authentication.md`

### 2.2 Admin Password Login
- **Status**: ✅ Implemented
- **Description**: Password-based fallback for admin user
- **Key Features**: Bcrypt hashing, first-time setup wizard
- **Changing the password in the app** (#3825): `PUT /api/users/me/password` `{current_password, new_password}` — a signed-in session only (no MCP key), the current password required, the setup complexity rule, wrong current passwords capped at 5 per 15 minutes per account in their own bucket (not the login one), audited as `password_changed` / `password_change_failed` with no password material. Only an account that already has a password can change it; an email-only account gets 409 `no_password` and never gains one. A change signs every other session of the account out (per-user cutoff; the response carries the caller's fresh token), optionally revokes the MCP API keys the person created (keys are not sessions; the response says how many still work) and survives a restart: boot re-applies `ADMIN_PASSWORD` only when it differs from the value it last applied, so a NEW value in `.env` still rotates or recovers the password. Settings → General carries the form. Admin reset of another user's password is out of scope: no other account has a password.

### 2.4 Agent Sharing
- **Status**: ✅ Implemented
- **Description**: Share agents with team members
- **Key Features**: Share via email, access levels (Owner/Shared/Admin), sharing tab for owners
- **What a share grants (trinity-enterprise#820, operator ruling 2026-10-15)**: one flat grant, no tier column on `agent_sharing`. A share holder chats with the agent, sees their own conversations, and browses and edits the agent's files **except** credentials, runtime config and its instructions. On the Files surface that is ruled per verb by one policy (`services/file_path_policy.py`, vendored into the agent server):
  - **Owner tier** (the agent's owner or an admin, as a person): instruction files (`CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `GEMINI.md`, `.gemini/GEMINI.md`, `.claude/**` including skills), files that run code (`.gitconfig`, `.config/git/**`, `.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.local/bin/**`), reading credential/secret-class files (ent#819), listing hidden or credential directories.
  - **Refused for every caller**: writing or deleting credentials, runtime config, `.trinity`, git metadata at any depth (including bare-repo `hooks/` and `config`), system paths; deleting any `CLAUDE.md`.
  - **Agent keys** keep their capability path (`instructions.manage` ent#164, `skills.manage` ent#596) and are refused files that run code.
  - Below the owner tier the list withholds hidden files and flags each node with the verbs the caller cannot use; every write, delete and mkdir writes an audit row.
  - The Access tab states the grant in one sentence.

### 2.7 Shared Imperative Auth-Guard Family (INV-8, #1310)
- **Status**: ✅ Implemented (2026-07-17)
- **GitHub Issue**: #1310 (split from #654's architecture-invariant drift report; carved off from INV-14/#1308 **because it is security-sensitive**)
- **Requirement**: Architectural Invariant #8 ("Auth Pattern") — duplicated inline auth wiring (`db.can_user_access_agent` / `db.can_user_share_agent` → 403, and inline `role != "admin"` → 403) collapses behind shared helpers. Threshold: **≤5 bespoke in-scope non-exception sites**.
- **Description**: `dependencies.py` already carried the **path-dependency** factories (`AuthorizedAgent` / `OwnedAgent[ByName]`, uniform-404, #186) and the imperative fences (`_enforce_connector_scope`, `reject_agent_principal`). #1310 adds a small **imperative-guard family** — callable from any router body, for the sites where the agent name is *derived from a resolved resource* or the check is *composite* (a session/notification/execution row must be looked up before the agent name is known), where a path-dependency can't reach.

  | Helper | Wraps | Raises | Replaces |
  |---|---|---|---|
  | `assert_admin(user, *, detail="Admin access required")` | `_reject_connector_principal` + `role != "admin"` | 403 | inline admin checks + 4 router-local `require_admin` dupes |
  | `assert_agent_access(user, agent_name, *, detail="Access denied")` | `_enforce_connector_scope(owner_op=False)` + `db.can_user_access_agent` | 403 | inline `can_user_access_agent` → 403 |
  | `assert_agent_owner(user, agent_name, *, detail=…)` | `_enforce_connector_scope(owner_op=True)` + `db.can_user_share_agent` | 403 | inline `can_user_share_agent` → 403. **NOT delete-authorization** (see below) |
  | `assert_owns_or_admin(user, owner_id, *, detail="Not authorized")` | `user.id != owner_id AND role != "admin"` | 403 | strict-self-**or-admin** session gates (voice/chat) |
  | `assert_owns(user, owner_id, *, detail=…)` | `user.id != owner_id` (id-only, **no admin bypass**) | 403 | strict-self session gate (`public.py` public-link session detail) |
  | `assert_person(user)` / `Depends(require_person)` | `is_person_principal` (JWT or the person's own `user` key) + no `vouched_source_agent` | 403 `HUMAN_ONLY_DETAIL` | owner-tier grant routes (§2.8, #2996) |
  | `Depends(require_interactive)` | `reject_non_interactive_principal` (JWT only) + no `vouched_source_agent` | 403 | credential / sign-in identity mint, bind, rotate (§2.8) |
  | `assert_own_agent(user, agent_name, *, detail=…, refusal=None)` | `agent_principal_name(user)` not in (None, `agent_name`) | 403 (or `refusal()`) | the hand-copied agent-key self-gates (§2.11, trinity-enterprise#840) |

- **Preserve-403 (not 404).** All five raise **403** — access-first inline handlers are already *self-uniform* per INV-8 (they check access before any existence lookup, so there is no 404-then-403 enumeration oracle). The platform precedent is `schedules.py` `create_schedule` (#1445: "Access-check FIRST … no 404-vs-403 name-enumeration oracle"). The clean `{agent_name}`-path sites *could* have adopted the uniform-404 path-dependencies, but were consciously kept 403 to minimize frontend blast-radius and hold **one** imperative convention.
- **Imperative vs path-dependency (when to use which).** Agent name **in the path** → prefer the path-dependency (`AuthorizedAgent[ByName]`/`OwnedAgent[ByName]`, uniform-404). Agent name **derived from a resolved resource** (notification/session/subscription/execution row) or a **composite** gate (owner-or-initiator, resource-404-then-access) → use the imperative helper. Both fences run `_enforce_connector_scope` first, so the two conventions enforce the connector boundary identically.
- **`assert_agent_owner` ≠ delete authorization.** It wraps `can_user_share_agent` (owner-or-admin) but does **NOT** carry the `is_system` guard that `can_user_delete_agent` (`db/agents.py`) does. A delete path must keep using the delete predicate — never reuse `assert_agent_owner` for delete.
- **Documented exceptions (permanent, not deferred).** `nevermined._require_read_access`/`_require_write_access` and `reports.get_report` stay on their own **intentional-404** helpers (#186 designs, enumeration-safe by construction). `sessions._session_or_404` stays a **compound uniform-404** (existence + user + agent binding in one `if`) — migrating it to `assert_owns` would regress 404→403 **and** leak session-id existence, so it is left as its own already-consolidated helper. `internal.py` is the INV-8 no-auth exception.
- **`slack.py` retired (#1710).** The 11 inline-auth sites #1310 deferred were migrated onto `assert_agent_access` (3 read) / `assert_agent_owner` (8 owner) — behavior-preserving (same 403 + `detail`; site #10's ent#223 human-only `reject_agent_principal` kept). No `# noqa: inv8` marker remains in the tree; a re-introduced inline gate now trips the static guard unless it carries a freshly-added, individually-reviewed marker.
- **Static guard**: `tests/unit/test_1310_auth_wiring.py` — a precise AST matcher forbids `db.can_user_access_agent(` / `db.can_user_share_agent(` Call-nodes whose negation guards a `raise HTTPException`, and inline `role != "admin"` deny-`If`s, in `routers/` (per-function allowlist; `# noqa: inv8` line-exemption retained for a future, individually-reviewed exception — none in-tree after #1710). Filter/capability/allow-branch sites (assignments, `role == "admin"` selection, WS-`close(4003)` dict handlers) are **not** flagged.
- **Behavioral proof**: `tests/unit/test_1310_auth_consolidation.py` (real-DB `db_harness`) locks status + detail + admitted-principal set per migrated site; `test_186_enumeration_uniformity.py` extended for the five helpers.
- **Flow**: `docs/memory/feature-flows/role-model.md`

### 2.8 Human-Only Grant Surfaces (INV-8, #2996 / trinity-enterprise#711)
- **Status**: ✅ Implemented (2026-09-28)
- **GitHub Issues**: #2996 (autonomy toggle), trinity-enterprise#711 (sign-in email rebind), trinity-enterprise#717 (the manual whitelist grant)
- **Problem**: `get_current_user` resolves an agent-scoped or system-scoped MCP key to its **owner, carrying the owner's role**. #1890 made the admin gates refuse agent keys; the **owner** tier (`can_user_share_agent`, `assert_agent_owner`, `OwnedAgentByName`) and the self-service routes (`get_current_user` alone) kept admitting them. The owner gates cannot simply refuse agent keys the way the admin gates do, because agents legitimately use owner-gated routes (MCP schedule tools, file writes). So the rule is applied per route, and a route census makes the next route choose a side.
- **Two principal rules** — both **allowlists** over `User.mcp_scope`, fail-closed on a principal without the attribute (sentinel, never `getattr(..., None)`), and each treats a backend-minted event-loopback JWT (`mcp_scope=None`) differently: PERSON refuses every loopback token outright (`is_person_principal` checks `is_event_loopback`, ent#751), while INTERACTIVE refuses only one carrying `vouched_source_agent`. For INTERACTIVE that second layer is not the only one: the backend also mints loopback JWTs without a source agent, and `require_interactive` does not refuse those; the `get_current_user` entry fence refuses **every** loopback JWT on every route but the subscriber-task dispatch (ent#614):

  | Rule | Admits | Refuses | Primitive |
  |---|---|---|---|
  | **PERSON** | JWT session; the person's own `user`-scoped key | agent, system, connector, portal_delegate, ops, any future scope, a missing `mcp_scope`, a `user` principal carrying an agent/connector/delegate identity | `assert_person` / `Depends(require_person)` (predicate `is_person_principal`, ent#611) |
  | **INTERACTIVE** | JWT session only | every key | `Depends(require_interactive)` (predicate `is_interactive_principal`, #1854) |

  They are **credential-class** rules, not proof of human origin: a `user` key is the person's delegated credential, and a JWT counts as interactive only because non-human JWTs are fenced at `get_current_user`.
- **Assignment rule**: a route that **grants or changes what an agent may do** takes PERSON; a route that **mints, binds or rotates a credential or sign-in identity** takes INTERACTIVE — a minter must be stricter than the principal class it produces, or the PERSON rule is circular.

  | Route | Rule |
  |---|---|
  | `PUT /api/agents/{name}/autonomy` (#2996 — decides whether **unattended cron** fires; a manual `trigger_schedule` is not gated by autonomy) | PERSON |
  | `PUT /api/agents/{name}/{api-key-setting, capabilities, capacity}` | PERSON |
  | `PUT /api/agents/{name}/{read-only, resources, timeout, public-channel-model, guardrails}` | PERSON **or** an agent holding `agents.manage` (§2.9) |
  | `PUT /api/users/me/email` (ent#711) | INTERACTIVE |
  | `PUT` / `DELETE /api/users/me/github-pat` (a credential future agent creations inherit, ent#162) | INTERACTIVE |
  | `POST /api/mcp/keys` (every scope), `POST /api/mcp/keys/ensure-default` | INTERACTIVE (security.md §20.10) |
  | `GET /api/mcp/keys` (trinity-enterprise#712 — the key inventory; no machine consumer) | INTERACTIVE |
  | `POST /api/agents/{name}/voice/start` (trinity-enterprise#595 — mints the voice socket's single-use ticket) | INTERACTIVE; the Workspace start (`/api/enterprise/client-portal/agents/{name}/voice/start`) applies the same `require_interactive` predicate to the platform user it already resolves, and stays a `portal` route |

- **WebSocket tickets name their surface (trinity-enterprise#595)**: every consumer of a single-use WebSocket ticket passes the exact scope it accepts — `/ws` takes `user`, the VoIP media stream `voip:{call_id}`, the voice socket `voice:{voice_session_id}` — and `consume_ticket` refuses any other scope after consuming it, so a ticket minted for one socket can never open another. The voice ticket is minted only by the two voice start routes above, from an interactive session.
  | `POST /api/settings/email-whitelist` (trinity-enterprise#717 — every role, the default `user` included: each whitelist role yields an interactive session at first sign-in, and `operator` and above can mint keys) | admin **and** INTERACTIVE |

- **Whitelist grants (trinity-enterprise#717)**: `POST /api/settings/email-whitelist` takes `Depends(require_interactive)` and keeps the handler's `assert_admin`, both before the request body is read, so a refused caller gets 403, never a validation 422, and no row is written or replaced. An admin's own `user`-scoped key and the `system` key pass the shared admin gate (#2323, unchanged) but not this route. A loopback JWT carrying a vouched source agent is refused by the route gate; every loopback JWT is refused on this route by the entry fence. Signed-in admins keep the same success body, duplicate wording, existing-account note and validation reasons.
- **Refusal**: 403. PERSON routes return `HUMAN_ONLY_DETAIL` (`{"code": "person_required", ...}`, the same machine code as ent#611's ask endings, whose own detail is unchanged); INTERACTIVE routes return `reject_non_interactive_principal`'s existing detail. The refusal depends only on the principal, never on whether the addressed agent exists, so answering 403 before a path's 404 is not an enumeration oracle (#186).
- **Still working**: the owner's `user` key and ops tooling on a `user` key keep the PERSON routes; the UI and CLI use JWTs everywhere; heartbeat, the result callback, reports and notifications do not use these gates; `trinity-system` keeps `require_admin` (#2323) and has no caller of the routes above.
- **Route census (the inheritance mechanism)**: `tests/unit/test_2996_human_only_routes.py` walks every `*.py` under `src/backend/` (`rglob`, `enterprise/` excluded — the private tree carries its own), every HTTP method (GETs included), both `@<router>.<verb>(...)` and `add_api_route(...)`. Each route must resolve to exactly one policy class: `person` / `interactive` (the Depends form, or the imperative call as the handler's **first** statement on its principal argument, with the name imported from `dependencies`), `admin_tier` (`require_admin` / `assert_admin`, counted and printed), `admin_widened` (an `allow_scopes` opt-in, listed per route), `portal` (`get_portal_principal`), `agent_callable_self` (the `assert_own_agent` self-gate recognised **and** listed with a reason, §2.11), `agent_callable_any` / `own_auth` / `delegated` (listed per route with the `METHOD /path` pinned and a reason; `agent_callable_any` also answers why a sibling agent may reach it), or `unclassified_at_freeze` — the frozen baseline `tests/unit/fixtures/human_only_route_baseline.json`. The baseline is **shrink-only**: exact count literal, stale entries fail, an entry that becomes gated must be removed. WebSocket routes are pinned as a literal set. `tests/unit/test_2996_route_census_runtime.py` imports the real app in a subprocess (fails, never skips) and checks every registered route maps to a census key and every stored `METHOD /path` matches.
- **Not closed here**: the census does not classify the routes it freezes as `unclassified_at_freeze` — the baseline is a to-do marker, not a judgement (`tests/unit/fixtures/README.md`). Each entry leaves it through a per-route ruling (tracked in trinity-enterprise#719), and the baseline only lets it shrink.
- **Tests**: `tests/unit/test_human_only_principals.py` (primitives), `tests/unit/test_mcp_key_creation_requires_session.py`, `tests/unit/test_2996_human_only_routes.py`, `tests/unit/test_2996_route_census_runtime.py`, `tests/unit/test_2996_owner_config_person_only.py`, `tests/unit/test_2996_self_service_session_only.py`, `tests/unit/test_2996_agent_schedule_tools_unchanged.py` (the agent's own schedule tools stay agent-callable), `tests/unit/test_ent717_whitelist_session_only.py` (the whitelist grant through the real settings router: every key scope and a missing scope refused at every role and before the body is read, the vouched loopback refused by the route gate, an unvouched loopback JWT refused by the real entry fence, signed-in admin unchanged, a signed-in non-admin still refused).
- **Flows**: `feature-flows/autonomy-mode.md`, `feature-flows/email-authentication.md`, `feature-flows/mcp-api-keys.md`

### 2.9 Self-Change Grants (trinity-enterprise#164)
- **Status**: ✅ Implemented (2026-10-05)
- **GitHub Issues**: trinity-enterprise#164 (re-scoped 2026-10-02: grants, not per-action approval); the Settings toggles are trinity-enterprise#756
- **Problem**: an agent's key resolves to its owner (Invariant #8), so the owner gates let any agent reshape any agent of the same owner — its instructions, schedules, configuration, or the fleet itself. ent#596 closed that for skills with one capability grant; this extends the same seam to the rest of the agent's shape.
- **Rule**: five capabilities in a closed set (`db/capability_grants.CAPABILITIES`). Humans (JWT, `user` key, `system`) are never fenced; an agent principal without the grant is **refused** — no pause, no approval-and-resume. The 403 names the missing permission (`*_management_not_permitted`) and tells the agent to raise an ask (`type: question`) whose title **includes the permission id** (`schedules.manage`); answering that ask does **not** grant anything — an instance admin grants it from a signed-in session, in the agent's Settings → *Permissions to change itself* (ent#756) or `PUT /api/agents/{agent}/capability-grants/{capability}`. An `agents.manage` holder reaches only agents its owner owns, and cannot change its own read-only mode or guardrails. Every refusal is audited (`capability_refused`).

  | Capability | Covers | Exempt |
  |---|---|---|
  | `skills.manage` (ent#596) | skill writes, skill sets, `.claude/skills/**` via the file routes | — |
  | `schedules.manage` | create / update / delete / enable / disable a schedule, and its webhook + webhook secret | the agent's **own** schedules (#2996 — its own use, bounded by autonomy); "trigger now" |
  | `instructions.manage` | `CLAUDE.md`, `AGENTS.md` and `.claude/**` except skills, via the file routes (write, create-folder, delete — a delete of an ancestor counts); `git/reset-to-main-preserve-state` | — |
  | `agents.manage` | create a durable agent, delete, `deploy-local`, `systems/deploy`, the chat model, and the five reconfigure writes in §2.8 | spawning / discarding an **ephemeral** agent (ent#69 governs ghosts) |
  | `projects.manage` (ent#588) | start a Workspace project **on its owner's behalf** — the owner is creator and first member, the agent its steward, members-only — and import one of the agent's **own** folder projects (MCP `create_project` / `import_project`) | working on a project the agent is already active on (tasks, log, health) needs no grant; members and visibility are never grantable |

- **Not grantable**: autonomy, api-key-setting, capabilities, capacity (PERSON, §2.8) and rename (ent#69 Part 2, human-only). A calibrating companion (owner readiness stamp, ent#663) cannot be granted `instructions.manage` (422 `calibrating_agent`); ephemeral and system agents cannot be granted anything.
- **Grant surface**: `GET /api/agents/{name}/capability-grants` (owner-level: all five, held or not, with who/when — an agent may read its own); `PUT /api/agents/{name}/capability-grants/{capability}` `{granted}` — admin **and interactive**, idempotent, audited (`capability_grant` / `capability_revoke`). The ent#596 `PUT /skill-manager` route is kept.
- **Upgrade effect**: no agent holds `schedules.manage` / `instructions.manage` / `agents.manage` after deploy. An agent that orchestrates others (creates durable agents, writes another agent's schedules or instructions, reconfigures) is refused until an admin grants it.
- **Known limit**: the fence is on the platform's routes. An agent can still edit files inside its **own** container with its own tools; `instructions.manage` governs the platform write path, not the agent's shell.
- **Tests**: `tests/unit/test_ent164_self_change_grants.py` (fences read off FastAPI's dependant graph, behaviour per class, ghost and own-schedule exemptions, calibrating refusal), `tests/unit/test_2996_owner_config_person_only.py` (real keys: an ungranted agent gets the named refusal, a granted one changes the stored value, the grant does not open the PERSON writes; the grant route), `tests/unit/test_2996_human_only_routes.py` (census class `person_or_grant`).
- **Settings surface (trinity-enterprise#756)**: Agent Settings → **Permissions to change itself** — the five as toggles (skills · schedules · instructions · other agents · projects), each with a plain line of what it allows and what is refused without it, and *granted by · when* (absolute time on hover). Read by the owner (and admins); a non-owner's read 404s and the card does not render. Editable only by an admin — the owner sees the state with *Only an instance admin can change these*; the PUT itself stays the gate (admin **and** interactive). A fresh agent shows all five **off** with a one-line explanation. **Autonomy** is shown beside them as a person's switch, never a grant. The agent's **open permission requests** are listed — pending queue items from this agent whose title contains a permission id (the refusal tells it to put one there) — each linking to Operations. Toggle refusals (calibrating, system, ephemeral) render next to their own toggle in the backend's words. **OSS-core, ungated** — the UI for #3236's grants follows #3236's open-core ruling.
- **Flow**: `feature-flows/self-change-grants.md`

### 2.10 Workspace-Only Rung (ROLE-002, trinity-enterprise#837)
- **Status**: ✅ Implemented. PR 1 is OSS core (the floor, sign-in routing, sharing); PR 2 adds the role on the Access-tab row, a platform account before the first sign-in, and assigning a `user` to a companion.
- **GitHub Issue**: trinity-enterprise#837 (ruled 2026-10-07: no new role)
- **Rule**: platform role `user` means *a member who works with agents through the Workspace*. The operator UI starts at `operator`. `ROLE_HIERARCHY` and `VALID_ROLES` are unchanged. A role that is not in the hierarchy ranks below `user` and is Workspace-only too (fail closed).
- **The floor**: `get_current_user` is the door every operator route authenticates through (`CurrentUser`, `AuthorizedAgent*`, `OwnedAgent*`, `require_role`, `require_admin`, `get_optional_user`, `get_user_or_anonymous` — OSS and enterprise). It refuses a Workspace-only principal with `403 {"code": "workspace_only", "message": "This account works in the Workspace. Open /workspace."}`, except:
  - an **interactive session** (the SPA's JWT) on a route marked `@workspace_route("<reason>")` — an operator-side route the Workspace itself calls (session identity, sign-out, the `/ws` ticket, preferences, loops, the voice canvas, an `authorized` canvas link, the public chat page's history). A key, even the person's own `user`-scoped one, does not pass: a key scripts the Workspace through its own doors;
  - an **agent** principal whose owner is Workspace-only, on its own runtime surface (reports, notifications, self-info, its own asks, the skill-gate check; heartbeat and result delivery authenticate elsewhere), with any `{name}` in the path equal to its own name. An agent never exceeds its owner; everything else it did is refused until an admin raises the owner's role (there is no ownership transfer; the agent's key also stays bound to the account that minted it).
  The refusal depends only on the principal and the route, never on whether an addressed agent exists (Invariant #8).
- **Workspace doors** resolve the credential through `resolve_platform_user_unfloored` (every scope fence, no floor): `get_portal_principal`, the rooms principal and the Workspace voice start. A guard pins that caller set. The rooms door still refuses an agent whose owner is Workspace-only (rooming with the owner's agents is agent-to-agent chat). A Workspace-only member's roster is unchanged: agents shared with them, plus any they own.
- **WebSocket doors**: `/ws/events` and the agent terminal refuse a Workspace-only principal. `/ws` needs a ticket from the marked `POST /api/ws/ticket` (browser session only); its events are scoped to accessible agents (ent#467) and, for a Workspace-only account, to the kinds the Workspace reads (`WORKSPACE_WS_EVENT_TYPES`), each cut to the fields it reads (`WORKSPACE_WS_EVENT_FIELDS`): the operator queue, notifications, reports, room triggers, the agent lifecycle and the sharing events never reach a member's socket, and neither do an activity's prompt or reply previews.
- **Connector keys** of a Workspace-only owner pass the floor on the two routes the ent#46 fence already confines them to (the bound agent's chat and playbook list), so the agent's external consumers keep working.
- **Shared canvases**: an `authorized` link recognises a Workspace session (someone the agent is shared with signs in to the Workspace, not at `/login`), limited to an agent on their roster and a `roster`-audience canvas; its "Sign in" goes through the Workspace and back.
- **Whitelist grants**: a deliberate grant replaces a row that sharing or an access-request approval wrote, so an admin can add such an email as `operator`; the form names an existing account's role, which only User Management changes. Adding an entry takes an admin's signed-in session whatever role it selects, `user` included; an API key gets 403 (trinity-enterprise#717, §2.8).
- **Other surfaces**: `/m` sends a signed-in member to the Workspace; the MCP server and `trinity init` report the `workspace_only` refusal instead of reading it as "no permission" or reporting success.
- **Inside the Workspace** a `user` keeps the team view — every canvas audience, the agent's whole activity (loop runs included), voice and model choice — because the Workspace resolves the account as a platform principal (`is_platform`). The narrower client view (`roster` canvases, their own work) is for people without an account. Nothing new is exposed: a `user` saw all of it on Agent Detail before #837.
- **Known limit — loops**: the marked loop routes keep their pre-#837 reach: a member lists every loop on an agent they can reach and may stop any of them (the starter, the owner or a share), and `start` takes the request's model and tools. Narrowing the Workspace rail to the person's own runs is a follow-up.
- **Sign-in routing (SPA)**: `/login` lands a `user` in `/workspace`, honouring `?redirect=` only for Workspace, shared-canvas and public-chat paths. The router guard sends a `user` on any operator URL to `/workspace` (`/agents/:name/*` → `/workspace?agent=:name`). A `workspace_only` 403 on an operator page refreshes the profile and moves the tab to `/workspace`. A platform session stays a Workspace session (ent#357); sign-out ends whichever credential is live (#2258).
- **Sharing**: `POST /api/agents/{name}/share` and access-request approval no longer write the login whitelist. A person an agent is shared with signs in to the Workspace with the emailed code. Existing sharing-sourced whitelist rows stay and yield Workspace-only accounts. The manual whitelist (now with a role picker), CLI self-signup and SSO first sign-in keep writing.
- **Admin aids**: Settings → Access → User Management lists the Workspace-only accounts; the role pickers label the rung "user — Workspace only"; the Access tab says that adding a person grants Workspace access.
- **The role on the Access tab (AC5)**: for an admin whose role the server has verified, each other Active person on Agent Detail › Access has a role select (its accessible name says the role applies to every agent; one fixed-width slot per row, so the controls line up); an admin's own row stays read-only (the route refuses a self-change). Every change asks first — lowering to `user` says the person loses the operator UI on every agent and that agents they own keep only their runtime routes. A cancel or a refusal puts the select back on the stored role. Everyone else sees the role as a label and the pointer to Settings.
- **A platform account before the first sign-in**: a Pending person (shared, no account) gets **Give a platform account**, confirmed first (a platform account sees the team's view of every agent shared with the address — for colleagues, not outside clients). It creates the account now, as their first sign-in would, so the person can be assigned at once and signs in at `/login` (or SSO). `user` is the default for a new member; an earlier deliberate allow-list entry keeps its role, and the row says so. An existing account is refused, naming its role. The act is audited, and an invite email goes out when email is configured.
- **Changing a role is a person's act**: `PUT /api/users/{username}/role` refuses every key (`reject_non_interactive_principal`), since `require_admin` alone admits `trinity-system`'s key and an admin's user-scoped key; a change writes one `role_change` audit row (from → to), a no-op or a refusal none. Before the role is written, the person's whitelist row (if any) is capped at the new role — lowered, never raised: the row is what an account created for the address gets, again after a re-bind, so a row above the account would let a demoted person re-bind away and sign in with the old address at the old role, and a row raised on a promotion would arm the old address with a second account at the new role.
- **A `user` serves a companion (AC7)**: a `user` can be an agent's primary, approver, collaborator or viewer, and answers the agent's asks in the Workspace Inbox. An assignment is a relationship, not access (ent#500), and the Inbox lists asks only from agents on the person's roster, so assigning someone on the Access tab also shares the agent with them — after the assignment is written; never the owner, the admin themselves, or an account with no email. Each person's role shows in "People this agent serves" and its pickers; an admin sees "Not shared with …" with **Share with them** on an assignment the agent isn't shared for. Removing an assignment does not unshare.
- **Upgrade effect**: every existing `user` account (sharing, manual whitelist, CLI self-signup, SSO first sign-in) loses the operator UI and keeps the Workspace. An admin raises anyone who operates agents to `operator`. Runbook: `docs/migrations/WORKSPACE_ONLY_USER_ROLE_2026-10.md`.

### 2.11 Agent-Key Self-Gate (INV-8, trinity-enterprise#840)
- **Status**: ✅ Implemented (2026-10-23)
- **GitHub Issues**: trinity-enterprise#840 (triggered by trinity-enterprise#839, the seat-decisions route that shipped without the gate)
- **Problem**: an agent-scoped key resolves to its owner carrying the owner's role, so `AuthorizedAgent` / `assert_agent_access` answer "may this key reach that agent" — since ent#629 the agent itself, its permission-edge targets and the agents it spawned — never "is this key acting on its own agent". Every route an agent key may call that reads or changes one agent's state therefore needed a second check, copied by hand into ten modules, invisible to CI.
- **Rule**: one helper, `dependencies.assert_own_agent(current_user, agent_name, *, detail=…, refusal=None)` — 403 with the route's own `detail` when the principal is an agent key whose agent is not the path agent; a no-op for every other principal (person, `user` / `system` / connector key, event loopback), exactly like the copies it replaces. `refusal` builds the exception instead, for a router whose access dependency answers a uniform 404 so the two refusals stay byte-identical. Called as the handler's **first** statement (after the docstring), it runs before any lookup, so the refusal discloses nothing about the target (#186).
- **Census classes** (§2.8): `agent_callable` splits in two.
  - `agent_callable_self` — **recognised and listed**: the handler's first statement is `assert_own_agent(<principal>, <agent>, …)` with the name imported unaliased from `dependencies`, `<principal>` a `Depends(get_current_user)` / `CurrentUser` parameter and `<agent>` the `name` / `agent_name` path parameter of every route decorator; or the signature takes `Depends(get_self_acting_agent)`. Each such route also has an `AGENT_CALLABLE_SELF` entry naming why it is a **use, not a grant** — the review the census exists to force: the gate alone never classifies a route. The reviewed reason, not a code check, is the guard: a self-scoped grant (an agent changing what it may do itself) that someone lists passes every check, as entries in the old `AGENT_CALLABLE` table did. A self-gated route with no entry, and an entry whose route carries no recognised gate, both fail.
  - `agent_callable_any` — listed in `AGENT_CALLABLE_ANY` with the reason it is agent-callable AND a separate written answer to "why may an agent other than the one in the path reach this" (a capability grant bounds it, the key itself names the agent, the handler authenticates the agent's own key, or a read inside the agent's reach).
- **Hand copies are refused**: `tests/unit/test_1310_auth_wiring.py` fails any inline comparison of a principal's agent name (attribute, `getattr`, `agent_principal_name`, or a local bound from one, also as an operand of `or` / `and` / `… if … else …`; the principal annotated `User` / `CurrentUser` in any form, defaulted `Depends(...)`, or unannotated and named like one) against a `name` / `agent_name` parameter or a local alias of one — `!=`, `is not`, `not in`, a negated `==`, or an `==` whose `else` refuses — that guards any `raise` or a returned 401/403/404, anywhere under `src/backend/` (allowlist: `aauth_person.assert_own_key`, the stricter own-key-only AAuth gate). Stated limit: a comparison against a differently-named parameter is not matched, so header checks such as `x_source_agent != current_user.agent_name` stay legitimate.
- **Converted** (behaviour-preserving, each module keeps its message): reminders (×3), seat decisions (×2), user memory, metric points, reports, canvas writes and deletes (×4), canon roles, objectives, shared files, voice reply, outbound A2A call and poll, and the Nevermined delegation read (its uniform 404 kept through `refusal=`) — and `get_my_ask` joins the two ask routes as a `get_self_acting_agent` fence. Three refusals change only for a caller refused either way: user memory now refuses an out-of-reach agent key with its self message (was "Not authorized", both 403); outbound A2A checks its kill switch as a dependency, so with the switch off a schema-invalid or missing body answers 404 (was 422; JSON that does not parse is still 422); and a test double whose `agent_name` is not a string (or that has none) is no longer treated as an agent key.
- **Not closed here**: a `system`-scoped key and the event loopback pass every self-gate (they carry no agent name) — per-route rulings for them are trinity-enterprise#719. Reads such as the canvas list and report list admit an agent inside its reach by design of the owner-breadth model; they stay in the baseline until ruled.
