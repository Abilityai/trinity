## Authentication & Authorization Architecture

### 1. User Authentication (Human → Platform)

| Mode | Flow | Token |
|------|------|-------|
| **Email** (primary) | Email → 6-digit code → `POST /api/auth/email/verify` | JWT with `mode: "email"` |
| **Admin** (secondary) | Password → `POST /api/token` | JWT with `mode: "admin"` |

- Email whitelist controls who can login via email; admin login always available for 'admin'.
- **JWT revocation on logout** (#187): every access token carries a random `jti`; `POST /api/auth/logout` writes `jwt:revoked:{jti}` to Redis with a TTL equal to the token's remaining life, and `get_current_user` / `decode_token` (WS) / `/api/auth/validate` (nginx) reject a revoked `jti`. Closes the "exfiltrated 7-day token survives logout" gap (pentest 3.3.4). Fail-open (Redis down or a legacy no-`jti` token → not revoked), so the check can never lock out a valid session; backend restart still rotates `SECRET_KEY` and invalidates everything. Token-lifetime reduction + refresh tokens deferred (separate issue).
- **Per-user session cutoff** (#3825): changing a password writes Redis `trinity:user_sessions_revoked:{username}` (`{"at", "at_ms", "keep"}`), and the same three readers refuse a platform token issued at or before the cutoff, except the fresh token (`keep` = its `jti`) the change handed back. Every platform token now carries `iat` and `iat_ms`; the millisecond claim decides, so a sign-in later in the same second survives while a token minted earlier in it does not (a token dated only by `iat` is refused for the whole cutoff second). Event-loopback tokens (`scope == EVENT_LOOPBACK_SCOPE`, EVT-001: `sub` = admin, no `iat`) are not sessions and are exempt, or an admin password change would refuse every event dispatch for the cutoff's TTL. Reads fail open like the `jti` check. MCP API keys are outside the cutoff; the change revokes the person's own keys only on request (`revoke_api_keys`). The boot fingerprint that keeps an in-app change across restarts, and the change route itself, are in `feature-flows/admin-login.md`.
- **4-tier role hierarchy** (ROLE-001): `user` < `operator` < `creator` < `admin`. Agent creation requires `creator`+. Enforced via `require_role()` in `dependencies.py`.
- **The operator floor — `user` is Workspace-only** (trinity-enterprise#837, requirements `auth.md` §2.10): `get_current_user` = `resolve_platform_user_unfloored` (every scope fence) + `enforce_operator_floor`, so every route that authenticates through it — `CurrentUser`, `AuthorizedAgent*`, `OwnedAgent*`, `require_role`, `require_admin`, `get_optional_user`, `get_user_or_anonymous`, OSS and enterprise — refuses a principal below `operator` (`is_workspace_only_role`: the `user` rung or a role outside the ladder) with `403 {"code": "workspace_only", "message": "This account works in the Workspace. Open /workspace."}`. Three exceptions: a connector key, which the ent#46 fence has already confined to its bound agent's chat and playbook list; an interactive session (a JWT — a key, even the person's own `user` key, does not pass) on a route marked `@workspace_route("<reason>")` (read from `scope["route"].endpoint`; the marked set is pinned in `tests/unit/test_837_workspace_route_census.py`, which also checks that every operator-side `/api/` call in the Workspace's own frontend files reaches a door or a marked route), and an agent whose owner is Workspace-only on its own runtime surface (`_AGENT_SELF_ROUTES` = `_EPHEMERAL_ALLOWED_ROUTES` + its own asks + `POST /api/skill-gate/check`, `{name}` bound to the key and carried by the matched route's own parameter, so a static route that merely spells the name — `GET /api/agents/slots` for an agent named `slots` — is not its own). The refusal depends only on the principal and the matched route, so it is answered before any agent lookup (Invariant #8). Doors outside `get_current_user` apply it themselves: `/ws/events` (`owner_is_workspace_only`) refuses at the handshake (HTTP 403, before `accept()`) and the agent terminal WebSocket closes 4003; `/ws` needs a ticket from the marked `POST /api/ws/ticket`, and its events are scoped by agent and, for a Workspace-only account, by kind: `resolve_ws_identity` hands the socket `WORKSPACE_WS_EVENT_TYPES`, and `WORKSPACE_WS_EVENT_FIELDS`, so it receives only what the Workspace reads, each event cut to those fields — never the operator queue, notifications, reports, room triggers, the agent lifecycle or the sharing events (`architecture/integrations.md`). Inside the Workspace a `user` keeps the team view (`architecture/workspace.md`). An `authorized` shared-canvas link also recognises a Workspace session, limited to an agent on that person's roster and a `roster`-audience canvas (`canvas_share_service.WorkspaceViewer`). The Workspace doors (`get_portal_principal`, `get_room_principal` — which still refuses an agent whose owner is Workspace-only — and the Workspace voice start) call `resolve_platform_user_unfloored` directly — `tests/unit/test_837_workspace_only_floor.py` pins that caller set, so a new door is a reviewed edit. Fail-closed by construction: an unmarked route (or a call with no matched route) refuses the rung. Known limit: `GET /api/agents/{name}/files/preview` is not part of the Workspace set, so a canvas path image falls back for a `user` as it does for an external client.
- **Whitelist-driven role on first login** (#314): new email users inherit the `default_role` on their `email_whitelist` row (fallback `user`). Callsites pass explicit intent — public `/api/access/request` self-signup → `user`; admin whitelist UI → caller-specified (the role picker defaults to `user`). Adding a whitelist entry (`POST /api/settings/email-whitelist`) takes an admin's interactive session for every role, `user` included (trinity-enterprise#717): each role yields an interactive session at first sign-in, so `require_interactive` refuses the admin's own user-scoped key and `trinity-system`'s key, which `assert_admin` alone admits. Public self-signup keeps its separate switch, below. Since trinity-enterprise#837, `/share` and access-request approvals write **no** row: sharing grants the agent and the Workspace (code sign-in), never a platform login; rows earlier shares wrote stay and yield Workspace-only accounts. Admins promote people explicitly via `PUT /api/users/{username}/role` — an interactive session only (`reject_non_interactive_principal`: `require_admin` alone admits `trinity-system`'s key and an admin's user-scoped key), audited as `role_change` (trinity-enterprise#837 PR 2), and offered on the Access tab's rows as well as in User Management; the change first caps the person's whitelist row at the new role (lowered, never raised), so a demotion cannot be undone by re-binding away and signing in with the old address, and a promotion does not arm the old address. Closes a privilege escalation where any access grant silently promoted the recipient to `creator`.
- **First-run admin claim** (#2381, ent#580): the unauthenticated `POST /api/setup/admin-password` provisions the first admin and refuses (403) whenever a usable one exists. An install booted with `ADMIN_PASSWORD` set is never claimable; a blank one is — deliberately so on a marketplace one-click image (`ADMIN_PASSWORD_SOURCE=browser`), where the first browser visitor creates the admin. That is why `docker-compose.hosted.yml` — the file the marketplace runs, via `start.sh --hosted` — uses `${ADMIN_PASSWORD?}` (unset refuses to render, explicit blank renders); `docker-compose.prod.yml` keeps `:?`, since nothing that claims in the browser runs it. Hosted also forwards `ADMIN_PASSWORD_SOURCE=${ADMIN_PASSWORD_SOURCE:-unset}`, and the endpoint refuses a blank password under `unset` (a hand-run hosted compose), after the existing-admin check and before hashing; absent (dev compose) and `browser` pass. `instance-id` (#3004, PROV-018, the AWS image) gates the claim on the EC2 instance ID: provisioning writes it to `/data/setup-claim` (0600, owner 1000:1000; the backend never queries IMDS), `GET /api/setup/status` returns `claim_required: "instance-id"`, and the POST — after the existing-admin and `unset` refusals, before any password work — applies the per-IP login rate limit (`routers/auth.py::check_login_rate_limit`, keyed by the canonical client address — `routers/public.py::_get_client_ip` reads what §1a resolved), compares trimmed, lowercased bytes with `hmac.compare_digest`, and answers every failure (wrong or missing code, missing or empty file) with one 403 detail. After password and email validation the file is taken by an atomic rename, so of two concurrent correct claims only one proceeds (the other gets the same 403); it is renamed back if hashing or the password write raises, and deleted after success. A failed delete is logged and non-fatal, since the existing-admin refusal then precedes any read. Email is optional in this mode only. The allowlisted prod↔hosted env difference is pinned in `test_2280_hosted_compose_parity.py`. The creation-to-first-visit window is an accepted, documented risk (`docs/DEPLOYMENT.md` → Security Recommendations); the MCP server needs no password in its default `MCP_REQUIRE_API_KEY=true` mode and refuses to start without one otherwise (#692).
- **Public self-signup is default-OFF** (trinity-enterprise#10): the unauthenticated `POST /api/access/request` returns **403** unless an operator opts in via `PUBLIC_ACCESS_REQUESTS_ENABLED` (env) or the `public_access_requests_enabled` system setting. When off it never auto-whitelists, so the email whitelist stays authoritative against self-enrollment. Login-code requests for already-whitelisted emails are unaffected.

### 1a. Client address behind the proxy (trinity-enterprise#873, #3047)

One canonical client address per HTTP/WebSocket request, decided once and read by everything: every per-IP limiter key (`login_attempts_ip:`, public-link, setup claim, webhook, A2A, AAuth, portal sign-in) and every request-derived audit `actor_ip`. Behind a trusted proxy that address is the client the proxy saw; the proxy's own address is used only when it forwards no client identity (`proxy_fallback`, which includes a request that arrived on the legacy listener). `routers/public.py` no longer keeps a trust rule of its own.

- **Resolver:** `utils/client_ip.py`, a pure leaf (no routers, services, DNS, Docker, threads or refresh). `ClientAddressMiddleware` is pure ASGI, registered in `main.py` immediately inside `HostHeaderGuard`; it rewrites `scope["client"]` **in place** (so uvicorn's access log shows the same address), keeps the socket peer and a provenance (`peer`/`xff`/`cf`/`proxy_fallback`) under `scope["trinity.client_address"]`, and leaves every header untouched (`public._is_caddy_ask` reads their presence). `public._get_client_ip` is now only `request.client.host` or `unknown`. uvicorn's own forwarded-header processing is off in every launcher (`--no-proxy-headers` in the image CMD and all compose commands, `proxy_headers=False` in `main.py`'s `__main__`); the old image CMD's `--forwarded-allow-ips=*` is gone.
- **Who is trusted:** only the bundled nginx (`<prefix>.2`) and cloudflared (`<prefix>.3`) on prod/hosted (`TRINITY_BUNDLED_PROXY_TRUST=1`, `TRINITY_PROXY_PREFIX`, default `172.30.0`), plus an operator's own proxies in `TRUSTED_PROXIES` (default empty). Never: the bridge gateway (`.1`, what a published port delivers host-forwarded callers from), the backend (`.4`), the MCP server (dynamic pool), agents, or an address merely for being private. Dev and a bare `docker run` grant nothing; Vite is just a peer.
- **Rule:** an untrusted peer is its own address whatever it sends. From a trusted peer, `X-Forwarded-For` fields are read right to left as one list; trusted entries are skipped, the first untrusted entry is the client, and nothing to its left is read. When the authenticated suffix reaches the bundled cloudflared (as the peer, or as an entry nginx appended), its single `CF-Connecting-IP` is the client. `X-Real-IP` and RFC 7239 `Forwarded` are never read. Literals only (IPv4-mapped IPv6 canonicalised; private/loopback and Cloudflare's `240.0.0.0/4` accepted as clients; host names, ports, brackets, zone IDs, unspecified and multicast refused). IPv6 stays keyed by the full address (prefix aggregation is a separate decision).
- **Absent vs invalid:** a trusted proxy that forwards no identity (no XFF field; or the cloudflared hop with no CF field) keeps the request on that proxy's own address (`proxy_fallback`, a shared bucket, a WARNING at most once a minute, never a guess from the unverified prefix). A chain of only trusted hops (nginx appends every peer, so a listed proxy that forwards nothing, or a client inside a listed range, arrives this way) is attributed to its left-most hop, also `proxy_fallback`. Identity that is present but empty, malformed, a duplicated CF field, or a consumed suffix over 4 KiB / 32 elements is refused: HTTP 400, or WebSocket close 1008 before accept. A long unread left prefix is ignored, not refused. Malformed headers from an untrusted peer are ignored.
- **Validation at startup:** `main.py` calls `get_config()` at import; `ClientIPConfigError` names the setting and entry. `TRUSTED_PROXIES` refuses wildcards, default routes, loopback (a host-local proxy uses the PROXY listener below), IPv4-mapped IPv6, and anything overlapping `172.28/16`, `172.29/16` or the active ingress `/24`; `TRINITY_PROXY_PREFIX` must be three decimal octets not overlapping the two platform networks.
- **Ingress network (prod/hosted only):** `trinity-proxy-network`, `<prefix>.0/24`, gateway `.1`, dynamic pool `.128/25`; frontend `.2` (its ONLY network — off the agent network, so no agent can be handed its address), cloudflared `.3` (plus `extra_hosts` mapping `backend` and `trinity-backend` to `.4`, so direct-to-backend Tunnel rules arrive from `.3`), backend `.4`, MCP server from the pool (nginx's `/mcp` upstream). Agents, Redis, scheduler, Vector, Postgres and OTel never join. `start.sh --hosted` refuses an overlapping Docker network before any pull or `up`, naming it; the already-owned network with the same address plan passes.
- **Caddy transport (#3047):** Docker's loopback publishing replaces a host Caddy's clients with the gateway, so nginx has a second listener, `:8082 proxy_protocol`, with `set_real_ip_from ${TRINITY_PROXY_GATEWAY}` / `real_ip_header proxy_protocol` confined to it, published only on `127.0.0.1:${CADDY_PROXY_PORT:-18082}`. Both servers include the same `nginx-server.conf` (and `/ws` now sends XFF/X-Real-IP/X-Forwarded-Proto like the other locations). `render-nginx.sh` substitutes only `TRINITY_PROXY_GATEWAY` (validated IPv4) into the template at start and writes the result to `/etc/nginx/generated`, a directory created for it and owned by UID 101 (`conf.d/default.conf` is a root-owned one-line include of it). Caddy's protected upstream uses `transport http { proxy_protocol v2; keepalive off; versions 1.1 }` — `keepalive off` because a PROXY header describes a connection. The ordinary `:8080` publication keeps every interface unless `FRONTEND_BIND_ADDRESS` is set (provisioning sets `127.0.0.1`).
- **Automatic migration:** `provision_caddyfile` picks the upstream on every render (first boot, `--caddy-only`, IP refresh, post-upgrade) by a LIVE check: the running `trinity-frontend` publishes `8082/tcp` at `127.0.0.1:<port>` and `scripts/deploy/probe-proxy-listener.sh` (PROXY v2 TCP4 header + `GET /`, bounded) gets a 200. Otherwise it keeps the ordinary `127.0.0.1:8081` block byte-for-byte and prints a warning, so a checkout ahead of the web image never points Caddy at a missing listener. On a host Trinity provisioned (`/etc/trinity/public-ip` + an installed `caddy` unit), `start.sh --hosted` takes `/run/trinity-provision.lock` (`provision_lock`, shared with `--provision` and the refresh timer, which never queues) before touching `.env` or compose, moves an empty `FRONTEND_BIND_ADDRESS` to `127.0.0.1`, and after backend health plus a web-listener answer re-renders Caddy itself. The first switch restarts Caddy once (live streams reconnect); unchanged renders do not.
- **Not covered:** relayed MCP audit payloads and MCP inline sign-in (#848) keep the MCP container as their source — no end-user address reaches that boundary, which is why that path's limits are account-only. Historical audit rows are not rewritten. Cloudflare's own header delivery on every request class is not something this code can verify (observed on a quick tunnel, 2026-10-22: the edge always sent `CF-Connecting-IP` and `X-Forwarded-For` with the real client appended, and answered 403 itself to a client-supplied `CF-Connecting-IP`); absence degrades to `proxy_fallback`, not refusal. The loopback PROXY-protocol listener (`CADDY_PROXY_PORT`) trusts whatever connects to it from the host, so any process with a shell on the host can state a client address on that path: the boundary there is the host shell, by design, not this code.

### 2. MCP API Keys (User → MCP Server)

Created via UI `/settings?tab=mcp-keys`; format `trinity_mcp_{random}` (44 chars); SHA-256 hash stored in SQLite; sent as `Authorization: Bearer trinity_mcp_...`; MCP server validates via `POST /api/mcp/validate`.

Client config (`.mcp.json`):
```json
{
  "mcpServers": {
    "trinity": {
      "type": "http",
      "url": "http://localhost:8080/mcp",
      "headers": { "Authorization": "Bearer trinity_mcp_..." }
    }
  }
}
```

### 3. MCP Server → Backend (Key Passthrough)

The FastMCP `authenticate` callback validates the user's key via the backend and returns the `McpAuthContext`; MCP tools then call the backend API with the user's own key — the backend's `get_current_user()` accepts JWT OR MCP API key. In production (`MCP_REQUIRE_API_KEY=true`) the MCP server holds NO admin credentials.

### 4. Agent MCP Keys (Agent → Trinity MCP)

Each agent gets an auto-generated agent-scoped key (`scope='agent'`, `agent_name` stored for permission checks), injected as `TRINITY_MCP_API_KEY` env var and auto-added to the agent's `.mcp.json` pointing at the internal URL `http://mcp-server:8080/mcp`.

**Regenerable + self-healing (#1854).** The injection the agent server runs on every start early-returns unless **both** `TRINITY_MCP_URL` and `TRINITY_MCP_API_KEY` are set, and the creation-time mint is `try/except`-swallowed and sets them together — so a failed mint leaves an agent that never self-heals, and a Trinity-pointing `.mcp.json` entry under any name other than the literal `trinity` is never touched at all. Three surfaces close that: a **container config-truth probe** (`POST /api/agents/{name}/mcp-key/verify` — one `docker exec` returning ONLY `sha256(bearer token)` per entry, matched against `mcp_api_keys.key_hash`), a **start-time drift predicate** (`check_agent_mcp_key_matches`, the ninth `check_*_matches` in `start_agent_internal`; exempts `trinity-system` and ephemeral ghosts; fail-safe on error), and **owner-driven rotation** (`POST .../mcp-key/regenerate` — mint → reconcile `spawned_by_key_id` → deliver → DELETE the *captured* superseded ids; fail-closed lock; DB-only for a stopped agent; **returns no plaintext**). The self-heal takes the **same** per-agent lock as rotation and does nothing at all without it — the two run the identical capture→mint→DELETE sequence and there is no per-agent start lock, so an unserialised heal can delete the key a concurrent heal is about to bake in; a skipped pass mutates nothing and the next start retries. Delivery rides a new `env_overrides` kwarg on `recreate_container_with_updated_config`, applied last. No `docker/base-image/**` change — it works on every deployed agent with no rebuild. See [agent-mcp-key.md](../feature-flows/agent-mcp-key.md).

### 5. Agent-to-Agent Permissions

Enforced at **both** layers. The **MCP server** (`src/mcp-server/src/access.ts`) is the first fence and the readable refusal: `list_agents` returns only permitted agents + self; `chat_with_agent` and every `enforce` row block non-permitted targets. The **backend** holds the same line for an agent key used raw (trinity-enterprise#629). An agent-scoped key still resolves to its owner carrying the owner's role (Invariant #8), so every owner/access predicate said yes for any sibling — on an admin-owned install, every agent — and with its injected key and `TRINITY_BACKEND_URL` an agent could chat with, task, loop, read the history and logs of, or replace the git token of any sibling. `dependencies.agent_may_reach(current_user, target, manage=)` narrows it **in the shared gate, not per endpoint**: the **use** tier (`get_authorized_agent[_by_name]`, `assert_agent_access`, A2A inbound) admits itself, an `agent_permissions` edge target, or an agent it spawned with the key it holds now; the **manage** tier (`get_owned_agent[_by_name]`, `assert_agent_owner`) admits only itself or an agent it spawned — an edge means "may call", never "may manage". Outside its reach reads as the uniform 404 (#186). Every other principal is unchanged (`agent_name` is set only for scope `agent`). A capability is the explicit grant to manage the owner's other agents, so `get_skill_managed_agent_by_name` (ent#596) keeps the plain owner fence. Every inline `can_user_access_agent` / `can_user_share_agent` call ANDs the reach in, and `tests/unit/test_ent629_agent_reach.py` fails the build on a function that does not (exemptions carry their reason). **Fleet-level routes narrow the same way (trinity-enterprise#872).** Routes that take no single agent in the path (lists, counts, timelines, the event stream) read one reach source: `dependencies.principal_reach(current_user)` is `{self} ∪ agent_permissions edges ∪ agents spawned with its current key` for an agent principal (the same `agent_principal_name` predicate `agent_may_reach` uses) and None for everyone else. It is pure DB, bounded by a non-admin owner's accessible set, memoized on the request's principal, and every read fails closed to `{self}`; per-request capability reach is not part of it. `helpers.get_accessible_agents` / `accessible_agent_names` / `visible_agent_names` intersect with it (the two name accessors return the reach itself, never None, so `narrow_to_agent` access-gates `?agent=`), and so do the operator queue (`_accessible_set`, `narrow_to_agent_key`), the event-subscription list, `/api/tags`, the strict permissions view, onboarding, `/api/agents/slots`, `/api/telemetry/containers` and each row's `agents` on `GET /api/subscriptions`. Two fleet sweeps keep an agent key at its owner's accessible set (trinity-enterprise#706 D12): `GET /api/fleet/sync-audit` and `GET /api/monitoring/status` (MCP `get_fleet_health`), which return git/health state and no task text or emails; both are allowlisted in the guard with that reason. An admin shortcut that is not a reach read uses `dependencies.is_fleet_admin` (admin role on anything but an agent key), as the chat resume-session check does. Every `/api/system-views` route takes `require_person` (UI state, no MCP surface), and a view's `agent_count` counts only the agents the caller may see. The context-stats cache is written only by a fleet admin. `PUT /api/agents/{name}/shares/proactive` and `POST /api/ws/ticket` take `require_person`; `/ws/events` with an agent key connects as a non-admin slot whose roster is the reach (`ws_identity_service.event_stream_identity`, also on `refresh`), and an access-changing event (agent created, deleted, shared, unshared, renamed) re-reads that reach off the event loop, keeping the previous roster if the read fails; `GET /api/mcp/keys/{id}` answers an agent key for its own key only. For a non-admin person, `/api/agents/slots`, `/api/telemetry/containers` and `/api/tags` cover only that person's accessible agents, and `POST /api/ws/ticket` refuses system keys as well as agent keys. An admin person's views are unchanged. `tests/unit/test_ent872_fleet_reach.py` holds the behaviour per route and two AST guards: in `routers/`, `services/`, `client_portal/` and `main.py`, every `role == "admin"` comparison (any spelling) sits in a function that reads the reach (`principal_reach`, `is_fleet_admin`, `agent_principal_name`, `agent_may_reach`) or a person/admin gate, and every raw roster read (`db.get_accessible_agent_names`, `db.get_all_agent_metadata`, `db.list_subscriptions_with_agents`, `db.get_all_agents_*`, `list_all_agents_fast`) additionally passes when it calls a narrowing accessor; anything else is allowlisted with its reason. A narrowing accessor beside a role compare does not pass it, because the admin branch can still return the raw fleet; every call to a `db` method that runs `can_user_access_agent` / `can_user_share_agent` itself (the set is derived from `db/`) sits behind a narrowed gate. The MCP agent-to-agent gate asks `GET /api/agents/{caller}/reach/{target}`, which decides from the edge and the spawn record in the database, so a target with no container and a Docker read fault never read as "not permitted". Before #629 the backend applied only the owner's ownership/sharing checks. `current_user.agent_name` is read by notifications, event subscriptions, the ent#727 metrics cross-read, and the operator-queue broad list (trinity-enterprise#815): `GET /api/operator-queue` **narrows** an agent-scoped key to its reach (pure DB, `services/operator_queue_service/listing.py::narrow_to_agent_key` over `principal_reach`) so the page is complete before its limit. That is narrowing for completeness, **not an authorization point**; per-agent operator-queue routes are narrowed by the shared gate below (ent#629). **Restrictive default**: new agents start with zero permissions; grants are explicit via the Permissions tab (`agent_permissions` table).

**The MCP tool set is not an authorization boundary (#2996).** A `# mcp: none` header records what the MCP server exposes, not who the backend admits, so a human-only route must be fenced in the backend itself. Autonomy and the agent-config toggles (`routers/agent_config.py`) and the self-service credential/identity routes (`routers/users.py` email and GitHub PAT) are therefore fenced **at the backend** as human-only (§6, requirements `auth.md` §2.8), not only left out of the tool set.

**Residual, stated plainly (#1854).** The enforcement is `scope === "agent"`-conditional, so it holds only while the container's `.mcp.json` actually carries the agent's own key. A **user-scoped** key pasted into that file authenticates as the owner and bypasses the matrix silently — the platform accepts it. #1854 **detects** this (the config-truth probe above, verdicts `foreign_user_key` / `foreign_agent_key` / `shadow_entry`) and **repairs** it (drift predicate + rotation); it does not **prevent** it. Prevention needs a trustworthy request-origin signal, which does not exist on the MCP path today — the MCP server forwards no origin marker, and client IP cannot substitute: port 8080 is published on all interfaces, and an MCP call reaches the backend from the MCP container whatever the end user's address. (§1a moved the frontend off `trinity-agent-network` on prod/hosted, but a resolved client address is attribution, never an origin or authorization signal.) Deferred as Part 2b/3; if built it must be an explicit allowlist over **all five** scopes, since "reject non-agent" breaks the system agent, the connector and portal_delegate.

**Source-agent attribution is an allowlist over identity (ent#614).** `X-Source-Agent` is a raw client header. Every router that reads it — `/chat`, `/task`, `/fan-out`, loops, reminders, the manual schedule trigger — resolves it through `dependencies.resolve_source_agent` (the #1310 imperative family) before anything consumes it, and the three dispatch routers **rebind** the parameter so the raw value is unreachable downstream. The helper honours the header only when the principal can prove it names itself: an **agent-scoped** key naming its own agent (`User.agent_name`, the SELF-EXEC-001 rule that previously guarded `/task` alone) or the EVT-001 **event loopback**, whose `User.vouched_source_agent` the backend derived itself. A mismatch under either is a 403; **every other principal** — a JWT human, a user / system / ops / connector / portal-delegate key, any scope a later PR invents — is refused with a named 403, never trusted and never silently ignored. Before #614 a permitted user could set the header on `/chat` and forge an `actor_type='agent'` SEC-001 audit row (the human dropped, the hash chain certifying it), a `triggered_by='agent'` execution, and an `AGENT_COLLABORATION` activity plus a WebSocket edge on an agent they could not access — the third occurrence of the "header-keyed auth arm" class after #1672 and ent#265, which is why the fix is one gate rather than three more endpoint patches. The attribution-only routers read `current_user.agent_name or resolve_source_agent(...)`: the validated key first, because the MCP client sends no header on those paths. On the audit sites the agent branch now also carries the key owner's `actor_email` and the presented credential, so an agent row joins back to a human. The MCP server sends the header only for `scope === "agent"` on every tool (the schedules tool was the one exception, aligned in #614). The loopback token is a SECRET_KEY-signed JWT with `scope=event_loopback`, fenced in `get_current_user` to `POST /api/agents/{name}/task` and carrying a `source_agent` claim only for an agent-originated event — `emit_event` writes a JWT caller's USERNAME into `agent_events.source_agent`, which must never be certified as an agent. One stated residual, and one thing deliberately NOT vouched: `emit_event_for_agent` is `AuthorizedAgent`-gated (read access, not ownership), so any accessor of `{name}` — including a sibling agent's key, which resolves to the owner — may emit an event whose `agent_events.source_agent` is `{name}`; that is the endpoint's own contract and is tracked in the debt inbox, but the loopback **does not certify it** (`agent_originated=current_user.agent_name == name`), so such an event wakes the subscriber as an ordinary MCP-triggered execution and cannot mint an `actor_type='agent'` row or a collaboration edge on `{name}`. Separately, the enterprise skill runner deliberately lets a human act as an *accessible* agent via `assert_agent_access` — a different semantic, not this rule. Guard: `tests/unit/test_ent614_source_agent_attribution.py` walks the OSS tree and fails any function that reads `x_source_agent` without routing every use through the helper, plus a literal scan for the header name.

**What an edge exposes — declared skills by default (abilityai/trinity-enterprise#662).** The edge decides *whether* B may reach A; `services/peer_skill_policy.py` decides *what* B may invoke there. A peer (`Requester.kind == "agent"`, not A, not `trinity-system`, not a parent calling an agent it spawned with its current key — the ent#629 relation, parent → child only) may invoke A's **declared** skills; a **library-assigned** one — any `agent_skills` row for A, individual or set-propagated (`assigned_by="system"`, ent#530), except a #2914 `conflict` row whose on-disk copy is A's own — needs a per-skill grant (`agent_peer_skill_grants`, caller × target × skill; the ent#590 primitive). Enforced in the backend, not the MCP layer, so a raw-HTTP agent key is held too: `skill_gate_service.enforce` runs the peer check first (every admission seam), and the `execute_task` backstop no longer skips `enforce` on an agent with no gates while it holds library skills. A refusal is `SkillGateRefused(403, "skill_not_granted")` — the gate's named shape, so MCP and A2A render it unchanged — plus an `authorization` audit row `peer_skill_refused`; an unreadable assignment/grant read refuses a peer (503 `peer_surface_unavailable`). Granting is admin + interactive (`PUT/DELETE /api/agents/{caller}/peer-skills/{target}/{skill}`); the read (`GET …/peer-skills`) filters targets by viewer access AND `agent_may_reach`. A grant goes with its edge (`db/permissions.py` remove/replace delete it). The upgrade is surfaced, not silent: `GET /api/skills/peer-grants/drift` (admin) lists the pairs used in the last 30 days that are now refused (Settings → Agents notice). **Known gap:** matching is the gate's own text matcher, so a peer that asks in prose without naming the skill is not caught — the fix needs the runtime skill-origin marker (#2914) checked in-container (the ent#752 lane); follow-up abilityai/trinity-enterprise#925. Guard: `tests/unit/test_ent662_peer_skill_surface.py`.

### 5a. Agent Capabilities — the backend fence for owner-equivalent keys (trinity-enterprise#596)

§5's matrix lives at the MCP layer; the backend still resolves an agent key to its owner. For an act whose effect is to write into **another** agent, that is a fleet-wide skeleton key, so the backend now carries its own fence: a **capability** an instance admin grants to a named agent (`agent_capability_grants`, `db/capability_grants.py`). `skills.manage` is the first — changing any agent's skills, **its own included**, requires it.

- **Gate**: `dependencies.capability_refusal` / `enforce_agent_capability`, composed into `get_skill_managed_agent_by_name` on the four skill write routes. An **allowlist** (#2323): `ADMIN_GATE_SCOPES` (JWT, user key, `trinity-system`) pass unchanged; `agent` passes only with a live grant; every other scope is refused; an absent `mcp_scope` fails closed via the `_SCOPE_ABSENT` sentinel.
- **Order**: capability first, owner fence second — a non-holder gets one uniform named 403 (`skill_management_not_permitted`) for an existing, nonexistent or foreign target alike (#186), and a holder gains no reach beyond its owner's agents.
- **Orthogonal to §5**: the gate never reads `agent_permissions`, granting never writes it. Permission to call an agent and permission to change its skills imply each other in neither direction (ruling 2026-09-17).
- **A fence on the named routes is not enough** — the generic `PUT`/`DELETE /files` and `POST /files/mkdir` wrote the same `.claude/skills/**` bytes behind an ACCESS check, so they take the capability for that subtree (a delete of an ancestor counts). When a fence guards an effect, enumerate every route that produces the effect, not every route with the effect's name.
- **Audited**: every refusal (`capability_refused`, with agent and key id) and every grant/revoke.
- **Attribution**: `acting_agent_name` names the agent behind a write — `agent_name` for `scope=agent`, `trinity-system` for `scope=system` (which the backend otherwise strips) — recorded on `agent_skills.assigned_by_agent` (Tandem R29).
- **The gated-skill check (trinity-enterprise#751)** freezes a held request in `skill_gate_requests` and raises its approval to a person; only a person it is addressed to may end it (`may_end`), an admin may cancel but never approve, and those rows are among the person rows a machine key never reads (#715). The check reads the requester's own text, and every "could not tell" refuses.
- **The skill gate map (trinity-enterprise#753)** uses the same capability with two tighter bounds, through `require_person_or_capability("skills.manage", self_person_only=True)` (the trinity#3236 helper): a holder reaches only agents its owner OWNS (owner equality — never `can_user_share_agent`'s admin short-circuit, 404 otherwise) and never itself, because a gate constrains the agent and the constrained agent must not lift it (grant-vs-use). Every other principal must be a PERSON (`assert_person`), so the system key cannot change gates. An agent's unassign of a gated library skill keeps the explicit gate, so the skill writes' wider reach cannot launder one away. The read (`get_skill_gate_readable_agent_by_name`) is an allowlist decided on the principal first; an agent key reads its own gates or, as a holder, an owner-owned agent's.
- **Stated limits**: an agent writing its own `~/.claude/skills` from its shell; git pull into a sibling; (the other owner-equivalent routes were closed by ent#629).
- **ent#164 extends the seam** to `schedules.manage`, `instructions.manage` and `agents.manage` ([self-change-grants.md](../feature-flows/self-change-grants.md)). One place it LOOSENS rather than narrows: the five reconfigure routes were person-only under #2996 and now admit an `agents.manage` holder (`require_person_or_capability`). Those handlers authorise through `assert_agent_owner` → `can_user_share_agent`, which admits any admin — so the dependency itself bounds the holder to agents its owner **owns** (`owner_username` equality, 404 otherwise), and keeps `read-only` and `guardrails` person-only when the holder targets itself. The same bound (`_refuse_unless_owners_agent`) runs inside `capability_fence` for every fenced route that names a target, since those handlers go through `can_user_access_agent`, which has the same admin short-circuit. The out-of-scope routes are listed in the flow doc.
- **ent#629 × capability holders.** ent#629 narrows an agent key to itself, its edges (use only) and the agents it spawned. A capability is the grant to act on the owner's OTHER agents, but only on the routes that check it, so the reach it earns is **per request**: a capability fence (`capability_fence`, `require_person_or_capability`) that admits a holder records the target on the request's principal (`_admit_capability_reach` → `User._capability_reach`, private, one object per request), and `agent_may_reach` honours that record on both tiers. The fence records only after its owner bound (`owner_owns_agent`: `owner_username` equality, never the admin short-circuit), so a `schedules.manage` holder reaches a sibling's schedule routes, an `agents.manage` holder its reconfigure routes, and neither reaches anything else. Holding a grant is never reach by itself. The file routes check their capability inside the service, so `files._may_reach_for_path` applies the same bound directly: each file class the path touches (skills → `skills.manage`, instructions → `instructions.manage`) needs its grant, on an agent the owner owns. `skills.manage`'s own dependencies keep the plain owner fence (`get_capability_owned_agent[_by_name]`, also used by the skill-gate writes, trinity-enterprise#753). Manual schedule trigger carries no capability fence, so it stays narrowed. Reads are not widened.

### 5b. Outbound endpoint allowlist for A2A (trinity-enterprise#838, outbound-only since trinity-enterprise#885)

The one admin-declared relaxation of the A2A address rules (`services/a2a_trusted_networks.py`, setting key `a2a_trusted_networks`, requirements `mcp.md` §32.7):
- **Outbound:** `validate_a2a_endpoint_url` falls back to `_validate_trusted_a2a_url` only after the public-HTTPS rule refuses for scheme or address, at registration and on every call. An allowed host may be private/CGNAT and `http://`. Metadata, loopback and the platform's own networks stay refused.
- **Inbound: nothing reads the list.** Every inbound A2A call needs a Trinity credential or an x402 payment; a caller with no credential gets 401 whatever network it arrives from. The keyless door and internal-only scope #3361 shipped in rc1–rc3 were removed before 1.0 (ent#885), so no network position grants access and no source address is resolved for trust.
- **Load-bearing guards:**

  - Nothing broader than /8 (IPv4) or /32 (IPv6), and no one-label wildcard.
  - The generic settings PUT refuses the key.

### 5c. Agent Files surface — a ruled tier per verb (trinity-enterprise#820)

`db.can_user_access_agent` (admin | owner | shared) means "may chat with this agent". The six `routers/agent_files.py` file routes no longer inherit it as "may do anything to its files": each verb resolves through `services/file_path_policy.py::decide(tier, verb, path)`, one table for three tiers — `owner` (a person passing `_passes_owner_tier`: the owner or an admin), `share` (any other person, by JWT or by their own user-scope key), `key` (agent, system, connector, ops keys). `tests/unit/test_ent820_files_tier_census.py` fails when a `/files*` route has no ruled tier.

- **One policy, three consumers.** The module is pure stdlib and vendored byte-identical into the agent server (Invariant #5). It exports two write floors on purpose: the backend **route floor** (`write_denied` / `delete_denied`) and the agent server's narrower **platform floor** (`agent_server_edit_protected` / `agent_server_delete_protected`), because platform writers reach the agent server directly and write paths the user routes refuse (read-only mode writes `.claude/settings.local.json` without `platform=true`). `test_ent820_path_policy_parity.py` holds the platform floor to a subset of the route floor, the two copies to byte identity, and `hooks/guardrails-baseline.json::path_deny` to the policy in both directions.
- **Lexical vs resolved.** The backend decides on the path the caller named; the agent server resolves links. A link the agent made on request in chat could make one reach another class (`workspace/x/CLAUDE.md` with `x -> ../.claude`). PUT, mkdir, DELETE and the list root therefore resolve once (the parent only, for a mutation), refuse with `resolved_path_mismatch` when the resolved path's class set differs from the named one, then act by walking the resolved path with `O_NOFOLLOW` + `dir_fd`, so a link appearing after the check is refused, not followed. A link that stays in its class keeps working. A final-component link is never written through; DELETE unlinks it, never its target. The list never descends a link and stops at 20 000 nodes.
- **Published read surface.** `.trinity/pipelines` and `.trinity/pipeline-state` stay listable by share holders although they sit under a hidden directory (`PUBLISHED_LIST_DIRS`): the MCP pipeline tools read them for anyone with access (CLAUDE.md rule 8).
- **Old images.** A share holder's write, delete or mkdir is refused with `agent_restart_required` until the agent runs an image whose router carries `_walk_dir_nofollow` (probed like ent#819's read probe, cached per container + image). Agent keys pass and their audit row carries `unverified_image: true`.
- **Hard links.** Below the owner tier, download/preview refuse a file whose link count (`X-File-Nlink`, sent by the agent server) is above 1 (`hardlinked_file`): a second name for a credential is invisible to every path pattern. A pre-#820 image sends no count and is served as before.
- **Audit.** One `agent_files` row per write / delete / mkdir (`file_write`, `file_delete`, `file_mkdir`), every caller; tier refusals are `authorization` rows (`file_*_refused`).
- **Residuals (ent#926).** The agent itself can still be asked, in chat, to copy or edit what these routes refuse; the Files tier is the platform boundary on the API, not on the agent's own tools. `/app` is owned by the agent user, so the image probe reads a file the agent could rewrite (pre-existing).

### 6. System Agent

`trinity-system` has `scope='system'`: bypasses all permission checks, can call any agent/tool, cannot be deleted via API. Purpose: platform operations (health, costs, fleet management).

| Scope | MCP Enforcement | Backend Enforcement |
|-------|-----------------|---------------------|
| `user` | Owner/admin/shared checks | Owner/admin/shared checks |
| `agent` | Explicit permission list (`agent_permissions`) | Resolves to owner user; ownership/sharing checks, plus the §5a capability fences (`skills.manage`, `schedules.manage`, `instructions.manage`, `agents.manage`) |
| `system` | **Bypasses all checks** | Resolves to owner user (system agent owner) |
| `connector` | Consumption-only, bound to ONE agent (ent#46): connector-only tool set (`list_playbooks` / `run_playbook` / `ask`), operator tools hidden via `connectorOnly`; the playbook allow-list is authoritative | `_enforce_connector_scope` at the single auth entry point **fences it to two routes** — its bound agent's `/chat` + `/connector/playbooks`; every other path 403s (ent#46 → #118) |
| `anonymous` | #848 keyless pre-login tier, **only when `MCP_INLINE_AUTH_ENABLED`**: sees `request_login`/`verify_login` + the connector tools, which refuse to act until an email is verified. Never satisfies `operatorOnly` — `scope` stays `anonymous` after login | Holds no *key*, so it never authenticates to the backend directly; the MCP server relays over `/api/internal/mcp-auth/*` and the backend re-gates every call on `db.email_has_agent_access(agent, email)`. It is **not credential-free**, though: with nothing on the wire to re-present, the verified identity is resolved per request from a store keyed on `Mcp-Session-Id`, which makes that header **bearer-equivalent for this tier** — serve the MCP port over TLS only, keep it out of logs, and note the 30 min idle / 4 h absolute expiry is the only thing that ends a session (#2035) |
| `portal_delegate` | n/a (not an MCP tool principal) | **Fenced to a single route** — may only exchange an asserted end-user email for a portal session; every other path 403s (ent#163) |
| `ops` | n/a (not an MCP tool principal — `OPERATOR_SCOPES` is an allowlist, so it is excluded by construction) | **Fenced to a read-only route allowlist** — fleet health, telemetry, roster/capacity, execution reads and the live log relay, subscription reads. Every write 403s. Admin-minted and human-only to mint. Additionally kept OUT of `ADMIN_GATE_SCOPES`, so an admin-gated ops route must opt in with `assert_admin(..., allow_scopes={"ops"})` — or `Depends(require_admin_allowing("ops"))`, the `Depends` spelling added in #2389 because `require_admin` took no `allow_scopes` and an allowlisted route gated that way was dead to ops keys **with no opt-in available**. The opt-in makes the grant **per route** (a new ops route is inaccessible until added), and it is an **ADDITIONAL gate, never a substitute one**: the scope is admitted and `role == "admin"` still runs afterwards, so an ops key is a *narrowing* of its owner, not a *decoupling* from them. The tier therefore does **not** survive its owner being offboarded — demotion 403s it, and `get_current_user` rejects a suspended owner (#995) one layer up regardless; an earlier revision of this row claimed otherwise, which an operator would have acted on. Dropping the role check for the opted-in scope was refused: it would make the bounded tier harder to revoke than the unbounded `user`-scoped key it exists to displace, while still not delivering the claim. Mint ops keys under a service admin account that is not offboarded with people (#2323/#2389). **The fence and the gate must agree**: `GET /api/subscriptions/{id}/usage` shipped admitted by the fence and refused by its own bare `assert_admin`, so the subscription-pressure read the fence was measured for could not work — a guard asserting only the fence half gave false assurance. A live-handler scan now reds when any allowlisted route calls `assert_admin` without the opt-in, and a sibling scan reds on bare `require_admin` — closing the *shape* rather than the instance (#2389) |

Only `user`/`agent`/`system` are the credentialed **operator** tier — the allow-list `OPERATOR_SCOPES` in `server.ts`. Every other scope is deliberately outside it, and widening that set is a deliberate edit pinned by `tool-visibility.test.ts`: the gate was previously a `!== "connector"` deny-check, which admitted every scope it had not heard of — including a null auth context, where FastMCP skips `canAccess` filtering entirely (#848). `portal_delegate` (ent#163) is the clearest illustration of why the deny-check shape was untenable: it is not an MCP tool principal at all, yet a `!== "connector"` gate would have advertised it every operator tool the day it was introduced.

**`/ws/events` is a second auth entry point, and it is allowlisted too (#2389).** That handler
calls `db.validate_mcp_api_key` itself and never runs `get_current_user`, so **none** of the
fences above reach it — the ops fence's own "enforced at the single auth entry point" claim was
false for exactly one surface, and it is the broad one: the stream carries fleet-wide
`agent_activity` and execution events scoped by the **owner's** accessible agents, which for an
admin owner is everything. `dependencies.WS_EVENT_STREAM_SCOPES = {None, "user", "agent",
"system"}` gates it (close code 4003), so `ops` cannot read outside its allowlist, and
`connector`/`portal_delegate` — fenced to one or two routes everywhere else — lose a hole that
predates #2323 rather than keeping it out of politeness. An unknown future scope is refused by
construction, matching the allowlist rule below. `agent` is admitted but **not wholesale**: the
same absence of `get_current_user` also skips `_enforce_ephemeral_key_fence`, whose entire point
is that a ghost's key on an untrusted workspace must not be a fleet skeleton key — so the gate
takes the key's `agent_name` and refuses an `is_ephemeral` row, using the fence's own predicate.
That sub-check fails **CLOSED**, deliberately inverting the ephemeral fence's fail-open: that
fence guards heartbeats and result callbacks where a DB blip must not take the fleet down, while
losing this stream costs an observability client a reconnect. Presence of the `is_ephemeral` key
is what makes the answer real — `get_agent_ephemeral_info` coalesces the column for every live
row, so a dict without it is no row at all (or a stand-in), and a bare `.get()` would map that
onto the same falsy value a genuine durable agent gives.

**Fences read the routed path, never `request.url` (#3102).** Starlette rebuilds `request.url` from the `Host` header, so a Host carrying `/`, `?` or `#` makes `request.url.path` name a different route from the one dispatched. Every route fence in `get_current_user` (event loopback, `portal_delegate`, connector, ephemeral, ops) and every audit `endpoint=` label reads `request.scope["path"]`. Nothing sets `root_path`; adding one makes the allowlists 403 (fail closed) until the fences strip it. Defense in depth: `utils/host_header.HostHeaderGuard`, a pure-ASGI middleware registered last in `main.py` so it runs first, rejects a Host containing `/ ? # \ @`, whitespace or control characters (HTTP 400, WebSocket close 1008). Guard: `tests/unit/test_3102_host_header_fences.py` drives each fence with a real Starlette request and a crafted Host, and fails on any `.url.path` read in `src/backend`.

The same reasoning governs the backend side. `scope` is a free-text column with **no CHECK constraint**, so this table is a snapshot of live values, not a closed set. Guards over it must be **allowlists**: `reject_agent_principal` + `_reject_connector_principal` between them cover only `agent` and `connector`, and a `scope='system'` key sets neither field, so both are no-ops for it while it still resolves to the key owner carrying the owner's role. `reject_non_interactive_principal` (#1854) inverts this — it passes only when `User.mcp_scope is None`, i.e. the caller came through the JWT branch — and gates the credential-lifecycle routes (agent MCP-key read/verify/rotate). Key revoke/delete (`/api/mcp/keys/*`) and the connector key mint additionally run the agent+connector pair, because `db.revoke_mcp_api_key`/`delete_mcp_api_key` skip the ownership check entirely for admins and an agent key inherits its owner's role (#1854).

**Two human-only rules, one primitive family (#2996 / ent#711).** The owner tier cannot refuse agent keys inside `can_user_share_agent` / `assert_agent_owner` the way #1890 did at the admin tier — agents legitimately drive owner-gated routes (MCP schedule tools, file writes) — so the rule is applied per route, from `dependencies.py`: **PERSON** (`assert_person` / `Depends(require_person)` over `is_person_principal`: JWT or the person's own `user` key) for routes that grant or change what an agent may do, and **INTERACTIVE** (`Depends(require_interactive)`: JWT only) for routes that mint, bind or rotate a credential or sign-in identity, including `POST /api/mcp/keys`, `ensure-default` and the whitelist add (`POST /api/settings/email-whitelist`, every role, its `assert_admin` kept; trinity-enterprise#717 took it out of the frozen baseline) — a minter must be stricter than the class it mints or PERSON is circular. Both are allowlists and fail closed on a missing `mcp_scope`. They differ on the backend-minted event-loopback JWT: PERSON refuses every loopback token (`is_person_principal` checks `is_event_loopback`, ent#751); INTERACTIVE refuses only one carrying `vouched_source_agent`, so a loopback JWT without a source agent passes the INTERACTIVE route gate and is stopped only by the `get_current_user` entry fence, which refuses every loopback JWT on every route but the subscriber-task dispatch. The shared admin allowlist (`ADMIN_GATE_SCOPES`) is unchanged. **The inheritance mechanism is a route census**, not a gate change: `tests/unit/test_2996_human_only_routes.py` classifies every OSS HTTP route (all methods, `rglob` over `src/backend/`, `enterprise/` excluded) into exactly one policy class — gated, admin tier, widened admin, portal, or a reviewed `agent_callable_self` / `agent_callable_any` / `own_auth` / `delegated` entry with its `METHOD /path` pinned — and freezes the rest in a shrink-only baseline (`tests/unit/fixtures/human_only_route_baseline.json`, exact count), so a new route of any method fails CI until it chooses a side. A runtime sibling (`test_2996_route_census_runtime.py`) imports the real app in a subprocess and cross-checks the stored paths.

**The agent-key self-gate is one helper the census recognises (trinity-enterprise#840).** Because an agent key resolves to its owner, the access check answers "may this key reach that agent" (its ent#629 reach), never "is it acting on its own agent"; ten modules had copied that second check by hand, and `seat_decisions` shipped without it (ent#839). `dependencies.assert_own_agent(current_user, agent_name, *, detail, refusal=None)` is now the only spelling: a 403 with the route's own message when an agent key names another agent, a no-op for every other principal, called as the handler's first statement so it runs before any lookup. The census recognises that shape — the name imported unaliased from `dependencies`, a `get_current_user` / `CurrentUser` principal, and the `name` / `agent_name` parameter named in every route path — or `Depends(get_self_acting_agent)`, and **also** requires an `AGENT_CALLABLE_SELF` entry saying why the route is a use, not a grant (the `admin_widened` shape). The gate alone never classifies a route, so every self-gated route reaches review with a written reason — and that reviewed reason, not a code check, is what keeps a self-scoped grant out: a listed entry passes every check, as entries in the old `AGENT_CALLABLE` table did. Every other agent-callable route is an `AGENT_CALLABLE_ANY` entry that answers, in its own field, why an agent other than the one in the path may reach it. `test_1310_auth_wiring.py` refuses a hand copy anywhere under `src/backend/` — the principal's agent name as an attribute, a `getattr`, `agent_principal_name` or a local bound from one (also as an operand of `or` / `and` / `… if … else …`), compared with `!=`, `is not`, `not in`, a negated `==`, or an `==` whose `else` refuses, guarding any `raise` or a returned 401/403/404 — against a `name` / `agent_name` parameter or a local alias of one (the stated limit: a comparison against a differently-named parameter is not matched), and `test_ent840_agent_self_gate.py` calls every `AGENT_CALLABLE_SELF` handler with a sibling's key. Not closed: a `system` key and the event loopback carry no agent name and pass every self-gate (trinity-enterprise#719).

### 7. External Credentials (Agent → External Services)

CRED-002 file-injection model (Invariant #12): `.env` (KEY=VALUE source of truth) + `.mcp.json` edited directly; encrypted backup `.credentials.enc` (AES-256-GCM, safe for git); auto-import on startup if `.credentials.enc` exists without `.env`. Flow: Quick Inject writes `.env` → Export encrypts to `.credentials.enc` → agent start decrypts and writes files. OAuth providers for agent credentials: Google, Slack, GitHub (PAT), Notion. Common MCP servers inside agents: google-workspace, slack, notion, github, n8n-mcp.

**File routes (trinity-enterprise#819/#823).** Owner tier (PERSON gate, then owner-or-admin) for reading credential paths (`services/agent_service/files.py::_enforce_owner_tier_read`, audited); the per-verb tier follows separately. The agent server opens reads without following any link and serves that descriptor (`agent_server/routers/files.py::_open_for_read`); PUT / mkdir / DELETE never reach the runtime config paths, matched on the resolved target (`_RUNTIME_CONFIG_PATHS`). Agents not yet on that image (a conclusive probe is cached per container and image) refuse reads by anyone but a person who is the owner or an admin, agent keys included, until stopped and started through Trinity. Write side: hook `path_deny` and the agent-server name lists. Detail: `feature-flows/file-browser.md`.

## Container Security

- **Non-root execution** (Invariant #17, #874): backend and scheduler as `trinity` (UID 1000), MCP server as `node` (UID 1000), frontend as `nginx` (UID 101), agents as `developer` (UID 1000). Backend needs `group_add: ${DOCKER_GID:-999}` for Docker socket access on Linux.
- `CAP_DROP: ALL` + `CAP_ADD: NET_BIND_SERVICE`; `security_opt: no-new-privileges:true`; tmpfs `/tmp` with `noexec,nosuid` (RAM-backed, default 512 MB — operator-tunable via `AGENT_TMP_SIZE` on the backend service, validated `^\d+[mg]$` with invalid→default; `noexec,nosuid` stay fixed; counts against the agent memory cgroup; creation-time, so existing agents pick up a change on recreate not restart, #1231. Heavy scratch like pip/npm/ML wheels is redirected via a default `TMPDIR=/home/developer/.tmp` on the disk-backed home volume, created at start by `startup.sh`; mount spec + TMPDIR default live in `services/agent_service/capabilities.py` so create/recreate/system-agent can't drift, #1098); no external UI port exposure; network isolation per Network Topology above.
- **Bounded container logs (#1871).** Docker's `json-file` driver has no default `max-size`/`max-file`, so every container log grew forever under `/var/lib/docker/containers/` — silently, until the Docker data root hit 100%, dockerd could no longer parse its own logs, and the whole fleet wedged at once (2026-07-27). Two halves, because compose cannot reach agents: the platform services share an `x-logging` anchor in **all three** compose files (`CONTAINER_LOG_MAX_SIZE`/`_MAX_FILE`, default `10m`×3; the #2280 hosted file's parity with prod is CI-guarded), and SDK-created agent containers use `AGENT_LOG_CONFIG` in `services/agent_service/capabilities.py` (`AGENT_LOG_MAX_SIZE`/`_MAX_FILE`, same default), threaded into the three agent-container create sites beside `AGENT_TMPFS_MOUNT`. Validation is fail-safe in **both** directions — malformed *and* out-of-range (>1g, >10 files) fall back to the bounded default, because a well-formed absurd value like `1000g` passes a format-only check while effectively removing the cap, which is the exact failure the constant prevents; an explicitly-set rejection logs a WARNING (a silently-ignored knob is the #1039 inert-by-obscurity class). Creation-time like the tmpfs spec: platform services adopt on the next `docker compose up`, existing agents on **recreate**, not restart. The raw Docker log is a *secondary* copy — Vector's aggregate at `/data/logs` is the primary queryable one and keeps its own `LOG_RETENTION_DAYS`; live streaming is lossless across rotation (only post-hoc `docker logs` history shortens, and the UI's log endpoint defaults to `tail=100`). `tests/unit/test_1871_log_config_parity.py` is the CI guard that fails when a **new** durable-container create site ships without `log_config` (the `learnings.md` 2026-07-10 "the create path is never one call site" class).
- **Compose files are three standalone stacks, not base + overlays (#2528).** `docker-compose.prod.yml` and `docker-compose.hosted.yml` each restate `security_opt`/`group_add`/`cap_drop` because nothing else supplies them — they are the hardening, not duplicates of the dev file. Stacked on `docker-compose.yml`, Compose concatenates list keys: ≥ 2.24 rejects the duplicate items, older versions silently double the frontend `ports` and the container never joins its network. So the "remove the duplicates from prod" hotfix strips the hardening from the file that runs alone. The supported sets (dev[+override], prod[+enterprise], hosted[+override]) are rendered in CI (`container-security.yml` → `verify-compose-file-sets`, `--env-file /dev/null`), stated in both file headers, and tabulated in `docs/DEPLOYMENT.md`; `quickstart.sh` is an alias for `start.sh` so no entrypoint bypasses the HOST-015 data-switch guard, which now names prod and warns when both stores exist. Requirements: `infrastructure.md` HOST-019..021.
- **Internal API security (C-003)**: `/api/internal/` endpoints (scheduler, agent containers) require the `X-Internal-Secret` header; falls back to `SECRET_KEY` if `INTERNAL_API_SECRET` unset.
- **Agent-server inbound auth (#1159)** (details in [agent-server-authentication.md](../feature-flows/agent-server-authentication.md)): every backend→agent call carries a per-agent `X-Trinity-Agent-Token` = `HMAC-SHA256(AGENT_AUTH_SECRET, "trinity-agent-auth:v1:"+name)` — *derived*, not stored; the master lives only in backend env, so a compromised agent can't compute a sibling's token. A **pure-ASGI** middleware (`docker/base-image/agent_server/middleware/auth.py`) enforces it on **all** HTTP **and** WS routes via constant-time compare, exempting only exact `/health` (+ `OPTIONS`) — pure-ASGI (not `BaseHTTPMiddleware`) so it gates WS scopes too and never buffers SSE. The dead unauthenticated `/ws/chat` route (ran arbitrary Claude) was removed; CORS dropped (internal-only). Grace path: empty `TRINITY_AGENT_AUTH_TOKEN` → allow (old-image); `check_agent_auth_token_env_matches` forces a one-pass recreate so a missing/stale token re-injects. Backend fail-closed (`derive_agent_token` raises on empty secret; `start.sh` auto-generates the hex32 master, all three compose files forward it (dev, prod, and the #2280 hosted file)). Callers route through `services/agent_auth.py`; a static guard (`tests/unit/test_agent_auth_header_guard.py`) fails any raw `agent-{name}:8000` caller that skips them.
- **WebSocket security (C-002, #550)**: single-use ticket auth — see [Real-time Delivery](integrations.md#real-time-delivery-reliability-003-306).
- **Guardrail registration is root-owned (ent#345)**: the GUARD-002 hooks are registered in `/etc/claude-code/managed-settings.json` — Claude Code's admin-controlled managed-settings path, which takes precedence over user/project settings and sits **outside** the agent's HOME and the git-synced tree. It ships root:root `0444` inside a root-owned `0755` dir, so without `sudo` the file cannot be rewritten and the dir cannot be used to replace it or shadow it via `managed-settings.d`. `developer` holds `NOPASSWD:ALL`, so `sudo` can still rewrite it (see the root-ownership note below); `bash_deny` denies the obvious spellings (any `sudo` command naming `/etc/claude-code`, `/opt/trinity` or `/etc/sudoers`, `visudo`, and root shells via `sudo -i`/`-s`/`su`/bare shell, #3105). That is a speed bump against a determined agent. It used to be `/home/developer/.claude/settings.json`, owned by `developer` at 0644 *inside the synced repo*: the guarded agent could edit its own guardrail registration (one `Edit` disables the bash deny-list, file guard, read-only guard and output-scanner for every later tool call — observed in the wild during #2036), and a push to the agent's repo could set it from outside. No platform-owned `settings.json` is shipped into `~/.claude` any more. The failure mode of the new path is **silent** (no registration ⇒ no hooks, nothing logged), so `startup.sh` asserts existence + non-writability each boot and logs `GUARDRAILS: ERROR …`; it reports and continues, since a registration fault must not become a fleet outage. The agent's `/health` re-stats the file on every request and reports `guardrails_registration` (`ok`/`missing`/`not_root_owned`/`writable`, enum only, #3105); a `sudo` rewrite that keeps root:root `0444` still reads `ok`. The four GUARD-002 hooks (`bash-guardrail`, `file-guardrail`, `read-only-guard`, `output-scanner`) register in exec form (trinity-enterprise#787): `/usr/bin/env -i HOME=/home/developer /usr/local/bin/python3 -I -S /opt/trinity/hooks/<hook>.py` as `command` + `args`, `timeout` 30. No shell runs, so `CLAUDE_CODE_SHELL_PREFIX` does not wrap them, and no inherited `PYTHON*`/`LD_*` variable or user site reaches them; the file's policy `env` pins `CLAUDE_CODE_SHELL_PREFIX` to `""`, and the name is in `execution_env.PROTECTED_KEYS`, so `.env` cannot set it. The image build runs `guard002-smoke.py`, which executes each hook exactly as the managed file registers it against known inputs and fails the build otherwise. Read-only mode adds no second registration: it writes a config file the baked hook reads. That file is `/opt/trinity/read-only-config.json`, root-owned `0444` on the container's writable layer, written or removed by the backend through a root `docker exec` and re-synced on every agent start; it decides whenever it exists, in both the guard and the Codex runtime. The backend also writes the agent-owned `~/.trinity/read-only-config.json`, which decides only while the root file is missing (after a recreate drops the writable layer and before the start-time sync, or under an older backend) and is the only file a pre-trinity-enterprise#787 image reads; neither present means not read-only.
- **The gated-skill hook (trinity-enterprise#752)** is registered the same way, but in its OWN drop-in, `/etc/claude-code/managed-settings.d/50-skill-gate.json` (root:root 0444, dir 0755). The main file stays unedited, and a rejected entry voids only the drop-in. It runs in exec form under `env -i` + `-I -S`, so neither a repo-settings `CLAUDE_CODE_SHELL_PREFIX` / `BASH_ENV` nor a user-site `usercustomize` reaches it, and `LD_PRELOAD` / `LD_LIBRARY_PATH` / `LD_AUDIT` are pinned empty by managed `env` (policy scope, applied last). It reads its identity from `/proc` (the claude process's launch env; the container's), clears its own env before any network call, and follows no proxy or redirect. Its check (`POST /api/skill-gate/check`) takes the agent from the KEY (`dependencies.get_self_agent` → `get_self_acting_agent`): an agent key acts as itself, the system key as `trinity-system`, and every other principal gets the uniform 403 `agent_identity_required` before the access 404. It is a use, not a grant (census `AGENT_CALLABLE_ANY`: the agent comes from the key, so there is no sibling to name); ephemeral keys stay outside `_EPHEMERAL_ALLOWED_ROUTES`. It fails closed only where the root-owned marker says the agent has gates. Same caveat as above: it stops accidents and the ordinary prose path, not an agent using `sudo`; the boundary is credential confinement (R23, trinity-enterprise#558). The four GUARD-002 hooks in the main file register under the same exec-form invocation (trinity-enterprise#787, above).
- **Git credentials never enter a remote URL (ent#615)**: a remote Trinity persists carries **no userinfo**; the credential is resolved per operation by the `trinity` **git credential helper** (`/usr/local/bin/git-credential-trinity`, registered in `/etc/gitconfig`), which git speaks to over stdin — a channel that never reaches argv and is never persisted. Before this, every agent's remote was `<scheme>://oauth2:<PAT>@<host>/…`, so the fleet-wide PAT was at rest in `.git/config` on the workspace volume AND expanded into `git-remote-https`'s argv on every fetch/push (including the 60s sync-health poll), from where `ps` → the agent server's reaped-cmdline logging → Vector → the host log files → the logs API carried it into **another agent's LLM context**; ent#292 closed the last hop of that chain and was rated P0. Three properties are load-bearing and each cost a design iteration: the helper is registered as **`trinity`**, never as its filename (git prepends `git-credential-` to any non-absolute value, so the filename resolves to a command that does not exist and the helper silently never runs — a fleet-wide fetch/push outage that no source-only CI can see); it is registered **unscoped** and matches protocol+host **exactly, port-inclusive**, inside itself, because `TRINITY_GIT_BASE_URL` is a *runtime* value a build-time `credential.<base>.helper` could not know (a suffix match here would instead be an exfiltration primitive); and its ladder is **`.env` → baked `Config.Env` → `/home/developer/.trinity/git-credential`**, the INVERSE of `startup.sh`'s, because `startup.sh` runs at boot where baked env is the freshly-recreated truth while the helper runs in steady state where `Config.Env` is immutable without a recreate and `.env` carries the live-injected token — baked-env-first would make a global rotation (#1967) a silent no-op until the old token is revoked. **Root ownership is neither confidentiality nor a boundary**: `GITHUB_PAT` remains in the agent's env and `.env` and invoking the helper returns it, and `developer` holds `NOPASSWD:ALL`, so an agent that wants to rewrite `/usr/local/bin/git-credential-trinity` or `/etc/gitconfig` can `sudo` and do it. What root ownership buys is that nothing rewrites them BY ACCIDENT (an errant `pip install`, a template hook, a skill writing to `$HOME`) — do not build a guarantee on it. The structural fix is a broker outside the container (ent#558, AAuth). Standing rule for every path that touches a remote: **never strip a credential you have not already replaced** — `git_service.scrub_git_remote_tokens` proves the helper resolves (by **exit code**; `git credential fill` prints the credential on stdout and the sweep's output crosses the `docker exec` boundary into the platform log) before it strips anything, and refuses-and-reports otherwise. **The report must be earned**: both config writes are `|| true`, so a container whose exec can read but not write (`agent_full_capabilities=false` withholds `DAC_OVERRIDE`, and the home is 0700 `developer`-owned) silently kept its token while the counter was incremented anyway — the sweep now re-reads and counts only what is really gone. For the same reason it reports `root_readable`: all-zeros is ALSO what a clean agent reports, so without that flag *“could not even look”* is indistinguishable from success on exactly the hardened installs that act on it (the #1638 class). Requirements: `security.md` §20.9b, `github.md` §11.16.
- **Frontend XSS (H-005)**: all markdown rendering uses DOMPurify via `utils/markdown.js`; no direct `v-html` with unsanitized content.
- **Rate limiting (#1023)**: shared sliding-window limiter `services/rate_limiter.py` — Redis sorted-set rolling window (no fixed-window boundary burst), fail-open with bounded per-worker in-process fallback; `enforce(key, limit, window)` raises 429 + `Retry-After`, `check(key, limit, window)` is the non-raising variant for background loops. New request-rate limits reuse this primitive — don't hand-roll Redis counters. Current consumers: webhook trigger (#1023), agent reports (#918), operator-queue create ingestion (per-agent + fleet, `check`, #1632). Intentionally NOT unified under it: the auth login/OTP limiters in `routers/auth.py` are failure-counters (increment on failure, reset on success) — a different pattern. Every per-IP key, in either pattern, is the canonical client address of §1a, never a header value. A global ASGI middleware with a route→policy table is a tracked follow-up.
- **Secret scanning (#1164)**: `.github/workflows/secret-scan.yml` runs the gitleaks MIT CLI on every PR (commit-range scope, `contents: read`, `--redact=100`) to block a re-landed credential (the `re_`-prefixed Resend key removed in #1158); config + custom `re_` rule + allowlists in `.gitleaks.toml`. Commit-time source scanning — complementary to GUARD-002's runtime output scanning. Non-blocking until a repo admin makes it a required check (follow-up).
