### MCP Server (`src/mcp-server/`)

FastMCP, Streamable HTTP transport, port 8080. API-key auth via `Authorization: Bearer` header; FastMCP `authenticate` callback validates keys against the backend and stores an `McpAuthContext` in session: `{userId, userEmail, keyName, agentName?, scope: "user"|"agent", mcpApiKey}`. Agent-to-agent collaboration uses agent-scoped keys for access control.

**Tools** — 129 across 33 tool modules (`src/tools/`), plus `dynamic-agents.ts`, which registers the per-agent `chat_with_<slug>` tools at runtime (#846). Every backend router outside the by-design exclusions (`internal`, `setup`, `auth`, `public`, `paid`) declares its MCP surface in a first-line `# mcp:` header — `# mcp: <module>.ts (<tools>)` when its tools live in a differently named module, `# mcp: none — <reason>` when it is deliberately unexposed (Invariant #13). The tool table follows the policy note below:

**A self-acting tool takes its identity from the key, and the platform's own agent has a system-scoped one (#2975).** `report`, the four canvas tools and the four metrics tools declare no agent-target parameter on purpose — they act as the caller, so there is nothing to spoof and the identity must come from the credential. Each resolved that itself with `scope === "agent" && agentName`, which refused `trinity-system`: `system_agent_service` mints its key agent-scoped and then flips the scope to `system` (`_set_system_scope`), and #1816 makes that permanent — the orchestrator's key is never re-minted as `agent`, so "give it an agent-scoped key instead" is not an available fix. The platform's own agent could read every surface and publish nothing; its daily fleet-health report and its canvas fell back to files and the operator queue. `access.ts::resolveActingAgent` is now the single rule, for the same reason `checkAgentEdge` is: the refusal had three copies and the fourth would have shipped with the old one. It stays an ALLOWLIST over a free-text `scope` column (#1854, #2323) — `agent` and `system`, and only when the key CARRIES an `agentName`, which comes from the key row and never from a parameter. `connector` is the one worth naming as excluded: it carries an `agentName` too (it is bound to one agent) but it is an END USER's consumption key, so admitting it would let a client publish as the agent serving them. The backend half already worked: those routes are `AuthorizedAgent` plus a self-gate that reads `current_user.agent_name`, which is set only for `scope == "agent"` (`dependencies.py`), so a system key was never the thing refusing.

**Agent-access policy is a mechanism, not a per-tool discipline (ent#628).** `src/access.ts` holds ONE implementation of the agent-scope permission edge (`checkAgentEdge`: system bypasses; an agent key reaches itself and its `agent_permissions` targets, read fail-closed; a user key passes through because the backend already scopes it by role and per-user grant; any other scope is denied — an allowlist, #2323) and `TOOL_ACCESS_POLICY`, one row per registered tool: `enforce:{param}` (the registration wrapper `withAgentAccess` gates the parameter before `execute`), `in-tool:<how>` (the tool resolves its own target — a loop/item/report id, a bound agent, or a module-local gate not yet consolidated), `baselined:<owner>` (ungated at the MCP layer; the owner is the issue or backend fence that holds the line — the ent#629 rows are that ruling's work list), or `none:<why>`. `server.ts::addToolWithAudit` runs `policyFor` for every tool: no row, an `enforce` on an undeclared parameter, or a `none` on a tool whose parameters name an agent throws at startup, so a tool added tomorrow cannot register without declaring. Dynamic tools pass their policy to `registerDynamicTool`. Before this, the gate had ten spellings across nine modules and the tool added last called none of them. It is a tool-surface gate: the REST routes behind the tools resolve an agent key to its owner (Invariant #8); whether that boundary should hold one hop down is ent#629. `access.test.ts` boots `createServer` against the real table. A denial any gate RETURNS is labelled on its audit row (`success: false`, `denied: true`, `error: <reason>`) by the stamp `access.ts::accessDenied` leaves on the per-call context and `audit.ts::withAudit` reads back after `execute` (#2807); the caller's JSON is unchanged, and `audit-denial.test.ts` fails a deny branch or an `error: "Access denied"` envelope that bypasses the helper.
