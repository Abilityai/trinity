### Agent Containers

**Base image** `trinity-agent-base:latest`: Python 3.13, Node.js 24, Go 1.21, Claude Code (latest), common Python packages.

**Node major vs the persistent npx cache (#3886):** the Node runtime is in the image, but `~/.npm/_npx` is on the home volume and survives a recreate, and npx reuses a cached tree without rebuilding it — so after a Node major bump an npx-launched MCP server with a native addon fails with `NODE_MODULE_VERSION` mismatch. `startup.sh` stamps the image's Node major in `~/.trinity/node-major` and drops `~/.npm/_npx` when it differs (a cache with no stamp predates the stamp and counts as a change); project `node_modules` are never touched. Every Node pin in images and CI is held to a non-EOL LTS line by `tests/unit/test_3886_node_runtime_lifecycle.py` — date-dependent by design, so the day a pinned line reaches end-of-life every PR goes red.

**Internal server** `agent-server.py` (FastAPI, port 8000):
- `/api/chat` - Claude Code execution (messages persisted to database)
- `/health` - Health check. Returns `{status}` plus `active_tasks` (concurrent executions across `/api/chat` + `/api/task`), `last_task_at`, `consecutive_failures` (reset on success — consumed by the dispatch breaker #526 and fleet health #307), the #333 `diagnostics` gauges (#1020), and `clone_status` (`ok`|`failed`, #1439) — a coarse, server-computed identity-clone signal read defensively from the untrusted `.git-clone-status` marker (enum only, never the agent-supplied repo/branch/error strings, since `/health` is unauthenticated) that lets `monitoring_service` mark a silently-failed GitHub-template clone **unhealthy** instead of reporting a running-but-empty agent healthy. `guardrails_registration` (#3105) and `skill_gate_hook` (trinity-enterprise#752: `ok` / `missing` / `not_root_owned` / `writable` / `unsupported_runtime` — the gated-skill hook's drop-in, its directory and both scripts; `unsupported_runtime` off Claude Code) say whether the hooks are in force, enum only. `mailbox_depth` intentionally NOT emitted — no agent-side mailbox until the actor model (#945); the backend derives queue depth from `CapacityManager`. Counters live in `agent_server/state.py`; backend reads them in `monitoring_service.py` with graceful defaults for older images.
- `/api/executions/{id}/result` (#2944) - The terminal this agent RETAINED for a finished turn (`services/retained_results.py`): every terminal exit of `/api/task` / `/api/chat` writes the #1083-shaped envelope to `~/.trinity/retained-results/<id>.json` BEFORE the response is sent, so a backend recreate mid-turn — which destroys the only consumer of a sync turn's result — no longer costs the result. 200 → envelope + `retained_at` + `truncated_log`; 404 `{"detail":{"code":"no_retained_result"}}` for missing AND malformed ids (the coded body is the old-image discriminator — a new image must never emit the bare `{"detail":"Not Found"}`). Bounded: TTL 6 h (outlives the backend's 120-min stale sweep + the widest execution timeout + an `unknown` in-flight verdict while Redis is down), 50 newest files, transcript dropped past the callback's 16 MB cap (response/metadata/session always kept). Same-id overwrite (SUB-003 retry). Separate directory from `pending-results` ON PURPOSE — that directory's startup sweep re-POSTs to the callback, where a sync envelope is a permanent 409 and is deleted. `TRINITY_RETAINED_RESULTS_DIR` overrides the path (the unit suite points it at a tmp dir). See [execution.md § Retained Terminals](execution.md#retained-terminals--a-sync-turn-survives-the-loss-of-its-consumer-2944)
- `/api/executions/running` - The watchdog's agent-side proof-of-life: `executions` (running), `recently_completed_ids` (the #921 window ∪ handles that exited but are not yet unregistered) and `pending_ids` (#2433 — accepted at `/api/task` / `/api/chat` / the #1083 async spawn but not yet spawned: queued in the headless pool or waiting on the chat lock). Headless runs use a dedicated 32-thread pool (`_HEADLESS_EXECUTOR`) rather than the CPU-sized default; `terminate` on a pending id is consumed at spawn. See [In-Flight Dispatch Proof-of-Life](execution.md#in-flight-dispatch-proof-of-life-2433)
- `auth_override` on `POST /api/task` and `POST /api/chat` (#3470) — a request-scoped credential (`oauth_token` XOR `api_key`) for THAT ONE spawn: `execution_env.auth_override_env_layers` makes it the top env layer (`build_execution_env(extra, drop=…)` — `drop` exists because the oauth route must take `ANTHROPIC_API_KEY` away from the spawn and a mapping cannot express an absence); nothing in the container changes, so concurrent turns may run on different credentials and a `docker restart` cannot desynchronise anything. The response (success AND HTTPException) carries `X-Trinity-Auth-Override: <kind>`; an older image omits both the field and the header, which is how the backend's SUB-003 walk tells "ran on the trial" from "ran on the baseline". Claude runtime only (`AgentRuntime.supports_auth_override`); the value is staged for log redaction and never persisted.
- `disable_auto_memory` on `POST /api/task` and `POST /api/chat`, and on the pull envelope payload (#4156) — the backend marks a turn that serves someone other than the owner; the Claude runtime (`AgentRuntime.supports_auto_memory_switch`, keyword built once by `execution_env.auto_memory_spawn_kwargs` for all four entry points) puts `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in that spawn's `extra` layer (`execution_env.auto_memory_env_layer`), above `.env`. Default `False`; an older backend never sends it. See [write-user-memory.md](../feature-flows/write-user-memory.md#auto-memory-is-off-on-a-turn-that-serves-someone-else-4156).
- `/api/credentials/reload-token` - Surgical subscription-token hot-reload (#1089): mutates the agent-server process `os.environ["CLAUDE_CODE_OAUTH_TOKEN"]` so the NEXT claude subprocess uses the rotated token while in-flight subprocesses keep theirs; persists to the writable-layer override `/var/lib/trinity/oauth-token` (0600). Does NOT touch `.env`/`.mcp.json`. See [Subscription Token Rotation](agent-lifecycle.md#subscription-token-rotation-via-hot-reload-1089)
- `/api/chat/session` - Context window stats
- `/api/files`, `/api/files/download` (100MB limit), `/api/files/mkdir` (workspace-confined, #37)
- `/api/brain-orb/data` - Streams the agent's `resources/agent-visualization/data.json` (Brain Orb read surface, #58); 404 when absent. `/api/brain-orb/scopes` + `/api/brain-orb/scope` run the agent's `~/.trinity/brain-orb/{scopes,scope}` convention hooks for live scope control (#58 Phase 2); `/api/brain-orb/tool` runs the read-only `~/.trinity/brain-orb/search` hook (#60 Phase 3)

The agent server also runs three loops: the 15-min git `auto_sync` push heartbeat, the git pull cycle beside it (trinity-enterprise#703, `GIT_SYNC_PULL_INTERVAL_SECONDS`, defaulting to the push interval; both in [Git Sync Health](agent-lifecycle.md#git-sync-health-389390)), and the 5s liveness heartbeat (see [Heartbeat Liveness](reliability.md#heartbeat-liveness-reliability-004-307)). `GET /api/git/status` is not a loop but is driven like one (backend poll every 60 s, plus the UI git panel and the MCP tool): since #2742 it is single-flighted on the event loop, computed in one `to_thread` worker, sweep-registered, and takes **no** `.git/index.lock` — see the same section.

**Execution environment assembly (#1999):** a spawned runtime subprocess no longer inherits the agent-server's long-lived `os.environ`. `agent_server/services/execution_env.py::build_execution_env` rebuilds it per spawn from three inspectable inputs — `INITIAL_ENV` (the container baseline captured at import, i.e. what `docker exec` shows) → `~/.env` parsed fresh (**authoritative for credentials**, so a removed key is removed) → `RUNTIME_OVERRIDES` (values that are deliberately not `.env` credentials; the #1089 token rotation and the #2114 subscription-shadow arm, applied AFTER the file so a stale token in `.env` can't beat an explicit rotation, with `None` meaning force-unset) → the caller's `extra` (last, so `EXECUTION_TAG_NAME` #407 can't be displaced). All five spawn sites (`claude_code`, `headless_executor`, `codex_runtime`, `gemini_runtime` ×2) route through it. The credential endpoints still mirror `.env` into `os.environ` for **in-process** readers (error classifier, `AGENT_RUNTIME`, the sanitizer's redaction set) but now with a **delete phase** that restores the container baseline rather than popping blind, and only for keys the mirror itself wrote. `.env` may not set loader/exec-redirecting names (`PATH`, `LD_PRELOAD`, `BASH_ENV`, `CLAUDE_CODE_SHELL_PREFIX` (trinity-enterprise#787), …) — it is agent-writable and is now read at every spawn. **ent#615 widened that set and added a prefix rule** (`is_protected_key`): `GIT_CONFIG_COUNT` was listed but its SLOTS (`GIT_CONFIG_KEY_*` / `GIT_CONFIG_VALUE_*`, an unbounded family) were not, so the guard covered the count and left the payload writable — and a slot can set `core.sshCommand`, `core.pager`, `diff.external` or `credential.helper`, i.e. the same execution vectors by another route. `GIT_CONFIG_NOSYSTEM`, `GIT_ASKPASS` and `GIT_PROXY_COMMAND` join them; `NOSYSTEM` is load-bearing because `/etc/gitconfig` is where ent#615 registers the git credential helper, alongside the #1595 gc guards, so one `.env` line would disable both — and a helper that stops running is a fetch/push outage with no error that names it. `GET /api/credentials/status` reports per-key `env_drift` (**names only, never values**). Before this, the file and the execution environment were independent channels that synced one-way with no delete phase, so a key removed from `.env` outside the credentials API kept reaching every execution until container restart — invisible to both `/proc/<pid>/environ` and `docker exec`, i.e. silent failure of credential revocation. **`.env` is deliberately NOT authoritative for API-key-style Claude auth while subscription auth is active (#2114):** #1999's re-read made a stale `.env` `ANTHROPIC_API_KEY` (preferred by Claude Code over the OAuth token, and never cleaned by any recreate — it lives on the workspace volume) shadow subscription auth at every spawn, which SUB-003 then mis-attributed to each healthy subscription in turn. At boot, `arm_subscription_auth_guard()` force-unsets `ANTHROPIC_API_KEY` + `ANTHROPIC_AUTH_TOKEN` through the same override layer when the baseline carries a truthy `CLAUDE_CODE_OAUTH_TOKEN` on a Claude runtime — restart-durable because `startup.sh` exports the rotated override token *before* the server launches, so it is always baseline; non-Claude runtimes never arm (a vestigial token must not strip a key their scripts may use). The suppression is **data, not just a memoized per-key WARNING**: `env_drift_report` marks force-unset keys `suppressed_for_spawn` (iteration set includes override-only keys), so the one surface built to expose file/spawn divergence cannot show all-green over an active suppression.

**Traffic routing is the platform's (trinity-enterprise#1001):** where a runtime sends its model traffic, and the API key or OAuth token on it, comes from the container baseline, never from a file the agent can write. `execution_env.ROUTING_KEYS` (proxy names in both cases, `NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`, `SSL_CERT_FILE`) are refused from `.env` on every runtime; `RUNTIME_ENDPOINT_KEYS` holds each runtime's own endpoint names (the `ANTHROPIC_*` base URLs, `CLAUDE_CODE_API_BASE_URL` (the CLI's Files API fallback when `ANTHROPIC_BASE_URL` is empty) and `ANTHROPIC_UNIX_SOCKET`; Codex's `CODEX_*` URL overrides and `CODEX_CA_CERTIFICATE`; `GOOGLE_GEMINI_BASE_URL`, `GOOGLE_VERTEX_BASE_URL`, `CODE_ASSIST_ENDPOINT`), refused only on that runtime (`runtime_family()`, read from `INITIAL_ENV`), so a Claude agent's `.env` keeps `OPENAI_BASE_URL` for its MCP servers. `AGENT_RUNTIME` joins `PROTECTED_KEYS`: `get_runtime()` reads `os.environ` per request, so a mirrored `.env` value would run one runtime under another's protection set. Each runtime's file routes are closed where it reads them, because refusing the `.env` line is not enough on its own: Claude Code applies settings `env` from the agent-writable user and workspace `settings.json`, so the root-owned policy drop-in `/etc/claude-code/managed-settings.d/60-routing-env.json` (written by `hooks/write-routing-env.py`, all-empty at build under `env -i`, rewritten by `startup.sh` through `sudo -E` with the container's own values before the server starts) pins every Claude name to the baseline value or `""`; Codex gets `-c model_provider="openai" -c openai_base_url="" -c chatgpt_base_url=<default>` on every `codex exec` (above every agent-writable `config.toml` layer), and `strip_protected_env_lines` removes `.env`-protected names from `$CODEX_HOME/.env`, which the CLI loads OVER the process env; the Gemini CLI loads `~/.env` itself but only fills unset names, so `build_execution_env` hands a Gemini spawn every pinnable name set (`routing_pins`), to the baseline value, `""`, or `CODE_ASSIST_ENDPOINT`'s default. `SSL_CERT_FILE` and `ANTHROPIC_UNIX_SOCKET` are refused but never pinned (OpenSSL opens an empty `SSL_CERT_FILE`; Claude Code ignores the socket name in every settings file). The facts are read from the pinned CLIs; `test_ent1001_endpoint_env.py` fails when a pin moves. Claude Code's provider switches (`CLAUDE_CODE_USE_*`) stay settable: with every base URL pinned they reach only the provider's official endpoint with the agent's own cloud credentials.

**Durable subscription-token override (#1089):** `startup.sh` exports `CLAUDE_CODE_OAUTH_TOKEN` from `/var/lib/trinity/oauth-token` (when present, non-empty) **before** launching the agent server, so a token rotated via hot-reload survives any plain stop+start of the same container (historically that included `routers/ops.py`'s fleet restart, which bypassed `start_agent_internal` entirely; since #1860 a fleet restart routes through `lifecycle.restart_agent_internal` — a no-drift agent keeps its container and the override survives, a drifted agent is recreated and cleanly re-bakes `Config.Env` from the DB). The path is deliberately on the writable layer, **not** under the persisted `/home/developer` volume: it survives `stop`→`start` (same container) but is wiped on recreate (fresh layer), so a DB-driven recreate cleanly re-bakes `Config.Env` from the DB and the stale override is gone — self-reconciling, no marker logic. Dir created+chowned to UID 1000 in the base-image Dockerfile.

**`.mcp.json.template` rendering (#2007):** `startup.sh` runs `agent_server/mcp_template.py` after the credential-import steps — the missing implementation of the contract `docs/TRINITY_COMPATIBLE_AGENT_GUIDE.md` publishes. It renders `~/.mcp.json.template` into `~/.mcp.json`, substituting `${VAR}` / `${VAR:-default}` from `.env` **inside `env` blocks only** (the only form `mcp_validator` accepts — a `${VAR}` in `args` is rejected as a shell metacharacter and `command` must be a literal allowlist entry, so substituting there is the #590 RCE-by-config class). It lives in-container because that is where the files are: a `github:` agent's template is cloned by `startup.sh`, so the backend renderer (`template_service.generate_credential_files`, `local:`-only and reads `.mcp.json` not the `.template`) never saw it and every declared server was silently absent. Each candidate server is validated individually through the **vendored** `mcp_validator` (byte-identical to the backend copy, Invariant #5); a server whose placeholders don't resolve, or that the validator rejects, is **withheld with a named reason on stdout** rather than blanked (the #1929 contract), and the rest still install. Merge-only-missing, so the `trinity` entry and any owner edit survive; idempotent across restarts and order-independent with respect to `inject_trinity_mcp_if_configured()`. Never fails the boot.

**Template-supplied pre-check** (SCHED-COND-001, #454): if the template ships an executable `~/.trinity/pre-check`, the backend's internal endpoint `POST /api/internal/agents/{name}/pre-check` runs it via `docker exec` before a cron-triggered chat. Language-agnostic — interpreter selected by shebang. The hook's stdout becomes the chat message; empty stdout + exit 0 records a skipped execution (Claude never invoked). The firing schedule reaches the hook as `TRINITY_SCHEDULE_ID` / `TRINITY_SCHEDULE_NAME` / `TRINITY_SCHEDULE_MESSAGE` in the exec environment (#3966) — one hook gates every cron schedule on the agent. Uses the same `execute_command_in_container` primitive as `git_service/`, `ssh_service.py`, and the agent terminal — no agent-server HTTP endpoint.

**Gated-skill hook (trinity-enterprise#752, Claude Code only):** `/opt/trinity/hooks/skill-gate.py` (a bootstrap) + `_skill_gate.py` (the decision), registered for `PreToolUse` on `Skill|Agent|Task` by its OWN managed-settings drop-in, `/etc/claude-code/managed-settings.d/50-skill-gate.json` (root:root 0444 in a 0755 dir). It is separate from `managed-settings.json`, so an entry the CLI rejects voids only that file, and it runs in exec form (`/usr/bin/env -i /usr/local/bin/python3 -I -S …`: no shell for `CLAUDE_CODE_SHELL_PREFIX` / `BASH_ENV` to reach, no user site, an empty env) with `LD_PRELOAD` / `LD_LIBRARY_PATH` / `LD_AUDIT` pinned empty by the drop-in's managed `env`. It asks `POST /api/skill-gate/check` whether the run may load the skill a call loads — a `Skill` call, or a subagent definition's `skills:` preloads. Identity is read from `/proc`, never its own env: `TRINITY_EXECUTION_ID` from `/proc/<parent>/environ` (the claude process's launch env, set per spawn by `build_execution_env`), the backend URL and agent key from `/proc/1/environ`. Every outcome is exit 0 or 2 (this CLI lets the tool run on exit 1, a crash or its own timeout), under a 10 s in-process deadline. With no verdict from the platform, the root-owned marker `/opt/trinity/skill-gates-active`, written by the backend's root `docker exec` on agents with gates only, decides: present refuses, absent allows. This is deliberately the opposite failure direction from `read-only-guard.py`. Facts read from CLI 2.1.281 are pinned in `SKILL_GATE_CLI_VERIFIED` with a ratchet test against the Dockerfile's `CLAUDE_CODE_VERSION`; the image build runs `skill-gate.py --self-test`. **A self-approved `/chat` turn** arrives with `isolated_session: true` (`ChatRequest`); `execute_claude_code` runs it with no `--resume`, keeps no session id, changes neither `current_model` nor the session counters (the model rides `_execute_claude_code_once(cli_model=…)`), and the `/api/chat` router leaves the shared session's stats alone. Gemini and Codex accept the flag and ignore it (D4).

**Skill listing facts (trinity-enterprise#754):** `GET /api/skills` (`agent_server/routers/skills.py`) reports per skill `source` (`platform` when the platform's `.trinity-skill.json` marker is in the directory — the same `isfile` test the backend's managed-skill listing and the gate fingerprint use — else `agent`), `dir`, and `approval` (the closed set `{recommended}`, read with `skill_packaging.extract_contract`'s `trinity:`-block-first precedence). The marker name and value set are duplicated from the backend (this image cannot import it) and a behavioural parity table runs one set of documents through both parsers. Informational only: the agent can write the marker and its own frontmatter, so the gate map stays the authority. An older image omits the three fields; the Skills tab then splits Own/Shared by assigned names — see [skills-tab.md](../feature-flows/skills-tab.md).

**Persistent chat:** all chat messages auto-saved to SQLite (`chat_sessions`, `chat_messages`) with full observability (costs, context, tool calls, execution time); sessions survive container restarts/deletions; users see only their own messages (admins see all).

### Agent Runtimes — multi-runtime / "harness == runtime" (#1187)

A Trinity **harness IS an `AgentRuntime`** — the pluggable execution engine inside the agent container. Four ship today: **Claude Code** (default), **Gemini CLI**, **OpenAI Codex** (#1187) and **OpenCode** (#2981). `AGENT_RUNTIME` (container env, set from `template.yaml runtime:` via `crud.py`; also a `trinity.agent-runtime` label) selects one; `runtime_adapter.get_runtime()` is the factory — it **validates** the value against `KNOWN_RUNTIMES` and raises on an unknown one rather than silently defaulting to Claude.

**ABC** (`agent_server/services/runtime_adapter.py`): `execute` (chat), `execute_headless` (stateless task), `configure_mcp`, `is_available`, `get_default_model`, `get_context_window`, plus a non-abstract `capabilities()` returning a `RuntimeCapabilities` dataclass (`chat_continuity`, `session_tab_resume`, `mcp_support`, `cost_reporting: "native"|"estimated"`) — conservative by default (an un-overridden runtime is least-capable). Each runtime is a singleton (`get_<name>_runtime()`).

**Claude chat continuity is the chat's own session (#2958).** `execute_claude_code` resumes `agent_state.chat_session_id` with `--resume <id>`, never `--continue` (which took the newest JSONL in the shared project dir, i.e. a scheduled run's). The id is captured only after a successful turn, only if `chat_session_generation` is unchanged (a `DELETE /api/chat/history` mid-turn bumps it and the capture is dropped), and published to `~/.trinity/chat-session.json` (`services/chat_session_marker.py`, atomic, cleared on reset and at startup) so the backend JSONL reaper keeps it. A different effective model starts a fresh session and resets the session counters. The subprocess body is `_execute_claude_code_once`; the wrapper owns the session choice and ONE cold retry, taken only when the resumed JSONL is absent after the failure, no tool ran and the turn was not cancelled (re-registered pending first). Any exit-0 `is_error` result (`execution_error`) is a failure on every chat turn, cold or resumed, whatever text it carries (#2968, parity with the headless #1673 check): first #1870's evidence-gated completed-turn recovery (`headless_executor._recover_completed_turn_into`, on-disk `stop_reason=end_turn` only), otherwise a 502 with a structured `{message, metadata}` body (502, not 503, so SUB-003 never treats it as an auth failure). A failed `--resume` lands here too, and the cold retry still applies to it. Compact events are read from the JSONL, as on the headless path.

**Context-window catalog (#1521):** the `% context used` denominator is model-specific, not a flat 200K. The runtime-reported `modelUsage.contextWindow` is the **primary** value (the only source that knows the effective plan/auth/beta window) — but `modelUsage` carries **one entry per model the turn touched** (Claude Code bills side work like tool-permission checks to a cheap Haiku), so `model_context.py::pick_context_window` matches the entry to the model that *answered* (`metadata.model_name`, from the latest assistant message) instead of taking an arbitrary one; an unidentifiable model keeps the seeded fallback rather than guessing, since picking the largest window is the direction that hides a compaction wall (#1840 — taking the first entry made the same agent report 1M and 200K on alternating runs). When the runtime value is absent, `services/model_context.py::resolve_context_window` is the **fallback** — `[1m]`→1M, Gemini→1M, Codex `gpt-5.6`→1.05M (a verified window, not a guess) / older Codex families→272K, bare Claude→200K *safe floor* (a 1M-capable model shows real 1M via the primary value; the floor is deliberate so an unknown tier never hides an imminent compaction wall), unknown id→200K + logged warning. It seeds `metadata.context_window` at construction in the Claude/headless paths (`get_context_window` is dead-code for Claude — the stream value overrides the seed) and backs `get_context_window` for the other runtimes + the non-abstract ABC default. Pure-stdlib, **vendored byte-identically** into `docker/base-image/agent_server/model_context.py` (Invariant #5, parity-tested); backend downstream fallbacks use the shared `DEFAULT_CONTEXT_WINDOW` constant. **The available-model picker is NOT this map** — the *selectable* catalog (id, label, note, and the `public_channel`/`admin_default_selectable`/`recommended` policy flags) is centralized in `services/model_catalog.py` (#2086, a stdlib-only leaf), which emits the checked-in `src/frontend/src/constants/modelCatalog.js` via `scripts/gen_model_catalog.py`; `ModelSelector.vue`, the `Settings.vue` admin dropdown, and `settings_service.PUBLIC_CHANNEL_MODELS` all derive from it, and `tests/unit/test_2086_model_catalog_parity.py` byte-matches + structurally validates the mirror on every PR. `model_catalog.py` is deliberately separate from this context-window map: it is not vendored (not consumed by the agent runtime), so folding the two together would break the Invariant #5 vendoring contract.

**Codex** (`codex_runtime.py`, built independently on the per-runtime primitives — NOT a shared helper, so it never inherits Gemini's blanket `kill_cgroup_orphans()`): `codex exec --json … -- -` with the prompt on stdin (#3838: one argv element is capped at 131,072 bytes on Linux) → JSONL events (`thread.started`→session id, `turn.completed.usage`→tokens with `reasoning_output_tokens` ⊂ `output_tokens`, `item.completed`→activity, `turn.failed`/`error`); `-o/--output-last-message` is the authoritative result (read-then-delete in `finally`); `codex exec resume <thread_id>` for continuity; cost estimated via `CODEX_PRICING`. Concurrency-safe orphan cleanup via `_drain_bounded` (`kill_cgroup_orphans(extra_pids=…)` preserves siblings). Error→HTTP: auth→503, rate→429, runtime-unavailable→**500** (avoids the AUTH collision), pipe-drop→**502** (SUB-003 guard).

**Gemini** (`gemini_runtime.py`; argv built only in `gemini_cli_args.py`, #2971): the base image pins `@google/gemini-cli` (currently 0.62.0, `GEMINI_CLI_VERSION` must match the Dockerfile) and the image build runs `gemini_cli_args.py --smoke`, a real `--list-sessions` argument parse of every argv shape the runtime builds, so a CLI release that drops a flag fails the build instead of every turn. Its parser is strict and has no `--system-prompt` or `--max-turns`: the platform system prompt is prepended to the turn input as on Codex (`GEMINI_SYSTEM_MD` would replace the built-in tool/safety prompt wholesale), and because stream-json echoes the whole stdin as the turn's `role:user` message, the chat reader rewrites that event's content back to the caller's prompt so the persisted execution log never carries the composed platform prompt, and `max_turns` is logged and bounded only by the wall-clock timeout. Every spawn passes `--skip-trust` (without it the CLI exits 55 and downgrades `--yolo`). Chat resumes only its own session, as Claude does (#2958): `--resume <agent_state.chat_session_id>`, never a bare `--resume` (= newest session in the store headless runs share); captured after a successful turn under an unchanged `chat_session_generation`; a model change starts fresh; a resumed session the CLI cannot find (`Error resuming session`, exit 42) gets one cold retry unless the turn was cancelled. Gemini sessions live under `~/.gemini/tmp/`, outside the JSONL reaper, so no chat-session marker is written.

**OpenCode** (`opencode_runtime.py`, Abilityai/lilu#257 — same per-runtime primitives as Codex, so `_drain_bounded` preserves siblings): `opencode run --format json --auto` → JSON lines (`step_start`/`step_finish`/`tool_use`/`text`/`reasoning`/`error`; `sessionID` on EVERY line, so capture never depends on one event type arriving). **There is no separate result line** — the response is the LAST step's concatenated `text` parts. Cost is **native** (`step_finish.cost`), so there is deliberately no pricing table (#2207); `tokens.reasoning` ⊂ `tokens.output` and `tokens.cache.read` ⊂ `tokens.input` and neither is ever summed in. **An empty final text is a FAILED turn (#520), and exit 0 is not proof**: `qwen3.6:27b` via Ollama answers in a non-standard `reasoning` field with `content: ""` while reporting success — empty+reasoning fails `reasoning_only` (500) and the reasoning is NOT promoted into the response, empty+tools is `"(Task completed)"` (Codex parity), empty+nothing fails `empty_response` (500). `opencode run` has **no system-prompt flag** (verified against the real `--help`), so the platform prompt travels via the `instructions:` config key in a **per-turn** `XDG_CONFIG_HOME` — per-turn because one shared config file would race across the parallel `/api/task` path — with the image's pre-seeded provider `node_modules` symlinked in (OpenCode otherwise installs providers from the live npm registry on every cold container). `-m` takes `provider/model`, shape-validated at both boundaries as a parity pair (`helpers.validate_runtime_model` / `validate_provider_model`) because the backend cannot import the base image. Error→HTTP matches Codex: auth→503, rate→429, generic→**500**, pipe-drop→**502**, timeout→504. **Trinity MCP reaches the session by TRANSLATION, not a second store** (step 2, `opencode_mcp.py`): `.mcp.json` stays the one store (Claude's, the Trinity injector's, credential injection's) and is mapped per turn onto OpenCode's `mcp:` key against the published v1.18.32 schema — `url` ⇒ `McpRemoteConfig` (`type: remote` + headers), `command` ⇒ `McpLocalConfig` (Claude's `command` + `args` collapse into OpenCode's single `command` **array**, `env` ⇒ `environment`). `url`, not `type`, is the discriminator: Claude makes `type` optional and Trinity's own template omits it on stdio entries. A second persistent copy was rejected precisely because a re-injected Trinity key would then reach one file and not the other. An unmappable entry is skipped with a named warning rather than emitted half-formed — OpenCode rejects a malformed `mcp` entry at config-parse time, killing a turn that had nothing to do with MCP — and a missing/corrupt `.mcp.json` degrades to "no MCP tools this turn". The per-turn config now holds the Trinity bearer token, so it is written **0600**. **OpenCode is a THIRD tool-naming scheme:** tools are `<server-id>_<tool>` (measured — a real `ollama/gemma4:12b` turn emitted `tool: "trinity_list_agents"`), so the backend's `_adapt_instructions_for_runtime` **rewrites** `mcp__trinity__` → `trinity_` for `opencode`; the Claude spelling and the Codex bare spelling are both unknown tools to it. **The custom-provider block is computed per turn, not baked at boot** (step 6, `opencode_provider.py`): OpenCode resolves models.dev providers itself but a local Ollama it does not, so `provider.ollama` (`@ai-sdk/openai-compatible` + `<OPENCODE_OLLAMA_BASE_URL>/v1` + the union of the turn's `-m`, `AGENT_RUNTIME_MODEL` and `OPENCODE_OLLAMA_MODELS`) is merged into the per-turn `opencode.json` — per turn because `.env` is re-read at every spawn (#1999) and a boot-baked block is stale from the operator's first change onward; an operator's own declaration wins on `npm`/`options` and has its models unioned, and an unset base URL emits no `provider` key at all so the Anthropic path is untouched. **A silent turn is a failed turn:** `step_start` is the FIRST stdout line and everything before it (config load, session create, the cold ripgrep fetch from github.com, the git/project walk, the provider's prefill) emits nothing, so a wedged turn produces zero bytes and would burn the whole execution timeout holding the chat lock — `OPENCODE_STALL_TIMEOUT_SEC` (default 300s, clamped to the turn timeout) kills the group and relaunches on a **fresh** session up to `OPENCODE_STALL_RETRIES` times (default **2** → 3 attempts, clamped 0–5), and zero bytes is 504, never a success, however many attempts it took. **The stall is host-dependent and unexplained** — 16/16 completions on one agent container against ~13% per attempt on the control plane, same binary/flags/provider/Ollama — so the retry count is a knob rather than a constant, the ceiling is the turn's OWN deadline (each attempt gets the time actually left; no retry starts under 90s, below the measured 59.3s worst-case silent window it could only delay the 504), and every relaunch plus the give-up detail carries the greppable `[OpenCode][STALL-RETRY]` marker while a recovered turn reports `metadata.stall_retries`. Without that field a flaky host is recorded as a plain success and reads as slow-but-fine; the empty-stdout-is-failure rule is deliberately not loosened to compensate. The settling instrument is the DGX agent container, which nobody has yet (Abilityai/lilu#257 F6, open). 300s is ~5x the worst measured silent window (7.2s–59.3s for byte-identical configs on a real DGX Ollama — the variance is the provider's model load, not OpenCode), because a watchdog that kills healthy turns is the worse failure.

**OpenCode as a full platform citizen (Abilityai/lilu#655).** `/name args` runs DETERMINISTICALLY as `opencode run --command name -- args`: each turn mirrors `.claude/commands/<name>.md` then `.claude/skills/<name>/SKILL.md` (skill wins a clash; an operator's own `command:` entry wins over both) into the per-turn config's `command.<name>.template`, frontmatter stripped and `$ARGUMENTS` appended when the body has none; an argument-less command sends no message. An unknown `/name` returns exactly `Unknown command: /name` without spawning a model, so the backend's #1410 `detect_unresolved_slash_command` records SKILL_NOT_FOUND for OpenCode the same way it does for Claude; a leading absolute path is a message, not a command. `metadata.input_tokens` is the LAST `step_finish`'s `tokens.input` (each step re-sends the session, so the sum counted the context once per step); output tokens and cost still sum. The context window prefers `provider.<pid>.models.<mid>.limit.context`, then `OPENCODE_PROVIDER_<PID>_CONTEXT`, then the catalog. `images` are decoded into the turn dir and attached with `-f`. `capabilities()` declares `session_tab_resume` (the Session tab sends `resume_session_id` → `--session`) and `async_dispatch`, which `result_callback.runtime_supports_async` reads next to the Claude-by-name rule for the #1083 202 path; Codex and Gemini leave both off. **Env-delivered controls and stdin (#2981 review B1/B2).** The per-turn global config is OpenCode's LOWEST-precedence layer — a workspace `opencode.json` or `.opencode/opencode.json` merges over it — so a control that lives only there is advisory. Two are therefore also put in the child env, which OpenCode applies after every file: `OPENCODE_DISABLE_SHARE=1` on every spawn, and in read-only mode `OPENCODE_PERMISSION={"edit":"deny","bash":"deny"}` (popped otherwise, so a stale value never leaks into a writable turn). Guardrail `disallowed_tools` are still config-only. The message travels on **stdin**, never argv (the dev #3838 fix, same class): `--` is kept, stdin is closed after the write, and a `BrokenPipeError` on the handoff ends the child and unregisters it — otherwise a >128 KiB prompt made `Popen` raise `E2BIG` before the turn existed.

The same step fixed three fallthroughs that decided a non-Claude runtime's behaviour from the Claude branch: `state.py`'s availability probe ran `claude --version` for a Codex agent (now table-driven per runtime; an unknown runtime reports unavailable rather than probing an unrelated binary), `routers/chat.py`'s `/api/model` offered Claude aliases to a Codex agent and rejected `gpt-5.6-sol` as an "Invalid Claude model" (now one surface per runtime with a named 400), and `routers/info.py` compared `== "claude-code"` literally so the equally-valid `claude` alias reported a null version. **`plugins_reinstall` is Claude-gated** — every subprocess it runs is `claude plugin ...` — and the `CLAUDE.md -> AGENTS.md` mirror is now a **symlink** shared by Codex and OpenCode, not a one-shot `cp` that froze at first boot.

**Execution-ledger boundary (trinity-enterprise#643):** the always-tier `### Stay inside Trinity's execution ledger` section, placed directly before `### Nothing survives the end of your turn`, tells every agent not to run `claude`, `codex`, `gemini` or any other coding-agent CLI as a subprocess, directly or through scripts or wrappers, because a nested run escapes the execution ledger (cost attribution, autonomy gates, permission enforcement, audit). "Turn-scoped by design" is worded as **authorization, not storage**: credentials can be readable in the container (`ANTHROPIC_API_KEY` / `CLAUDE_CODE_OAUTH_TOKEN` / `GEMINI_API_KEY` in the container env, a persisted Codex `auth.json`; GUARD-004 is not started), so the section never claims a nested CLI cannot authenticate. Whether one signs in depends on the auth mode (`CLI_FACTS_TO_REAUDIT` in `_skill_gate.py`), so the section doesn't claim that it always does either. Its in-turn alternative is runtime-conditional through the `__CLI_IN_TURN_ALTERNATIVE__` marker and `_adapt_instructions_for_runtime`: Claude Code is offered its `Agent` subagent tool (also named `Task`) "where you have it", since a per-agent deny list or a task's `allowed_tools` can remove it; every other runtime is offered its own tools. Delegation goes through `chat_with_agent` with `parallel=true` for self-targeting or a `model` override (sequential mode queues on the target's own chat session, and `model` applies only in parallel mode) or `fan_out`; the ent#568 delegation contract is referenced, not restated. On an agent with no gates it is advisory: no deny pattern, denied tool or admission check. On an agent with gates it is enforced (trinity-enterprise#1002): `bash-guardrail.py` adds the baseline's `gated_bash_deny` rows while the root-owned skill-gate marker exists. The key is not overridable, and the rows stay out of `bash_deny` so a skill on an ungated agent that shells out keeps working. The in-container skill check cannot do this itself, since a nested `claude` carries whatever execution id it was started with and a `/<skill>` prompt fires no hook in it. It is hard-coded until the ent#140 prompt-injection registry exists.
