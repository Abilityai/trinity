# Workspace Build

**Requirements**: `docs/memory/requirements/core-agent.md`, Workspace Build

A page in the Workspace with the ordinary conversation on the left and the person's world on the right. The world is a view of the real instance: the agents it shows are created on that instance by the person's own guide, Atlas, which belongs to them.

## Flow

```
First admin, on the Dashboard: FirstRunOverlay carries three more steps (profile, company, audit), in onboarding-wizard.md
  Starting the audit, or choosing a first agent with the guide, explains who they're about to meet, then leaves the panel for /workspace/build
An admin who opens the Workspace with no answers yet is sent to that same panel (`?onboarding=1&from=workspace`), so an admin only ever has one flow. Leaving it counts as skipping what's unanswered, and goes back to the Build page.
Anyone else who can build, with no answers yet, arriving at the Workspace or its plain Inbox address (shouldOpenOnboarding: can build, no chats, no agents beyond any guide, guide has no state)
  PortalBuildOnboarding.vue: a window that can't be dismissed, only skipped
    welcome -> about you (newcomers: "What's an agent?"; then what to build first) -> Connect Claude if missing -> set up the guide if missing -> company and website -> the AI audit: start, skip, or talk it through
    Skip for now -> profile incomplete: red in the sidebar and on the page's stepper, both reopen the window
Both read and write the same answers (loadIntake / saveIntake), so nothing is asked twice.
/workspace/build (Portal.vue branch, rail-free)
  PortalBuild.vue
    questions unanswered -> asks the Workspace to open the window
    Claude not connected (feature flags) -> link to /?onboarding=1, recheck on return
    no guide of their own on the roster (myGuideCard) -> offer POST /api/systems/deploy (buildManifest(<their address>))
    otherwise -> PortalConversation (their guide's Main chat; it never moves to another agent)
                   first message: intakeMessage(), sent once through autoSendPrefill after the window has closed
    PortalBuildWorld.vue
      reads GET /api/enterprise/client-portal/agents/<their guide>/canvas/build (and canvas fleet)
      4 s while a turn runs, 30 s otherwise, and at the end of every turn
```

```
their guide --/build-agent: /create-agent:custom, questions and approval in this chat--> the new agent, owned by them
     |
     +-- set_canvas(canvas_id: "build", blocks: [summary, state]) --> the world
     +-- set_canvas(canvas_id: "fleet", blocks: [proposal]) --> a Confirm card the page writes --> the main app's own route, with the person's session
     ^
     +-- fleet-state.json, written by the page into its workspace with the person's session
```

## One guide per person

- **Each person who can build has their own guide**, owned by them because they deploy it, so everything it builds is theirs. The page finds it with `myGuideCard`: a roster card they own (`owned: true`) named `build-guide` or `atlas-<8 hex>` (`isGuideName`). Someone else's guide, even one shared with them, is never used. A new one is named `guideNameFor(username)`: FNV-1a of the username, so no personal data reaches an address, stepping to `-2`, `-3` when Trinity still holds the name (`deployMyGuide`). The original `build-guide` stays its owner's.
- **No guide is one of the person's own agents** (`isBuildCrew`, and the backend's `services/build_crew.py` for the first-run state), nor is an old `agent-builder` an instance still runs.
- **The guide has a face and a name.** `config/agent-templates/build-guide/avatar.webp` is installed by the deploy as its default avatar (#2693 bundled avatars), so it never shows as the initials of its address. In the Workspace sidebar the person's own guide reads "Builds and runs agents" under its name, always: other agents show their latest chat or their address, but a chat title there ("AI audit for ...") read as the guide's description, and the line has 141px beside the time, so the longer "builds and manages" was cut off (`portalSidebarGuideLine.mount.spec.js`). On the Build page the composer doesn't offer `@` to add an agent, which would open a room and leave the page.
- **The grant to create agents** comes with the deploy only when an admin deploys in a signed-in session. Anyone else's guide can't create agents until an administrator turns on "Manage other agents" for it; the page reads its `capability-grants` and says so (`guideCannotCreate`).
- **Saved answers from phase 1's handover** (`buildChat`, `handoffSent`, `handoffBefore`, `handoffReported`) are dropped when answers load (`forgetHandover`).
- **Answers belong to the guide they were sent to** (`sentTo`; before Part 2 that was `build-guide`), and research to the guide that ran it (`research.guide`). A person whose guide is new to them (their own after a shared one, or one set up again) has their answers sent again and its own research run (`rebindToGuide`). A guide's address comes from the person, so one set up again after a deleted one has the same name: on entering the chat, a guide with no `build` canvas and no used chat of theirs (no thread with a message) counts as new too (`rebindToGuide(..., { fresh: true })`, `rebindIfNew`). The roster is read again after every turn (`onTurnDone` emits `retry-roster`, whether or not the guide wrote the page: an agent it created ticks Level 1 from the roster alone), and every 15 seconds while the guide reports a built agent the roster doesn't have, so a new agent reaches the page and its fleet without a reload. A page read asked for while one is in flight (a turn ending during a poll) is not dropped: `refresh` reads once more as soon as the first is back, so the page never shows the state from before the turn for the next 30 seconds.

## Settings changes in the chat

- **What the guide can see:** its own key reads only itself and the agents it made, so the page reads the person's own agents with their session (permissions, shares, schedules, public links, skills) and writes `fleet-state.json` into the guide's workspace (`fleetActions.readFleet`, `writeFleetFile`) when the chat opens, when their agents change, and after each change.
- **Proposals:** `/fleet` writes canvas `fleet` with one JSON block `proposal`, the skill showing the exact call. A block the guide named otherwise (after the proposal's own id, seen 9 Nov as `share-l4-1`, when no card showed while the guide said to click it) is still read: the last JSON block shaped like a proposal (`proposalFrom`), the card's words always coming from the page. A new proposal is judged against a fleet read after it arrived (`fleetReadFor`), and fleet reads run one at a time: on 9 Nov the guide created a schedule and proposed its walk in one turn, and the card said the page couldn't make the change, because the fleet had been read before the schedule existed. `fleetChanges.cardFor` makes a card only for an exact known change (`KNOWN_CHANGES`: allow or stop a call, share or unshare, a schedule on or off, a public chat link, add a skill) on the person's own agents; the card's words come from that table, never from the guide. Anything else is a refusal that says why, and changes nothing.
- **Confirm** calls the same route the main app's own control calls, with the person's session, once (`runChange`), reads it back (`changeHeld`), refreshes the fleet file and tells the guide `Done: ...`; **Not now** tells it `Not now: ...`; a refusal (a 4xx) shows `Nothing was changed. <why>` and tells it `That didn't work: ...`; no answer, a 5xx, or a change that doesn't read back shows `This may or may not have been made.` and tells it `Not sure it worked: ...`. Answered ids are kept in `fleetHandled`. The line the page sends after a card shows in the chat as a note (`fleetChanges.outcomeNote`, through `PortalConversation`'s `asNote`), as the level line does: it is the page telling the guide, not something the person typed.
- **Show me** (`components/onboarding/showMe.js`, `ShowMeSpotlight.vue`): a link to the real page with `?showme=<key>`, opened in a new tab. The agent page and Settings light up the control marked `data-tour="showme-<key>"` with a one-stop `PortalBuildTour`, waiting up to 6 seconds for it to draw; if it never does, a note says so. It is the only way for anything that needs a secret or a sign-in elsewhere, anything that deletes, and anything not in the table.
- **Show me, walked: an agent's credentials** (`components/onboarding/showMeWalk.js`, `ShowMeWalk.vue`, AC-13b): `credentials` is a walk, not a jump. The card's link is `/?walk=credentials&walk_agent=<name>[&walk_keys=A,B]` (key names only, validated, at most ten), opened in a new tab. `ShowMeWalk` is mounted once in `App.vue` beside the router view so it survives page changes; it reads the walk from the address, takes it out at once, and lights one stop at a time with four covering panels around the lit part (only it takes clicks). The first walk on a browser opens with "This is the Dashboard", the whole Dashboard lit (`data-walk="dashboard"` on its `<main>`), the card in the middle and a Next; remembered as `trinity-walk-dashboard-seen` in localStorage, so later walks start at the agent. Stops: the agent's name on the Dashboard (`data-walk-agent` in the timeline, grid and list views; off screen counts as not found), its Settings tab (`data-walk="settings-tab"`), the Credentials rail item, the agent-stopped note (only if shown, until it goes), each key's row (`data-walk-credential`, Next), then Save credentials, which waits for the page's own success line (`data-walk="credentials-saved"`). The first three move on from the address (`stepDone`), so a page already open there passes through them. Which rows: the keys the guide named that aren't set, else every missing required key; an agent that lists none of them gets the Quick Inject box instead. A stop not found within 5 seconds offers a button to that page. The guide asks them to come back and checks with `get_credential_status`. Tests: `showMeWalk.spec.js`, `showMeWalk.mount.spec.js`, and `e2e/show-me-walk.spec.js` (mocked backend, from the Workspace card through Save).
- **Show me, walked: sharing, calling and schedules** (`showMeWalk.js` `peopleWalk` / `permissionsWalk` / `schedulesWalk`, AC-13c): the same engine and link, `/?walk=<people|permissions|schedules>&walk_agent=<name>[&walk_to=<agent>][&walk_schedule=<id>]` (`to` only for permissions, one of theirs and not the agent itself; a schedule id only for schedules; never an email). A step is done from the address through its `at` (`{ tab, section }`); a tab step has an `alt` target, More (`[data-overflow-trigger]`), lit with "It's under More" while the tab itself isn't in the strip (`OverflowTabs` marks each visible tab and More item with `data-tab`, never its hidden measuring row). An `expand` step reads that walk's rows: `data-walk-permission` + `data-walk-checked` (`PermissionsPanel`), or `data-walk-schedule` + `data-walk-enabled` + `data-walk-schedule-name` (`SchedulesPanel`). Stops: People's `data-walk="people-form"` until `people-added` (only the add's own success line); a permission row until it is ticked, then `permissions-save` until `permissions-saved`; a schedule's `schedule-toggle` until its row is enabled, then the Autonomy switch at the top of the agent's page, `autonomy-switch` (`AgentHeader`, Manual / AUTO), with the Schedules tab's `autonomy-enable` as its `alt` while that switch isn't shown (only while `data-walk-autonomy="off"`, until it says `on`). Cases with nothing to do end or say so: `already`, `none`, `pick` (the whole list, Next). `fleet-state.json` gains `autonomy` per agent (`GET /api/agents/{name}/autonomy`, null when unreadable). Confirm cards that turn something on carry `walk` for "See where this is set"; the ones that turn it off keep the spot. The page rewrites `fleet-state.json` when the person comes back to the tab: on every return for ten minutes after a walk was opened, otherwise at most every five minutes, and never while the last read is still running (`fleetActions.js` `fleetRefreshDue`). A list a walk picks from that never shows (slow, or failed to load) offers a way on instead of reading as empty, a schedule named that is gone is never swapped for another one, the schedules walk's last word claims only what it saw, and Escape closes the More menu rather than the walk.
- **A first agent, one level at a time** (`build-agent/SKILL.md`, "First agent: one step at a time", AC-18): when `fleet-state.json` lists no agent of theirs, each level is one ask and one yes. The plan is read back as the steps, one level each, with the keys it will need named and said to be asked for at Level 3, not now (`plan-agent/SKILL.md`). Level 1 asks only "shall I create it?" and creates the agent with nothing but its identity: the plan's playbooks are moved to `~/builds/<slug>.held/<name>/SKILL.md` first and marked `planned` on the `build` canvas, the plan's keys are named in its `template.yaml` (`credentials:` / `credential_setup:`, names only, nothing asked), no schedule is made, and every gap the wizard raises is settled by the guide from the plan's defaults (a question for a key's value is never passed on, at any step). The turn ends once the agent exists, so the page's first look holds only the wizard's standard playbooks and Level 1 is told. Level 2: each held playbook is proposed and, on a yes, sent to the agent with `chat_with_agent` to save exactly as written (`building`, then `done`), so the page sees it as new. The keys are named at Level 1, not later, because the page shows Level 3 as "Not needed" while Trinity lists no keys for any of their agents, and an instruction to declare them alongside a playbook was skipped in a live run (6 Nov). Level 3: any key a playbook uses that isn't named yet is added, then the `credentials` walk. Level 5: the guide creates the plan's schedule with `create_agent_schedule`, off, then the `schedules` walk. The wizard only writes a folder in `~/builds/<slug>`: an agent exists only once `scripts/deploy-agent.sh` has packed the folder and posted it to `/api/agents/deploy-local` itself (an archive pasted into a tool call arrives altered, and is refused as drift) and `get_agent_info` returns it; the wizard's "created" and "try it locally" are never passed on. Held playbooks left over mean the steps aren't finished; the Levels help for Level 2 points at them first.
- **The person's own idea wins** (template `CLAUDE.md`, "Their idea is the one you set up"): when they name the agents, the job or the direction, the guide sets that up, asks one question if unclear, offers its own idea only as a second option, and only says one agent can call another when `may_call` in `fleet-state.json` shows it.
- **A job one agent did for another** (`handoff.js`, `PortalBuildHandoff.vue`): the first time the jobs the page reads for the levels hold a finished job on one of the person's agents that another of their agents asked for (`triggered_by: agent`, `source_agent_name` one of their own, never the guide), the side panel says "<B> just did a job for <A>" on any tab, with Show me and Not now. Show me opens the `tasks` walk with `walk_from=<A>` (Dashboard, the agent, Tasks), whose last stop says the rows tagged "agent" are the jobs <A> asked for. Offered once: `handoffSeen` on the saved answers, set by either press.
- **The end of the levels**: when no level is left to do (each one reached, not needed or left for later), the Levels card shows "You're done. There is so much more to Trinity, but you're certified to get started." (`build-levels-done`), naming any level still waiting for keys. The last level's moment says the same, and the guide closes in the same words when the page's line ends `That was the last level.`, with no next step pushed.
- **Where an agent's keys are** (template `CLAUDE.md` and `build-agent/SKILL.md`): every playbook and agent `CLAUDE.md` the guide writes that uses a key says the keys are environment variables in the agent's own container (`~/.env`), read as `$NAME`, never through `fetch_credential`, which reads another store and reports set keys as missing.
- **A look at the data before a playbook relies on it** (template `CLAUDE.md`, section of that name, and `build-agent/SKILL.md`): once an agent's keys pass the test, the guide has it make one read-only look at each service and save `data-map.md` in its home folder (what is there, the fields, a few shortened examples, what was not checked). Playbooks are written from the map's real names and start by reading it; a first agent's playbook, written before its keys existed, is corrected from it. A look, not a playbook: sent again when the data changes shape. Its message never starts like the connection test the page reads.

## The company, once

`GET`/`PUT /api/workspace-build/company` (`routers/workspace_build.py`, `services/workspace_company.py`, setting `workspace_build_company`) keeps the company's name, website, research report and context once per instance, for people who can build (`require_person` and the creator role; never an agent key). The Build page reads it first and publishes only what this person's guide adds (`companyToPublish`); the server keeps the kept text wherever new text is empty (`merged_with`), so nobody blanks a colleague's research or context. A colleague with no company answers starts from it (`companyFromProfile`, in the Workspace and in the setup panel): their answers are filled in, no second research runs, and the page copies `company-research.md` and `context.md` into their guide before its first message, which says the research is shared.

## Levels

Eight levels under the page's You tab, with the person's role and experience (`PortalBuildWorld.vue`: You, Your company, Findings, Context; once the guide is working on an agent (`focus.agent`) the right side shows You, so the person sees their levels as they go, and Your company opens on that agent; the levels card is `PortalBuildLevels.vue`, rules in `levels.js`, reads in `levelSignals.js`; core-agent AC-15 to AC-17). They are about the person, not the company, so the Company card carries only the company. Each level has three lines of copy: `todo`, what to do, shown under the next level; `means`, what reaching it means, shown when it is celebrated; and `why`. The page reads the person's own agents (owned, minus their guide, `trinity-system` and Trinity's seeded samples; at most 20) with their own session, through routes the main app already uses: when the chat opens, after each guide turn, when their agents change, when they come back to the page, and at most every minute otherwise. It never reads while the page is hidden, and never before `firstRunStore` has said which agents are samples (the page fetches it itself, since `/workspace/build` can be opened directly). A read that fails keeps what the last good read saw; before any good read it counts as not seen. Nothing is shown when a read fails.

| Level | Ticked when |
|---|---|
| 1. First agent | They have an agent of their own (any agent that counts, above), whether or not it has run. |
| 2. A new playbook | One of their agents has a playbook (`/api/agents/{name}/playbooks?last_known=true`, the Skills tab's list) that it didn't have the first time the page saw it. That first look is kept on the saved answers as `levelsBase` (`playbookBase`: once per agent, never replaced, at most 100 names each and 40 agents, the oldest no longer theirs dropped first), so the playbooks an agent was built with, the build wizard's included, never count. An agent whose playbooks couldn't be read yet gets no first look, and one no longer theirs is forgotten (unless the list may be cut at 20), so an agent built again under its name is looked at afresh. The first look is saved on the newest copy of the answers (`intakeWithBase`: another tab's save is never overwritten, and a first look a save dropped is saved again). |
| 3. Connected | One of their agents has every required key set: `/credential-requirements` with state `ok` or `declaration_incomplete`, `summary.blocking` 0 and `summary.set` above 0. While every one of their agents reports `no_credentials_required` or no required key it is still the next step, with its own text ("None of your agents needs a key, so there is nothing to connect") and a button asking the guide to move on; it shows as "Not needed" (counted as done, never celebrated) only once the guide has written `keys_not_needed: true` on the world, which it does on the person's yes. That route is rate limited, audited and runs in the agent's container, so "all set" isn't read again during the visit, and anything else, "not needed" included, at most every two minutes, after a turn, or when they come back to the tab (keys get declared and set while they watch, through the walk in another tab). A declared key that isn't marked optional counts as needed until it is set, even when Trinity reports its `required` as "unknown" (a `credential_setup:` written inside `credentials:`, 7 Nov). "Not needed" is also read again when that agent's playbooks change (`levelSignals.js`). **And tested (10 Nov):** the level is reached only when the newest test of that agent's connections passed. A test is one of the agent's own runs whose request starts with `Test your connections` (`levelSignals.js` `CONNECTION_TEST_PREFIX`; the guide's `build-agent` Level 3 sends exactly that) and the page reads that run in full once (`/executions/{id}`): its reply has to carry the line `CONNECTIONS: OK`, and a `CONNECTIONS: FAILED` line wins. Nothing the guide writes or says ticks it. Kept (`levelsKept[3]`) once seen, while those keys stay all set and no newer test fails, because the run scrolls out of the recent list. Keys set but not tested show "Your keys are in. Ask Atlas to test the connection" under the level. **Later:** when they have no working keys yet and agree with the guide to carry on, the guide writes `keys_later: true` on the world; the level then shows "Later" (`deferred`: no tick, not counted) and the next level is the one after (`nextLevel`). The person can also press **Do this later** on the card (`PortalBuildLevels.vue`, shown while Level 3 is the next level and `canDefer`): that sets `keysLater` on their saved answers and tells the guide `Level 3, Connected: left for later.` with the real `Next:` line (`laterMessage`, shown in the chat as a note by `laterNote`). A test that passes ticks it regardless. **Where they are, for the guide:** the page adds `levels` (`reached`, `later`, `not_needed`, `next`; `levelsSummary`) to `fleet-state.json` on every fleet write and whenever the levels move, because levels are not reached in order and the guide must not count. |
| 4. In control | A share (`/shares`), or a permission to call an agent that isn't their guide or itself (`/permissions`). New agents get no permissions by default. |
| 5. On a schedule | One of their agents has a schedule turned on and Autonomy on (`/api/agents/{name}/schedules` with one `enabled`, and `/autonomy` with `autonomy_enabled`), so it is set to run by itself: the first run can be a day away, and the step is theirs today. A successful run with `triggered_by: schedule` that their guide didn't start counts too. |
| 6. A small team | Three or more of their agents. Read as it is now, never kept. |
| 7. Working together | With three or more of their agents, one allowed to call another of theirs (`/permissions`), so they can talk and need not wait for a call. It counts too with a completed `agent_collaboration` call (`/api/activities/timeline?limit=200`, action `chat` or `parallel_task`) from one of theirs to another of theirs. |
| 8. Running on its own | Completed calls from one of their agents to two or more different agents of theirs started inside one of its jobs (between `started_at` and `completed_at`, since Trinity keeps no job-to-call link), and an answered approval on one of their agents (`/api/operator-queue`, `responded` or `acknowledged`, matched on `responded_by_email`). |

The routes show only recent history (the newest 100 executions per agent; for an admin, the newest 200 collaboration rows across the instance; rows kept 90 days), so a level built on history (5, 6, 7) is kept on the saved answers with the agents that made it true (`levelsKept`) and stays reached while those agents are still theirs. Having an agent, its playbooks and settings (keys, shares, permissions) are read as they are now. Answers saved by the six-level version (before 4 Nov) are moved to the eight-level numbers when read (`levelsOf`, `levelsVersion: 7`).

A level reached and not in `levelsSeen` (the saved answers, merged with what another tab saved) is celebrated once on the card (the highest named) and told to the guide in one visible message: a `Level reached: Level 1, First agent.` line per level, then `Next: Level 2, A new playbook.` (or `That was the last level.`). On the visit where the page sends the person's answers itself, the levels already reached at its first read are celebrated on the card only, not told over the guide's first question. It is sent once the guide has the person's answers, isn't replying, and the composer is empty; it waits otherwise and joins any other line waiting for the guide. The guide's template answers it (CLAUDE.md, "Levels") and helps with a `Help me reach Level N` request, which each level's "Do it with" button puts in the composer; Level 2's request has the guide agree one new job with them and ask that agent to write the playbook into itself (`chat_with_agent`), Level 3's leads to Show me `credentials`, and Levels 4 to 8 offer the walks first.

Level moments (`levelMoments.js`, shown with `PortalBuildTour` as one or two stops): the intro once when the first build starts (`introDue`, saved as `levelsIntroSeen`), and for each level told to the guide the Levels card lit with its tick (`reachedSteps`), after the new agent's sidebar row (`data-tour-agent`) for Level 1. A level reached waits for `momentFree` (chat open, guide not replying, no tour or setup window, first reply in); the intro shows while the guide is still writing (`momentBase`), because the guide's words say the page is lighting the levels up now, and the guide writes the canvas before those words. Every moment switches the right side to You with `PortalBuildWorld.showLevels()`, lights the card every time, however much of it was on screen, and puts the right side back afterwards (a move the guide made meanwhile, to a new agent, is followed then). The chat renders the page's level line as a note (`PortalConversation` `asNote`, `levelNote`). Show me steps that only open something (`press` in `showMeWalk.js`) have Next, which clicks the lit part.

## Routes by experience

- **The route** comes from the AI agent experience answer alone (`experienceRoute`): `none` ("I've never built one") is `newcomer`, `tried` ("I've built a few") `standard`, `built` ("I build them all the time") `experienced`. Missing or unknown reads as `newcomer`. The ids are the saved ones, so older answers read with the new labels. The software answer changes only wording.
- **"What's an agent?"** (`components/onboarding/whatIsAnAgent.js` for the words, `WhatIsAnAgent.vue` to play them): a 26-second silent video with captions (`public/intro/what-is-an-agent.mp4`) of one everyday job done by an agent, then one line on what an agent is. The captions are also its transcript, for screen readers and in place of the video if it can't play; they come from the video's source, outside this repository, and must change with it. A developer gets a more technical last line. It shows once, right after `none` (`needsAgentExplainer`, `markAgentExplained` sets `agentExplained`): in the setup panel in place of the next question (`BuildQuestions.vue`, which scrolls it into view, since it lands under the answers just given), and in the window as step `explain` (`onboardingSteps({ explain })`). The window waits a tick after each answer before moving on, because the step after it can depend on it. Get help has it as "What's an agent?" for anyone.
- **What to build first** (`plans`: `not_yet`, `rough`, `exact`) is optional, so nobody who finished before it existed is sent back to it. It is asked the next time they open About you. `exact` makes "Talk it through with Atlas" the audit step's main button, with the audit still offered and recommended (`auditEmphasis`, `auditLead`); the window then drops "Skip it and build a test agent". The guide is told (`What to build first: ...`).
- **Experienced people** still answer the essentials. On the panel's audit step they also get "Or just tell Atlas about your work". Skipping the audit there ends on the Dashboard rather than the Build page (`auditSkipDestination` names `/`, so arriving from the Workspace doesn't turn it into the Build page).
- **The feature tour** (`components/onboarding/featureTour.js`) reuses `PortalBuildTour.vue` with a `steps` prop: the Dashboard's view switcher (`data-tour="view-modes"`) and the nav's Operations, Library, Workspace and Settings links. Only links shown inline carry `data-tour`, so one collapsed into "N more" drops out, and with fewer than two stops on screen (a phone) there is no tour. The Dashboard opens it once (`featureTourDue`: answers done, experienced, `featureTourSeen` unset), only after the setup panel has had what it needs to decide whether to open, never while it is open or `?onboarding=1` is pending, and not when the panel closes to go to another page (it emits `leave`). It marks the tour seen on close, including that immediate close. A stop whose part leaves the screen after the tour started (the nav measures itself a moment later) is dropped, not pointed at. Get help in the Workspace has "Show me the advanced features" for anyone who can open the Dashboard, which goes to `/?tour=features`; the Dashboard removes the parameter, so a reload doesn't show it again.

## The profile

- **Complete** means Trinity knows who the person is and what the company does: the guide's state says `profile_complete` (questions answered, company research read or no website, and their own work known, from the audit or `/about-your-work`), or the audit is `done` (`worldView`). Answering the questions alone is not enough any more.
- **Red** on the page's stepper and badge, and in the Workspace sidebar: right away after a skip, as before; otherwise only once the guide has written a state, and never while the audit is in progress. The Workspace reads the guide's `build` canvas once when it loads, and the Build page passes on every change (`state` event), so the sidebar uses the same `worldView` rule.
- **Clicking the red** opens the questions while one is unanswered; otherwise it asks the guide for the short talk (`finishProfileAction`, `chooseProfileChat`). If the guide already has their answers, the message is only `Profile: I'd like to tell you about my work first...`; otherwise it is the full first message with that line, and it never claims they chose a test agent. It is sent at once if they are already on this page (a watch on `tellGuide`), after any reply the guide is in the middle of.
- **`/about-your-work`** (`config/agent-templates/build-guide/.claude/skills/about-your-work/`): about 2 minutes, one question at a time, on what a normal week involves, what repeats or takes the most time, and what they'd hand to an agent first. It writes "Their work" into `profile.md`, and the guide also asks these before planning when the audit was skipped and the profile isn't complete. If the company research couldn't run, one question about what the company does counts instead, so the red can always be cleared.

## How the profile reaches the agents

- **The guide's name** is Atlas to people (`BUILD_GUIDE_NAME`, set as its label after deploy), whatever its address. Deploying also sets `BUILD_CREW_MODEL` as its default model, and the research task asks for it directly, because tasks don't read the per-agent default.
- **The first message** states the sign-in email, role, experience, what they'd like to build first if they said, level, company, website and the audit choice, or the first agent they'd like to talk through, and `Profile:` when they asked to tell the guide about their work (`intakeMessage`).
- **The guide** keeps it in `profile.md` and matches how it talks to the level. `AI audit: yes` starts `/company-audit`, which reads the website, asks from the person's role, and ends by recommending the first agent. `AI audit: skipped` builds any agent as a test, and someone who doesn't know what to build is pointed back to the audit.
- **The company research** is its own job, `POST /api/agents/<their guide>/task` running `/company-research`, started once the company is known. The first real use of Claude, so the setup panel follows it and says if Claude isn't answering. It writes `company-research.md` and canvas `company-research`, which the Findings tab reads. It never touches the `build` canvas, so it can't overwrite the audit running in the chat. The guide reads the file each turn and tells the person when it appears.
- **The plan:** `/plan-agent` agrees what the agent is for and what good looks like, and saves it as `plans/<agent id>.md`. How to build it, including skills, connections and keys, is left to the create-agent wizard in `/build-agent`.
- **The build:** `/build-agent` (adapted from Ability AI's Agent Builder 0.2.1) runs the `create-agent@abilityai` wizard headless, with the plan as its brief. Its one batch of questions and its one approval are asked in this chat; every schedule it creates is off; without a `GITHUB_TOKEN` the agent is uploaded with `scripts/deploy-agent.sh`. It checks the agent exists before setting `live_name`, then offers `/fleet`.
- **The profile line** (`portalBuild.js` `worldView().profileIncomplete` / `profileNote`, `stepState` `'filling'`): red ("Profile incomplete: finish it", the danger badge, the stepper's `!`) only while a Get started question is unanswered. With every question answered and the guide not yet saying the profile is complete, it is calm: a neutral badge "Profile in progress", a plain stepper step, and in the sidebar one offer, "Profile: tell Atlas about your work", which sends the profile message once (`profileAsked`); after that the line only says "Profile: Atlas fills it in as you talk" and cannot send it again.
- **The setup panel's order** (`firstRunSteps.js`): Optional extras (`keys`) comes after Usage sharing, so nothing before the audit waits on optional keys. **The Workspace tour** (`portalBuildTour.js`) has a stop on the sidebar's Dashboard link, between the Inbox and help.
- **A welcome per account type** (`accountWelcome.js`, `PortalAccountWelcome.vue`, opened by `views/Portal.vue` `openAccountWelcomeIfNew` on arrival): a platform session whose server-reported role is `user` or `operator` cannot build, so it gets no guide, no levels and no Get started. It gets one window instead that names the account ("You have a Workspace account." / "You have an operator account."), what it can do, what is **not part of this account**, a line when no agent is shared with them yet, and "Need more? Ask your admin." **Show me around** lights the Agents list and the Inbox; an operator's last stop is the sidebar's Dashboard link, whose button opens the Dashboard on their first agent's Tasks (the `tasks` walk in `showMeWalk.js`: the agent, its Tasks tab, what the rows are; not one of the guide's walks). Shown once per kind of account (`accountWelcome` on the saved answers), so someone raised from user to operator is welcomed again. Someone an agent was shared with by email (no platform session) gets none. A creator's Get started window says once that setting up Trinity belongs to their admin (`CREATOR_NOTE`).
- **Who gets what in the sidebar** (`portalBuild.js` `buildAvailableFor` / `dashboardAvailableFor`): Build is for a platform session that is not Workspace-only and not an `operator` (creating an agent needs `creator`); the Dashboard link is for anyone not Workspace-only, so an operator gets it without Build. **Build an agent** shows only until the person's own guide's row is on screen in the Agents list (`PortalSidebar.vue` `guideShown`): then that row is the door, and it is marked current while the Build page is open (`onGuidePage`).
- **The way to the Dashboard** (`PortalSidebarBuildLink.vue` `data-tour="dashboard"`, `portalBuildTour.js` `walkDoorSteps` / `walkDoorDue`, `PortalBuild.vue` `onShowMe` / `closeDoor`): the sidebar has a Dashboard link under Build an agent, shown only with that block (a platform session that is not Workspace-only), opening `/` in a new tab. A person's first Show me press does not open the walk at once: the page lights that link ("This is how you get to the Dashboard") and its button, Open the Dashboard, opens the walk's tab. Once per browser (`trinity-walk-door-seen`); with no sidebar on screen (a phone) the card's link opens the walk as before.
- **The guide has one page** (`portalBuild.js` `opensBuild`, wired in `views/Portal.vue` `guideDoor`): the person's own guide's row under Agents, and its main chat (in the chat lists, or reached by a `/workspace/c/<id>` or `/workspace/a/<guide>` link), open `/workspace/build`, never the plain chat, which has no levels, no page beside it and no cards. Any other chat of the guide's, and every other agent, opens as before.
- **The welcome** (`PortalBuildWelcome.vue`, in the conversation's `#empty` slot): a Build chat with nothing said in it has the guide say who it is, what it is for and, for a first agent, how it goes (pick the job, Level 1 create it, Level 2 its first job). One press sends a start line (`WELCOME_STARTS`: `Let's build my first agent.` or `Suggest a first agent for me.`; for someone with agents of their own, `Let's build a new agent.` or `I'd like to improve one of my agents.`), which the guide's CLAUDE.md answers. It stays hidden while the answers are on their way (`answersOnTheirWay`). When they chose the AI audit and it isn't done (`auditFirst`), the audit is the first step and the one button sends `Let's do the AI audit now.`: nothing on it offers to build before the audit. The guide's own first reply also opens with who it is and the first agent it is there to build; with the audit skipped it goes straight to the first agent and asks none of the audit's questions. The chat follows the session its first send adopts (`session-adopted`), as the Workspace's own chat does, and the guide's card keeps its object until something on it changes (`keepGuideCard`): without both, the roster read at the end of the first turn made the conversation empty itself, and the welcome came back over a chat that had started.
- **The tour** (`PortalBuildTour.vue`, `portalBuildTour.js`) walks round the Workspace the first time someone lands on this page, before the first message goes. It marks `tourSeen` on the answers, and Get help takes it again.
- **The wizard** only knows what the guide tells it, so `/build-agent` puts the plan, the company's `context.md` and the audit's finding into its brief, and asks the person at their level.

## The audit playbook

`.claude/skills/company-audit/PLAYBOOK.md` is the method the audit follows: goals, walking through the work, four kinds of opportunity (thinking work such as the business model among them), sizing, data, whether an agent is the right tool, risk, ranking, and a recommendation with a target number. Its sources are at the end of the file.

## Reaching the team

`BUILD_SUPPORT` in `portalBuild.js` holds the addresses. `PortalBuildHelp.vue` opens from the sidebar, the world's footer and the onboarding window, and the setup panel's rail links to the email. The guide is told when to suggest it, including after a second failed build.

`public/intro/trinity-intro.mp4` is a motion graphic with music and sound effects that starts muted (browsers only autoplay muted video), played by `components/onboarding/IntroVideo.vue` as the first step of the setup panel and under Get help. ## Rules worth knowing

- **All logic is in `components/portal/builder/portalBuild.js`** and is pure, so `tests/unit/portalBuild.spec.js` reaches it.
- **The state is written by an agent, so it is not trusted.** `normalizeState` types, bounds and defaults every field. `variables` keeps only bare names, so a pasted value is never drawn.
- **`live` is checked.** `liveAgentFor` looks the agent up on the roster.
- **`buildManifest('build-guide')` is a copy** of `config/manifests/workspace-build.yaml`, because the bundle cannot read outside its own tree. A unit test compares them.
- **The folder is `builder/`, not `build/`**, because `.gitignore` ignores `build/` at any depth.

- **Deleted guide**: Trinity keeps a deleted agent's name and its workspace volume reserved, and refuses it (a 500 whose `failed` list says "already exists"). `deployMyGuide` then steps to the next address, twice; when those are held too, `deployFailureMessage` says an administrator can release them. A name a live agent already has gets `_2` from Trinity; the page labels and uses the name in `agents_created`, and `isGuideName` accepts it.

## Known gaps

- The answers are stored on the account (`stores/buildIntake.js`, preference key `workspace_intake`), so signing in as admin or with that account's email reads the same ones on any browser. The browser keeps a copy, and it is all there is for anyone without a platform account.
- A stopped guide isn't started again when someone messages it, so guides stay running. A template change reaches a guide only when it is deployed again.
- An `@mention` in the chat opens a room, which leaves the page. The rest of what would leave it is hidden by the conversation's `focused` prop (agent picker, New chat, tabs, star, project, reset, voice).
- `orchestration_available` gates what the page offers. The guide is told to respect it but cannot read it, so someone who asks in the chat could still get an orchestrator designed.
