# Feature: Agent Guardrails (GUARD-001 / 002 / 003)

## Overview

Guardrails are a **defense-in-depth safety layer** baked into every Trinity
agent container. They combine three independent controls, all enforced
*inside* the agent (not the backend):

1. **Bash command deny-list** — regex patterns block dangerous shell commands
   (`rm -rf /`, force-push, pipe-to-shell, fork bombs, fs format, host
   shutdown, …) via a Claude Code `PreToolUse` hook on the `Bash` tool.
2. **File path deny-list** — glob patterns block writes/edits to credential
   files, SSH/AWS/cloud config, and Trinity's own protected directories via a
   `PreToolUse` hook on `Write|Edit|NotebookEdit|MultiEdit`.
3. **CLI budget & scope controls** — turn caps (`max_turns_chat` /
   `max_turns_task`), a wall-clock `execution_timeout_sec`, and a
   `disallowed_tools` list passed straight to the `claude` CLI on every
   invocation.

A **platform baseline** (`guardrails-baseline.json`, baked into the base image,
root-owned `0444`) always applies and is **not** overridable by the agent or by
owners. Owners may layer **narrow per-agent overrides** — numeric caps and
literal substring deny-lists only; never regex, never the credential scanner —
via `PUT /api/agents/{name}/guardrails`. A `PostToolUse` scanner additionally
logs (never blocks) credential-shaped strings in `Bash` output.

The whole mechanism is **fail-closed**: any hook error exits `2` (deny), the
runtime config is generated by root at boot so the agent can't rewrite it, and
the hooks themselves live in `/opt/trinity/hooks/` (root-owned, path-protected).

## User Story

As an agent owner, I want a dangerous-command and dangerous-write safety net
that's always on, plus the ability to tighten turn/timeout budgets and add my
own deny rules for a specific agent — without being able to *weaken* the
platform's baseline protections.

## Entry Points

- **UI (Agent Detail)**: owner-only Settings › **Guardrails** pane (`components/agent-settings/GuardrailsPane.vue`, the one Settings home of trinity-enterprise#887/#3798). Its first section is **Tool access** (`agent-settings/ToolAccessSection.vue`, trinity-enterprise#341 — see [Tool-access profiles](#tool-access-profiles-guard-008-trinity-enterprise341)); the turn caps are edited in `GuardrailsPanel.vue` (embedded under "Guardrail rules"). Old `?tab=guardrails` deep links resolve via `LEGACY_TAB_SECTIONS`.
- **API (tool access)**: `GET|PUT /api/agents/{name}/tool-access` — the profile that sets read-only mode and `disallowed_tools` together.
- **API (read)**: `GET /api/agents/{name}/guardrails` — any authenticated user; 404 if no container.
- **API (write)**: `PUT /api/agents/{name}/guardrails` — **owner-only** and **person-only** (`Depends(require_person)`, #2996: agent- and system-scoped keys get 403 `person_required`); empty body clears overrides. Requires agent restart to apply.
- **Agent creation**: overrides serialized into the `AGENT_GUARDRAILS` env var (`crud.py`).
- **Agent restart**: env var re-serialized from DB (`lifecycle.py`); runtime config regenerated at boot (`startup.sh` → `write-runtime-config.py`).
- **Tool-call time**: Claude Code `PreToolUse` / `PostToolUse` hooks fire on every `Bash` / file-write tool call.

> **UI scope is narrower than the API.** The rules editor only edits the two turn caps; `execution_timeout_sec` and the `extra_bash_deny` / `extra_path_deny` lists remain API-only and are *preserved* by the panel's whole-config PUT. `disallowed_tools` is edited through **Tool access** (Custom) since trinity-enterprise#341; once a profile is stored the guardrails PUT neither writes it nor `tool_access`.

## Tool-access profiles (GUARD-008, trinity-enterprise#341)

One owner-facing answer to "what may this agent do?". A profile is a fixed bundle that sets the read-only layer ([read-only-mode.md](read-only-mode.md)) and `disallowed_tools` together, so the two can no longer disagree; read-only mode IS the Strict read-only profile. Requirement: `requirements/security.md` §28.10.

| Profile | Read-only layer | `disallowed_tools` | Codex `--sandbox` |
|---|---|---|---|
| Full access (default) | off | — | `danger-full-access` |
| Workspace-only | off | the 7 send tools | `danger-full-access` |
| Read-only + report | on | the 7 send tools | `read-only` |
| Strict read-only | on | the 7 send tools + `mcp__trinity__report` | `read-only` |
| Custom | owner's switch | owner's list (≤50, 1–256 chars) | per the switch |

The send tools (`services/tool_access_profiles.py::SEND_TOOLS`, closed at seven): `send_message`, `send_group_message`, `send_notification`, `send_voice_reply`, `call_user`, `post_to_room`, `share_file`, named `mcp__trinity__<tool>` (pinned against the MCP server's registry and the `"trinity"` key in `trinity_mcp.py`).

**Layers**
- `services/tool_access_profiles.py` — pure policy: bundles, card copy, `resolve()` (stored or derived profile + `applied`), `plan_selection` / `plan_shortcut` / `merge_guardrails_put`, `denies_tool`, per-runtime `coverage_line`.
- `services/agent_service/tool_access.py` — reads the row, applies the plan, writes it in ONE compare-and-set (`db.write_tool_access_row`: `guardrails_config` + `read_only_mode` + optional `read_only_config`, `WHERE` both unchanged → 409 on a lost race), applies the read-only layer live (`inject_/remove_read_only_hooks`) and then re-reads the row once, applying what is stored if a racing writer moved it, audits (`configuration` / `tool_access_change`, actor + before → after: profile, read-only, list), answers with `restart_required` (the container's `AGENT_GUARDRAILS` tool list differs from the stored one — the tool list only, so a pending turn-cap change is not named twice — or a running agent whose live apply failed). Limit: a failed live apply is reported by that save only; the next start re-syncs.
- `services/tool_access_guard.py::assert_tool_allowed` — the send block refused by Trinity: the first action of the nine routes behind the send tools and `report` (messages, Telegram/Slack group posts, notifications, voice reply, VoIP call, room post, shared files, reports). An agent-scoped caller whose ENFORCED list names the tool gets 403 naming the tool and the profile; the four routes that send AS their path agent (`as_agent=`) check that agent's list too. People, the system key and Workspace visitors are never checked.

**Storage — materialized.** `disallowed_tools` and the read-only columns stay exactly what is enforced, so the env injection (`crud.py`, `lifecycle.py` ×2) and `write-runtime-config.py` are unchanged — no base-image change. `guardrails_config.tool_access = {profile, custom: {read_only, disallowed_tools}, before_strict}` is bookkeeping: it rides in `AGENT_GUARDRAILS`, the container's whitelist drops it, and `check_guardrails_env_matches` ignores it on both sides, so a save whose enforced fields are unchanged never recreates.

**Upgrade — nothing changes.** No row is written. A profile-less agent's profile is derived: read-only on and no list → Strict read-only with `applied: false` (the card reads "Send block not applied" + Apply); any list → Custom; else Full access.

**Writers**
| Route | What it does |
|---|---|
| `PUT /tool-access` `{profile, custom?}` | the one writer of the profile; gate = the composed routes' (`require_person_or_capability("agents.manage", self_person_only=True)` + `assert_agent_owner`); system agent 403 |
| `PUT /read-only` `{enabled, config?}` | the header/list toggle = shortcut: ON → Strict (`before_strict` remembered), ON from a list that removes tools Strict allows → 409 naming them (never loosens silently), OFF from Strict → back (Full if none), OFF on another read-only profile → 409, already off → 200 unchanged |
| `PUT /guardrails` | keeps the stored `tool_access` (never from the body); with a stored profile, `disallowed_tools` absent/`[]`/equal is kept and a different list is 409 naming `/tool-access`; profile-less agents unchanged |

**Reads.** `GET /guardrails` (access tier) shows `tool_access` as `{profile}` only. `GET /tool-access` (owner tier — it shows Custom's remembered list): profile, `derived`, `applied`, the enforced layers, `custom`, `before_strict`, `runtime`, the five cards (bundle + statement + coverage line for the agent's runtime), `restart_required`. `GET /read-only` adds `profile`, `applied`, `read_only_layer`; its `enabled` is the toggle (Strict only). Agent detail and the fleet payload carry `tool_access_profile` (same resolver).

**Per-runtime coverage** (one line per card for the agent's runtime):
| | Claude Code | Codex | Gemini |
|---|---|---|---|
| Read-only layer | file tools can't write code/config files; shell commands aren't covered | the sandbox blocks every shell command, reads included | not enforced |
| Send block | refused by Trinity + removed from the tool list | refused by Trinity | refused by Trinity |
| Other removed tools | removed from the tool list | not enforced (`codex_runtime` logs them) | not enforced (`gemini_runtime` reads only the timeout) |

**Frontend.** `ToolAccessSection.vue` (radio cards from the API, Customize → Custom pre-filled, named list errors from `utils/toolAccess.js` mirroring the backend, Apply on a not-applied profile, reports `tool-access` to `stores/agentRestart.js`, re-reads when the page's `tool_access_profile` moves); a save emits up through `GuardrailsPane` (`tool-access-saved`) so `AgentDetail` updates the header toggle; store actions `getToolAccess` / `setToolAccess` / `setReadOnly`; the header (`AgentHeader.vue`) and list (`AgentListPanel.vue`) toggles bind to `tool_access_profile === 'strict_read_only'` and send through `setReadOnly`. `GuardrailsPanel.vue` stops echoing `tool_access` / `disallowed_tools` once a profile is stored, and remounts after a Tool access save.

**No MCP surface (deliberate boundary).** No MCP tool reads or writes a profile — it is the operator's choice about the agent, not the agent's (`# mcp:` header of `routers/agent_config.py`). Agent self-selection of its tool surface is a later, separately granted capability. An agent can only see the effect: the tools it is not offered, a 403 on a refused send, and the read-only refusals.

**Tests.** `tests/unit/test_ent341_tool_access_profiles.py` (policy + name pins), `test_ent341_tool_access_routes.py` (real routes, CAS, shortcut, guardrails PUT, drift, payloads), `test_ent341_send_block.py` (helper + all nine routes + AST pin); frontend `toolAccess.spec.js`, `toolAccessSection.mount.spec.js`, `readOnlyShortcut.mount.spec.js`, `agentHeaderIdentityEdit.mount.spec.js`.

## Agent-Side Enforcement (`docker/base-image/`)

This is where guardrails actually *bite*. All hooks are root-owned in `/opt/trinity/hooks/` and registered in root-owned `/etc/claude-code/managed-settings.json` (ent#345) — the agent cannot deregister them without `sudo` (the file is also in `path_deny`).

### Routing env pins — `managed-settings.d/60-routing-env.json` (trinity-enterprise#1001)

Claude Code applies settings `env` from `~/.claude/settings.json` and the workspace `.claude/settings.json`, both agent-writable, so either could set `ANTHROPIC_BASE_URL`, a proxy or a TLS trust override and send the CLI's traffic, credential included, to another host. `hooks/write-routing-env.py` writes a root-owned `0444` policy drop-in whose `env` pins each of those names to the container's own value, or `""` when it has none; policy `env` beats user and project settings and the process env, and `""` makes the CLI use its default. The image build runs it under `env -i` (every pin empty); `startup.sh` reruns it through `sudo -E` before the agent server starts, so a proxy set on the container keeps working. Its own file, so a rejected entry voids only itself. The `.env` half of the same rule is in [credential-injection.md](credential-injection.md).

### Hook registration — `hooks/managed-settings.json`

Each hook registers in exec form (trinity-enterprise#787): `"command": "/usr/bin/env"`, `"args": ["-i", "HOME=/home/developer", "/usr/local/bin/python3", "-I", "-S", "/opt/trinity/hooks/<hook>.py"]`, `"timeout": 30`. No shell runs, so `CLAUDE_CODE_SHELL_PREFIX` does not wrap the hook; `env -i` drops inherited `PYTHON*`/`LD_*` variables and `-I -S` drops the user site. The file's policy `env` pins `CLAUDE_CODE_SHELL_PREFIX` to `""`, and `CLAUDE_CODE_SHELL_PREFIX` is in `execution_env.PROTECTED_KEYS`, so `.env` cannot set it. The image build runs `/opt/trinity/hooks/guard002-smoke.py`, which executes each hook exactly as this file registers it (`[command] + args`) against known inputs and fails the build otherwise. None of this is a boundary against an agent using its passwordless `sudo`.

| Event | Matcher | Hook(s) |
|-------|---------|---------|
| `PreToolUse` | `Bash` | `bash-guardrail.py` |
| `PreToolUse` | `Edit\|Write\|NotebookEdit\|MultiEdit` | `file-guardrail.py`, then `read-only-guard.py` |
| `PostToolUse` | `Bash` | `output-scanner.py` |

### Shared library — `hooks/lib.py` (103 lines)

| Symbol | Behavior |
|--------|----------|
| `load_config()` (39-53) | runtime → baseline → `{}`; never raises |
| `read_stdin_json()` (56-63) | parse hook stdin; **fail-closed** (exit 2) on bad JSON |
| `compile_patterns()` (66-78) | compile regex list; skips + logs bad patterns |
| `deny(msg, **fields)` | log to `/logs/guardrails.jsonl`, stderr, `exit(2)`; every call site passes a stable `code=` (trinity-enterprise#165) |
| `allow()` (88-90) | `exit(0)` |
| `run_hook(main_fn)` (93-102) | wraps `main()`; any uncaught exception → log + `exit(2)` (**fail-closed**) |
| `log_event()` | append structured JSONL; never raises. Adds the spool contract (`v`, `event_id`, derived `kind`/`hook`, `code`, `execution_id`, `session_id`, `tool_use_id`) — see [Guardrail event spool and forwarder](#guardrail-event-spool-and-forwarder-trinity-enterprise165) |

**Hook protocol**: exit 0 (silent) = allow; exit 2 + stderr = deny (message shown to model); exit 1 / uncaught = Claude treats as non-blocking, so hooks deliberately convert all errors to exit 2.

### Bash deny — `hooks/bash-guardrail.py` (66 lines)

Loads config → takes `bash_deny`, plus `gated_bash_deny` while the root-owned skill-gate marker exists (trinity-enterprise#1002) → compiles them → first match wins → `deny`. Then checks `extra_bash_deny` (per-agent literal substrings). `allow()` if clean. Logs `tool`, `pattern`, `rule`, `command_prefix[:120]` and `code` (`bash_deny_pattern` / `bash_agent_rule`) on deny; `command_prefix` stays in the container.

### File deny — `hooks/file-guardrail.py` (89 lines)

`_normalise(path)` → absolute (expands `~`, prefixes `/home/developer` for relative, collapses any run of leading slashes to one — `normpath` keeps exactly two, which made `//home/developer/.ssh/x` match no absolute pattern, trinity-enterprise#792; `read-only-guard.py` normalises the same way). `_matches_glob` runs `fnmatch` against **both** the full path and the basename, so `.env` patterns catch nested copies. Checks `path_deny` (baseline globs) then `extra_path_deny` (literals). A basename on `path_allow` (`.env.example`, #3868 — names only, required by compat check K-001) skips the slash-free `path_deny` patterns (`.env.*` and the other basename rules); absolute patterns, `extra_path_deny` and a symlinked `.env.example` still deny. `deny` with `tool`, `path`, `pattern`.

### Credential scanner — `hooks/output-scanner.py` (58 lines, PostToolUse)

Scans combined `stdout`/`stderr`/`output` of Bash against `credential_patterns`. Logs **matched pattern names only** (never the value) to `guardrails.jsonl`. **Always exits 0** — log-only, never blocks.

### Runtime config merge — `hooks/write-runtime-config.py` (83 lines)

Runs as **root** via `sudo` from `startup.sh`. Reads baseline + `$AGENT_GUARDRAILS`, sanitizes overrides (`_sanitise_number` clamps to bounds, `_sanitise_string_list` caps 50×256), and atomically writes `/opt/trinity/guardrails-runtime.json` via tmp-file + `chmod 0444` + `os.replace`. Only `OVERRIDABLE_NUMBERS` (3) + `OVERRIDABLE_STRING_LISTS` (3) are merged; regex lists and `credential_patterns` are never touched. Malformed `AGENT_GUARDRAILS` → ignored (baseline stands).

### CLI budget/scope — `agent_server/services/_runtime_config.py` (33 lines) + consumers

`_load_guardrails()` (runtime → baseline → `{}`) is read on **every** Claude invocation, so backend-driven changes (via container recreation) apply without restarting the agent-server process. Defaults: `_DEFAULT_MAX_TURNS_CHAT=200`, `_DEFAULT_MAX_TURNS_TASK=200` (equal to the baseline JSON, pinned by `test_ent471_turn_default_parity.py`), `_DEFAULT_EXECUTION_TIMEOUT_SEC=1800` (30 min).

| Consumer | Lines | Applies |
|----------|-------|---------|
| `claude_code.py` (chat) | 209-222 | `--max-turns max_turns_chat`, `--disallowedTools`, wall-clock `execution_timeout_sec` |
| `headless_executor.py` (task) | `_setup_headless_command`, `_finalize_headless_result` | `--disallowedTools`, `--max-turns` = `max_turns_task`, or a lower per-task `max_turns` (a per-task value may only tighten it, #2328); the turn-limit 422 suggests raising `max_turns_task` only when the guardrail bound |

### Platform tool denials — `PLATFORM_DENIED_TOOLS` (#2454 → #2468)

`_runtime_config.py` also owns the **platform** half of the deny list: `merged_disallowed_tools(guardrails)` is the ONE builder both spawn sites call (`claude_code.py:232`, `headless_executor.py:761`), unioning the operator's `disallowed_tools` (first, deduped, junk-skipped) with `PLATFORM_DENIED_TOOLS` — the Claude Code built-ins whose results promise a future event, a peer session, or work outliving the turn, all false in a one-shot `claude --print` (#2467 is the measured incident shape: work killed at exit, `success` recorded).

### Guardrail event spool and forwarder (trinity-enterprise#165)

Before this, no guardrail decision left the container: the hooks appended to `/logs/guardrails.jsonl`, nothing read it, and the file is lost on recreate. Requirement: `requirements/security.md` §28.2.2. The platform store and per-agent read are the ingest side (§28.5).

**Spool record (`hooks/lib.py::log_event`).** Each record keeps its old fields and gains:

| Field | Source |
|---|---|
| `v` | `SPOOL_SCHEMA_VERSION` (`1`) |
| `event_id` | `uuid4`, the dedupe key on resend |
| `kind` | derived from the legacy `event` by `_KIND_BY_EVENT` (closed set `EVENT_KINDS`); `deny` with `code="redaction_writeback_refused"` maps to that kind; `skill_gate_unknown` is `deny` only when the marker refused; anything else is `null` and stays local |
| `hook` | derived from `sys.argv[0]` by `_HOOK_BY_SCRIPT` (closed set `EVENT_HOOKS`); `null` for any other script |
| `code` | passed at every deny call site; defaults to the legacy event name |
| `execution_id` | `TRINITY_EXECUTION_ID` from `/proc/<ppid>/environ`, read once per hook process; `null` past 128 chars. Attribution, not authority |
| `session_id`, `tool_use_id` | the hook input, kept by `read_stdin_json` |

Derived fields win over a caller's value of the same name, and a fault computing them still writes the legacy record (no `v`). Deny codes: `bash_deny_pattern`, `bash_agent_rule` (bash); `protected_path`, `path_agent_rule` (file); `read_only_path` (read-only); `shell_owner_only`, `shell_visitor_off`, `mcp_owner_only`, `mcp_visitor_off`, `owner_only_path`, `owner_only_search`, `tier_unreachable` (turn tier, which now records the turn's kind as `turn_kind`); `skill_refused`, `skill_check_unreachable` (skill gate). New codes need no backend change (`^[a-z0-9_]{1,64}$`).

**Forwarder (`agent_server/guardrail_events.py`).** `schedule_guardrail_forwarder(app)` in `main.py`, gated like the heartbeat (`TRINITY_BACKEND_URL` + `TRINITY_MCP_API_KEY`).

```
hook ──append──► /logs/guardrails.jsonl ──tail (offset in /logs/.guardrails-forwarder.json)──►
   project() allowlist + sanitize_text ──batch ≤500 / ≤256 KiB──►
   POST {backend}/api/agents/{name}/guardrail-events  (Bearer: the agent's own key)
   body {"schema":1, "runtime":"claude-code|codex|gemini|unknown", "events":[…], "dropped":n}
```

- Projected event keys: `event_id`, `ts` (ISO-8601 `Z`, ms), `kind`, `hook`, `tool`, `code`, `execution_id`, `session_id`, `tool_use_id`, `verb`, `tier`, `turn_kind`, `patterns`, `rule` (≤200), `path` (≤512). A lone surrogate becomes U+FFFD (httpx encodes the body as strict UTF-8, so one would fail every POST of its batch; the platform applies the same rule). An id the sanitizer or that replacement would change, or one past its bound, is sent as `null`. Never sent: `command_prefix`, `traceback`, `error`, `reason`, `pattern`.
- `tick(now)` on a monotonic clock: poll 0.5 s, 1 s debounce after the first unsent append (delivery ≤2 s), keepalive (empty `events`) every 5 min, first one right after the 5 s start delay.
- Responses: 2xx commits the offset and zeroes `dropped`; 413 halves the batch size (a single event still refused is dropped and counted); 422 drops the batch and counts it; 429 waits `Retry-After` (1 s–1 h, default 60 s); 404/401/403 waits an hour, logging once; 5xx/transport backs off 2 s → 5 min with jitter, logging once.
- Rotation: past 5 MiB the live spool becomes `guardrails.jsonl.1`; the forwarder reads `.1` to its end and stays on it for a 2 s grace before moving to the new file. A line with no newline left at the end of `.1` past the grace (a write cut short) is counted in `dropped` and skipped. No second rotation happens inside the grace. Rotating again while `.1` is undelivered drops its rest and counts it, so the spool stays ≤ ~10 MiB.
- Skipped: records without `v` (logged once), records with `kind`/`hook` null; unparseable lines and oversize lines (>64 KiB) count as `dropped`.
- Loss window: no shutdown flush runs (PID 1 is bash with no SIGTERM handler; `docker stop` kills the server). What was unsent at a stop or recreate is lost.
- Codex and Gemini agents run no guardrail hooks, so they send keepalives only.

Tests: `tests/unit/test_ent165_guardrail_spool.py` (record contract, derivation table, every shipped hook's codes, the AST guard on reserved fields and missing codes, the smoke's new check) and `tests/unit/test_ent165_guardrail_forwarder.py` (projection, latency on a fake clock, each response, offset resume, rotation race, bounded spool, wiring).

## Configuration & Defaults

### Baseline — `docker/base-image/hooks/guardrails-baseline.json`

Immutable, root-owned `0444`. Contents:

- **`bash_deny`** (12 regex+reason rules): recursive root/home delete, `chmod 777`, pipe-to-shell, git force-push, `kill -9 1`, raw `dd of=/dev/sd…`, `mkfs.*`, fork bomb, read-only-config tamper, host shutdown/reboot/poweroff, `sudo` naming `/etc/claude-code`/`/opt/trinity`/`/etc/sudoers` or `visudo`, root shells (`sudo -i`/`-s`/`--login`/`--shell`, `sudo su`, `sudo <shell>` with no script, bare `su`) (#3105).
- **`gated_bash_deny`** (1 rule, trinity-enterprise#1002): `claude`, `codex` or `gemini` in command position, after any run of `VAR=value`, shell keywords and launchers (`env`, `nohup`, `timeout`, `sudo`, `xargs`, …), or inside `sh -c "`. A command that starts no session passes: `--version`, `--help`, `mcp`, and `plugin` on `claude` and `codex` (`gemini` has no `plugin` subcommand and reads the word as its prompt), unless a `-p` or `--print` comes before any `--`: that skips subcommand parsing, so `claude mcp -p x` is a session. `claude = x` passes too, as a variable in an inline script. Applies only on an agent with gates; not overridable from `AGENT_GUARDRAILS`. Quote-unaware like the `su` row. No nested quantifiers, no `\s*` after a command position, no inner token that can swallow `;`, `&`, `|`, `(` or `)`, and the `-p` scan after an allowed word stops at 512 characters, because a hook that outlives its 30 s timeout lets the tool run.
- **`path_deny`** (16 globs): `.env`, `.env.*`, `.mcp.json`, `.credentials.enc`, `~/.ssh/*`, `~/.aws/*`, `~/.gcp/*`, `~/.claude/settings.json`, `~/.claude/settings.local.json`, `.claude.json`, `~/.claude/.credentials.json`, `~/.gemini/settings.json`, `~/.tmp/codex/*` (the runtimes' login and MCP config, trinity-enterprise#823), `~/.trinity/read-only-config.json`, `/opt/trinity/*`, `/etc/claude-code/*`. The image-build smoke (`guard002-smoke.py`) includes a `~/.claude.json` row and a `.env.local` deny / `.env.example` allow pair.
- **`path_allow`** (`[".env.example"]`, #3868): not overridable from `AGENT_GUARDRAILS`; mirrored into the platform prompt as `_GUARDRAIL_PATH_ALLOW`.
- **`credential_patterns`** (9): Anthropic key/OAuth, OpenAI, GitHub PAT (classic + fine-grained), AWS access key, Slack bot/user token, Google API key.
- **Budgets**: `max_turns_chat: 200`, `max_turns_task: 200` (raised from 50 in trinity-enterprise#471), `execution_timeout_sec: 1800`. The baseline is baked into the agent image, so a deployed agent adopts a new default only after `./scripts/deploy/build-base-image.sh` and a **cold start** (stop → start; image drift is evaluated only when the agent was not already running, #1809). No recreate is needed, and a per-agent override (`AGENT_GUARDRAILS`) is unaffected.
- **Override slots** (empty by default): `extra_bash_deny: []`, `extra_path_deny: []`, `disallowed_tools: []`.

## Guardrail event store and read (GUARD-005, trinity-enterprise#165 S1)

The backend half of the guardrail event surface. The hooks' spool and the agent-server forwarder that pushes it are slice S2 (not described here). Requirement: [security.md §28.5](../requirements/security.md).

```
forwarder (agent's own TRINITY_MCP_API_KEY)
  └─ POST /api/agents/{name}/guardrail-events          routers/guardrail_events.py
       ├─ authorize_heartbeat (own key only) ......... 403
       ├─ guardrail_event_service.check_rate ......... 429 + Retry-After (60 / 60 s / agent)
       ├─ body > 256 KiB / events > 500 .............. 413
       ├─ authorize_heartbeat again, body in hand .... 403 (a body that outlived a delete / rename)
       ├─ GuardrailEventBatch (envelope only) ........ 422
       └─ guardrail_event_service.ingest
            ├─ normalize_event, one at a time ........ rejected++ on a shape failure
            ├─ db.insert_guardrail_events ............ ON CONFLICT (agent_name, event_id) DO NOTHING RETURNING id
            └─ record_report → Redis agent:guardrail_reporter:{name}

owner / admin (OwnedAgentByName, uniform 404)
  └─ GET /api/agents/{name}/guardrail-events?since&until&kind&execution_id&limit&before
       └─ list_events → {events, next_cursor, reporting}
```

| Piece | Where | What it decides |
|---|---|---|
| Ingest + read routes | `src/backend/routers/guardrail_events.py` | Status order the forwarder branches on (403 → 429 → 413 → 422 → 200). The body is read under the byte cap, never buffered past it, and the own-key check runs again once it is in, so a slow body cannot write after its agent was deleted or renamed. |
| Validation, reporting, counts | `src/backend/services/guardrail_event_service.py` | `KINDS` / `HOOKS` (the §6.1 closed sets; unknown → `other` + `kind_raw` / `hook_raw` in `details`), the open `code` (`^[a-z0-9_]{1,64}$`), `execution_id` > 128 chars → null, the field allowlist (`patterns`, `verb`, `tier`, `turn_kind`, `rule` ≤ 200, `path` ≤ 512, `session_id`, `tool_use_id`), free text through `sanitize_text`. A NUL or a lone surrogate (no store can hold either) becomes U+FFFD in display text and drops an id, so one such event never fails the batch or the read. A `ts` later than the receive time is stored at the receive time (`occurred_at` ≤ `received_at`; the agent's value kept as `details.occurred_at_reported`), so a skewed clock neither loses the event nor keeps it in every window. Reporting state: `never` / `reporting` (≤ 15 min) / `stale`; a missing Redis record falls back to the newest row's `received_at`. `first_report_at` is the coverage start: `HSETNX` on the first report (first write wins), else the oldest row's `received_at`, else `last_report_at`; capped at `last_report_at` (two racing reports can write the start after a later-dated last); null exactly when `never`. A lost Redis can only move it later. The create path (`crud.create_agent_internal`) clears a recycled name's reporter record beside the #1560 breakers, so a predecessor's start (a fail-open teardown clear, or an ingest in flight during the delete) never dates a new agent's coverage. `count_by_execution` reads reporting before the counts. |
| Store | `src/backend/db/guardrail_events.py`, table `guardrail_events` | Keyset paging on `(occurred_at, id)`; `count_by_execution` (one `IN` query, filtered by agent); `count_by_agent`; the retention count and prune share one predicate on `received_at`. |
| Migrations | `db/migrations.py::guardrail_events_table`, Alembic `0123_guardrail_events` | Additive table + three indexes on both tracks (Invariant #9). |
| Lifecycle | `db/agent_cleanup.py` `AGENT_REFS` (CASCADE); `services/agent_runtime_state.py` `CLEARED_KEYSPACES` | Rows rename with the agent and go with its hard delete. The reporter key is cleared on teardown only — not on start, or a restarted agent would read `never`. |
| Retention | `guardrail_event_retention_days` (default 90, `0` off) in `config.py`; `cleanup_service._sweep_guardrail_events_retention` | Pruned by server receive time behind the #1644 guard, in bounded chunks. |
| Censuses | `services/agent_route_tiers.json` (POST `self`, GET `owner`); `tests/unit/_route_census.py` `AGENT_CALLABLE_ANY` | Both routes classified; the frozen baseline does not grow. |

**Seams for other features.** `count_by_execution(agent, execution_ids)` → `{"reporting": {...}, "executions": {id: {"by_kind": {...}, "by_hook_code": {"hook:code": n}}}}` (executions without events are absent; `reporting.first_report_at` lets a consumer read a run that ended before coverage started as "no data", not as a clean 0); `count_by_agent(hours, agent_names=None)` → `{"agents": {name: {"by_kind": {...}}}}`. Consumers read at request time: an event lands a few seconds after the hook fired. Neither reads the spool. **Consumer (#4281):** the execution reads put a schedule-backed run's `turn_tier_guard` count on `ExecutionSummary` / `ExecutionResponse` (`services/execution_refusals.py`) — see [tasks-tab.md](tasks-tab.md).

**Not covered by S1.** No forwarder exists until S2 lands, so on this slice alone every agent reads `never`. No UI, no fleet endpoint (S4), no MCP tool. Events are agent-reported, not tamper-proof.

**Tests.** `tests/unit/test_ent165_guardrail_event_store.py` (real rows, SQLite + PostgreSQL), `test_ent165_guardrail_event_route.py` (real router over a real DB), `test_ent165_guardrail_event_retention.py`, `test_ent165_guardrail_event_contract.py` (enum parity with the hook library; skips until S2 adds `EVENT_KINDS` / `EVENT_HOOKS`).

## Relationship to Read-Only Mode (CFG-007 / #887)

Guardrails and read-only mode are **independent, complementary** layers:

- The read-only feature's live config `/opt/trinity/read-only-config.json` is root-owned `0444` in a root-owned directory, written by the backend through a root `docker exec`, and covered by `path_deny` via `/opt/trinity/*` (trinity-enterprise#787). The home copy `~/.trinity/read-only-config.json` decides only while the root file is missing (no effect while it exists) and is protected by `path_deny` (block Write/Edit) *and* by a dedicated `bash_deny` regex (block shell redirects/pipes at it).
- `file-guardrail.py` and `read-only-guard.py` both run on the same `Edit|Write|…` matcher. Guardrails fire **regardless of read-only state** — disabling read-only does *not* re-open `path_deny` targets.
- `#887` moved the read-only guard into the base image (`/opt/trinity/hooks/`, root-owned) and made it fail-closed via the same `run_hook()` wrapper documented above.

See [read-only-mode.md](read-only-mode.md).

## Security Properties

1. **Baseline immutable** — image-baked, root-owned `0444`; agent cannot read-modify-write it.
2. **Runtime config root-generated** — written by `sudo` at boot, `0444`; agent process cannot rewrite it post-start without `sudo` (`developer` holds `NOPASSWD:ALL`; `bash_deny` refuses the obvious `sudo` spellings, #3105).
3. **Hooks tamper-resistant** — in `/opt/trinity/*` (path-denied) and registered in root-owned `/etc/claude-code/managed-settings.json` (also path-denied; ent#345). `sudo` can still rewrite both; `bash_deny` refuses the obvious spellings and agent `/health` reports `guardrails_registration` per request (#3105).
4. **Override scope minimal** — numeric caps + literal substrings only; regex and credential scanner are platform-owned.
5. **Fail-closed everywhere** — bad stdin, bad config, or any uncaught hook exception → deny (exit 2).
6. **No value leakage** — credential scanner logs pattern *names*, never matched secrets.
