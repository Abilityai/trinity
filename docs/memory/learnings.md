Append-only. One entry per *class* of error/pattern worth knowing before the next

## 2026-06-23 — pitfall — Adding a column needs BOTH schema.py AND tables.py; parity test guards only one
**Context**: `agent_ownership.voice_name` (trinity-enterprise#28). `tests/unit/test_schema_parity.py` compares `db/schema.py` (raw DDL) against `db/migrations.py` (the SQLite runner) — it does **not** import `db/tables.py` (the SQLAlchemy Core MetaData that Alembic autogenerates from and that every `db/*.py` accessor binds columns against). So a change that adds a column to `schema.py` + `migrations.py` but forgets `tables.py` keeps the parity test green, yet `select(agent_ownership.c.<col>)` blows up at runtime on the first call.
**Lesson**: A schema change touches **four** files — `db/schema.py`, `db/tables.py`, a SQLite migration in `db/migrations.py`, and an Alembic revision under `db/../migrations/versions/`. Don't trust schema-parity to catch a missing `tables.py` Column. The real guard is a db-accessor unit test that executes a live `select(table.c.<new_col>)` against a migrated DB (db_harness) — it fails loudly if `tables.py` was missed.

## 2026-06-28 — pitfall — `@dataclass` on a fieldless str-Enum breaks member equality
**Context**: `TaskExecutionErrorCode(str, Enum)` is decorated `@dataclass` (`services/task_execution_service.py:75`). `@dataclass` synthesises an `__eq__` that compares the (zero) fields, so for enum members `AUTH == BILLING` — and even `TIMEOUT == AUTH` — all evaluate **True**. `apply_result`'s breaker line `envelope.error_code == TaskExecutionErrorCode.AUTH` therefore fired for *any* non-None code reaching it (504→TIMEOUT pre-existing; 429→BILLING after #1085 populated it), wrongly tripping the AUTH dispatch breaker. Found in the #1085 review; fixed by value-comparing (`error_code.value == "auth"`).
**Lesson**: Never put `@dataclass` on an `Enum` subclass. Compare enum codes by `.value` (or plain `is`/identity), never `==` against another member, until the stray `@dataclass` decorators are removed fleet-wide. Membership tests (`x in (A, B)`) are also broken by the same quirk.

## 2026-07-01 — pattern — Idempotency: `effect_guard` (#1084) is execution_id-scoped; user-initiated POSTs use `Idempotency-Key` (#18)
**Context**: Brain Orb Phase 4a KB-write actions (trinity-enterprise#61). The issue said "wire the #1084 effect guard," but `idempotency_service.effect_guard` builds its scope as `effect:{execution_id}` and `resolve_and_validate_execution` fail-opens to no-dedup when there's no execution — brain-orb capture/link are user→backend producer POSTs with **no** `execution_id`, so effect_guard would be a silent no-op (or collide on `effect:None`). The correct primitive is the trigger-boundary `Idempotency-Key` path (`idempotency_service.begin/complete/fail` over `make_agent_scope`, Invariant #18).
**Lesson**: `effect_guard` is for **agent-turn side effects** keyed by the per-fire `execution_id` (messages/voip/share_file). For a **user-initiated** write endpoint that creates no execution, use the `Idempotency-Key` header + `begin/complete/fail`, and **fold the action verb into the key** (`{action}:{client_key}`) so a client that reuses one key across different verbs can't replay the wrong verb's snapshot. Also: `Idempotency-Key` dedups the **HTTP POST**, not the downstream sink write — exactly-once at the sink is still the sink's job; and a fresh-key-per-call client (like the orb) only dedups transparent network retries, so guard double-submits client-side too.

## 2026-07-01 — pitfall — A feature kill-switch is only as airtight as its least-gated entry point
**Context**: Brain Orb Phase 4 (trinity-enterprise#61 arc). `BRAIN_ORB_WRITE_ENABLED` gated `/action`/`/actions`/`/postprocess`, but a later commit added `/refresh` — which drives the same agent `action` hook (exec/reindex) — gated only on the *base* `BRAIN_ORB_ENABLED`, not the write flag (final-review F1). Flipping the write kill-switch off left `/refresh` (and thus the action hook) reachable. Recurs because routes reaching a gated subsystem get added incrementally; each new one must re-assert the gate.
**Lesson**: When adding a route/entry point that reaches a flag-gated subsystem (exec surface, write path, paid feature), gate it on the **same** flag as its siblings — audit *every* path into the subsystem, not just the first. Add a test that toggles the specific kill-switch (not just the base flag) and asserts the new route 404s + never calls downstream. Related idempotency footgun surfaced same review: awaiting `audit.log()` **after** `idempotency.complete()` unguarded — an audit throw 500s a *completed* write, and a fresh-key client retry then double-writes; make post-write audit best-effort.
## 2026-07-01 — pitfall — A CSP fetch/media/object directive that omits `blob:` silently breaks browser features using createObjectURL; and there are TWO CSP copies to keep in sync
**Context**: #1400 (misdiagnosed as #784). The Files-tab preview builds a `blob:` URL (`URL.createObjectURL`) and renders it per type: text/download via `fetch(blobUrl)` (governed by `connect-src`), `<img>` (`img-src`), `<video>/<audio>` (`media-src`), and PDF `<embed>` (`object-src` **and** `frame-src` — Chrome renders the embedded PDF in an internal viewer frame, so the blob is checked against `frame-src` too, not just `object-src`). `blob:` is **not** covered by `'self'` — it must be listed explicitly in the specific directive the load uses. `img-src` listed `blob:` (images previewed) but `connect-src` did not (text failed with "Failed to load text content"), and `media-src`/`object-src`/`frame-src` were unset (fell back to `default-src 'self'` → also blocked; the PDF showed Chrome's "This content is blocked"). The breakage is per-feature and invisible until you exercise that exact path — #784's `Content-Disposition: inline` "fix" never touched the CSP, so preview stayed broken across every release since the CSP landed (#549/#641). Trinity has **two** CSP copies that must move together: `src/frontend/security-headers.conf` (prod nginx) and `src/frontend/vite.config.js` (dev-server middleware). Same class already bit #979 (voice `srcdoc` under prod `script-src 'self'`) and #1116/ask-trinity (`connect-src` external origin).
**Lesson**: When a browser feature loads a `blob:`/`data:` URL, add that scheme to the SPECIFIC directive the load uses (`fetch`→`connect-src`, `<img>`→`img-src`, `<video>/<audio>`→`media-src`, `<object>/<embed>`→`object-src`; a PDF `<embed>` **also** needs `frame-src` because Chrome renders it in an internal viewer frame) — `'self'` does not cover `blob:`/`data:`. Change **both** `security-headers.conf` and `vite.config.js` together (a dev-only CSP hides prod-only breakage and vice-versa). "Works for images but not text" ⇒ suspect a `connect-src` gap first. Guard with a test asserting the scheme in each directive of both files (`tests/unit/test_1400_csp_blob_preview.py`).

## 2026-07-04 — pattern — An opaque "session identifier" is an overloaded key: split scope / attribution / memory-source before re-keying
**Context**: #903 (Slack thread-scoped sessions). The single `SlackAdapter.get_session_identifier` string secretly encoded **three** orthogonal concerns that a single-user session kept accidentally aligned: conversation *scope* (what replays), speaker *attribution* (who said each turn), and per-user memory *source* (whose turns feed whose MEM-001 profile). The issue's suggested one-liner (drop `sender_id` from the key so channel threads share context) fixed scope but silently broke the other two — `public_chat_messages` had no sender column so multi-participant history replayed as a flat `User:`, and `summarize_user_memory_background` reads *all* session messages and writes them to the *current* user's durable, re-injected memory, so Bob replying in Alice's thread would persist Alice's turns into Bob's profile (cross-user PII leak). Verified in code before planning; scope escalated to add a per-message `sender_email`/`sender_label` so each axis has its own home.
**Lesson**: Before changing what a shared/opaque key encodes, enumerate every concern that key currently disambiguates. A key that "just works" often works because one variable (single participant) collapses several axes into one; loosen that variable (multi-participant thread) and each hidden axis needs its own explicit column/filter. In particular, any "shared context" change to a chat surface must check the **memory summarizer** — it silently reads whole-session history and writes to one user's durable store, so broadening the session scope without a per-sender filter is a cross-user leak.
## 2026-07-04 — pitfall — After the #1093 SQLAlchemy-Core rewrite, `db.get_chat_session()` returns a Pydantic model, not a dict — `.get("k")` raises and is swallowed
**Context**: #1444 review. `db.get_chat_session()` now returns `Optional[ChatSession]` (Pydantic `BaseModel` via `_row_to_chat_session`). The new persistence owner-gate correctly uses attribute access (`session.user_id != user_id`, `chat.py:1016`), but the pre-existing sibling `_finalize_self_task` (`chat.py:1273`) still uses **dict** access `session.get("user_id") == user_id`. `ChatSession` has no `.get()`, so it raises `AttributeError` — caught by the surrounding `except Exception` at :1291 and logged as a warning. Net effect: self-task `inject_result` into a chat session **silently never works**, and its ownership check never actually runs. Pre-#1093 the accessor returned a dict, so `.get()` was correct then; the Core rewrite flipped the return type and this call-site was missed.
**Lesson**: Any accessor rewritten by #1093/#300 from sqlite3.Row/dict to a Pydantic model breaks every `.get("field")` / `row["field"]` caller — and a swallowing `except` turns the break into a silent no-op, not a crash. When touching one owner-check on a `get_chat_session` result, grep **all** call-sites (`grep -rn "get_chat_session\b"`) and confirm each uses attribute access. Add a db-accessor unit test that asserts the returned object is the model and that `.get`/subscript access is not used downstream.
## 2026-07-04 — pitfall — A critical invariant with zero unit exercise lets a `sys.modules` stub leak masquerade as a real violation
**Context**: #1446. Canary B-01 (queue-status coherence, Tier A critical) false-fired under full-suite load — `db.get_queued_count('a1')=1` vs a 0-queued snapshot — but never in isolation. Root cause was **test harness, not production**: several modules do a module-level, never-restored `sys.modules.setdefault("database", MagicMock())` (`test_watchdog_unit.py`, `test_validation.py`, `test_cb_probe_execution_close.py`, …). `setdefault` is first-writer-wins + session-persistent; `int(MagicMock().get_queued_count("a1")) == 1`, so the canary's `_collect_queued_count_via_service` (`from database import db` resolved at *call* time) read `1` for every agent. B-01 had **no end-to-end unit coverage** — only synthetic `_snap`-built comparator tests — so nothing exercised the real `collect_snapshot`→accessor path where the leak bites. On the shipping SQLite backend the two B-01 read paths (raw `sqlite3` `DB_PATH` vs `get_engine()`) resolve to the same file → no production coherence bug; the Postgres divergence (raw-sqlite readers vs `get_engine()`) is a real but deferred gap, tolerable only because the canary is default-OFF.
**Lesson**: (1) A canary/invariant check that only has *synthetic-snapshot* tests is untested where it actually runs — give every invariant one end-to-end test that drives `collect_snapshot()` against the fixture DB so a harness/wiring leak can't hide. (2) Any test reading an ambient `sys.modules["X"]` (esp. `database`) is at the mercy of leaked stubs; the fixture must **own** that dependency via `monkeypatch.setitem` (auto-restored, last-write-wins overrides a leak), and the stub should **delegate to the real backend seam** (`get_engine()` over the temp DB) — not a hand-fed constant, or the coherence test degrades to a tautology. (3) `sys.modules.setdefault(...)` at module scope is the worst offender: first-writer-wins means it survives even an explicit preload and poisons every downstream `from X import ...` for the whole session (the `test_904 database.db` leak family).

## 2026-07-04 — pitfall — `update = none` submodules: skip exits 0, `--init` copies the strategy local, and existing clones inherit the flip asymmetrically
**Context**: #1443 made both private submodules (`.claude`, `src/backend/enterprise`) `update = none` so OSS clones init without credentials. Three git behaviors (all empirically verified) make naive rollouts break silently: (1) a skipped submodule **exits 0** — any script judging init success by exit code (deploy-dev.yml did) takes its success branch while the checkout is absent/stale; (2) **every** init path (plain `--init`, `--init --checkout`, `clone --recurse-submodules`) **copies `update = none` into `.git/config`** — `--init --checkout` is only special in that it additionally clones once — so later plain `git submodule update` silently skips again; a one-shot flag is not a durable opt-in; (3) existing clones are protected from a `.gitmodules` flip **only if** an `update` key existed there at init time (init copied it into local config, which wins): `.claude` clones were protected (`update = checkout` predated the flip), enterprise clones were not.
**Lesson**: When flipping a submodule to `update = none`: patch every automation that inits it to (a) set the durable local override `git config submodule.<path>.update checkout` before init and (b) judge success by a populated marker file, never exit code; document the config-first opt-in (config line, then plain `--init`) as the primary instruction; and check `git config submodule.<path>.update` on existing clones to know who silently changes behavior.

## 2026-07-06 — pitfall — Stripping tzinfo without converting mis-compares non-UTC datetimes; schedules store AWARE next_run_at
**Context**: #1472. `agent_schedules.next_run_at` is written by `_get_next_run_time` as a **timezone-aware** value in the schedule's own zone (e.g. Europe/Kiev `+03:00`). `_get_missed_schedules` (`src/scheduler/service.py`) did `expected.replace(tzinfo=None)` — stripping the offset **without converting** — so a Kiev schedule compared 3h off and a genuinely-missed window looked "future" and was skipped. Separately, a naive `stored > datetime.utcnow()` against an aware value raises `TypeError: can't compare offset-naive and offset-aware` (bit the new advance-guard + a test assert). The scheduler helper, the new advance-guard, and the new canary E-06 check all needed the same UTC-aware handling.
**Lesson**: When comparing a stored schedule/execution timestamp, **convert to UTC, never strip tzinfo**: `dt.astimezone(pytz.utc)` for an aware value, `dt.replace(tzinfo=pytz.utc)` only when it's known-naive-UTC — then compare against `datetime.now(pytz.utc)`. `replace(tzinfo=None)` on an offset-bearing value silently shifts it by the offset; a bare `aware > naive` crashes. Any codepath touching `next_run_at`/`last_run_at`/`started_at` of a non-UTC schedule is in this class.
**Update (#1474)**: the scheduler DB mapper (`src/scheduler/database.py`, via `parse_scheduler_ts`) now returns **naive UTC** for every row timestamp — it *converts then strips* (the instant is preserved, not the #1472 anti-pattern), so the model types stay naive and duration math stays `naive − naive`. The `_get_missed_schedules`/`_advance_next_run_only` comparisons above therefore hit the `known-naive-UTC` (`replace(tzinfo=pytz.utc)`) branch for DB-sourced schedules and remain correct; the aware branches stay for datetimes sourced outside the mapper. Backend-written `next_run_at` remains aware `+00:00`/offset — this section's "schedules store AWARE next_run_at" is true of the *backend* writer, not the scheduler read path.

## 2026-07-06 — pattern — Validate a config with the SAME parser the executor uses, or bad configs pass then fail silently
**Context**: #1472. The schedule create/update API validated cron with a bare `croniter(expr)` and never validated the timezone, but the dedicated scheduler registers via a strict 5-field `_parse_cron` + APScheduler `CronTrigger` + `pytz.timezone`. `@daily`, 6-field seconds-crons, quartz `L`/`#`, and any bad timezone **clear croniter** but throw in `_add_job` — the schedule is accepted, never registers, never fires, and its `next_run_at` freezes ("Next: Nd ago"). The producer-side validator was looser than the consumer-side parser.
**Lesson**: When an API validates input a **different** component will later parse/execute, validate with that component's exact parser, not a convenient looser one. For schedules the parity primitive is `services/schedule_validation.py` (mirrors `src/scheduler/service.py::_parse_cron` + `CronTrigger` + `pytz`) — keep them in sync. Pair it with executor-side resilience (classify a failed registration transient-retry vs permanent-bounded) so a config that still slips through is never a permanent silent orphan.

## 2026-07-06 — pitfall — A new db-layer accessor needs an explicit DatabaseManager facade delegation; wholesale-mocked `database` tests are structurally blind to it
**Context**: trinity-enterprise#93 review (C1). `get_git_config_agent_names_for_repo` was added to `ScheduleOperations` (db/schedules.py) and called via `db.` in crud — but `DatabaseManager` (database.py) has no `__getattr__` fallback; every accessor needs a hand-written one-line delegation. The call would have raised `AttributeError` on the first real request. The 35-test unit suite stayed green because it mocks the entire `database` module with `MagicMock`, which synthesizes any attribute.
**Lesson**: When adding a db-layer method, grep `database.py` for a sibling's delegation and add yours next to it — the facade is manual, not dynamic. And every new accessor needs one test that touches the REAL facade (e.g. `DatabaseManager.__new__` + a mocked `_schedule_ops`, or a db_harness live-select) — a `MagicMock`-ed `database` module can never catch a missing delegation, a typo'd method name, or a wrong return shape.

## 2026-07-07 — pitfall — Frontend e2e specs rot silently: they run only on `ui`-labeled PRs, so a UI refactor merged without the label breaks them invisibly
**Context**: #1500. The #954 spec `agent-detail-chat-width.spec.js` anchored on `page.locator('nav.-mb-px')`; #1114 (OverflowTabs) later added a second, aria-hidden `nav.-mb-px` measuring mirror — a strict-mode violation that made the spec fail on contact. Nobody noticed for weeks because the `frontend-e2e` workflow is path/label-gated (`ui` label), and #1114-era PRs that reshaped the tab strip didn't re-run the older spec. The next `ui`-labeled PR (this one) inherited a red suite for a pre-existing breakage.
**Lesson**: (1) When a PR touches shared UI structure (tab strips, nav, layout wrappers), run the EXISTING e2e specs that anchor on that structure locally — green CI on the refactor PR proves nothing if the suite didn't run. (2) In specs, prefer `data-testid` or `.first()`-disciplined locators over bare structural selectors like `nav.<class>` — hidden measuring/mirror twins (the #1114 pattern) turn bare locators into strict-mode violations. (3) Budget for repairing pre-existing spec rot in whatever `ui`-labeled PR discovers it — it blocks that PR's CI either way.

## 2026-07-08 — pitfall — A fresh-install-only modal (the onboarding wizard) auto-opens on a zero-agent CI stack and its full-screen backdrop intercepts every `/`-spec's clicks
**Context**: #1500's first e2e run. `dashboard-grid-view.spec.js` (and a flaky `browser-tab-titles`) timed out clicking the dashboard mode toggles — the `OnboardingWizard` (trinity-enterprise#52) `fixed inset-0` backdrop intercepted the pointer. `Dashboard.vue::maybeAutoOpenOnboarding` auto-opens the wizard once on a fresh install with **zero user-created agents** (`trinity-system` is filtered out), gated only by `localStorage['trinity_onboarding_dismissed_v1']`. The CI stack is exactly that shape (fresh DB, only the system agent), so the wizard auto-opens; it's a **race** — the open fires after fleet-load resolves, so a spec that clicks fast sometimes wins and sometimes doesn't (flaky, not deterministic). Local dev never reproduces it because a developer's stack has real agents, so the wizard never auto-opens. No e2e spec dismissed it, so it was latent until the `ui`-gated workflow actually ran.
**Lesson**: Fresh-install-only UX (onboarding, empty-state CTAs, first-run modals) is invisible in local dev but is the DEFAULT state of the CI stack — treat "zero user agents" as the e2e baseline. Seed the product's own "remembered" dismissal key in the shared `auth.setup.js` storageState (same origin as `token`, captured by the snapshot) so every inherited context is modal-free, rather than dismissing per-spec; specs that WANT the wizard opt back in via `?onboarding=1` (which bypasses the key). When adding any auto-opening global modal, grep the e2e suite for `/`-navigating specs and confirm the setup seeds its dismissal.

## 2026-07-07 — pitfall — Any subprocess the agent-server spawns is invisible to the orphan sweep unless explicitly vouched for
**Context**: #1501. `resolve_allowlist`'s hard-protect walk goes from the sweeper UP to PID 1 — never down to the agent-server's other children — so a bare `asyncio.create_subprocess_exec` child of the agent-server (a brain-orb convention hook) matched none of the four allowlist categories and the 30s periodic sweep SIGKILLed it mid-run (the 180s `refresh` reliably → exit -9 → 502). #1494 had already fixed this exact class for post-voice `claude -p` by dispatching a registered execution; `refresh` was left on the bare-hook path. Same investigation surfaced two siblings: gemini's 3 post-turn sweeps ran with NO `extra_pids` (a finishing Gemini turn could kill concurrent in-flight work — the #912 class, unfixed on that path), and user `persistent-processes.allow` patterns protected only the bare matched pid, so an allowlisted daemon's worker children were reaped anyway.
**Lesson**: A new agent-server spawn site (hook, helper subprocess) must either wrap the run in `ProcessRegistry.add_transient_pid`/`remove_transient_pid` (finally-paired, fail-open) or dispatch as a registered execution — otherwise it dies whenever it straddles a sweep tick (P ≈ runtime/30s, ≈certain past 30s). And a new `kill_cgroup_orphans` call site must pass `extra_pids=active_execution_pids()` — a bare call kills concurrent in-flight work. Known residual exposure: `agent_server/routers/git.py` `subprocess.run` children (short-lived git ops; follow-up candidate alongside the descendants_of(sweep_pid) seam discussion). Test-side corollary (the #1446 class, re-confirmed by this PR's first CI run): production code that resolves the registry via a CALL-TIME lazy import cannot be stubbed by patching an attribute on the module object your test file imported — sibling test modules (`test_agent_server_auto_sync.py`, `test_git_status_dual_ahead_behind.py`) evict `agent_server*` from `sys.modules` at module level during collection, so the lazy import re-creates a fresh module your patch never touched (fails in the full suite, passes in isolation). Own the key instead: `monkeypatch.setitem(sys.modules, "agent_server.services.process_registry", stub_module)`.
**Update (#1595)**: the same re-exec mechanism also breaks **`is`-assertions**, not just patches: two agent_server test files each evict+reload the package at collection, so a test's import-time capture of a function and the code-under-test's call-time relative import can resolve to *different module generations* — `recorded_fn is captured_fn` then fails only in combined runs (passes in isolation). Assert against the live object resolved through `sys.modules["agent_server.routers.git"]` at assert time, never an import-time capture.

## 2026-07-08 — pitfall — A consolidation refactor that swaps a resolver's body is a no-op if nothing calls the resolver
**Context**: #1521. Plan was to fix wrong context-window denominators by swapping the body of each runtime's `get_context_window`. But `ClaudeCodeRuntime.get_context_window` was **dead code** — never called anywhere (grep-confirmed: only the def + the ABC). For the Claude runtime (the platform default), `metadata.context_window` is set ONLY by `stream_parser` (from `modelUsage.contextWindow`, the primary) or the static Pydantic field default `ExecutionMetadata.context_window: int = 200000`. So the *real* fallback is a static class-attribute default, not the method that looks authoritative. Gemini/Codex genuinely call `get_context_window`, so their body-swaps worked — Claude was the asymmetric trap. Shipping the "obvious" version would have been a green diff, passing (unrelated) tests, and the exact bug still live on the default runtime. Fix: seed `metadata.context_window` from the catalog at metadata *construction* (so the stream value overrides it and the catalog is the real fallback), guarded by a regression test that asserts the catalog value actually reaches `metadata.context_window`.
**Lesson**: Before "consolidate the scattered logic into one resolver and call it everywhere", grep each call site of the method you're changing and confirm it's actually invoked on the path you care about. When a value has a static default (a Pydantic field default, a dataclass default, a `dict.get(k, DEFAULT)`), THAT default — not the nicely-named resolver — is the fallback that ships; verify the resolver is on the live path or wire it in explicitly. Always add a test that asserts the new value reaches the persisted/consumed field, not just that the resolver returns the right number in isolation.

## 2026-07-09 — pitfall — `UPDATE ... WHERE id = (scalar subquery)` double-applies under Postgres concurrency, and a sequential test cannot catch it
**Context**: #1081 pull `claim_next_queued` (C1); `db/schedules.py`. A single `UPDATE schedule_executions SET status='running',… WHERE id = (SELECT id … WHERE status='queued' ORDER BY queued_at LIMIT 1)` handed one queued row to up to N concurrent workers — each stamped a distinct `claim_token` and double-**ran** the turn (real-PG harness: 25/25 iterations, head row claimed by all 16 workers). Mechanism: the uncorrelated scalar subquery compiles to an **InitPlan evaluated once → constant id X**; under READ COMMITTED every updater that blocks on X's row lock re-runs EvalPlanQual against the **outer** WHERE only (`id = X`, still true for the now-`running` row — the InitPlan is not re-evaluated and there was no status predicate outside the subquery), so each blocked updater re-applies to X and RETURNs it. The token CAS on the *result* write does not save it — the N turns already executed.
**Lesson**: For an atomic claim/dequeue `UPDATE ... WHERE id = (SELECT … LIMIT 1)`, the inner subquery's `status='queued'` filter is NOT the concurrency guard — put the mutated predicate in the **outer** WHERE too (`AND status = 'queued'`) so a losing updater's CAS is a no-op, and/or add `FOR UPDATE SKIP LOCKED` to the subquery so concurrent claimers lock distinct rows (Postgres only; SQLite serialises writers and lacks the clause — the outer re-check is the cross-dialect backstop). Ship both. **Test corollary:** a *sequential* claim test (claim w1, then w2, assert w2 gets None) proves nothing here — the inner subquery already makes the second sequential claim a no-op, so the test passes with or without the fix. The guard is only exercisable under real multi-process/thread contention on a real Postgres engine; a committed regression MUST be a multi-process (or thread) harness on PG, not the SQLite/sequential default. (Contrast the reaper transitions in the same file, which were correct from the start because their precondition lives in the outer WHERE.)

## 2026-07-09 — pitfall — A counter column is only as truthful as its writer, and wholesale-mocked `database` tests cannot see that the writer is dead
**Context**: #1533. The Sharing-tab client roster showed `message_count = 0` for every external client, `last_active` was frozen at `/login` time, and clients who never ran `/login` never appeared at all — because `get_or_create_chat_link` AND `increment_message_count` (Telegram + WhatsApp) had **zero callers** outside the `database.py` facade. The shared inbound path (`message_router._handle_message_inner`) writes `public_chat_sessions`, a *different* table, so the `*_chat_links` rows were only ever created by `set_*_verified_email`. Nothing failed loudly: `client_roster_service`'s own docstring asserted the channels "record the full `(verified_email, message_count, last_active)` triple", and the read path faithfully echoed a column nobody wrote. The issue's own Context paragraph then mis-diagnosed it ("`last_active` is touched on inbound traffic via `get_or_create_chat_link`") — reading the code, not the issue, was what found the real shape. ## 2026-07-12 — pitfall — A new heavy test file entering the randomized unit suite inherits the #762 sys.modules-stub leaks; own your real modules at collection time

## 2026-07-15 — pitfall — A mutable code default read at ACTION time is a live control surface: lowering it retroactively destroys existing data. Apply new policy by seeding, not by defaulting.

## 2026-07-17 — pitfall — A resource's self-description is not its ownership, and renames are what prove it
**Context**: #1664. Docker volumes carry the agent name twice — in the volume name (`agent-{name}-workspace`) and in an immutable `trinity.agent-name` label — and rename can change neither, so it keeps both. The #1581 orphan sweep read that pair as ownership truth (`is_agent_name_reserved(label)` → no such agent → orphan → `volume rm -f`) and would destroy a **live** renamed agent's `/home/developer` the moment a container recreate left it briefly unattached. Its "double-guard" (name AND label must match) could never catch this: it verified the two halves of the identity agreed *with each other*, and after a rename both are equally, consistently stale — a self-consistent lie. The docstring claimed "a live/durable agent's data is unreachable by a bug"; rename falsified it. The same root produced three more bugs in different directions, all invisible until the identity model was made explicit: the purge removed `agent-{new}-*` (volumes that never existed) and leaked the real ones; soft-delete recovery (`recreate_missing_container`) mounts a fresh **empty** volume for a renamed agent (#1665); and because rename frees the old *name* while the old *volume* lives on, creating a new agent under that freed name silently **reuses the renamed agent's home volume** — `crud.py` does `volume_get(...)` → found → mount, so a different owner's new agent boots on agent A's `.env` (verified against a real daemon: it read A's API key).
**Lesson**: When a resource can be renamed but its durable identity cannot, **ownership must live in a row you control, never in the artifact's own name/labels** — ask "does any owner claim this?", not "is this name an owner?". Corollaries, each learned by getting it wrong in the fix itself: (1) An identity guard that only checks internal consistency (name matches label) proves the *caller aimed correctly*, not that the target is dead — it is a last line of defence, never liveness; state that in the docstring or the next reader will trust it as safety. (2) A renamed resource can own artifacts under **both** identities at once — here the workspace keeps the old base while `get_public_volume_name`/`get_shared_volume_name` name off the *live* name, so the ownership predicate must be a **union** (`agent_name OR volume_base_name`); matching only the pin deleted a live agent's public volume, which the attached-check could not save because that volume is unmounted whenever file-sharing is off. Whenever you replace a predicate, check the new one is a **superset** of the old — `is_agent_name_reserved` turned out to be exactly the union's first branch, which is what made the union provably safer rather than merely different. (3) A destructive sweep's evidence must be *positive* and *repeated*: "in use" is a fact (skip it), "not in use right now" is a snapshot that a recreate gap forges — require a streak, and fail **closed** when the mount table is unreadable, since "unknown" must never read as "unused". (4) Mock-based unit tests cannot see a facade gap: mocking `db` made three `db.<new_method>()` calls green that would have raised `AttributeError` in production and — because the sweep swallows per-cycle exceptions — silently degraded the reclaim to a permanent no-op. The `test_database_facade_delegation` guard caught it; a mock-free run against the real DB + real daemon is what actually proves wiring.

## 2026-07-17 — pitfall — A periodic sweep gated on the store's near-expiry window structurally misses most items when the window is narrower than the sweep cadence
**Context**: #1616 review. The wired-up expired-SSH-key sweep removed a key's `authorized_keys` line only while its Redis TTL was in `[0, 60]s` (`ssh_service.cleanup_expired_credentials`), but the sweep runs on the 5-min (`300s`) `cleanup_service` cadence. A 60s catch-window against a 300s tick means a cycle lands in the window only ~60/300 = **20%** of the time; the other ~80% the auto-expiring Redis key vanishes from `scan_iter` between two ticks, unobserved, and the file line — the *only* thing that revokes key-auth access on a preserved-volume agent — was never removed. So the "security fix" was ~20% effective and its docstring claimed it "makes file-side expiry actually happen." Not a regression (pre-fix: zero callers → 0% removed), which is exactly why it read as done. Mocked unit tests pinned the gap as correct (`ttl=30 → removed`, `ttl=3600 → not`) — they asserted the window, not the outcome. Fix: drive the sweep off the stored `expires_at` (`now >= expires_at`) and keep the Redis metadata alive a grace (`> cadence`, 600s) past true expiry so every expired item is observed by ≥1 cycle before the store forgets it; forget the row only *after* the external side-effect succeeds so a transient failure retries.
**Lesson**: When a best-effort background cleanup races an **auto-expiring** store (Redis TTL, cache eviction, a queue's visibility timeout), the cleanup must **outlive** the store, not race it — either the store keeps the record past its logical deadline (grace) so the sweep is guaranteed an observation, or the sweep reconciles the *external* artifact against the store directly. A catch-window keyed on "about to expire" is a coin-flip whenever the window < the cadence, and it fails **silently** because the record is simply gone next cycle — no error, nothing to log. Two review tells for this class: (1) a fix whose effectiveness depends on a timing window — compute `window/cadence` and if it isn't ≥1, most items slip; (2) tests that assert the *mechanism's trigger* (a TTL threshold, a flag) rather than the *end state* (the artifact is actually gone) will green-light the miss — always add one test that puts the item outside the window but past its true deadline and asserts it's still handled.

**Context**: trinity#1804 review. ## 2026-07-28 — pitfall — `if: always()` + a `cancelled` result clause silently defeats `cancel-in-progress`
**Context**: trinity#1782 review. The fix for the `changes` path-filter (files API + fail-open) was correct and independently re-verified. **Context**: trinity#1871 review. ## 2026-07-30 — pitfall — When a diff adds an unbounded loop to a shared reader, the cap belongs in THAT PR — capping the new sibling and not the extended one leaves the amplification fully open
**Context**: trinity-enterprise#128 PR-B review. The plan had already found and named this exact failure (W8: *"400k malformed entries yielded 1 capped record and 400,000 uncapped errors — a 35 MB response built out of the cap that was supposed to prevent exactly that"*), and the implementation duly shipped `_MAX_CREDENTIAL_ERRORS = 100` on the **new** function, `normalize_credential_requirements`. **Lesson**: (1) A cap is a property of the **producer**, not of the PR that invented the concept. When you write `_MAX_*` for a new function, immediately grep the module for the *other* functions feeding the same response field (here `credential_errors`, fed by two producers) and cap them in the same commit — the review question is "which producers reach this surface", never "did I cap the thing I just wrote". (4) Test corpora built to prove *verdict* correctness are structurally blind to *size* regressions — they use small fixtures by design. Size needs its own adversarial fixture, and the honest one is "small source, huge parsed walk".

## 2026-07-31 — pitfall — A WHATWG-URL credential scrubber silently no-ops on the exact shapes it exists for: verify the strip TOOK, never assume `new URL()` + setter worked
**Context**: trinity-enterprise#263 review, `stripUserinfo()` in `components/skills/contract.js` (library repo URLs are stored with embedded `user:token@` verbatim; the scrubber runs before display). The original two-lane design — `new URL()` setter, regex fallback in `catch` — leaked on five proven shapes. Two failure families: (1) the fallback regex under-matched what the primary lane rejects (`\w+:\/\/` misses `git+ssh://`; no protocol-relative `//user:token@host`; `^` anchor defeated by leading whitespace; schemeless/scp `user:token@host…` never matched at all); (2) worse, the primary lane *succeeds without stripping*: `user:token@host/path` PARSES as a WHATWG URL (scheme `user`, opaque hostless path) where `.username = ''` is a **silent no-op** per spec ("cannot have a username/password/port"), so the credential sailed through the success path and the fallback never ran. ## 2026-08-02 — pitfall — Catching the raise is half the fix; propagating it into the state machine is the other half — and a test that stops at "it was caught" cannot tell the two apart
**Context**: trinity-enterprise#127 review. `credential_requirements_service._safe_normalize` deliberately wrapped `normalize_credential_requirements` NARROWLY (the ent#128 `run_static` lesson: blanket swallowing turns a raise into a verdict indistinguishable from a pass) and returned `[], ["template declaration could not be read"]`. But `build_report` then set `requirements_source = "live_workspace"` and left `degraded_reason = None`, so an empty record list scored `state = "no_credentials_required"` → the UI headline "Ready — this agent needs no credentials." on a green background, with the real reason folded into a collapsed `<details>`. ## 2026-08-02 — pitfall — A single trailing dot in a hostname shifts every label one place right and silently defeats an eTLD+1 emphasis defence
**Context**: trinity-enterprise#127 review. `setup_url_display._registrable_domain` splits an already-punycode host on `.` and takes the last two labels, and the UI bolds that segment inside the dimmed full host so an operator can judge `accounts.google.com.`**`evil.tld`** before clicking a link that sits next to a "paste your API key" input. A trailing dot is the DNS root label — `evil.tld.` resolves identically in every browser — but it produces a trailing empty label, so `accounts.google.com.evil.tld.` emphasised `tld.` and `google.com.` emphasised `com.`: the bold moved off the true registrant onto the public suffix, defeating the module's stated PRIMARY defence (punycode canonicalisation is irrelevant to the all-ASCII subdomain attack) with one character the template author fully controls. More generally, when a defence works by emphasising a computed substring, test that the emphasis lands on the attacker-controlled part under every input form that resolves the same, not just the canonical one.
## 2026-08-02 — pitfall — A per-item swallow plus a count that ignores skips makes a validator's own bug invisible, and persistence replays the false verdict
**Context**: trinity-enterprise#89. `compatibility/static_checks.run_static` catches a raising check and records `_skip(..., "check_error")`; `compatibility/__init__._counts` counts only `status == "fail"`. So a raising check contributes **zero** to every count, and because `overall` is a bare `(hard_count + soft_count) > 0` test, a report flips `issues` → `compatible` exactly when the raising check's finding was the only failure — the failure direction is **open**: a validator that breaks reports "healthy". It is also durable — `build_report` persists `checks_json` and `_report_from_persisted` recomputes counts from that snapshot, so one transient raise is replayed as a clean bill of health on every stopped-agent read. And the swallow **logged nothing at all**, for all ~100 checks, so there was no operator signal anywhere. This was not hypothetical: `c_p006` — a **HARD** check — iterated `data.get("schedules") or []` with no `isinstance(..., list)` guard, unlike all four sibling readers of the same field, so a template with `schedules: 5` had been silently deleting a HARD check from the count in the field for months. The planned mitigation ("a test asserting no fixture leaves `skip_reason == check_error`") was necessary but not sufficient — a finite corpus cannot be a totality proof for untrusted `yaml.safe_load` output, and a T-018-only assertion would never have caught `c_p006` at all.
**Lesson**: when a framework converts a per-item exception into a *neutral* status, check what the aggregate does with that status. `skipped`/`unknown` treated as "not a failure" turns any bug **inside** a validator into a passing grade, and any persistence layer downstream replays it. Three fixes, in order of durability: (1) a check whose whole purpose is malformed-input tolerance must catch its own exception and return **fail**, never rely on the outer net (carry `type(e).__name__` only — `detail` is persisted and UI-rendered, so `str(e)` smuggles untrusted input into a stored blob); (2) **log** the swallow, so the class is measurable before you consider flipping it framework-wide; (3) assert the negative across the **whole** registry, not just the new item — the sibling-with-the-missing-guard is the one that has already been failing open. Corollary from the same change: four readers of one untrusted field carried an `isinstance` guard and the fifth did not — when you touch one reader of a field, grep every reader of that field.
## 2026-07-30 — pitfall — Consolidating two writers behind one function merges their gates, and the COMBINATION of differing gates is a third state the consumer already reads as a signal
**Context**: trinity-enterprise#109 PR 1 review. `_apply_git_env_from_db` unifies the GitHub-sync env derivation across both container-rebuild paths. Each half of the block kept its own, individually-correct gate: the repo half is gated on the **repo** (ent#123 — a tokenless public-template agent must still get `GITHUB_REPO`+`GIT_SYNC_ENABLED` or the rebuild yields a silently empty agent, #843/#1439), the PAT half keeps #211's narrower **per-agent** gate (a global-only platform PAT must never be injected into a previously-tokenless container, the ent#162 leak). Both preserved verbatim, both tested, both with a static call-site guard. The defect was the pair: for an agent bound post-creation via `POST /{agent}/git/initialize` on the *global* platform PAT — no baked git env, no per-agent PAT row, its only credential embedded in the container's `.git/config` origin URL, and not covered by startup.sh's #1264 workspace-`.env` fallback — the two gates disagree, and `GIT_SYNC_ENABLED=true` **with no** `GITHUB_PAT` is precisely the input `startup.sh` reads as "deliberately tokenless": the restart branch rewrites origin to the credential-less `CLONE_URL` (destroying the token) and `configure_push_remote` blackholes the push remote. Silent, unrecoverable without a per-agent PAT, and armed fleet-wide by the base-image drift the consolidation exists to fix. On `dev` it was unreachable because the config-drift path never *introduced* the block at all, so the combination could not occur.
**Lesson**: (1) When merging two writers, the review unit is not "is each gate preserved?" but "what new *combinations* of their outputs become reachable?" A consolidation makes previously-disjoint states co-occur; enumerate the cross-product against the **consumer**, which for env vars is the shell script that reads them, not the Python that writes them. (2) A downstream consumer that infers intent from an *absence* (`GIT_SYNC_ENABLED` present + `GITHUB_PAT` absent ⇒ "read-only by design") turns any newly-introduced key into a semantic change, not an additive one. Grep the consumer for the absence-branch before adding the presence. (3) "Correct what is carried, never introduce" is the safe default when a config-drift rebuild seeds from an old container: correcting a stale value fixes the replay bug, while introducing a block the container never had converts an unmanaged-but-working agent into a managed-and-broken one.

## 2026-07-30 — pitfall — A "convergence backfill" cannot distinguish a legacy discrepancy from a deliberate setting, and inherits the auth tier of whatever triggers it
**Context**: trinity-enterprise#109 PR 1 review. `GIT_SYNC_AUTO` is derived as `DB auto_sync_enabled OR baked env` because `crud.py`'s two creation writers genuinely disagree (the DB opt-in carries `and not config.ephemeral` inside a swallowing `try/except`, the env writer does not, column default `0`) — correct, and DB-only derivation would silently stop auto-push for that slice. The plan then added a write-back "so the OR retires itself". But the same observable has a **second, legitimate** producer: `PUT /{agent}/git/auto-sync {enabled:false}` writes the row and nothing else while the agent gates on container env (`agent_server/auto_sync.py`), and creation sets *both* true for the ordinary non-source-mode PAT agent — so "baked true / DB 0" is exactly what an owner's explicit disable looks like. The backfill re-enabled it on the next recreate and erased the only record of the intent, making the toggle unable to ever stick. When adding a write to a recreate/start/cleanup path, look up the auth tier of the endpoints that reach it and compare with the tier of the state's own setter; a tier drop is an authz finding even when the value written is fixed. (3) A test asserting `backfill.assert_called_once_with(...)` encodes the bug as intended behaviour — when a test's name contains the mechanism ("...and backfills"), check that the mechanism, not just its execution, was the thing the plan justified.

## 2026-08-02 — pitfall — A test double that derives the observed state FROM the state under test cannot witness divergence, so the regression test for a divergence bug passes against code that has it
**Context**: trinity-enterprise#109 PR 2 review. The bind engine's CAS is the commit point, so after it the DB row names the destination while the container's `origin` still names the old repo until the in-container rewire lands — that skew is the *normal* shape of a partially-applied bind, and all four post-commit error messages tell the user to retry. Both pre-flight gates read it as a refusal: `_classify` (origin ≠ row → 409 `BIND_STATE_UNCLASSIFIED`) and the destination policy (any branch → 409 `BIND_DESTINATION_EXISTS`, where the branches are the agent's own just-pushed history). Every documented retry was refused. The regression test written for exactly this — named after the contradiction it existed to prevent — was green, because the fixture's `fake_inspect` returned `origin_repo=fake_db.config.github_repo`: the container's observed state *was* the row, so the two could never disagree, and a second hand-set (`state["dest_state"] = "empty"`) stepped around the other gate. The feature-flow doc meanwhile justified cutting the drift predicate with "idempotent retry already supplies the convergence", so the cut and the broken retry compounded into no convergence route at all.
**Lesson**: (1) When the behaviour under test is *disagreement between two stores*, the double must model them as two independent variables. (2) A fixture that hand-restores state *between* two calls of the same operation is describing a convergence the production code does not perform; the reset lines are the finding, not the setup. (3) An unused parameter on a private helper is evidence about intent, not style: it is often the seam where a designed branch was dropped, and it is worth grepping the plan for the decision it was meant to implement before deleting it.

## 2026-08-02 — pitfall — Rejecting a bad secret at the Pydantic boundary leaks it: `errors()["input"]` echoes the value, and FastAPI's default handler returns it
**Context**: trinity-enterprise#109 PR 2 `/cso`. A GitHub PAT is sent as `Authorization: Bearer <pat>` (`github_service.py`) and h11 rejects an illegal header value **by echoing it** — verified: `LocalProtocolError: Illegal header value b'Bearer ghp_REAL_TOKEN\r'`. Since the `github_pat` validator only checked non-emptiness and returned the value **unstripped**, a token with a trailing `\r`/`\n` — what a paste from a terminal or clipboard routinely produces — reached httpx, and the resulting exception carried the raw token into a 500 body and, via `logger.exception`, into the Vector-captured platform log. The obvious fix (validate the charset in the model) is a lateral move on its own: Pydantic v2 records the rejected value in `errors()[i]["input"]` and FastAPI's default `RequestValidationError` handler passes `exc.errors()` through verbatim, so the same secret comes back in the 422 instead. Confirmed empirically against a real `TestClient` before shipping either half.
**Lesson**: (1) A `SecretStr` field is only as private as its *failure* path — before adding a validator that can reject a real credential, check what the framework does with the rejected value. Pydantic v2 + FastAPI echo it by default. (2) Strip before validating: for a pasted credential, trailing whitespace is the commonest input and rejecting it is user-hostile for precisely the case that motivates the guard. (3) Strip `input` from **every** 422 entry rather than from fields whose *name* looks sensitive — a name-matching allowlist is the new-producer-missing-from-the-consumer's-list class, where the next `SecretStr` field must remember to be named correctly and the one that forgets fails silently. The caller already has the value they sent, so `type`/`loc`/`msg` keep the 422 actionable at no disclosure cost.

## 2026-08-03 — pitfall — A cleanup deferral is only as true as the watchdog it names; "left for the X sweep" needs the sweep's own filter checked
**Context**: trinity-enterprise#313. `_rollback_failed_creation` (agent create) rolled back DB/quota handles and its docstring justified leaving the container behind as "left for the cleanup watchdog". No watchdog covers a **non-ephemeral** agent — the only Docker-as-truth container sweep, `cleanup_service._sweep_ephemeral_agents`, is gated on the `trinity.ephemeral` label. So a failure after `containers.run` left a RUNNING container with no `agent_ownership` row, and the two guards deadlocked: nothing removed the container, and because it kept its workspace volume mounted, `_sweep_orphan_agent_volumes` could never advance the #1581 unattached-strike counter, so the volume was unreclaimable too. **Lesson**: (1) A comment deferring cleanup to another component is a **claim about that component's filter** — go read it. `trinity.ephemeral`-gated, `deleted_at`-gated and "unattached for N cycles"-gated sweeps each cover a strict subset, and the subset is where the leak lives. When adding a "reclaimed later by X" deferral, check that nothing your inaction leaves behind is X's own blocker. (3) Reclaiming **by name** rather than by handle is a different security problem: on a shared Docker daemon (git worktrees, two stacks on one host) a name resolves to another install's live agent, and DB-scoped checks are structurally blind to it. (4) When a **characterization** test asserts the buggy behavior (`container_mock.remove.assert_not_called()` with a comment calling it PRESERVED), that assertion is documentation of the defect, not a contract — update it and say so loudly in the PR, or the leak is protected by its own test.

## 2026-08-03 — pitfall — A test that builds a boundary fixture from its own `datetime.now()` races the implementation's `datetime.now()`; the flake rate is a property of the machine, so "ran it N times" proves nothing
**Context**: #1909. `test_a13_exact_cutoff_row_is_not_expired` computed `exact` from the clock at setup while `expire_stale_queued` computed its threshold from the clock at query time. When the wall second rolled over between the two samples the threshold advanced, `exact` became strictly older, the row was expired, and `assert ops.expire_stale_queued(24) == 1` failed with `2 == 1`. Reported at 3.3% (5/150); reproduced here at **0.33%** (1/300) on faster hardware — same code, same test, a 10× difference, because the window is the wall-time *between the two samples*. CI runs the suite 6× per PR (3 seeds × 2 sides), so a rate that low still reddens `regression diff` on unrelated PRs — it was filed off #1902, whose diff was portal-token code and a Vue component.
**Lesson**: (1) A wall-clock flake's rate is a function of machine speed, not of the code, so a statistical gate is the wrong acceptance criterion in both directions — a green 300-run loop on a fast dev box says nothing about a slow shared runner, and by the rule of three you would need ~900 clean runs just to bound *your own* machine at the rate you were trying to disprove. Prove the race is gone **structurally** (one clock sample) and demonstrate it by **forcing** the interleaving: a ~20-line pytest plugin that busy-waits to park the runner ~1.5 ms before a second boundary turned this from 0.33% into **20/20**, and the same harness then showed **0/30** against the fix. A repro you can trigger on demand is worth more than any number of passive runs, and it is the only way to show a fix has power rather than luck. (2) The usual counter-pattern — give the fixture a wide margin, which `tests/test_backlog.py` documents as the "time-mock-free pattern" — is right for every sibling case and structurally impossible for a *zero-width boundary* case, which is exactly the one tight enough to lose the race often enough to notice. Don't "fix" a recurrence by nudging the fixture off the boundary: that deletes the property the test exists to pin and converts a visible flake into a silent coverage hole. (3) When you must patch a module-level clock, assert the patch took effect — `monkeypatch.setattr(mod, "datetime", …)` silently binds a name nothing reads if the module later aliases its import, and the test drifts back to flaky months later with no signal. (4) The durable seam already existed one screen away: `find_expired_leases(now_iso=…)` in the same module takes an injectable clock, which is why its `a16` tests are deterministic by construction.

## 2026-08-03 — pitfall — A shared helper imported from `services.*` becomes a MagicMock in half the suite
**Context**: trinity-enterprise#314. I put the `parse_template_yaml` policy wrapper in `services/template_service.py` and imported it into `services/agent_service/crud.py`.
