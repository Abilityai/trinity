Append-only. One entry per *class* of error/pattern worth knowing before the next

## 2026-06-23 — pitfall — Adding a column needs BOTH schema.py AND tables.py; parity test guards only one
**Context**: `agent_ownership.voice_name` (trinity-enterprise#28). `tests/unit/test_schema_parity.py` compares `db/schema.py` (raw DDL) against `db/migrations.py` (the SQLite runner) — it does **not** import `db/tables.py` (the SQLAlchemy Core MetaData that Alembic autogenerates from and that every `db/*.py` accessor binds columns against). So a change that adds a column to `schema.py` + `migrations.py` but forgets `tables.py` keeps the parity test green, yet `select(agent_ownership.c.<col>)` blows up at runtime on the first call.
**Lesson**: A schema change touches **four** files — `db/schema.py`, `db/tables.py`, a SQLite migration in `db/migrations.py`, and an Alembic revision under `db/../migrations/versions/`. Don't trust schema-parity to catch a missing `tables.py` Column. The real guard is a db-accessor unit test that executes a live `select(table.c.<new_col>)` against a migrated DB (db_harness) — it fails loudly if `tables.py` was missed.

## 2026-06-28 — pitfall — `@dataclass` on a fieldless str-Enum breaks member equality
**Context**: `TaskExecutionErrorCode(str, Enum)` is decorated `@dataclass` (`services/task_execution_service.py:75`). `@dataclass` synthesises an `__eq__` that compares the (zero) fields, so for enum members `AUTH == BILLING` — and even `TIMEOUT == AUTH` — all evaluate **True**. `apply_result`'s breaker line `envelope.error_code == TaskExecutionErrorCode.AUTH` therefore fired for *any* non-None code reaching it (504→TIMEOUT pre-existing; 429→BILLING after #1085 populated it), wrongly tripping the AUTH dispatch breaker. Found in the #1085 review; fixed by value-comparing (`error_code.value == "auth"`).
**Lesson**: Never put `@dataclass` on an `Enum` subclass. Compare enum codes by `.value` (or plain `is`/identity), never `==` against another member, until the stray `@dataclass` decorators are removed fleet-wide. Membership tests (`x in (A, B)`) are also broken by the same quirk.

## 2026-07-01 — pattern — Idempotency: `effect_guard` (#1084) is execution_id-scoped; user-initiated POSTs use `Idempotency-Key` (#18)
**Context**: Brain Orb Phase 4a KB-write actions (trinity-enterprise#61). The issue said "wire the #1084 effect guard," but `idempotency_service.effect_guard` builds its scope as `effect:{execution_id}` and `resolve_and_validate_execution` fail-opens to no-dedup when there's no execution — brain-orb capture/link are user→backend producer POSTs with **no** `execution_id`, so effect_guard would be a silent no-op (or collide on `effect:None`). The correct primitive is the trigger-boundary `Idempotency-Key` path (`idempotency_service.begin/complete/fail` over `make_agent_scope`, Invariant #18).
**Lesson**: `effect_guard` is for **agent-turn side effects** keyed by the per-fire `execution_id` (messages/voip/share_file). For a **user-initiated** write endpoint that creates no execution, use the `Idempotency-Key` header + `begin/complete/fail`, and **fold the action verb into the key** (`{action}:{client_key}`) so a client that reuses one key across different verbs can't replay the wrong verb's snapshot. Also: `Idempotency-Key` dedups the **HTTP POST**, not the downstream sink write — exactly-once at the sink is still the sink's job; and a fresh-key-per-call client (like the orb) only dedups transparent network retries, so guard double-submits client-side too.

## 2026-07-01 — pitfall — A feature kill-switch is only as airtight as its least-gated entry point
**Context**: Brain Orb Phase 4 (trinity-enterprise#61 arc). `BRAIN_ORB_WRITE_ENABLED` gated `/action`/`/actions`/`/postprocess`, but a later commit added `/refresh` — which drives the same agent `action` hook (exec/reindex) — gated only on the *base* `BRAIN_ORB_ENABLED`, not the write flag (final-review F1). Flipping the write kill-switch off left `/refresh` (and thus the action hook) reachable. Recurs because routes reaching a gated subsystem get added incrementally; each new one must re-assert the gate.
**Lesson**: When adding a route/entry point that reaches a flag-gated subsystem (exec surface, write path, paid feature), gate it on the **same** flag as its siblings — audit *every* path into the subsystem, not just the first. Add a test that toggles the specific kill-switch (not just the base flag) and asserts the new route 404s + never calls downstream. Related idempotency footgun surfaced same review: awaiting `audit.log()` **after** `idempotency.complete()` unguarded — an audit throw 500s a *completed* write, and a fresh-key client retry then double-writes; make post-write audit best-effort.
## 2026-07-01 — pitfall — A CSP fetch/media/object directive that omits `blob:` silently breaks browser features using createObjectURL; and there are TWO CSP copies to keep in sync
**Context**: #1400 (misdiagnosed as #784). The Files-tab preview builds a `blob:` URL (`URL.createObjectURL`) and renders it per type: text/download via `fetch(blobUrl)` (governed by `connect-src`), `<img>` (`img-src`), `<video>/<audio>` (`media-src`), and PDF `<embed>` (`object-src` **and** `frame-src` — Chrome renders the embedded PDF in an internal viewer frame, so the blob is checked against `frame-src` too, not just `object-src`). `blob:` is **not** covered by `'self'` — it must be listed explicitly in the specific directive the load uses. `img-src` listed `blob:` (images previewed) but `connect-src` did not (text failed with "Failed to load text content"), and `media-src`/`object-src`/`frame-src` were unset (fell back to `default-src 'self'` → also blocked; the PDF showed Chrome's "This content is blocked"). The breakage is per-feature and invisible until you exercise that exact path — #784's `Content-Disposition: inline` "fix" never touched the CSP, so preview stayed broken across every release since the CSP landed (#549/#641). Trinity has **two** CSP copies that must move together: `src/frontend/security-headers.conf` (prod nginx) and `src/frontend/vite.config.js` (dev-server middleware). Same class already bit #979 (voice `srcdoc` under prod `script-src 'self'`) and #1116/ask-trinity (`connect-src` external origin).
**Lesson**: When a browser feature loads a `blob:`/`data:` URL, add that scheme to the SPECIFIC directive the load uses (`fetch`→`connect-src`, `<img>`→`img-src`, `<video>/<audio>`→`media-src`, `<object>/<embed>`→`object-src`; a PDF `<embed>` **also** needs `frame-src` because Chrome renders it in an internal viewer frame) — `'self'` does not cover `blob:`/`data:`. Change **both** `security-headers.conf` and `vite.config.js` together (a dev-only CSP hides prod-only breakage and vice-versa). "Works for images but not text" ⇒ suspect a `connect-src` gap first. Guard with a test asserting the scheme in each directive of both files (`tests/unit/test_1400_csp_blob_preview.py`).

## 2026-07-04 — pattern — An opaque "session identifier" is an overloaded key: split scope / attribution / memory-source before re-keying
**Context**: #903 (Slack thread-scoped sessions). The single `SlackAdapter.get_session_identifier` string secretly encoded **three** orthogonal concerns that a single-user session kept accidentally aligned: conversation *scope* (what replays), speaker *attribution* (who said each turn), and per-user memory *source* (whose turns feed whose MEM-001 profile). The issue's suggested one-liner (drop `sender_id` from the key so channel threads share context) fixed scope but silently broke the other two — `public_chat_messages` had no sender column so multi-participant history replayed as a flat `User:`, and `summarize_user_memory_background` reads *all* session messages and writes them to the *current* user's durable, re-injected memory, so Bob replying in Alice's thread would persist Alice's turns into Bob's profile (cross-user PII leak). Verified in code before planning; scope escalated to add a per-message `sender_email`/`sender_label` so each axis has its own home.
**Lesson**: Before changing what a shared/opaque key encodes, enumerate every concern that key currently disambiguates. A key that "just works" often works because one variable (single participant) collapses several axes into one; loosen that variable (multi-participant thread) and each hidden axis needs its own explicit column/filter. In particular, any "shared context" change to a chat surface must check the **memory summarizer** — it silently reads whole-session history and writes to one user's durable store, so broadening the session scope without a per-sender filter is a cross-user leak.
## 2026-07-04 — pitfall — After the #1093 SQLAlchemy-Core rewrite, `db.get_chat_session()` returns a Pydantic model, not a dict — `.get("k")` raises and is swallowed
**Context**: #1444 review. `db.get_chat_session()` now returns `Optional[ChatSession]` (Pydantic `BaseModel` via `_row_to_chat_session`). The new persistence owner-gate correctly uses attribute access (`session.user_id != user_id`, `chat.py:1016`), but the pre-existing sibling `_finalize_self_task` (`chat.py:1273`) still uses **dict** access `session.get("user_id") == user_id`. `ChatSession` has no `.get()`, so it raises `AttributeError` — caught by the surrounding `except Exception` at :1291 and logged as a warning. Net effect: self-task `inject_result` into a chat session **silently never works**, and its ownership check never actually runs. Pre-#1093 the accessor returned a dict, so `.get()` was correct then; the Core rewrite flipped the return type and this call-site was missed.
**Lesson**: Any accessor rewritten by #1093/#300 from sqlite3.Row/dict to a Pydantic model breaks every `.get("field")` / `row["field"]` caller — and a swallowing `except` turns the break into a silent no-op, not a crash. When touching one owner-check on a `get_chat_session` result, grep **all** call-sites (`grep -rn "get_chat_session\b"`) and confirm each uses attribute access. Add a db-accessor unit test that asserts the returned object is the model and that `.get`/subscript access is not used downstream.
## 2026-07-04 — pitfall — A critical invariant with zero unit exercise lets a `sys.modules` stub leak masquerade as a real violation
**Context**: #1446. Canary B-01 (queue-status coherence, Tier A critical) false-fired under full-suite load — `db.get_queued_count('a1')=1` vs a 0-queued snapshot — but never in isolation. Root cause was **test harness, not production**: several modules do a module-level, never-restored `sys.modules.setdefault("database", MagicMock())` (`test_watchdog_unit.py`, `test_validation.py`, `test_cb_probe_execution_close.py`, …). `setdefault` is first-writer-wins + session-persistent; `int(MagicMock().get_queued_count("a1")) == 1`, so the canary's `_collect_queued_count_via_service` (`from database import db` resolved at *call* time) read `1` for every agent. B-01 had **no end-to-end unit coverage** — only synthetic `_snap`-built comparator tests — so nothing exercised the real `collect_snapshot`→accessor path where the leak bites. On the shipping SQLite backend the two B-01 read paths (raw `sqlite3` `DB_PATH` vs `get_engine()`) resolve to the same file → no production coherence bug; the Postgres divergence (raw-sqlite readers vs `get_engine()`) is a real but deferred gap, tolerable only because the canary is default-OFF.
**Lesson**: (1) A canary/invariant check that only has *synthetic-snapshot* tests is untested where it actually runs — give every invariant one end-to-end test that drives `collect_snapshot()` against the fixture DB so a harness/wiring leak can't hide. (2) Any test reading an ambient `sys.modules["X"]` (esp. `database`) is at the mercy of leaked stubs; the fixture must **own** that dependency via `monkeypatch.setitem` (auto-restored, last-write-wins overrides a leak), and the stub should **delegate to the real backend seam** (`get_engine()` over the temp DB) — not a hand-fed constant, or the coherence test degrades to a tautology. (3) `sys.modules.setdefault(...)` at module scope is the worst offender: first-writer-wins means it survives even an explicit preload and poisons every downstream `from X import ...` for the whole session (the `test_904 database.db` leak family).

## 2026-07-04 — pitfall — `update = none` submodules: skip exits 0, `--init` copies the strategy local, and existing clones inherit the flip asymmetrically
**Context**: #1443 made both private submodules (`.claude`, `src/backend/enterprise`) `update = none` so OSS clones init without credentials. Three git behaviors (all empirically verified) make naive rollouts break silently: (1) a skipped submodule **exits 0** — any script judging init success by exit code (deploy-dev.yml did) takes its success branch while the checkout is absent/stale; (2) **every** init path (plain `--init`, `--init --checkout`, `clone --recurse-submodules`) **copies `update = none` into `.git/config`** — `--init --checkout` is only special in that it additionally clones once — so later plain `git submodule update` silently skips again; a one-shot flag is not a durable opt-in; (3) existing clones are protected from a `.gitmodules` flip **only if** an `update` key existed there at init time (init copied it into local config, which wins): `.claude` clones were protected (`update = checkout` predated the flip), enterprise clones were not.
**Lesson**: When flipping a submodule to `update = none`: patch every automation that inits it to (a) set the durable local override `git config submodule.<path>.update checkout` before init and (b) judge success by a populated marker file, never exit code; document the config-first opt-in (config line, then plain `--init`) as the primary instruction; and check `git config submodule.<path>.update` on existing clones to know who silently changes behavior.

## 2026-07-06 — pitfall — Stripping tzinfo without converting mis-compares non-UTC datetimes; schedules store AWARE next_run_at
**Context**: #1472. `agent_schedules.next_run_at` is written by `_get_next_run_time` as a **timezone-aware** value in the schedule's own zone (e.g. Europe/Kiev `+03:00`). `_get_missed_schedules` (`src/scheduler/service.py`) did `expected.replace(tzinfo=None)` — stripping the offset **without converting** — so a Kiev schedule compared 3h off and a genuinely-missed window looked "future" and was skipped. Separately, a naive `stored > datetime.utcnow()` against an aware value raises `TypeError: can't compare offset-naive and offset-aware` (bit the new advance-guard + a test assert). The scheduler helper, the new advance-guard, and the new canary E-06 check all needed the same UTC-aware handling.
**Lesson**: When comparing a stored schedule/execution timestamp, **convert to UTC, never strip tzinfo**: `dt.astimezone(pytz.utc)` for an aware value, `dt.replace(tzinfo=pytz.utc)` only when it's known-naive-UTC — then compare against `datetime.now(pytz.utc)`. `replace(tzinfo=None)` on an offset-bearing value silently shifts it by the offset; a bare `aware > naive` crashes. Any codepath touching `next_run_at`/`last_run_at`/`started_at` of a non-UTC schedule is in this class.
**Update (#1474)**: the scheduler DB mapper (`src/scheduler/database.py`, via `parse_scheduler_ts`) now returns **naive UTC** for every row timestamp — it *converts then strips* (the instant is preserved, not the #1472 anti-pattern), so the model types stay naive and duration math stays `naive − naive`. The `_get_missed_schedules`/`_advance_next_run_only` comparisons above therefore hit the `known-naive-UTC` (`replace(tzinfo=pytz.utc)`) branch for DB-sourced schedules and remain correct; the aware branches stay for datetimes sourced outside the mapper. Backend-written `next_run_at` remains aware `+00:00`/offset — this section's "schedules store AWARE next_run_at" is true of the *backend* writer, not the scheduler read path.

## 2026-07-06 — pattern — Validate a config with the SAME parser the executor uses, or bad configs pass then fail silently
**Context**: #1472. The schedule create/update API validated cron with a bare `croniter(expr)` and never validated the timezone, but the dedicated scheduler registers via a strict 5-field `_parse_cron` + APScheduler `CronTrigger` + `pytz.timezone`. `@daily`, 6-field seconds-crons, quartz `L`/`#`, and any bad timezone **clear croniter** but throw in `_add_job` — the schedule is accepted, never registers, never fires, and its `next_run_at` freezes ("Next: Nd ago"). The producer-side validator was looser than the consumer-side parser.
**Lesson**: When an API validates input a **different** component will later parse/execute, validate with that component's exact parser, not a convenient looser one. For schedules the parity primitive is `services/schedule_validation.py` (mirrors `src/scheduler/service.py::_parse_cron` + `CronTrigger` + `pytz`) — keep them in sync. Pair it with executor-side resilience (classify a failed registration transient-retry vs permanent-bounded) so a config that still slips through is never a permanent silent orphan.

## 2026-07-06 — pitfall — A new db-layer accessor needs an explicit DatabaseManager facade delegation; wholesale-mocked `database` tests are structurally blind to it
**Context**: trinity-enterprise#93 review (C1). `get_git_config_agent_names_for_repo` was added to `ScheduleOperations` (db/schedules.py) and called via `db.` in crud — but `DatabaseManager` (database.py) has no `__getattr__` fallback; every accessor needs a hand-written one-line delegation. The call would have raised `AttributeError` on the first real request. The 35-test unit suite stayed green because it mocks the entire `database` module with `MagicMock`, which synthesizes any attribute.
**Lesson**: When adding a db-layer method, grep `database.py` for a sibling's delegation and add yours next to it — the facade is manual, not dynamic. And every new accessor needs one test that touches the REAL facade (e.g. `DatabaseManager.__new__` + a mocked `_schedule_ops`, or a db_harness live-select) — a `MagicMock`-ed `database` module can never catch a missing delegation, a typo'd method name, or a wrong return shape.

## 2026-07-07 — pitfall — Frontend e2e specs rot silently: they run only on `ui`-labeled PRs, so a UI refactor merged without the label breaks them invisibly
**Context**: #1500. The #954 spec `agent-detail-chat-width.spec.js` anchored on `page.locator('nav.-mb-px')`; #1114 (OverflowTabs) later added a second, aria-hidden `nav.-mb-px` measuring mirror — a strict-mode violation that made the spec fail on contact. Nobody noticed for weeks because the `frontend-e2e` workflow is path/label-gated (`ui` label), and #1114-era PRs that reshaped the tab strip didn't re-run the older spec. The next `ui`-labeled PR (this one) inherited a red suite for a pre-existing breakage.
**Lesson**: (1) When a PR touches shared UI structure (tab strips, nav, layout wrappers), run the EXISTING e2e specs that anchor on that structure locally — green CI on the refactor PR proves nothing if the suite didn't run. (2) In specs, prefer `data-testid` or `.first()`-disciplined locators over bare structural selectors like `nav.<class>` — hidden measuring/mirror twins (the #1114 pattern) turn bare locators into strict-mode violations. (3) Budget for repairing pre-existing spec rot in whatever `ui`-labeled PR discovers it — it blocks that PR's CI either way.

## 2026-07-08 — pitfall — A fresh-install-only modal (the onboarding wizard) auto-opens on a zero-agent CI stack and its full-screen backdrop intercepts every `/`-spec's clicks
**Context**: #1500's first e2e run. `dashboard-grid-view.spec.js` (and a flaky `browser-tab-titles`) timed out clicking the dashboard mode toggles — the `OnboardingWizard` (trinity-enterprise#52) `fixed inset-0` backdrop intercepted the pointer. `Dashboard.vue::maybeAutoOpenOnboarding` auto-opens the wizard once on a fresh install with **zero user-created agents** (`trinity-system` is filtered out), gated only by `localStorage['trinity_onboarding_dismissed_v1']`. The CI stack is exactly that shape (fresh DB, only the system agent), so the wizard auto-opens; it's a **race** — the open fires after fleet-load resolves, so a spec that clicks fast sometimes wins and sometimes doesn't (flaky, not deterministic). Local dev never reproduces it because a developer's stack has real agents, so the wizard never auto-opens. No e2e spec dismissed it, so it was latent until the `ui`-gated workflow actually ran.
**Lesson**: Fresh-install-only UX (onboarding, empty-state CTAs, first-run modals) is invisible in local dev but is the DEFAULT state of the CI stack — treat "zero user agents" as the e2e baseline. Seed the product's own "remembered" dismissal key in the shared `auth.setup.js` storageState (same origin as `token`, captured by the snapshot) so every inherited context is modal-free, rather than dismissing per-spec; specs that WANT the wizard opt back in via `?onboarding=1` (which bypasses the key). When adding any auto-opening global modal, grep the e2e suite for `/`-navigating specs and confirm the setup seeds its dismissal.

## 2026-07-07 — pitfall — Any subprocess the agent-server spawns is invisible to the orphan sweep unless explicitly vouched for
**Context**: #1501. `resolve_allowlist`'s hard-protect walk goes from the sweeper UP to PID 1 — never down to the agent-server's other children — so a bare `asyncio.create_subprocess_exec` child of the agent-server (a brain-orb convention hook) matched none of the four allowlist categories and the 30s periodic sweep SIGKILLed it mid-run (the 180s `refresh` reliably → exit -9 → 502). #1494 had already fixed this exact class for post-voice `claude -p` by dispatching a registered execution; `refresh` was left on the bare-hook path. Same investigation surfaced two siblings: gemini's 3 post-turn sweeps ran with NO `extra_pids` (a finishing Gemini turn could kill concurrent in-flight work — the #912 class, unfixed on that path), and user `persistent-processes.allow` patterns protected only the bare matched pid, so an allowlisted daemon's worker children were reaped anyway.
**Lesson**: A new agent-server spawn site (hook, helper subprocess) must either wrap the run in `ProcessRegistry.add_transient_pid`/`remove_transient_pid` (finally-paired, fail-open) or dispatch as a registered execution — otherwise it dies whenever it straddles a sweep tick (P ≈ runtime/30s, ≈certain past 30s). And a new `kill_cgroup_orphans` call site must pass `extra_pids=active_execution_pids()` — a bare call kills concurrent in-flight work. Known residual exposure: `agent_server/routers/git.py` `subprocess.run` children (short-lived git ops; follow-up candidate alongside the descendants_of(sweep_pid) seam discussion). Test-side corollary (the #1446 class, re-confirmed by this PR's first CI run): production code that resolves the registry via a CALL-TIME lazy import cannot be stubbed by patching an attribute on the module object your test file imported — sibling test modules (`test_agent_server_auto_sync.py`, `test_git_status_dual_ahead_behind.py`) evict `agent_server*` from `sys.modules` at module level during collection, so the lazy import re-creates a fresh module your patch never touched (fails in the full suite, passes in isolation). Own the key instead: `monkeypatch.setitem(sys.modules, "agent_server.services.process_registry", stub_module)`.
**Update (#1595)**: the same re-exec mechanism also breaks **`is`-assertions**, not just patches: two agent_server test files each evict+reload the package at collection, so a test's import-time capture of a function and the code-under-test's call-time relative import can resolve to *different module generations* — `recorded_fn is captured_fn` then fails only in combined runs (passes in isolation). Assert against the live object resolved through `sys.modules["agent_server.routers.git"]` at assert time, never an import-time capture.

## 2026-07-08 — pitfall — A consolidation refactor that swaps a resolver's body is a no-op if nothing calls the resolver
**Context**: #1521. Plan was to fix wrong context-window denominators by swapping the body of each runtime's `get_context_window`. But `ClaudeCodeRuntime.get_context_window` was **dead code** — never called anywhere (grep-confirmed: only the def + the ABC). For the Claude runtime (the platform default), `metadata.context_window` is set ONLY by `stream_parser` (from `modelUsage.contextWindow`, the primary) or the static Pydantic field default `ExecutionMetadata.context_window: int = 200000`. So the *real* fallback is a static class-attribute default, not the method that looks authoritative. Gemini/Codex genuinely call `get_context_window`, so their body-swaps worked — Claude was the asymmetric trap. Shipping the "obvious" version would have been a green diff, passing (unrelated) tests, and the exact bug still live on the default runtime. Fix: seed `metadata.context_window` from the catalog at metadata *construction* (so the stream value overrides it and the catalog is the real fallback), guarded by a regression test that asserts the catalog value actually reaches `metadata.context_window`.
**Lesson**: Before "consolidate the scattered logic into one resolver and call it everywhere", grep each call site of the method you're changing and confirm it's actually invoked on the path you care about. When a value has a static default (a Pydantic field default, a dataclass default, a `dict.get(k, DEFAULT)`), THAT default — not the nicely-named resolver — is the fallback that ships; verify the resolver is on the live path or wire it in explicitly. Always add a test that asserts the new value reaches the persisted/consumed field, not just that the resolver returns the right number in isolation.

## 2026-07-09 — pitfall — `UPDATE ... WHERE id = (scalar subquery)` double-applies under Postgres concurrency, and a sequential test cannot catch it
**Context**: #1081 pull `claim_next_queued` (C1); `db/schedules.py`. A single `UPDATE schedule_executions SET status='running',… WHERE id = (SELECT id … WHERE status='queued' ORDER BY queued_at LIMIT 1)` handed one queued row to up to N concurrent workers — each stamped a distinct `claim_token` and double-**ran** the turn (real-PG harness: 25/25 iterations, head row claimed by all 16 workers). Mechanism: the uncorrelated scalar subquery compiles to an **InitPlan evaluated once → constant id X**; under READ COMMITTED every updater that blocks on X's row lock re-runs EvalPlanQual against the **outer** WHERE only (`id = X`, still true for the now-`running` row — the InitPlan is not re-evaluated and there was no status predicate outside the subquery), so each blocked updater re-applies to X and RETURNs it. The token CAS on the *result* write does not save it — the N turns already executed.
**Lesson**: For an atomic claim/dequeue `UPDATE ... WHERE id = (SELECT … LIMIT 1)`, the inner subquery's `status='queued'` filter is NOT the concurrency guard — put the mutated predicate in the **outer** WHERE too (`AND status = 'queued'`) so a losing updater's CAS is a no-op, and/or add `FOR UPDATE SKIP LOCKED` to the subquery so concurrent claimers lock distinct rows (Postgres only; SQLite serialises writers and lacks the clause — the outer re-check is the cross-dialect backstop). Ship both. **Test corollary:** a *sequential* claim test (claim w1, then w2, assert w2 gets None) proves nothing here — the inner subquery already makes the second sequential claim a no-op, so the test passes with or without the fix. The guard is only exercisable under real multi-process/thread contention on a real Postgres engine; a committed regression MUST be a multi-process (or thread) harness on PG, not the SQLite/sequential default. (Contrast the reaper transitions in the same file, which were correct from the start because their precondition lives in the outer WHERE.)

## 2026-07-09 — pitfall — A counter column is only as truthful as its writer, and wholesale-mocked `database` tests cannot see that the writer is dead
**Context**: #1533. The Sharing-tab client roster showed `message_count = 0` for every external client, `last_active` was frozen at `/login` time, and clients who never ran `/login` never appeared at all — because `get_or_create_chat_link` AND `increment_message_count` (Telegram + WhatsApp) had **zero callers** outside the `database.py` facade. The shared inbound path (`message_router._handle_message_inner`) writes `public_chat_sessions`, a *different* table, so the `*_chat_links` rows were only ever created by `set_*_verified_email`. Nothing failed loudly: `client_roster_service`'s own docstring asserted the channels "record the full `(verified_email, message_count, last_active)` triple", and the read path faithfully echoed a column nobody wrote. The issue's own Context paragraph then mis-diagnosed it ("`last_active` is touched on inbound traffic via `get_or_create_chat_link`") — reading the code, not the issue, was what found the real shape. ## 2026-07-12 — pitfall — A new heavy test file entering the randomized unit suite inherits the #762 sys.modules-stub leaks; own your real modules at collection time

## 2026-07-15 — pitfall — A mutable code default read at ACTION time is a live control surface: lowering it retroactively destroys existing data. Apply new policy by seeding, not by defaulting.

## 2026-07-17 — pitfall — A resource's self-description is not its ownership, and renames are what prove it
**Context**: #1664. Docker volumes carry the agent name twice — in the volume name (`agent-{name}-workspace`) and in an immutable `trinity.agent-name` label — and rename can change neither, so it keeps both. The #1581 orphan sweep read that pair as ownership truth (`is_agent_name_reserved(label)` → no such agent → orphan → `volume rm -f`) and would destroy a **live** renamed agent's `/home/developer` the moment a container recreate left it briefly unattached. Its "double-guard" (name AND label must match) could never catch this: it verified the two halves of the identity agreed *with each other*, and after a rename both are equally, consistently stale — a self-consistent lie. The docstring claimed "a live/durable agent's data is unreachable by a bug"; rename falsified it. The same root produced three more bugs in different directions, all invisible until the identity model was made explicit: the purge removed `agent-{new}-*` (volumes that never existed) and leaked the real ones; soft-delete recovery (`recreate_missing_container`) mounts a fresh **empty** volume for a renamed agent (#1665); and because rename frees the old *name* while the old *volume* lives on, creating a new agent under that freed name silently **reuses the renamed agent's home volume** — `crud.py` does `volume_get(...)` → found → mount, so a different owner's new agent boots on agent A's `.env` (verified against a real daemon: it read A's API key).
**Lesson**: When a resource can be renamed but its durable identity cannot, **ownership must live in a row you control, never in the artifact's own name/labels** — ask "does any owner claim this?", not "is this name an owner?". Corollaries, each learned by getting it wrong in the fix itself: (1) An identity guard that only checks internal consistency (name matches label) proves the *caller aimed correctly*, not that the target is dead — it is a last line of defence, never liveness; state that in the docstring or the next reader will trust it as safety. (2) A renamed resource can own artifacts under **both** identities at once — here the workspace keeps the old base while `get_public_volume_name`/`get_shared_volume_name` name off the *live* name, so the ownership predicate must be a **union** (`agent_name OR volume_base_name`); matching only the pin deleted a live agent's public volume, which the attached-check could not save because that volume is unmounted whenever file-sharing is off. Whenever you replace a predicate, check the new one is a **superset** of the old — `is_agent_name_reserved` turned out to be exactly the union's first branch, which is what made the union provably safer rather than merely different. (3) A destructive sweep's evidence must be *positive* and *repeated*: "in use" is a fact (skip it), "not in use right now" is a snapshot that a recreate gap forges — require a streak, and fail **closed** when the mount table is unreadable, since "unknown" must never read as "unused". (4) Mock-based unit tests cannot see a facade gap: mocking `db` made three `db.<new_method>()` calls green that would have raised `AttributeError` in production and — because the sweep swallows per-cycle exceptions — silently degraded the reclaim to a permanent no-op. The `test_database_facade_delegation` guard caught it; a mock-free run against the real DB + real daemon is what actually proves wiring.

(2) **Never gate authorization on a spoofable request header.** `X-Source-Agent` is client-controlled and only bound for agent principals; key the gate on the authenticated principal / the sensitive input's presence, not the header. A header exemption is a bypass unless something *upstream* already proved the header. (3) **Ownership is a better guard than shape.** Dropping a UUID-shape check in favour of "does a row with this id, owned by this user, exist?" both closed the IDOR *and* avoided breaking Codex (whose session id is a `thread_id`, not a UUID) — a shape check would have been a silent regression for a second runtime. (4) **KeepAlive doubles every deep-link/route handler.** Any logic that reacts to `route.query` on entry must run in **both** `onMounted` and `onActivated` (extract one idempotent fn, call from both) — `onMounted` alone silently no-ops on the cached-revisit path, which is the *common* path, so it passes every fresh-reload manual test and fails in real use. (5) **A test that models the safe case masks the unsafe one**: the exempt-test set `user.agent_name = x_source_agent` (a real agent key) and went green while the regular-user-spoof bypass shipped; decouple the principal from the header in the fixture and assert the *attack*, not the happy path. The adversarial-review subagent, prompted to refute rather than confirm, is what caught the critical bypass the author's own tests endorsed.
## 2026-07-17 — pitfall — A periodic sweep gated on the store's near-expiry window structurally misses most items when the window is narrower than the sweep cadence
**Context**: #1616 review. The wired-up expired-SSH-key sweep removed a key's `authorized_keys` line only while its Redis TTL was in `[0, 60]s` (`ssh_service.cleanup_expired_credentials`), but the sweep runs on the 5-min (`300s`) `cleanup_service` cadence. A 60s catch-window against a 300s tick means a cycle lands in the window only ~60/300 = **20%** of the time; the other ~80% the auto-expiring Redis key vanishes from `scan_iter` between two ticks, unobserved, and the file line — the *only* thing that revokes key-auth access on a preserved-volume agent — was never removed. So the "security fix" was ~20% effective and its docstring claimed it "makes file-side expiry actually happen." Not a regression (pre-fix: zero callers → 0% removed), which is exactly why it read as done. Mocked unit tests pinned the gap as correct (`ttl=30 → removed`, `ttl=3600 → not`) — they asserted the window, not the outcome. Fix: drive the sweep off the stored `expires_at` (`now >= expires_at`) and keep the Redis metadata alive a grace (`> cadence`, 600s) past true expiry so every expired item is observed by ≥1 cycle before the store forgets it; forget the row only *after* the external side-effect succeeds so a transient failure retries.
**Lesson**: When a best-effort background cleanup races an **auto-expiring** store (Redis TTL, cache eviction, a queue's visibility timeout), the cleanup must **outlive** the store, not race it — either the store keeps the record past its logical deadline (grace) so the sweep is guaranteed an observation, or the sweep reconciles the *external* artifact against the store directly. A catch-window keyed on "about to expire" is a coin-flip whenever the window < the cadence, and it fails **silently** because the record is simply gone next cycle — no error, nothing to log. Two review tells for this class: (1) a fix whose effectiveness depends on a timing window — compute `window/cadence` and if it isn't ≥1, most items slip; (2) tests that assert the *mechanism's trigger* (a TTL threshold, a flag) rather than the *end state* (the artifact is actually gone) will green-light the miss — always add one test that puts the item outside the window but past its true deadline and asserts it's still handled.

## 2026-07-17 — pitfall — A credential resolved *once at create* and a credential resolved *live on every recreate* are different features; conflating them turns a Settings edit into a fleet recreate
**Context**: ent#162 (per-user GitHub PAT). The tempting "single source of truth" shape — extend the one PAT resolver to `per-agent → per-user → global` and call it everywhere — silently arms two opposite-direction bugs, because `agent_git_config.github_pat_encrypted` does **double duty**: it is both the *credential value* and the "don't global-propagate to me" marker (`has_agent_github_pat` → `skipped_per_agent_pat` in `github_pat_propagation_service`). (a) If the recreate/restart ladder (`helpers.check_github_pat_env_matches` → `get_github_pat_for_agent`, consumed by `lifecycle.needs_recreation`) is made to re-derive the *live* per-user tier, then a user **adding a PAT in Settings** flips the container-vs-effective-PAT comparison to mismatch → force-recreates every one of that user's running agents, killing in-flight work and clearing breakers (the #1560/#1557 "a config action silently recreates running agents" class). (b) If instead you resolve per-user live and leave `github_pat_encrypted` NULL to keep rotation working, the **admin's** next global rotation sees `has_agent_github_pat=False` and clobbers the per-user identity with the admin token. Grep every caller of the resolver you're about to widen and ask, per call site, "does re-deriving this on *this* path force an action?"; the recreate matcher is the one that bites. And when one column is both a value and a routing marker (here: credential + "skip me in propagation"), a new tier needs a third state the binary can't express — encode it as a distinct provenance (`tier`) at the write boundary, don't overload the value's presence. The load-bearing test is not "the resolver returns the right tier" but "**adding a per-user PAT does NOT flip `check_github_pat_env_matches` to False for a running global-fallback agent**" — drive the REAL matcher against a real container-env stand-in + real migrated DB, and prove it has teeth by temporarily making the ladder 3-tier and watching it go red (it does).

## 2026-07-20 — pitfall — Moving DB work to `asyncio.to_thread` to fix a timing oracle breaks SQLite thread affinity, and a fail-closed handler hides it as silence

**Lesson**: (1) Before starting a bug, search the tracker for the *symptom*, not the issue number — a duplicate filed by someone else is invisible to `gh issue view` on your own id, and P2 bugs sit long enough for two people to pick them up. Re-check at ship time: `git log origin/dev -S<symbol>` on the function you are about to touch costs one command. (2) When two fixes collide, the merged-and-reviewed one owns the contract; the later PR's value is its *residual* — the part the merged fix did not cover — and re-litigating the status code is worth less than shipping that residual. (3) A semantic conflict's blast radius is bigger than the conflict markers: after resolving, grep the losing error code repo-wide and treat every hit as a defect, especially in tests that construct their own fixture of the thing under test.

## 2026-07-28 — pitfall — "Mirror the upstream predicate" inherits the upstream's permissive edge, and re-opens the very bug the mirror was added to close
**Context**: trinity#1804 review. The fix turns the activity close into a lattice CAS whose predicate is documented as mirroring `schedule_executions`' terminal CAS "predicate-for-predicate", with an ASCII diagram and the stated invariant *"Nothing may overwrite an authoritative close. AUTHORITY: started < failed < {completed, cancelled}"*. The COMPLETED arm was copied literally as `activity_state != 'cancelled'` — and `!= 'cancelled'` matches `'completed'`, so `completed → completed` was permitted. Executed against the real code path: a 15-minute activity (`duration_ms=900000`) re-closed COMPLETED became `32286972` (~9h) with `completed_at` re-dated and `error` overwritten — i.e. the exact fabricated-duration symptom #1804 exists to eliminate, arriving through #1804's own fix. The literal copy was *faithful*: `update_execution_status`' SUCCESS predicate really is `status != CANCELLED`, which really does admit `success → success`. The execution row survives that edge only because an upstream guard (the #1083 callback's authoritative-terminal replay short-circuit) stops the duplicate before it reaches the CAS — a protection the activity's new call sites do not have. The branch's own five lattice tests covered `completed→failed`, `failed→failed`, `cancelled→completed` and `failed→completed`, and missed the one transition where source and target state are equal.
**Lesson**: (1) When a predicate is specified as an **ordering** ("A < B < C") but implemented as an **exclusion** (`!= C`), the two disagree exactly on the reflexive case `C → C`, and that is the case tests skip because it looks like a no-op. Implement the ordering literally (`IN (started, failed)`) rather than by exclusion, and always test `X → X` for every terminal state. (2) "Mirrors the upstream CAS" is a claim about *safety*, and it only transfers if the upstream's protections transfer too — an upstream whose permissive edge is covered by a guard one layer up (a replay short-circuit, an idempotency key) hands you the permission without the guard. Before copying a predicate, ask what *else* upstream stops the case this predicate allows. (3) Prose that states a stronger invariant than the code enforces is a review target in its own right: the docstring here was the evidence the code was wrong, not evidence it was right.

## 2026-07-28 — pitfall — Delegating a specially-provisioned agent to the shared lifecycle inherits every fallback in it, including ones that cannot reproduce its contract
**Context**: trinity#1816 review. `ensure_deployed`'s stopped branch and `POST /api/system-agent/restart` were changed from a bare `container_start` to `start_agent_internal`, which is exactly right for the nine drift predicates and the #1560 clear ordering — and which also carries a `container is None → recreate_missing_container(agent_name)` fallback (the #1559 soft-delete recovery rebuild). ## 2026-07-28 — pitfall — `if: always()` + a `cancelled` result clause silently defeats `cancel-in-progress`
**Context**: trinity#1782 review. The fix for the `changes` path-filter (files API + fail-open) was correct and independently re-verified. The defect was in the half the plan itself labelled *"defence in depth, not part of the bug fix"*: an extra `|| needs.changes.result == 'cancelled'` on the downstream `e2e` job's `if`, added so that "unable to determine ⇒ RUN" held for cancellation too. But GitHub cancels a run by **re-evaluating every job's `if` and keeping the job when it returns true** — that is precisely what `always()` means (docs: workflow-cancellation; `actions/runner#4411` shows a *pending* `needs:` + `always()` job being scheduled after cancellation). The workflow sets `cancel-in-progress: true` for PRs, so the dominant producer of `result == 'cancelled'` is a superseded push — and the clause turned every superseded push into a full 25-minute Docker-stack + Playwright run, whose failure would post the very red X the issue existed to remove. The clause had no scenario in which it helped: a cancelled run has been superseded, and the replacement run evaluates from scratch.
**Lesson**: (1) In GitHub Actions, `failure` and `cancelled` are **not** symmetric halves of "not success". `failure` means the work ran and lost — react to it. `cancelled` usually means *this run no longer matters*, and reacting to it fights the concurrency config. Never add a `cancelled` clause to a job guarded by `always()` without checking `concurrency.cancel-in-progress` in the same file. Prefer GitHub's own recommendation, `!cancelled()` over `always()`, when the intent is "run regardless of success or failure". (2) Generalises past CI: when a fix ships alongside a self-described "defence in depth" addition, review the addition **harder** than the fix — the fix has a reproduction and a test matrix behind it, the hardening has neither, and it is where the regression lands. A plan that pre-declares an extra as "not part of the bug fix" is naming the riskiest hunk in the diff, not excusing it.

## 2026-07-29 — pitfall — "Confirm on a second cycle" is not a delay when the service has no leader lease
**Context**: #1813 (canary H-01, `canary/invariants/h01_collector_blindness.py`). H-01 must not false-fire on the last-agent delete race — the DB row is deleted before the container finishes tearing down, so a snapshot landing in between sees an empty roster while Docker still lists a container. The gate was written as "arm a Redis marker on the first sighting, fire when a *later cycle* sees it again", reasoning that cycles are 300s apart. They are not: prod runs `uvicorn main:app --workers 2` (`docker-compose.prod.yml`) and `services/canary_service.py` holds only a per-process `asyncio.Lock` — it has **no** cross-worker leader lease, unlike `monitoring:leader` (#1464) and `opqueue:leader` (#1632). The bug is invisible in tests, which run one process; it only appears by reading the deploy command.
**Lesson**: (1) A confirmation/debounce gate must be expressed in **elapsed wall-clock**, never in "a second cycle"/"N observations", whenever its state lives in shared storage — cycle COUNT is a per-process notion, cycle GAP is not, and any multi-worker deployment silently converts one into the other. Compare timestamps and require a minimum delta (also absorbs cross-worker clock skew: a negative delta must not confirm). (2) Before relying on a loop's period for *any* timing property, grep the actual deploy command for `--workers`; a background service in this codebase is single-instance ONLY if it holds an explicit Redis leader lease, and most do not. (3) Corollary for reviewers: `asyncio.Lock` in a service class guards re-entrancy within one worker and says nothing about cross-worker exclusion — seeing one is a prompt to ask where the leader lease is, not evidence that there is one.

## 2026-08-06 — pitfall — "Ran and was fine" and "never ran" are the same bytes in a failure list, and the alarm that reads them is the one that most needs them apart
**Context**: #1813 review (canary H-01). `collect_snapshot` records failures in `sources_unavailable` and nothing on success, so "this collector succeeded" and "this collector never executed" are both the empty set. Normally harmless — except `collect_snapshot` **returns early** when the roster read raises, and that early return is the single path on which H-01's most severe arm (`roster_read_failed`) fires. So the one alarm whose entire job is legibility rendered `*Sources:* docker=up · redis=up` / `*Roster vs evidence:* 0 vs 0 agent(s)` on a cycle where neither source had been consulted: it read as "everything else is fine and the fleet is empty", the exact opposite of the truth. Two further traps sat beside it. First, the evidence sources were unioned as if interchangeable, but `orphan_redis_slots` is BY DEFINITION slot keys whose agent is absent from `agent_ownership` — the leaked-slot state L-03 exists to report — so an empty fleet holding one leaked key paged **critical** claiming the harness was blind, over a correct roster and an unrelated Redis leak. Second, the whole check was unreachable in the failure it most implied it covered: `_run_cycle_inner` read `db.get_latest_canary_violation_per_invariant()` *before* collecting the snapshot, unguarded, so a database outage raised out of the loop and H-01 never ran at all.
**Lesson**: (1) A diagnostic that records only failures cannot express *skipped*, and any consumer that infers "available" from its silence is wrong exactly where a collector was bypassed. Carry an explicit `collectors_ran`-style set and make the availability answer **tri-state**; render the third state (`not read`) rather than folding it into either boolean. (2) **Collector order is load-bearing whenever a function can return early.** Anything a check treats as independent evidence must be collected *above* the read whose failure short-circuits the rest — H-01's Docker read had no dependency on the roster and was simply sitting below it, which is why the arm that needed evidence most had none. (3) When a check unions two sources of evidence, ask what each one *means* on its own: two sources that both prove "something exists" can still disagree about what they prove — Docker presence contradicts an empty roster, a leaked Redis slot key is *itself* a known bug class and contradicts nothing. Asymmetric evidence needs an asymmetric severity ladder, and "corroborating only" in a docstring is not enforcement. (4) A guard is only as reachable as the code path that invokes it: before claiming coverage of a failure mode, follow the caller and check that the failure does not abort the run before the guard executes. Fail-open the pre-read — but notice that an empty "what was red last time" turns every violation into a fresh transition, so a fail-open needs a fallback authority in a *different failure domain* (Redis for a DB outage) or it trades silence for per-cycle alert spam.

**Context**: trinity#1871 review. The fix bounds Docker's uncapped `json-file` logs at the three agent-container create sites, and — explicitly *because* of the 2026-07-10 "the create path is never one call site" entry — shipped a static guard so a fourth site fails CI. (4) Test corpora built to prove *verdict* correctness are structurally blind to *size* regressions — they use small fixtures by design. Size needs its own adversarial fixture, and the honest one is "small source, huge parsed walk".

**Context**: #1909. `test_a13_exact_cutoff_row_is_not_expired` computed `exact` from the clock at setup while `expire_stale_queued` computed its threshold from the clock at query time. ## 2026-08-03 — pitfall — A detector whose output is independent of its input reads as a working signal; shallow-fetching both sides of a merge is one way to build one
**Context**: trinity#1941. `backend-unit-nightly.yml` merges each open PR into `dev` and runs the suite on the result. ## 2026-08-05 — pitfall — Two channels that sync one-way with no delete phase: the file says revoked, the runtime says still valid
**Context**: #1999. The agent-server's credential endpoints mirrored every `.env` key into the **long-lived server process's** `os.environ` (`os.environ[k] = v`, set-only), and all five runtime spawn sites passed `env={**os.environ, ...}`. The `.env` file was never read back into that process. So "what the operator inspects" and "what executions receive" were two independent channels kept in sync by exactly one code path, in one direction, for present keys only. A key **removed** from `.env` by any path that isn't the credentials API — SSH, `docker exec`, or an execution editing its own `.env` — kept applying to every subsequently-spawned process until container restart. (3) For a security control, ask what an operator would *inspect to verify it worked*: if every available inspection route reads a different channel than the enforcement path, the control has no verification story and a silent failure is indistinguishable from success. Add the route that compares the two (here, a name-only drift report) as part of the fix, not as a follow-up. (4) A revocation path deserves its own regression test in the negative direction — "assert the removed credential does NOT reach the consumer" — because "assert the new credential does reach it" passes in both the fixed and the broken world.

## 2026-08-05 — pitfall — A dwell/persistence gate must dwell on the IDENTITY of the thing, not on a count of it — and its first-write must be first-write-WINS
**Context**: ent#337. Canary R-01 paged critical on any single sample with a zombie `claude` process, so it fired on the sampling window rather than the #407 leak (6 pages in 13h on eu2, every one `zombie_count: 1`, every one self-resolved by the next cycle). The obvious fix — mark `first_seen` when the count goes positive, fire after a dwell, clear when the count returns to 0 — is wrong on a busy agent: three consecutive cycles catching three *different* short-lived zombies satisfy it, and clearing "when the count returns to 0" requires a zero to be OBSERVED, which under sustained load never happens. The count-based version reintroduces, by another route, the exact class the same issue correctly rejects `ps -eo etimes` for (etimes is time since process START, not since it zombified, so a process that ran 45 min and zombified 200ms ago reads as 45-min-old). Two further traps sat under it: writing `first_seen = now` on every positive cycle resets the clock each cycle, so the dwell never elapses and the invariant is **permanently blind** — strictly worse than the noise it replaced, and behaviourally indistinguishable from a correct implementation with a single writer; and a marker keyed by agent NAME under a `canary:` prefix evades the #1560 parity regex (`["']agent:([a-z_]+)`), so a recycled agent name inherits the previous incarnation's dwell.
**Lesson**: (1) A persistence gate is only as good as the identity it tracks. Dwelling on a *count* infers continuity; dwelling on the *identity* (pid, id, key) measures it — and the identity is usually one extra field in a command you already run. If the identity is genuinely unavailable, say the gate is heuristic rather than pretending the count is a proxy. (2) Elapsed-wall-clock ≠ observed-continuity. Store `last_seen` alongside `first_seen` and restart the dwell when the gap exceeds a cycle or two, or the first successful sample after an outage fires immediately with zero evidence — a false positive manufactured by the very gate meant to remove them. (3) Read the clock from the snapshot/event, never `time.time()` inside the check: it is the seam that makes the boundary assertable exactly (`dwell-1` silent, `dwell` fires) instead of with a margin, and it is free. (4) For a state write whose semantics are "don't overwrite", assert the *command* with a recording double — with one writer, `SET` and `SET NX` produce identical observable behaviour and only one of them works. (5) A new Redis key that is per-agent must carry the `agent:` prefix even when it belongs to a subsystem with its own namespace, or the parity guard that exists for exactly this hazard cannot see it. (6) An identity is only unique within the NAMESPACE that issues it, so a cross-cycle marker keyed on one must also store that namespace's *generation* and invalidate when it moves — a pid means nothing across a container restart, and the restart path that matters is the one OUTSIDE your own lifecycle hooks (`docker restart`, a restart policy after an OOM), which no `clear_*` hook of yours will ever fire on. The `pid_max`-wraparound argument for dismissing reuse is sound for a running container and simply does not apply to a restarted one; a fresh namespace hands out LOW pids immediately, which is exactly where the collision lands. Note the continuity check (2) cannot cover this — a restart inside one cycle leaves no observation gap at all, so `last_seen` stays fresh while the identity space underneath it is brand new. Check the cost before assuming you need a new probe: docker-py's `containers.list()` defaults to `sparse=False` and already full-inspects, so `State.StartedAt` was sitting in `attrs` for free.

## 2026-08-05 — pitfall — A byte ceiling applied to *decoded* bytes is not a byte ceiling; `Content-Encoding` reopens what `Content-Length` was hardened against
**Context**: trinity-enterprise#14. `template_registry_service._fetch_registry_text` streams a remote `registry.yaml` under a 256 KiB running-total ceiling, with a docstring explaining — correctly — why `Content-Length` cannot be the gate and why `resp.text` on a huge body OOMs the worker before any parse-time cap can act. Both true, and both defeated one level down: a custom `headers=` dict does **not** override httpx's default `Accept-Encoding: gzip, deflate`, and `resp.iter_bytes()` yields *decompressed* chunks. Measured against the shipped function: a **199 KB** wire body — under the cap, so the `Content-Length` early abort passes it — allocated **148.6 MB** inside the fetch before the running total tripped. gzip's 1032:1 ceiling puts the worst case at ~264 MB per request, on the event-loop thread. The same body through `resp.iter_raw()` peaked at **0.2 MB**.
**Lesson**: (1) "Bytes received" means bytes *off the socket*. Any cap on a decoded stream is a cap on the attacker's *post-amplification* choice, and the check can only run after a chunk has already been materialized — so the effective bound is `cap + one decoded chunk`, which the attacker sizes. Cap `iter_raw()`, then decode under your own bounded decompressor, or refuse a non-`identity` `Content-Encoding` outright the way you refuse a redirect. (2) Sending `Accept-Encoding: identity` is necessary but **not sufficient** against a hostile server, which can answer `Content-Encoding: gzip` regardless of what was requested — a request header is a preference, never a control. (3) An HTTP client's *defaults* are part of your threat model: `follow_redirects` got an explicit, argued `False` here while `Accept-Encoding` was never considered, because one default is famous and the other is invisible. When hardening an outbound fetch, enumerate what the client sends and does on your behalf, not just what you passed it. (4) **The harness hid it, and then inflated it.** `httpx.Response(content=…)`/`(text=…)` decodes and buffers in the CONSTRUCTOR, so every fixture here built a response the production `iter_raw()` path cannot even read (`StreamConsumed`) and that could only ever exercise `iter_bytes()` — the byte-ceiling tests were green against a shape incapable of expressing the failure. The same artifact means the 148.6 MB above was partly the *mock* decoding: re-measured on a true streaming response (`stream=httpx.ByteStream(...)`), the pre-fix peak is **458 MB** from a 199 KiB body and the post-fix peak is **0.01 MB**. A transport test whose mock does not stream is not a transport test.
**Fixed** (2026-08-05): the ceiling counts `iter_raw()`, any `Content-Encoding` is refused before the body is read (`encoding_refused`), `Accept-Encoding: identity` is sent as the polite half, and both fixtures convert every mock response to a real stream.

## 2026-08-05 — pitfall — A security gate that reads the *catalog's* cached metadata instead of the creation-path read standing one line above it
**Context**: trinity-enterprise#14 F2. The fix makes `fork_to_own: required` fail closed when a template's `template.yaml` is unreadable — correct in direction, wrong in source. It gates on `gh_template["metadata_unavailable"]`, derived from `_get_cached_metadata_result` → `_get_github_pat()`: the **global platform** PAT, off the **default branch**, through a **600 s** process cache. Meanwhile `crud.py` calls `fetch_template_metadata_for_create(repo, pat=<caller's resolved PAT>, ref=<parsed branch>)` — resolved per-agent→per-user→global, pinned ref, cache-bypassed — **one line earlier**, for `declared_schedules`. ent#89 had already written the warning, in that very function's docstring: *"Deliberately NOT the catalog's `gh_template[...]` … the exact silent-ignore class this feature exists to close, reintroduced one layer up."* Both error directions follow: GitHub answers **404** (not 403) for a repo a token cannot see, so a private `fork_to_own: required` template that only the creator's own PAT can read is classified *absent* and the gate passes (the ent#162 outcome the gate exists to prevent); and a poisoned shared cache entry 503s a creator whose own PAT would have read the file fine, for a full TTL.
**Lesson**: (1) A **catalog** read and a **creation** read are different reads with different credentials, different refs and different freshness, and the difference is invisible at the call site because both hand you a dict with the same keys. Before gating on a metadata field, ask *which credential produced this and how old is it* — if the answer is "the platform's, up to ten minutes ago" it cannot decide anything about *this caller's* repo. (2) When a codebase has already split a read into a catalog variant and a creation variant, that split **is** the warning; a new gate must consume the creation variant, and if it needs a field the creation variant drops (here: the fetch *reason*, which `_fetch_template_yaml_result` returns and the wrapper discards), extend that one — don't reach sideways for the cached copy. (3) Fail-closed on "unknown" is only as good as the classifier: a status code that conflates *absent* with *invisible-to-this-token* (`404` for private repos) turns the fail-closed branch into a fail-open branch for exactly the tenants who most need it. (4) **Fixing the availability half alone would not have closed the false pass** — the trap while fixing this. The obvious repair is "gate on the creation read's *reason*", but for a private template the catalog's `fork_to_own` VALUE is `None` for the same reason its verdict is wrong, so the gate would sail past a `required` it still could not see. Both inputs to a gate have to come from the same trustworthy read; repairing the predicate and leaving the operand is a half-fix that tests green.
**Fixed** (2026-08-05): both the verdict and the value come from `crud._read_source_template` (the creation-path read ent#89 already makes, so zero extra GitHub calls), and `required` from *either* read enforces — a union, so the change can only remove a false pass, never add one.

## 2026-08-05 — pitfall — Reasoning carefully about a flag's *code path* while it dies in *packaging*
**Context**: trinity-enterprise#14, caught by `/validate-pr` before merge. `config.py` reads `TEMPLATE_REGISTRY_ENABLED` — the feature's documented **hard** kill switch, the air-gap answer that no `system_settings` row may override — and `TEMPLATE_REGISTRY_URL`. Prod compose launches **standalone** (no base merge, no `env_file:` on any service) and is what every deploy path uses, so the explicit `environment:` list is the only route into the container: both levers were inert on every real instance, while working perfectly on a laptop where the shell environment reaches the process directly. Net effect — a default-ON feature making outbound requests, with no way to turn it off on a deployed install. (5) When verifying that a new guard would have caught the bug, delete the real line and watch it go red — but use `grep -vF`: in `grep -v 'VAR=${VAR'` the `$` is an **end-of-line anchor**, so the pattern matches nothing, the file is never modified, and the suite reports a false green against an unmodified tree. Confirm the file changed before believing the run.
**Fixed** (2026-08-05): both vars injected in both composes with `${VAR:-…}` and the URL's full non-empty default, documented in `.env.example`, and pinned by `tests/unit/test_ent14_registry_env_packaging.py` (both-composes parity, the form not just presence, compose↔config default agreement, and a meta-test that goes red on pre-fix content and on the hardcoded-value revert).

## 2026-08-10 — pitfall — A value reconstructed from two readings taken at different points in one collection cycle carries the cycle's own elapsed time as a bias, and a fixture that samples both at one instant can never see it
**Context**: ent#372. Canary S-03 cannot read a slot's *initial* TTL — Redis reports only what is left — so it reconstructs it as `ttl + age`, with `age = snapshot_time − ZSET score`. Both terms look like properties of the slot; they are not. `snapshot_time` is stamped at the top of `collect_snapshot()`, while the per-slot `pipe.ttl()` runs last, after the docker and roster collectors — measured on eu2 at `docker=1.0–1.4s`, `roster=0–0.5s`, always ≥1s, tail to 9s. Every one of those seconds is ticked off `ttl` without being added to `age`, so the sum lands short by exactly the collector's elapsed time and the `>= floor − 1` test fires. Result: 208 critical violations over 24h across 85 cycles — *every* cycle that ran — 9 agents, 100% `kind=below_floor`, 31 Slack pages, and it blocked trinity#1766's M7 soak ("canary green throughout") because the baseline had nothing green to measure against. The tell that it was collection timing and not the slots: the deficit was independent of the timeout value (2700 and 1200 both missed by 2–3s) and its tail tracked slower *cycles*, not sicker slots. The first hypothesis blamed `SlotService.acquire_slot` stamping the ZSET score before an awaited cleanup pass; probing live slots killed it — that gap is 0.8 ms, and reading `age` and `ttl` together reconstructs *on* the floor (3000.2 vs 3000).
**Lesson**: (1) When a check derives one quantity from two reads, the reads are an input — ask *when* each was taken, not just what it says. Two values that both describe "the slot" can still be separated by every collector that runs between them, and the separation is a systematic bias in one direction, not noise. Pair each reading with its own timestamp at the point of reading; never against a cycle-level stamp taken elsewhere. (2) **Stamp per item, not per collector.** A single timestamp for the whole Redis pass would have fixed eu2 and re-opened the identical gap at a larger fleet, because the per-slot loop's own elapsed time grows with slot count — the same reason widening the tolerance was rejected (collector elapsed time is unbounded, so no constant is both large enough to silence it and small enough to still catch a short TTL). (3) **Pick the stamp's side deliberately.** Taken *before* the round-trip, `age` can only be under-counted by one RTT — toward firing, never toward a false green; taken after, the bias hides real defects. State which direction the residual error runs and why that direction is the safe one. (4) **The fixture that writes both halves at one instant is the reason the suite was green.** Every S-03 test built `slot_scores` and `slot_ttls` from the same `T0`, so the two readings were simultaneous by construction and the bug was unrepresentable — the same shape as a mock that cannot stream (2026-08-05) or a test that stubs the accessor whose side effect is the defect. A regression test for this class must drive the two reads apart with a fake clock the stubbed collectors advance; asserting the *pre-fix* formula still lands under the floor on that same fixture is what proves the case is not a vacuous green. (5) When "skip when an input is missing" is already a module's stance, keep it for the new input too: falling back to `snapshot_time` when a read time is absent would quietly reinstate the exact bug on any future path that populated one field and not the other.

## 2026-08-10 — pitfall — `import services.x as a` + `patch.object(a, …)` patches the *package attribute*; function-local `from services.x import y` reads *sys.modules* — and this repo's conftest makes them diverge
**Context**: ent#356, moving `client_portal` from the private submodule into OSS core. Six tests copied verbatim from the enterprise repo — where they had always passed — failed in the OSS suite the moment they ran under `tests/conftest.py`. The two resolution paths are different by construction: `import services.docker_service as ds` compiles to `getattr(services, "docker_service")` — the **package attribute** — while `client_portal.service`'s function-local `from services.docker_service import get_agent_container` resolves **`sys.modules["services.docker_service"]`** at call time. Normally the same object. Reproduced in isolation: with the divergence staged by hand, the alias form returned `LIVE` (unpatched) and the string form returned `PATCHED`.
**Lesson**: (1) **Patch where the code *resolves*, not where it *lives*.** A module-level `from X import y` in the code under test binds at *that module's* import — patch the consuming module's attribute (`portal_router.platform_audit_service`), which is the object the test literally calls into. A **function-local** `from X import y` re-reads `sys.modules["X"]` on every call — so patch an object obtained from `sys.modules` too. `unittest.mock.patch("services.x.y")` does that; `monkeypatch.setattr("services.x.y", …)` does **not** (its `resolve()` walks package attributes), and neither does the import alias. Three routes, two of them wrong, and the two string forms are spelled identically. (2) The failure shape is the dangerous part: a patch that misses does not error, it lets the real dependency run, so the test fails **on the product's behaviour** and reads as a product bug. Two of these looked exactly like "upload is broken" and "logout forgot to audit". (3) **It cannot be reproduced small.** All six passed in every 2–4 file selection and in the enterprise repo; only the full ~9,100-test unit run creates the polluting predecessor. A green targeted re-run after a "fix" here proves nothing — re-run the whole tier, or stage the divergence deliberately. (4) Importing a test file into a *different* suite re-hosts it under a different conftest: assumptions about module identity, DB fixtures and autouse restores travel with the harness, not the file. Budget for that whenever code moves between repos.
**Fixed** (2026-08-10): every `services.*` patch in the portal tests routed through the resolver that matches the code — `quiet_audit` patches the router's own binding; both choices explained at the site; and `test_ent356_portal_is_oss_core.py` grows a guard that scans the seven portal test files for `patch.object(<alias>, …)`/`monkeypatch.setattr(<alias>, …)` where `<alias>` came from `import services.… as <alias>` — verified to go red on an injected offender, and it found a seventh site (`services.task_execution_service`) that had not failed yet.
**Correction, same day**: the first fix was half-wrong and the full tier said so — 8 failures became 1, not 0. "Use the string target" is not one rule, because `mock.patch` and `monkeypatch.setattr` accept the same-looking string and resolve it differently: `unittest.mock._get_target` reads `sys.modules` (agrees with the code), while `_pytest.monkeypatch.resolve()` reduces the dotted path with `getattr` and lands on the **package attribute** — the stale object. So converting alias-form patches to "the string form" fixed the `mock.patch` sites and left the `monkeypatch` ones broken in exactly the same way, with a tidier-looking diff. Corollary for the ledger: **a fix expressed as a style rule ("always use X form") is not verified until each distinct API behind that form is measured separately** — the shared spelling is what hides the divergence. The measurement is now an executable test (`test_the_two_resolvers_really_do_disagree`) that stages the divergence and asserts each resolver's answer, so the guards fail loudly if a future pytest changes `resolve()` instead of quietly becoming cargo cult.

## 2026-08-04 — pitfall — A fire-and-forget `create_task` gets more dangerous the more state you create before it
**Context**: trinity#1968 self-review. `_trigger_handler` was already spawning its run with a bare `asyncio.create_task(...)` whose result nobody kept — the event loop holds only a WEAK reference, so the task can be collected mid-flight (the asyncio docs say so outright). That was survivable while the handler created nothing first: a collected task meant the run silently didn't happen. The fix for #1968 moved the lock acquisition and the execution-row INSERT to BEFORE the spawn so the response could carry a real `execution_id` — and in doing so turned the same latent footgun into a stranded `running` row whose id the caller is holding, plus a schedule lock pinned until its Redis TTL. (2) A bare `asyncio.create_task` is a latent bug whose severity is set by what the caller allocated before it: nothing → a lost no-op; a lock or a DB row → a leak that outlives the request. (3) When the codebase already contains the guard pattern somewhere (here `_inflight` from #1083), the second site is not a new design decision — grep for the pattern before inventing one, and cite the precedent so the third site is obvious.

## 2026-08-11 — pitfall — A guard that scans ONE of two equivalent syntaxes reports a clean pass over the half it cannot see
**Context**: trinity#2094. #2081 (CSO M1) tightened schedule enable/disable/trigger to owner-tier and picked `OwnedAgentByName` — which reads `agent_name: str = Path(...)` — on routes declared `/{name}/...`. **Context**: trinity#2114. `_hot_reload_subscription_token` lazily imports `is_claude_runtime` from `services.agent_service.helpers` inside its function-level fail-open `except Exception → _restart_agent`. ## 2026-08-13 — pitfall — Adding an unrelated test FILE moves which tests fail, so a differing failure set is not by itself a regression
**Context**: trinity#2161, a client-portal + Vue change touching no backend module under test. Three full `tests/unit` runs, three disjoint failure sets: `dev` at HEAD → 2 errors in `test_subscription_auto_switch_pingpong.py`; the branch **minus** its new test file → **10** errors in that same file; the branch **with** it → zero there, and instead 3 unrelated failures in `test_1081_physical_meter.py` + `test_1966_ops_reset_audit.py`. All 3 passed in isolation. The new file adds no import surface the suite lacked (`test_ent360_workspace_agent_page.py` already imports `client_portal.agent_page`) — it changes collection order, which changes which module pollutes which, per the `sys.modules` stub-leak class already recorded on 2026-08-12 (#2114) and 2026-08-10 (ent#356).
**Lesson**: The 2026-08-12 entry says to check the base before claiming a regression; this is the sharper form. (1) The comparison is **whole-run to whole-run, never failure-identity to failure-identity** — a base run that fails *elsewhere* still exonerates you, and a base run that is clean while yours is not does **not** convict you until you re-run yours with the new test file deselected. Three runs (base, branch, branch-minus-new-tests) is the cheap decisive triple. (2) **Adding a test file is itself a perturbation**, not a neutral observation — expect it to relocate pre-existing order-dependent failures, sometimes to files with no relationship to the change, sometimes making previously-failing ones pass. (3) Corollary for CI triage: "this PR broke tests it does not touch" is a hypothesis, not a finding, until the deselect run is done; the honest report states all three runs rather than the branch run alone.

## 2026-08-14 — pitfall — In a predicate stack that borrows N checks from a library and hand-rolls one, the hand-rolled one is where input normalisation drifts
**Context**: trinity-enterprise#393. `utils/url_validation._is_internal_address` asks CPython's `ipaddress` six questions (`is_private`, `is_loopback`, `is_reserved`, `is_link_local`, `is_multicast`, `is_unspecified`) and adds ONE clause of its own — RFC 6598 CGNAT (`100.64.0.0/10`), added by ent#14 S3 precisely because the stdlib reports that range as neither private nor reserved. It was written `ip.version == 4 and ip in _SHARED_ADDRESS_SPACE`. The IPv4-**mapped** form `::ffff:100.64.0.1` reports `version == 6`, so the version gate never reached it — and CGNAT is exactly the range the six borrowed predicates also answer `False` for. Result: RFC 6598 space validated as a **public** destination on both `_validate_public_https_url` consumers — `validate_a2a_endpoint_url`, which then sends a credentialed `Authorization: Bearer` POST, and `validate_template_registry_url`. Every *other* internal range survives its mapped form for free, because CPython's `is_private`/`is_reserved` short-circuit **through `ipv4_mapped` before consulting their IPv6 tables**. The suite had already anticipated the evasion generically — it parametrised `::ffff:127.0.0.1` and `::ffff:10.0.0.1` — but those rows pass on borrowed delegation, so they proved nothing about the one clause that had to do the delegation itself, and mapped CGNAT was simply never added to the list.
**Lesson**: (1) **When a predicate mixes borrowed checks with a locally re-implemented one, the local clause does not inherit the library's input normalisation** — it must redo it explicitly. Here the fix is to resolve the v4 *view* once (`v4 = ip if ip.version == 4 else ip.ipv4_mapped`) and test membership against that, never to gate on `ip.version`. Same shape as Invariant #5 (vendored mirrors drift) and #1891 (CI must run the shipped interpreter): the piece we own is the piece that rots. (2) **A parametrised "evasion is covered" list is only evidence for the rows in it.** Rows that pass via a delegation the library performs cannot vouch for a sibling clause that performs none — when adding a bespoke clause to a borrowed stack, add its own evasion rows, not just the family's. (3) **Bound the whack-a-mole by proving which shapes need bespoke handling**, rather than adding one per report: `::ffff:0:0/96` is the ONLY v4-in-v6 embedding CPython short-circuits an IPv4 verdict through, so it is the only one that can inherit a v4 gap — `::/8` (IPv4-compatible RFC 4291, IPv4-translated RFC 2765), `64:ff9b::/96` + `64:ff9b:1::/48` (NAT64), `2002::/16` (6to4) and `2001::/32` (Teredo) are refused wholesale by prefix regardless of the address they carry. That fact is what makes the one-line fix complete; it is now pinned by `test_736_a2a_outbound_edges.py::test_C1_ipv6_transition_forms_*`, because the refusal is the interpreter's and not ours. (4) **A narrowing security fix needs the widening test too** — `test_C1b` asserts the mapped rows either side of the /10 stay public, since refusing every mapped address would be a worse bug than the leak it fixes.

## 2026-08-14 — pitfall — A vendor's "this is the end" signal stops meaning that the moment the vendor adds concurrency, and the failure is a silent SUCCESS
**Context**: trinity#2127. `headless_executor` treated any `{"type":"result"}` line as "the turn is definitively over" (#970's comment says exactly that) and SIGTERMed the process group 2s later with `return_code = 0`. That premise held when a `claude --print` run was one turn; it stopped holding when the CLI gained background subagents, which emit **one result line per turn segment** (measured 3–5) while the CLI deliberately stays alive to await them — the official headless docs say background subagents/workflows are exempt from the background-shell grace "because their result is part of the final output". So Trinity killed the CLI mid-wait and recorded the run as **success**, storing the model's "I'll wait for the notification" placeholder as the response, with the real answer never emitted and the subagents killed. Cost was billed; nothing logged a failure. The issue's own stated root cause ("the classifier trusts a clean `end_turn`") was wrong in a way that would have produced a fix for the *symptom* — a transcript scanner for unmatched invocations — because the classifier never runs: the process is killed first. #1870 is the same root cause with different timing (the notification lands early enough that the interrupted follow-on turn surfaces as `error_during_execution`), i.e. one defect had already been filed twice from opposite ends.
**Lesson**: (1) **Re-verify a terminal-signal assumption against the vendor's current documented behaviour before building a kill or a timeout on it** — "the process emitted its result" is a claim about a protocol, and protocols gain concurrency. The tell is a comment asserting definitiveness ("the definitive end of…") with no cited source; treat it as an expiring claim, not an invariant. (2) When a report says "X was recorded as success but the work was destroyed", establish **who destroyed it** before writing a detector for the symptom — grep our own teardown/kill paths first, because a detector layered on top of our own kill is a permanent workaround for a one-line gate. (3) **A signal being *correct* is not the same as it being *sufficient*, and the review that matters is the one that tries to break the premise, not confirm it.** The first fix here gated on the vendor's own state ledger (`background_tasks_changed`, a full in-flight snapshot) and rejected an output-idleness rule by citing the 2026-07-14 timing-window entry — reasoning that looks impeccable and was wrong, because it never asked whether the ledger covers the *reported* shape. It does not: once the fan-out ends the ledger reads empty while the model spends another 28s composing the synthesis the subagents were spawned to produce, so the ledger-gated build still stored `"ECHO reported."` over the real report. The tests passed throughout — they tested the shape the gate covered. Two tells, both cheap: a premise stated as "X means the work is in flight" deserves the dual question "does **not** X mean the work is finished?", and a gate whose covering test was written from the same mental model as the gate cannot falsify it — reproduce the *other* shape before believing the fix. (4) When the accurate signal *is* a timing window, do not reject it on the timing-window heuristic — **measure the bound instead**. #970's failure is literally "process alive, producing nothing", so idleness is the direct expression of it, and the only real question is how long a healthy run can be silent. Measuring took one cheap run and moved the constant from a guess to 7.4× a known worst case (40.54s of dead air for one 9,840-char message, because without `--include-partial-messages` a message is one stdout line emitted only when complete). Pair it with the asymmetry check: here too-large only delays a pathological finalize while too-small destroys a finished deliverable and records it as success, so the number is biased hard toward generous. (5) Filter such a ledger by **what the vendor itself waits for**: background *shells* sit in the same array but are killed after ~5s, so gating on the whole array re-opens the very hang (#970) the gate exists to preserve — and prefer a denylist, because an allowlist that has not heard of a future waited type restores the original bug silently while a denylist's miss costs only a bounded wait. (6) Reproduce a race with a **replayed stream in a unit test**, not by re-running the model: the end-to-end run passed on 3 of 4 attempts, and the deterministic test is what proves the placeholder loses to the real answer. (7) Operational: never run memory-heavy analysis (`strings`/`sort` over a 271 MB bundle) inside an agent container — it OOM-kills the container's cgroup and takes the agent down.

## 2026-08-16 — pitfall — a RE-IMPLEMENTED (not vendored) security policy across the backend/agent boundary has no parity test, so the two silently diverge
**Context**: #1704 plugin manifest. ## 2026-08-16 — pattern — When a module constant becomes a per-entity value, its hidden mirrors are function keyword defaults and cross-boundary fallbacks — delete the name so both fail loudly
**Context**: trinity#2214. `client_portal/service.py` bounded every Workspace turn with `PORTAL_TURN_TIMEOUT_SECONDS = 300` while the platform already had a per-agent knob (`execution_timeout_seconds`, TIMEOUT-001) that the engine's *lock* TTL consulted (`resolve_lock_ttl`) and the *turn* did not — the asymmetry was the bug. Making it per-agent exposed three places the 300 had quietly propagated to: (1) two derived module constants (`PORTAL_ATTEMPT_CEILING_SECONDS`, `PORTAL_MAX_TURN_SECONDS`) that had to become pure functions of the per-turn value; (2) a **function keyword default** — `mark_turn_inflight(..., ttl_seconds: int = PORTAL_INFLIGHT_TTL_SECONDS)` — which Python binds at *definition* time, so even after every reader was fixed a bare call would have sized the marker at the old arithmetic forever; (3) a **frontend fallback literal** (`REPLY_MAX_WAIT_MS_FALLBACK`) mirroring the server's arithmetic, which cannot follow a per-agent value at all. **Lesson**: (1) A `def f(x=CONST)` is a mirror of `CONST` with no owner — treat it exactly like the 2026-07-16 mirrored-constant class: when the source becomes dynamic, replace the default with a `None` sentinel resolved at *call* time, or make the argument required. (2) **Delete the old constant names rather than aliasing them**: an alias keeps every def-time consumer and every forgotten reader silently on the old value; a deleted name makes each one an `ImportError`/`AttributeError` at import, which is the loud failure you want (grep the enterprise submodule too — it imports OSS services freely). (3) A fallback whose remaining audience is *old servers* must be **frozen at the old server's real bound and say so**, never "synced" to the new arithmetic — there is no one number to mirror once the value is per-entity, and re-sizing it makes a client of an old backend wait for a turn that server already killed. (4) Before declaring a fallback "old-backend only", grep for callers that pass *nothing* — a fallback with a live caller is not a fallback.

## 2026-08-17 — pitfall — A "signed-out" flag over a credential installed as an axios DEFAULT header hides the disclosure instead of removing it
**Context**: trinity#2258. The Workspace's `signOut()` cleared only the portal token; since ent#357 a platform JWT is an implicit workspace session (`isPlatformSession = !portalToken && isAuthenticated`), so clearing the portal token *activated* the fallback and a refresh re-entered as the operator. The issue's own prescribed fix was a persisted "suppress the platform fallback" flag. Three reviewers converged on it before the fourth read `auth.js`: the platform JWT is installed as `axios.defaults.headers.common['Authorization']`, and per-request headers MERGE over defaults — omitting `Authorization` does not delete it. **Lesson**: (1) Never suppress a *derivation* of a live credential in UI state — ask what is still on the wire. If a credential lives in an axios default header (or a cookie), a per-request `{}` / a Pinia getter returning `{}` removes nothing; the only design where screen and wire agree is one that removes the credential. (2) Before adopting a flag design, enumerate every reader of the state it must shadow (getters, raw interceptors that cannot import a store, `fetch` sites, test restatements of a predicate) — that count is the design's cost, and it is usually the reason to reject it. ## 2026-08-18 — pitfall — `getattr(principal, "is_platform", True)` makes the absent attribute the privileged one
**Context**: trinity-enterprise#387 (`shared_sessions/service.py::_resolve_budget`), caught in `/review` of the same PR. ## 2026-08-20 — pitfall — Prefix-specific secret patterns rot silently; the vendor adds a variant and it ships in clear text
**Context**: trinity#2208, found in `/review` of the fix while verifying its own AC #3 ("the key never appears in argv, logs, or an error body") with a real key. `credential_sanitizer` carried three OpenAI/Anthropic rules — `sk-[a-zA-Z0-9]{20,}`, `sk-proj-…`, `sk-ant-…`. **Lesson**: (1) A sequence/generation guard protects a *surface*, not a *statement* — apply it at every exit that writes shared state (`try` **and** `catch` **and** `finally`), or the paths you forgot become the only ones a superseded request can still reach; `return` inside try/catch still runs `finally`, so the `finally` needs its own check rather than inheriting one. (2) Any map keyed by item id that a list refresh reconciles must exempt ids with an operation in flight, and exempt the WHOLE per-item record (a retryable failure path that promises to keep the selection and note cannot keep them if the reconcile deleted them). (3) A paged/windowed list is not a membership oracle: "absent from this response" means *outside the window* as often as *gone*, so never let it drive a destructive local decision. (4) A "forget everything" reset must not be spelled as the reconcile with an empty list once the reconcile grows exemptions — it silently inherits them; write the wipe out.
## 2026-08-24 — pitfall — A renumbered Alembic revision leaves a loadable `.pyc` behind, and boot fails naming a revision that exists in no source file
**Context**: ent#365 development, local stack. ## 2026-08-24 — pitfall — A transition table must accept each event from the state it is actually RAISED in, or the loop wedges holding hardware
**Context**: ent#440 (`voiceConversation.js`, Workspace voice loop), caught in `/review` of its own PR before merge. The machine accepted `silence` ("that clip held no speech, listen again") only from `listening` — the state a human reading the diagram would name. But `silence` is raised from `finishUtterance`, which runs on the recorder's `onstop`, i.e. **after** the machine has already moved to `transcribing`. The edge therefore never matched: the loop sat in `transcribing` forever with the microphone open, no timer able to advance it, and the only recovery a user pressing Stop. Nothing threw and no test failed — a no-op transition is indistinguishable from a deliberate one.
**Lesson**: for every event in a transition table, find the line that RAISES it and read what the state is at that moment — not what the state was when the condition became true. Asynchronous plumbing (a recorder's `onstop`, an audio element's `ended`, a fetch's `then`) advances the state between the decision and the dispatch, so the raising state is routinely one hop past the intuitive one. Two cheap guards, both worth having: a property test that from every live state at least one event the loop actually raises changes the state (catches the wedge without enumerating edges), and — for anything holding a device, a lock or a lease — a hard rule that the state it wedges in must still be reachable by teardown.

## 2026-08-24 — pitfall — A guard that pins a rule as ONE literal source string fails the next legitimate edit, and the tempting fix deletes the rule
**Context**: ent#440. `portalVoiceModePersistence.spec.js` (#2157) asserted `toContain('if (voiceMode.value && ttsEnabled.value && data.response) speak(data.response)')` and a `{0,120}`-character window between `watch(() => props.agent?.name` and `loadVoiceMode()`. ent#440 correctly added one more condition to that gate (`&& !voiceConvLive.value`, so a live voice conversation does not narrate every reply twice) and one line to that watcher. Both guards went red on a change that preserved everything they exist to protect, and the reflex fix — relax to a regex that matches "some line mentioning voiceMode", or delete the assertion — would have retired the guard rather than the brittleness.
**Lesson**: when a rule can only be expressed as source (no mount harness, so a template/branch rule is unreachable by execution), pin it **term by term** — one assertion per condition that must remain — instead of one whole-line literal, and size proximity windows to the surrounding block rather than to today's exact byte count. Then a future feature ADDING a condition passes while a feature REMOVING one still fails. And when such a guard does go red, the first question is which of its terms the change actually invalidated: if the answer is "none", the guard is over-specified and the fix belongs in the assertion, with the surviving terms re-stated so the next reader can see the rule is still enforced.
## 2026-08-24 — pitfall — `ScanlineReveal` does not hide its slot during the LOADING phase, only during the reveal — so a branch chain inside it renders its wrong terminal under the track
**Context**: ent#253 (`MetricsPanel`, `DashboardPanel`), caught in `/review` of its own PR by reading the primitive's CSS and then confirming it live against a held-open response. Converting a panel from `v-if="loading"` + spinner to `<ScanlineReveal :loading="firstLoad">` moves the branch chain INSIDE the slot. `.scan-content` carries a `clip-path` only while `.wiping` (the 550 ms reveal); during loading it is an ordinary child under a 50%-opacity `.scan-track` overlay. So with the data ref still `null`, the chain fell through to `v-else-if="!metricsData?.has_metrics"` and the panel spent the entire first load telling the operator this agent has no metrics / no dashboard — dimmed, but exactly the false claim the change existed to remove. The old bare `v-if="loading"` had been load-bearing in a second way nobody had written down: it short-circuited the chain.
**Lesson**: when adopting the scanline primitive, the slot must be **terminal-safe while loading** — either gate every terminal arm on "data has arrived" (`showEmpty = store.hasLoaded && !hasSkills`, which is what `LibrarySkillsSection`, the ent#245 reference adopter, does) or make the chain's FIRST arm a `v-if="firstLoad"` placeholder that also reserves height (principle 4). Neither is optional: `aria-hidden` on the wrapper hides the flash from a screen reader and not from a person. Generally: a primitive that replaces a `v-if` gate inherits everything that gate was silently doing, and "it is visually covered" is a claim to verify in the CSS, not to assume from the name.

## 2026-08-25 — pitfall — Demoting a wrongly-elevated severity silently removes everything gated on it
**Context**: trinity#2396 review. The provider's near-the-limit status `allowed_warning` was read as a hard rate limit, so a subscription at 78% utilization scored `crit`. Fixing the predicate correctly demoted it to `warn` — and `showsReset(severity, windows)` gates the row's reset time on `severity === 'crit' || some window in the high band`, with 78 below the 85 band. So removing a false "rate-limited" also removed *when the limit clears* from the one row whose entire message is "this is about to matter", and only in the sub-85% range where the provider is the sole source of the warning. Nothing caught it: the backend tests assert the predicate, and all 81 pre-existing tile tests assert the pure functions rather than what the row still carries afterwards. It surfaced only by grepping every reader of `severity` after the demotion. The same sweep found a comment in the same PR asserting a user-visible fix that the SFC does not render (`row.meta` is bound behind `v-if="row.windows"`), i.e. the diff's own prose over-claimed where the fix lands.
**Lesson**: (1) A severity/state value is a KEY that other behaviour is gated on, not just a label. Before demoting or reclassifying one, grep every reader of that value and ask what each one *stops doing* — a fix that removes a false alarm inherits responsibility for whatever the alarm was accidentally carrying, and the loss is invisible in a diff because the deleted behaviour has no line. (2) Assert the resulting ROW/response, not only the predicate feeding it: a predicate test cannot see a field that vanished downstream. (3) Before claiming a display fix is user-visible, follow the value into the template — a computed field bound behind a `v-if` on a sibling field may never render in the case you are fixing, and the honest scope belongs in the comment.

## 2026-08-26 — pattern — Read the data you already store about a system before building state that models it
**Context**: ent#434. The issue specified a durable per-subscription state machine — edge-trigger, a 70% hysteresis floor, a re-arm on window reset — to track weekly subscription limits. Before building it, one query against ent#433's `subscription_headroom_history` settled what the provider's window actually does: `seven_day_resets_at` held CONSTANT at one midnight-UTC instant across five days of probes while utilization climbed 36→90, then stepped exactly +7 days. Fixed-with-reset, not rolling. That made utilization monotonic within a window, which made the hysteresis floor **unreachable code**, which made `resets_at` the window's identity — so the deterministic alert id (`sub-headroom-{sid}-{reset-day}-{tier}`) plus the sink's existing `ON CONFLICT DO NOTHING` became the entire state machine, with no durable memo to leak, race, or clean up on delete. A reviewer independently argued the opposite design from a *doc* claiming the windows were rolling (`dashboard-grid-view.md`); the data beat the doc, and the doc was the thing that turned out to be wrong.
**Lesson**: When a plan calls for durable state that MODELS an external system's behaviour, first query whatever the platform already records about that behaviour — Trinity persists a lot of provider telemetry that nobody reads back. The measurement is usually one query, it frequently deletes a subsystem rather than confirming it, and it is the only way to catch a *documented* claim that is false. Corollary: a design argument sourced from a doc outranks nothing; if a table can answer the question, the doc is a hypothesis.

## 2026-08-26 — pitfall — Adding a second consumer to a rate-floored shared resource BLINDS one of them; it does not duplicate work
**Context**: ent#434 added weekly-headroom sampling beside #447's recovery probing, both reading the same per-subscription provider snapshot behind `_probe_floor_ok` (`MIN_PROBE_INTERVAL_SECONDS`, 60s). The intuition is "two consumers, maybe one wasted probe". The reality is the opposite: whichever consumer probes first resets the floor, so the second is refused and sees *no fresh data* — and the subscription most likely to be probed by recovery (believed rate-limited) is exactly the one whose weekly window is most likely saturated. Reversed, `recover_probe` returns `"floored"` and #447 silently stops clearing stale `LIMIT` badges. Fixed by collapsing to ONE probe decision per subscription per cycle (`ensure_reading`), with recovery ordered first so its zero-age snapshot is reused rather than re-fetched.
**Lesson**: A per-entity rate floor is not a cache — it is a mutual-exclusion primitive with no fairness. Before adding a second reader of a floored resource, name which consumer wins the race and what the loser observes; if the loser's fallback is "no data", the floor has converted a cost concern into a correctness one, and the fix is a single shared read rather than two independent decisions. Ordering then becomes load-bearing and must be commented at the call site, not left to the reader.

## 2026-08-26 — pitfall — A pure predicate can be right while its CALLER narrows the domain, and the narrowing looks like ordinary filtering
**Context**: ent#434 / PR #2410, found in review. `fleet_verdict()` correctly refuses a fleet-wide "every subscription is saturated" claim when any member is `UNASSESSABLE` — the ent#100 positive-evidence rule, unit-tested and honoured. But its caller built the input as `{r["sid"]: r["classification"] for r in results if r.get("classification")}`. A member whose sampling raised carries `classification: None` **by design** (the swallow is the isolation property protecting #447's recovery detection), and a mid-cycle leader-lease yield `break`s with `results` shorter than the subscription list. Either way the blocking member was not `UNASSESSABLE` in the map — it was *absent*, and absent members block nothing. Result on a 3-subscription instance: an operator-visible `high` alert reading "All 2 registered subscriptions are at or past 75%", with the per-subscription alerts suppressed by the fleet branch's early return, so the false claim was the only thing emitted. Every unit test of the predicate passed throughout.
**Lesson**: When a predicate's correctness depends on *seeing every member of a set*, the set must be built from the **authoritative roster**, never from the collection of successful results — and a truthiness filter (`if x`, `if x.get(...)`) over results is exactly how the roster silently shrinks. Two shapes make this likely and both are good practice on their own: a deliberate per-item exception swallow, and an early `break` on a cooperative yield. Test the predicate AND the wiring: a test that hands the pure function a complete map can never catch it. Reviewing rule of thumb — for any "all / every / none" claim, find where the denominator is constructed and ask what is missing from it, not what is in it.

## 2026-08-27 — pitfall — A load-balance sort key promotes exactly the resource that is unused because it is broken
**Context**: trinity#2409. `select_best_alternative_subscription` ordered candidates `agent_count ASC` and returned the first survivor of the 2h failure filter. A subscription nobody is assigned to has zero agents AND zero failure rows — including one whose token is dead — so the least-used key sorted it FIRST, and both auto-switch and #74 new-agent assignment preferred it. "Least loaded" and "least used because it never works" are indistinguishable to a load key; a filter fed only by traffic cannot see a resource that receives none.
**Lesson**: A load-balance key is a tiebreak under a health/capacity signal, never the primary key for choosing a resource an agent will FAIL on. When a filter is the only health input, ask what a resource that never receives traffic looks like to it (no traffic ⇒ no failure rows ⇒ "healthy"), and rank by a signal observed without traffic (here: the cached provider probe). Corollary: a fresh "the provider refuses this" reading is a FILTER, not a low rank — ranking it last still selects it whenever it is the only survivor.

## 2026-08-27 — pitfall — A lexicographic secondary key over a continuous primary is dead code
**Context**: trinity#2409 plan review. The premise gate had just confirmed "rank by 7d utilization, then 5h as a secondary key". Provider utilization is 1-decimal per subscription, so two candidates essentially never tie on the primary and the secondary term is unreachable — a 7d 20% / 5h 98% subscription would beat 7d 25% / 5h 10% and fail the #792 immediate retry. Caught by the independent strategy reviewer, not by the gate that confirmed it.
**Lesson**: When two signals must BOTH shape an ordering, compose them into the primary (nearest wall = `max` of the windows; a band with a tiebreak inside it; a veto tier) — never `(a, b)` lexicographic keys unless `a` is discrete enough to tie routinely. ## 2026-08-28 — architecture — A queue that sits between admission and dispatch must either be visible to every reaper or re-anchor the clocks it hides behind
**Context**: #2433. An admitted execution (row `running`, capacity slot held, `claude_session_id='dispatched'`) could wait in the backend agent-call semaphore (#904), the agent's CPU-sized default thread pool, the agent's chat execution lock, or the post-exit drain — none of which the cleanup watchdog's proof-of-life (`/api/executions/running`) could see. After the 60s grace the sweep wrote a false `failed` ("completed on agent but status not reported"), released the slot, and the parked call ran anyway (billed, overbooked; a late 200 silently overwrote the row via #378, a late non-success was discarded). Reproduced twice locally. The first plan fixed the *visibility* half only — two independent reviewers then found that every age check was **anchored at admission** (`started_at`, the slot's `ZADD` score + `EXPIRE`, canary E-01, `duration_ms`), so `park + run > timeout + 300` was still bulk-FAILed **mid-run** by the registry-blind Phase-1 sweep and its slot TTL-reclaimed — invisible to the issue's own acceptance criteria because a 4-minute park fits a 3900s window. The backlog spill already encoded the right rule (`queue.py`: "reset started_at so drain records a clean run window"); the limiter was a second queue nobody had classified as one.
**Lesson**: (1) Any wait between "admitted" and "the agent has it" is a *queue*, and a queue needs both halves: a liveness signal every reaper consults (agent-known ∪ live dispatcher, tri-state on an unreadable Redis — never fail-open on the *slow* case) **and** a re-anchor of every admission-anchored clock at grant (`started_at`, slot lease), because withholding one reaper does nothing about the others. Grep for every reader of `started_at` and every `ZADD`/`EXPIRE` before declaring a proof-of-life fix complete. (2) A liveness marker must be refreshed by the thing whose life it asserts (one per-process refresher, short TTL) — a static marker with a bounded skip window turns a dead dispatcher into an hour-long zombie. (3) The AC must include a long-run case (`park + run > timeout + buffer`), not only the short repro that surfaced the bug.

## 2026-08-28 — pitfall — A branch that stops asking the agent loses the agent-scoping the proxy gave it for free — and the proxy only ever scoped ONE of the two ids
**Context**: #2433 review + security verification. `terminate_execution(name, execution_id, task_execution_id)` is reached from three arms; the operator route (`routers/chat.py`) proves `name` via `get_authorized_agent` and takes BOTH ids from the request (`execution_id` from the path, `task_execution_id` from a query param that defaults to the path id). The proxy arm looked safe because the agent 404s an `execution_id` it does not own — but the CANCELLED CAS and the activity close are keyed on `task_execution_id`, which the agent never sees, so a caller authorised on agent A could pass agent B's row id and flip it to CANCELLED without B ever being contacted (B's later SUCCESS then loses the CAS). The review caught the new parked-cancel arm and the pre-existing BACKLOG arm (neither asks the agent at all) and added per-arm belts; the independent verifier then found the proxy arm had the same hole one id over. Fixed by ONE gate at the entry of `terminate_execution` — the row behind `task_execution_id` must belong to `name`, uniform 404 otherwise, fail-closed 503 on an unreadable row — with the per-arm belts kept as a second layer.
**Lesson**: When a code path replaces a call to a remote authority (the agent, a container, a service that only knows its own objects) with a local write, the ownership check that authority performed implicitly must be re-stated explicitly at the new site — and it must cover EVERY identifier the local write is keyed on, not just the one the remote call carried. Ask: *what stopped this from crossing tenants before, which identifier did that check actually bind, and does the write use a different one?* Put the check at the function entry so a fourth arm cannot forget it; per-arm belts are a second layer, never the mechanism.

## 2026-08-31 — pitfall — A cached copy of local state that a REMOTE actor acts on must be published before the local transition, and the remote must write its intent before reading it
**Context**: #2435 review (#2433). `agent_call_limiter` kept an in-process `InflightEntry.phase` and mirrored it to Redis (`execution:inflight:{id}`) from a 15s refresher. `acquire_agent_call_slot` flipped `parked → calling` in memory at grant and wrote nothing, so the mirror advertised `parked` for up to a full tick after the POST had begun. With `--workers 2` about half of all cancels are served by the worker that does NOT own the coroutine, so they read the mirror — finalized the row CANCELLED, released the capacity slot, and left the agent running a billed turn whose SUCCESS then lost the CAS. That is the #378 symptom, reintroduced in a narrower window by the very change that removed it. Fixed by ordering both sides rather than shortening the tick: the owner publishes the transition in the SAME round-trip that reads the cancel key (write-then-read), and the remote writes the cancel key BEFORE re-reading the phase (write-then-read). An observed `parked` then gives `W_remote(cancel) < R_remote(marker) < W_owner(marker) < R_owner(cancel)`, so the owner's check is guaranteed to see the key. Neither side pays an extra round-trip.
**Lesson**: A lazily-refreshed mirror of local state is safe for *observability* and unsafe for *decisions* — the moment a remote actor takes an irreversible action on it (write a terminal, release a lease, kill a process), the staleness window becomes a correctness bug, and shrinking the refresh interval only narrows it. Publish the transition synchronously on the path that acts on it, and order the two actors as store-then-load on both sides so the interleaving is closed by a happens-before chain rather than by timing. Ask of any cached phase/lease/heartbeat: *who else acts on this, and what do they do if it is one tick out of date?*

## 2026-08-31 — pitfall — Widening a liveness set without an age bound converts a self-healing leak into a permanent one
**Context**: #2435 review (#2433). `list_recently_completed_ids()` was widened to include registered processes that had EXITED but whose owner had not yet reached `finally: unregister()` — semantically right (that IS "completed, not yet reported"), but the added set had no clock, while the buffer it joined has a 300s TTL. A leaked registry entry was therefore reported to the backend as agent-known **forever**, so the orphan watchdog never recovered that row; before the widening the same leak self-healed, because `list_running()` filters on `poll() is None`. The same PR also made the leak newly reachable: `register()` SIGKILLs the group for a cancel that arrived while pending, so the `stdin.write` on the next line can raise `BrokenPipeError` — and the `finally: unregister()` began further down.
**Lesson**: Every membership signal a reaper trusts needs a clock, and the bound must be measured from the event that makes the entry eligible (here: when the exit was first *observed*), never from an unrelated timestamp like `started_at` — that would drop a legitimately long run the moment it entered its drain. When widening such a set, ask the inverse question too: *what used to clean this up, and does the wider predicate still let it?* And pair a `register()` with the failure path of every statement between it and its `finally`, not just the block the `finally` happens to wrap.
