## 2026-10-24 — pitfall — When dispatch moves to a new seam, the activity OPEN must move with it
**Context**: trinity#3932. Pull mode moved "dispatch" from `execute_task` step 3 to the worker's claim (`/api/internal/next-task`), but the CHAT_START open stayed in step 3, which a pull row never reaches. Every pull terminal writer already closed the dispatch activity (#1804), so the close owner sat idle with nothing to close and the Dashboard timeline went blank fleet-wide once agents moved to pull. The #1804 parity guards check closes only, so nothing caught a missing open.
**Lesson**: Opening and closing a dispatch activity are one contract. A new place where a turn actually starts (a claim surface, a direct dispatch, a re-delivery) calls the shared opener `task_execution_service.start_dispatch_activity` and does not write a CHAT_START itself. When reviewing a new claim or dispatch path, ask "where is the bar opened?" as well as "who closes it?".
