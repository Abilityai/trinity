## 2026-11-11 — pitfall — A card that moves between two `v-for` lists is a new element: restore focus by id after the patch, and never clear the remembered id in `onBeforeUpdate`
**Context**: trinity-enterprise#957, `ProjectTaskBoard.vue`. A task card that changes column is unmounted in one list and mounted in another, so keyboard focus falls to `<body>` on every move. Two obvious repairs both failed under a mount test. (1) A `Map` of id → element kept by a function ref ends up EMPTY for the moved card: Vue mounts the new element (ref called with it) and only then unmounts the old one (ref called with `null`), so the delete runs last. (2) Capturing `document.activeElement` in `onBeforeUpdate` and reading it in `onUpdated` lost the id, because one logical change ran `onBeforeUpdate` twice before `onUpdated` — the second time the old card was already gone, nothing had focus, and the capture overwrote the id with nothing.
**Lesson**: Carry the identity on the DOM (`data-*` with the row's id) and look the element up AFTER the patch; do not hold element references across a re-parent. In `onBeforeUpdate` only ever SET the remembered id (when focus is on such an element), and consume-and-clear it in `onUpdated`. Prove it with a mount test that asserts `document.activeElement` is the same task's control after the move — a source read cannot see either failure. Sibling rule from the same file: in Firefox a drag does not start from a `<button>` inside a `draggable` element, so the grab area of a draggable card is `role="button"` on a non-button element, with Enter and Space handled explicitly.
