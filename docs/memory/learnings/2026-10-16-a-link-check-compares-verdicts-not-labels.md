## 2026-10-16 — pitfall — When the gate decides on one spelling of a path and the actor acts on another, compare the gate's VERDICT across the two, not a proxy label
**Context**: trinity-enterprise#820. The backend tiers a Files request on the path the caller NAMED; the agent server resolves links before acting. The first fix refused a link only when the named and resolved paths fell in different *classes* (`same_class`). Independent review broke it in one line: `ws/l -> ~`, then `DELETE ws/l/.ssh`. Both `ws/l/.ssh` and `~/.ssh` classify as just "hidden" — the protection on `~/.ssh` is not a class, it is a delete-floor *anchor* (a directory above a protected path) and an ancestor rule, both evaluated on the named path only. The agent server's by-name floor did not name `.ssh`/`.aws`/`.config`/`.local`, so `rmtree` would have run. A share holder can get the link made by asking the agent in chat.
**Lesson**: (1) A check that the two spellings "are the same kind of thing" is only as strong as the label set — anything the gate decides from outside the labels (anchors, ancestors, depth, per-verb special cases) leaks through. Compare the decision itself: `decide(tier, verb, named) == decide(tier, verb, resolved)` for every tier, which is invariant to how the decision is computed. (2) Then act on the resolved path with a no-follow walk (`O_NOFOLLOW` + `dir_fd`), so a link swapped in after the comparison is refused rather than followed. (3) Test with the strongest link, not a convenient one: a link to the home directory itself turns every hidden top-level path into a reachable sibling; a link into one subdirectory exercises almost nothing. Same family as the ent#792 `//` normalisation entry and the ent#819 read-side link refusal: the check and the action must read one path.
