## 2026-10-30 — pitfall — A gateway rule can be model-specific; probe with the production model before designing around the refusal
**Context**: trinity-enterprise#1027 (PR #4115). Retrieval memory needed the platform Anthropic key to capture anything, so a subscription-only install remembered nothing. The first probe sent the memory extractor's own request (Haiku 5.5) on a stored subscription setup token and got 429 `Error` unless the system prompt opened with the Claude Code identity line, so the first build concluded "the backend cannot call the Messages API on a subscription token without impersonating Claude Code" and built an in-container door through the agent's runtime instead. Meanwhile `client_portal/service.py` had been generating Workspace thread titles on the same tokens in production for weeks — with Haiku 4.5. Re-probing per model showed the rule is model-specific: on a setup token, plain Bearer + the OAuth beta, `claude-haiku-4-5` answers 200 while Haiku 5.5, Sonnet 4.6 / 5.5 and Opus 4.6 / 5.5 answer 429 `Error`. The door was dropped and the real gap — six backend model callers, four request shapes, two auth strategies, no shared client — became `services/model_gateway`.
**Lesson**: When a provider refuses a request, vary one thing at a time (model, auth header, system prompt, user agent) before concluding what the rule is, and grep the codebase for a caller that already works against the same endpoint — a shipped precedent is a measurement. Design the seam around the measured rule (here: the model follows the credential), not around the first refusal. A new platform model call goes through `model_gateway`, never a fresh `httpx` call with its own credential lookup.
