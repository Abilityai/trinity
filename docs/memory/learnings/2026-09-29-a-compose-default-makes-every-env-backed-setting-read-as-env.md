## 2026-09-29 — pitfall — Forwarding an env-backed setting with a compose default makes "env" the reported source on every install

**Context**: trinity-enterprise#671. The ops keys in `config.ENV_BACKED_OPS_KEYS` resolve row → env → code default, and `GET /api/settings/retention` reports which tier answered. ent#478 forwarded them as `${METRICS_DAILY_POINT_CAP:-100000}` in all three backend compose files ("must reach the container or the .env lever is inert"), and set them outright in `.env.example`, which `start.sh` copies to `.env` on a fresh install. So on every install the variable was set, the reported source was `env`, and the #2085 seeder skipped the window, since it defers to a set variable. The Settings rows built on that source would have shipped read-only everywhere, with "unset the variable to edit it here" advice that could not work, because removing the line only brought back the compose default. Every green signal agreed: the resolver was right, and so were the values.
**Lesson**: For a setting whose SOURCE is observable (reported, or used to lock a UI, skip a seed, or pick a precedence), "reaches the container" and "has a default" are different requirements. Forward it with an empty default (`${VAR:-}`, the `SECRET_KEY` pattern), leave it commented in `.env.example`, and let the code default be the fallback. A compose default is right only for a plain value nobody asks the source of. Before building on "source = env", run `printenv` inside the real container. The source is decided by deploy config, not by the resolver.
