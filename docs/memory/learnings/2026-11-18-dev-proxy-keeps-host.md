## 2026-11-18 — pitfall — A URL the backend builds from the request is only as right as the Host every proxy in front of it delivers
**Context**: #4476, found in the v1.0.5 release testing. `_get_default_mcp_url` and `public_base_url` build caller-facing URLs (the advertised MCP URL, a schedule's webhook URL, the x402 resource URL, a slash-redirect `Location`) from the Host header. Production nginx sends `Host $host`; the dev Vite rule `/api/` carried `changeOrigin: true`, a Vite default from the initial commit, so every one of those URLs named the container (`http://backend:8080/mcp`) in development only. The `/a2a/` rule had been switched to `changeOrigin: false` for exactly this reason in trinity-enterprise#157; its `/api/` sibling was left as it was. Every unit test passed, because each one hand-set the Host header that the proxy was rewriting.
**Lesson**: When a proxy rule sits in front of code that reads the Host, it keeps the Host (`changeOrigin: false` in Vite, `proxy_set_header Host $host` in nginx). When one rule is fixed for this, check the rule's siblings (`/api/`, `/a2a/`, `/ws`, `/token`) in the same change. A test of a proxy rule sends a request through the resolved rule to a stub server and asserts what arrives (`src/frontend/tests/unit/viteApiProxyHost.spec.js`). Reading the option's value proves only that it was written, and a test that sets the Host itself cannot see what the proxy does to it.
