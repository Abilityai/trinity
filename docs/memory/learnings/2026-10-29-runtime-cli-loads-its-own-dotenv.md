## 2026-10-29 — pitfall — A name refused from the spawn env is not refused while the runtime CLI loads its own dotenv
**Context**: trinity-enterprise#1001 (`execution_env.py`, `codex_runtime.py`). `build_execution_env` refused the routing names from `~/.env`, and two of the three runtimes would have set them again themselves. The Gemini CLI loads `~/.env` (or `~/.gemini/.env`) and fills every name the process env does not hold. The Codex CLI loads `$CODEX_HOME/.env` and *overwrites* the process env, refusing only `CODEX_*` names. Claude Code applies settings `env` from the agent-writable user and workspace `settings.json`.
**Lesson**: Before adding a name to `PROTECTED_KEYS` (or any `.env` refusal), list every file each pinned runtime CLI reads env from, and close each one by the rule that file follows. A fill-only loader is beaten by handing the name over pinned (`""` or the CLI's default, never absent). An overwriting loader needs the line removed from the file before spawn, failing closed if it cannot be. Settings `env` needs a policy-level pin. The facts are version-specific, so pin them to the CLI version the image ships with a test that fails when the Dockerfile pin moves.
