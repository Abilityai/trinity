## 2026-09-24 — pitfall — `db/tables.py` metadata omits constraints `schema.py` declares; an ON CONFLICT target built on it can fail
**Context**: trinity-enterprise#530 (`db/skill_sets._apply`). `schema.py` creates `agent_skills` with `UNIQUE(agent_name, skill_name)`, but the SQLAlchemy `Table` in `db/tables.py` declares no such constraint. The first cut used `make_insert(agent_skills).on_conflict_do_nothing(index_elements=[agent_name, skill_name])`, and against a table created from `tables.py` metadata (every real-SQLite unit harness here) it failed with `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`. The same would happen on any install whose table predates the constraint.
**Lesson**: never pick an `ON CONFLICT` target on the strength of `schema.py` alone. Check that the constraint exists in `tables.py` and on both migration tracks, or avoid the conflict target: compute the missing rows inside the transaction, then do a plain insert in a `begin_nested()` savepoint and catch `IntegrityError`. The existing `SkillsOperations.set_agent_skills` already follows that shape.
