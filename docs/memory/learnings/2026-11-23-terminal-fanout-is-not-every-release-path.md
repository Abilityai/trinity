## 2026-11-23 — pitfall — "Every terminal writer reaches the hook" is false on a clean stop, so a lock released only there wedges after every deploy
**Context**: #4733, `services/caller_wake_service.py`. The first plan for the per-caller wake hold released it at the wake row's own terminal (`maybe_wake_caller` on a `caller_wake` row), on the strength of the #4536 module text "every terminal writer reaches it, restart included". `execute_task`'s `CancelledError` branch (backend shutdown, `task_execution_service.py`) writes the row FAILED and closes its activity but never calls `spawn_task_terminal_event` (a task spawned on a closing loop would not run), and startup recovery scans only `running` rows, so the hook never runs for that row. The 15 s window key had hidden this: a leaked claim cost 15 s. A per-caller hold released only at the terminal would have held the caller for the agent timeout plus the slot buffer (about 65 min by default) after every deploy that interrupted a wake, with no FAILED row to show it, only `parked` audits. Two independent plan reviews caught it. The tests could not: they drove the hook by hand (`_wake_turn_ends`), which production skips on a clean stop.
**Lesson**: never make the terminal fan-out the only release of a lock, a hold or a marker. Decide "is it still running?" from the rows (a live row of the right trigger, plus a short grace for the gap before the row exists), reclaim a stale claim by its owner token, and let the fan-out only make the release prompt. A restart test models the real shutdown shape: the row written FAILED and no hook call. And a lock's "busy" and "free" must come from one predicate: a claim path that calls a stale hold busy while the park's re-check calls it free parks and drains the same ending forever (the mutation battery for #4733 hung on exactly that).
