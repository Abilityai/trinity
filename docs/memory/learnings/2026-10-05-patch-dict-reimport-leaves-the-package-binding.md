## 2026-10-05 — pitfall — A re-import inside `patch.dict(sys.modules, …)` leaves the parent package bound to the module built on mocks
**Context**: trinity-enterprise#752 review. `test_ent751_gate_callers::test_a_channel_message_held_by_the_gate_is_answered_in_the_conversation` failed only in a full `-n auto` run, with `ChannelResponse(...).text` a `MagicMock`. It reproduced on the base commit with three files in order: `test_1533_client_message_count` (imports `adapters.message_router` at module level), then `test_channel_image_vision`, then the victim. `test_channel_image_vision` deletes `adapters.message_router` and re-imports it inside `patch.dict(sys.modules, {"adapters.base": MagicMock(), …})`. On exit `patch.dict` puts the ORIGINAL module back in `sys.modules`, but the `adapters` package's `message_router` attribute, which the re-import rebound, still points at the copy built on the mocked `ChannelResponse`. `import adapters.message_router as mr` resolves through that attribute (the 2026-08-10 divergence), so every later importer of the alias form got the poisoned module. New test files change the randomized order, so a pre-existing leak like this can surface on any PR as a "new" failure in the regression diff.
**Lesson**: (1) `patch.dict(sys.modules, …)` restores the dict only. A re-import performed inside it also rebinds the PARENT PACKAGE ATTRIBUTE, and nothing restores that. A test that re-imports a submodule under stubs must save and restore `pkg.<sub>` itself (an autouse fixture in that file, as `test_channel_image_vision` now has), or import the module under test with `importlib.import_module`, which reads `sys.modules`. (2) Reproduce an `-n auto`-only failure by running the suspected polluter files in collection order in front of the victim, then run the same selection on the base commit before deciding whose bug it is. A two-file pairing passed here; it took the module-level importer plus the re-importer to stage it.
