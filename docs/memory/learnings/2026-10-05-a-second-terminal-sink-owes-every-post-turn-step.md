## 2026-10-05 — pitfall — A second terminal sink owes every post-turn step the first one runs, and a claim token is never cleared at terminal
**Context**: #2329. The pull sink (`pull_coordination_service.apply_task_result`) wrote the row and stopped, while the push drain (`run_async_task`) also saved the turn to the caller's chat session and closed the collaboration and self-task activities. On a pull pilot a Chat-tab `/task` (`save_to_session`, trigger `manual`) succeeded and never reached the session. Same class as #1629 and #2317, on the return leg. The CAS that gates the sink only matched `claim_token` and `status != cancelled`, and the token survives the terminal write, so a worker's retried result POST won the CAS twice.
**Lesson**: Post-turn delivery lives in one helper, `chat_execution_service.run_post_turn_delivery`, and the queued request is rebuilt in one function, `backlog_service.request_from_metadata`. A new terminal sink calls both and adds no third copy. An activity the producer opens (collaboration, self-task) is closed by the single close owner, `activity_service.close_execution_activity`, reading its id from `backlog_metadata`, so every terminal writer closes it. A token-gated SUCCESS write excludes rows already SUCCESS or SKIPPED. Without that, any sink step that is not idempotent (chat messages, events, reports) runs once per retry.
