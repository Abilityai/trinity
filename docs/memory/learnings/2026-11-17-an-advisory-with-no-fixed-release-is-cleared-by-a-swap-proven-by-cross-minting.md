## 2026-11-17 — pattern — State reachability before priority; an unfixed advisory is cleared by a swap; prove the swap with fixtures minted by the OLD version
**Context**: python-jose (abilityai/trinity-enterprise#1124). The backend image pinned 3.3.0; OSV showed 7 entries, and the newest release (3.5.0) still showed 2 with no fixed version, so a bump could never clear the scanner. Three things were true that the issue text did not say. (1) The entries double-count: at 3.5.0 the two ids are one vulnerability (CVE-2024-33663, HMAC algorithm confusion when a DER-encoded *public key* is the verifier's key), and at 3.3.0 the seven are three. (2) It was never reachable in Trinity — every `jwt.decode` pins `algorithms=["HS256"]` and the key is a shared hex secret (`config.py`), both preconditions of the class fail — so the work was hygiene, not a hotfix, which decides the release train. (3) Dependabot could not have helped: `.github/dependabot.yml`'s pip entry watches `/src/backend`, which has no manifest; every backend pin is inline in `docker/backend/Dockerfile`, invisible to it, and a Dockerfile comment claiming otherwise had gone unchallenged. The swap itself (PyJWT 2.14.0 was already in the image) was five files; the risk was the proof: 35 unit files minted AND verified with python-jose, so no test could see a byte divergence between the old minter and the new verifier — the one failure that logs every person out on upgrade (7-day tokens). Probing the two installed libraries also found what no changelog states: PyJWT refuses `exp == now` and a future `iat`; a `None` token is a `DecodeError` where python-jose raised a bare `AttributeError` that no `except JWTError` caught; `InvalidKeyError` is a `PyJWTError` but not an `InvalidTokenError`.
**Lesson**: Before pricing an advisory, dedupe OSV by alias and check the exploit's preconditions against the call sites — a CVSS 9.1 with an unreachable precondition is hygiene, and saying so in the plan is what decides hotfix-vs-release. When the advisory has no fixed version, plan the library swap, not the bump. Prove a token/serialisation swap with (a) fixtures minted once by the OLD library at the IMAGE's exact version and decoded through the new code's own helpers — never a live import of the old library in tests (a floor runs the wrong version, and `importorskip` turns the proof into a silent skip the day the pin drops), (b) a byte-identity check of the new library against one such fixture, and (c) a bad-input matrix (expired, wrong key, malformed, empty, `None`, `alg=none`, a sibling algorithm, a non-JWT bearer) at every decode site, catching the base exception class. Move the tests off the old library in the same PR and add an AST guard over `src/` and `tests/`, or the pin can never be dropped. Pins that live inline in a Dockerfile have no bump channel; the durable fix is a manifest Dependabot can read.
