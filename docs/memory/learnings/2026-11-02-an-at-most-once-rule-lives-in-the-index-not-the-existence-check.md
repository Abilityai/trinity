## 2026-11-02 — pattern — "at most once per X" is a unique index over X, never a read-then-insert
**Context**: `claim_tier1_row` (#3790, abilityai/trinity-enterprise#936) checked "no Tier-1 row for this run under any model" and then inserted a row keyed `platform:tier1:<model>` on the `(evaluator, target_kind, target_id)` unique index. Two claimers under different model ids both passed the check and both inserted; the docstring said the opposite. Once the judge's model started following the agent's credential (subscription → Haiku, key → ladder), two workers resolving different models for one run became an ordinary case, not a race.
**Lesson**: an existence check before an INSERT is a cheap early answer, not a rule. State the rule as a (partial) unique index over exactly the columns the rule names — here `(target_kind, target_id) WHERE evaluator LIKE 'platform:tier1:%'`, on both migration tracks — and make the `IntegrityError` the loser's answer. If the existing unique key embeds something the rule does not (a model id, a user id), it does not enforce the rule, however close it looks; add the index that does and dedupe existing rows in the same migration.
