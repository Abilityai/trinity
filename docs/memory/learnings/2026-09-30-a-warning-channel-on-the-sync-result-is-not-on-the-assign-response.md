## 2026-09-30 — pitfall — "It rides the existing warnings channel" is a claim about ONE response; trace the channel to every response it is promised on
**Context**: trinity-enterprise#672. The agreed design was that assigning a deprecated library skill "succeeds, and the existing per-skill warnings channel carries it, returned verbatim by MCP". That channel exists on the injection result (manual Sync, start path). It does not exist on the assign response: `skill_service.deliver_assigned` reduces each per-skill result to `{status, error?}`, and two of its outcomes (`pending_start`, `docker_unavailable`) never run an injection at all, while `in_progress` answers before one finishes. The Skills tab's per-skill warning list has the same gap one layer up — it renders `injectionResults`, which only a manual Sync from that screen fills, never a Save. Built as first planned, assigning a deprecated skill to a stopped agent, or saving on the Skills tab, would have said nothing. Same family as the #2914 entry (a warning on a surface the actor never reads), arriving through a projection instead of a missing renderer.
**Lesson**: Before relying on a channel, name each response the fact must appear on and follow it to the line that builds that response — a projection between the producer and the caller drops whatever it does not name, and an outcome that never runs the producer has nothing to project. A fact about the THING being acted on (this skill is deprecated) belongs to the thing's own record, not to a run's result: read it from the record so every outcome carries it, including the ones where nothing ran. Pin it with a test on an outcome that skips the run (here: a stopped agent).
