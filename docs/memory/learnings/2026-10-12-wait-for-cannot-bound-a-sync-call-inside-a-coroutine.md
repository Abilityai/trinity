## 2026-10-12 — pitfall — `asyncio.wait_for` cannot bound a synchronous call inside the coroutine it awaits
**Context**: trinity-enterprise#837 PR 2 review. An account-creation route bounds its best-effort invite email with `asyncio.wait_for(send(...), timeout=10)` so a hung provider cannot outlast the SPA's 30 s request timeout. `services/email_service.py::send_email` is `async`, but its SMTP branch calls the synchronous `_send_smtp` (`smtplib.SMTP(...)` with no timeout) inside the coroutine: the event loop is blocked for the whole send, so the timeout cannot fire, and every other request on that worker stalls with it. The HTTP providers (`await httpx`) are bounded; SMTP is not. The test used a cancellable `asyncio.sleep`, which is exactly the case that works.
**Lesson**: a timeout around an `async def` bounds only its awaits. Before trusting one, read every branch for a blocking call (sockets, `smtplib`, `subprocess.run`, sync DB drivers) — those need `asyncio.to_thread` (and their own socket timeout) to be boundable at all. A test for the bound must block the way the real provider does (a thread-blocking fake), not with `asyncio.sleep`.
