## 2026-09-23 — pitfall — A reader that maps "could not parse" to "empty" turns a read failure into a destructive write
**Context**: trinity#2915, `services/operator_queue_service.py::_sync_agent`. A `JSONDecodeError` on the agent's `~/.trinity/operator-queue.json` set `queue_data = {"requests": []}` while `file_exists` stayed True, so the write-back — which rebuilds the file from `queue_data` plus the reconstructed responded rows — overwrote the agent's file with only those rows. A torn or half-written file (both writers were plain overwrites) therefore cost the agent every pending entry it held, and the poller logged one WARNING. The same shape existed one level up: `list_all_agents_fast()` returns `[]` when Docker is unreadable, and a sweep keyed on "not in the running list" would have marked the whole fleet unconfirmed on a daemon blip (#2196).
**Lesson**: (1) A read that fails must never produce the *empty* value of its type when that value later drives a write or a sweep — "could not read" and "read nothing" are different facts, and only one of them may feed a mutation. Represent the failure (a `None`, an `unconfirmed` state, an early return) and make every downstream writer branch on it. (2) Grep the WRITERS that consume a reader's result before softening the reader's failure path: a `try/except` that degrades to a default is safe only if nothing downstream treats that default as authoritative. (3) The tri-state pattern (`None` = could not look, `{}` = looked and found nothing) is the house answer, and a helper that collapses the two is a bug waiting for its first caller with a write behind it.
