## 2026-10-01 — pitfall — A SQLite migration test that calls the function proves nothing about the registration, and schema parity cannot see a missing one
**Context**: PR #3169 (trinity-enterprise#729). The PR added `_migrate_metric_points_restatement` and its migration test called the function directly. A mutation that deleted its `MIGRATIONS` entry left every suite green, including `test_schema_parity.py`. On a real install the result would have been an existing SQLite database that never gains `revision`, and `record_metrics` failing on every call. It was found by an independent test-quality review, not by CI.
**Lesson**: A migration's live consumer is its `MIGRATIONS` entry, not the function. The test must reach it through the registry: `migrate = dict(migrations.MIGRATIONS)["<name>"]`, run on the OLD table shape, run twice for idempotency. `test_3064` and `test_ent720` already do this. Do not count on `test_schema_parity` for this. Its checks are one-directional: `production_snapshot − schema_snapshot`, a column the migrations produce that `schema.py` lacks. A column that `schema.py` declares and no registered migration adds is invisible to it. That is exactly the shape of an unregistered `ADD COLUMN`.
