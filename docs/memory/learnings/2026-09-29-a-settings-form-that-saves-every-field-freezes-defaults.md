## 2026-09-29 — pitfall — A settings form that saves every field turns untouched defaults into stored rows, and for an env-backed key that silently ends the variable's authority

**Context**: trinity-enterprise#671. The Settings → Retention panel's Save PUT every field on every save. For a key with no `system_settings` row, the operator saw the code default, and one save of an unrelated window wrote that default as a row. From then on the row won: a later change to the code default no longer applied (the #1638 class, reached from the UI instead of from a migration). For the env-backed ops keys (`config.ENV_BACKED_OPS_KEYS`, precedence row → env → default) it was worse. The first save froze whatever the environment said into a row, and `METRICS_DAILY_POINT_CAP` was ignored from then on, while the setting's own description still read "Bootstrap via METRICS_DAILY_POINT_CAP until a value is saved here". Two independent plan reviewers found it; no test would have, because every value round-trips.
**Lesson**: A save path for tiered settings must send only what the operator changed (diff against the loaded snapshot), and must never send a field whose source is a lower tier the operator cannot see, such as env; render that field read-only instead. The unit to test is the body builder: "nothing changed → empty body" and "env-sourced + edited → omitted" are the two cases that catch it. Keep the rule in a util the view calls, since a large view cannot be mounted and a rule left inline is reviewed by eye forever. Related JS trap in the same builder: `parseInt` on a value `v-model.number` produced collapses `1e22` to `1`, so a huge typed quota saved as one point a day. Send the `Number` as typed and let the server reject it by name.
