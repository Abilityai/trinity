## 2026-11-27 — pitfall — A retired event kind fails nothing: its listeners, its docs and a second publisher keep waiting
**Context**: #4813. When scheduled runs moved to the backend's task path, their live signal became the dispatch activity (`agent_activity`, `activity_type: "chat_start"`, `details.triggered_by: "schedule"`). Nothing went red, and three things kept describing the old world for months: the scheduler still published `schedule_execution_*` on a Redis channel with no subscriber; ten docs and the `/ws/events` docstring said the backend relayed them; and `stores/executions.js` refreshed the Executions list only on `schedule_start` / `schedule_end`, which no run writes, so its live refresh was the 30 s poll. The store's own spec fed it hand-written `schedule_start` events and stayed green throughout. The issue that reported the dead publisher named the wrong replacement event too, copied from the same docs.
**Lesson**: When a path changes which event kind it emits, or stops emitting one, sweep the consumers of the old kind in the same change: `grep -rn "<kind>" src/frontend/src src/mcp-server scripts docs`. A kind with an emitter and no consumer, or a consumer and no emitter, is the finding. Read the replacement from the emitter (`activity_service.track_activity` and its callers), never from a doc or an issue. A consumer spec must be fed the payload the emitter sends today, copied from the code that builds it; a hand-written event keeps passing after the emitter is gone.
