## 2026-10-22 — pitfall — A close that each terminal writer must opt into leaks on every writer that doesn't; put it in the owner
**Context**: trinity#3651 (sixth occurrence of the #1804 class after #45, #767, #1804, #3589, #3588). #3588 added a row-derived companion close (`activity_service.close_companion_activities`) and called it from the one writer the issue named, the watchdog claim. The shared owner `close_execution_activity` kept finding companions only through `backlog_metadata`, which a direct-dispatch `/task` hop never has, so five other recovery writers (watchdog and startup `_recover_execution`, lease-reaper park, stale-slot reclaim, bulk stale sweep) still left the caller's collaboration row `started`. The #1804 parity guard stayed green throughout: it passes any function that calls *a* closer, and never asks which activities that closer reaches. A row-derived lookup by `related_execution_id` then also matched the AAuth inbound record (`aauth_inbound.record_activity`), an `agent_collaboration` row written already closed FAILED while an async task is `working`, which an authoritative close would have upgraded.
**Lesson**: (1) When a fix adds a side effect that every terminal writer owes, put it in the shared owner every writer already calls, guarded on the persisted row (terminal NOW), never as a per-writer call or opt-in flag: the guard counts calls, not coverage. (2) Before widening a lookup from "ids the producer named" to "rows sharing this foreign key", grep every producer of that row type for the key, and exclude any that writes the row for a different purpose (here `triggered_by='a2a'`).
