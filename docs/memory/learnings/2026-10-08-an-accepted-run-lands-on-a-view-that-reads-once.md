## 2026-10-08 — pitfall — A call that moves from awaited to accepted hands its landing view a record that is still running; a view that reads once shows it running forever
**Context**: trinity-enterprise#754 (the merged Skills tab, localhost eyeball). The Playbooks tab's Run used to await the run, then open the Tasks tab on a finished row. The merged tab sends `async_mode: true`, because the shared client times out at 30 s, so the Tasks tab now opens on a row that is still running. `TasksPanel` read its rows once on mount, and its 5 s poll refreshed only the queue chip, so the row said "running" until Refresh. Every unit test was green: the Run tests stopped at "it navigated with the execution id", one hop before the view that shows it.
**Lesson**: When a trigger switches from awaiting a result to accepting it (`async_mode`, a 202, a backlog), the change is not finished at the call site. Every view the trigger lands on must keep the record current until it settles: poll while it is non-terminal, or subscribe. Then check its one-shot behaviours. Expanding and scrolling to a highlighted row has to happen once, not on every refresh. A details cache filled while the record ran has to be dropped when its status flips. A local placeholder row must not be listed twice beside the server's copy. Test the landing view mounted, with fake timers: land on a running record, advance the poll, settle it, and assert the row and its details changed and the extra reads stopped.
