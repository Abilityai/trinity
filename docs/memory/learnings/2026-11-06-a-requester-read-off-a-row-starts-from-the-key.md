## 2026-11-06 — pitfall — A requester rebuilt from what producers stamp inherits every producer's stamping quirk; start from the credential
**Context**: abilityai/trinity-enterprise#925. The ent#662 peer check decided "is this a peer?" from `source_agent_name` at the `execute_task` backstop (`requester_for_dispatch`), while the `/chat`/`/task` seams used `current_user.agent_name or X-Source-Agent`. Two producers stamp differently: fan-out writes the TARGET as its own source when the caller sent no `X-Source-Agent` (`routers/fan_out.py`, `fan_out_service.py` `source_agent_name or agent_name`), and A2A records no source agent at all. So an agent key fanning out or calling A2A without the header read as "the callee itself" or "a person", and a request naming `/pay-invoice` went through, while every test of the rule passed — each one built its requester by hand. Both independent plan reviewers found it; the code had no failing test. The in-container check, which reads the same row, would have inherited the hole.
**Lesson**: When a policy needs "who made this request" and the answer is reassembled from columns producers write, do not trust the column a producer chooses to fill. Prefer the credential that authenticated the request (`source_mcp_key_id` → the key's agent when the key is agent-scoped), which every authenticated producer records the same way, and fall back to the stamped value only where there is no key (event loopback, pull replays). Test it per producer row shape (fan-out-without-header, A2A, self-task, person key), not with a hand-built requester — a hand-built object proves the predicate, never what the producers wrote.
