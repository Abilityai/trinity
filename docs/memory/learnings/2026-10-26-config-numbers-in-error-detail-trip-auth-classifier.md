## 2026-10-26 — pitfall — A configurable number in an agent error detail is an input to the auth classifier
**Context**: trinity#2328 (slice S2), `headless_executor._finalize_headless_result`. The first draft of the per-task turn-limit 422 said "below the agent's guardrail of {G}". The backend substring-matches every task error detail against `failure_classifier.AUTH_INDICATORS`, which holds bare `"401"` and `"403"`, and `max_turns_task` is owner-set in 1–500 — so an owner who picked 401 or 403 would have turned every per-task turn-limit failure into a SUB-003 subscription rotation plus a retry of a turn that legitimately hit its cap. Every test with the usual guardrail (50, 200) stayed green.
**Lesson**: Before putting any value into an agent-side `HTTPException.detail` (or any text that reaches `is_auth_failure`), ask whether its domain can contain 401 or 403: owner-configured numbers, counts, ports and ids all can. Leave the value out (name the setting instead), or put it where the classifier does not read; and pin it with a test parametrized over 401 and 403 that runs the real backend `is_auth_failure` on the real detail (`test_2328_turn_cap_tighten_only.py::test_the_per_task_422_is_not_read_as_an_auth_failure`). Same class as the hex-UUID trip in the #1849 entry; word-boundary anchoring of the indicators would retire it for good.
