## 2026-09-25 — pitfall — A transport test cannot prove a tool filters its own arguments: the framework drops unknown keys first

**Context**: trinity-enterprise#611 PR B, the `ask_operator` MCP tool (`src/mcp-server/src/tools/operator_queue.ts`). The tool forwards only its schema's declared fields to `POST /api/agents/{name}/operator-queue`, so an `agent_name` smuggled into the arguments can never reach the backend. The real-transport test (`access-wiring.test.ts`) sends exactly that and asserts that the stub backend never sees it, and it passed. A mutation that forwarded the raw `params` also passed both suites: FastMCP parses the arguments through the tool's zod object before `execute()` runs, and zod strips undeclared keys, so the transport test was vacuous for the tool's own filter.
**Lesson**: When a tool narrows or filters its own input, pin that at the unit level by calling `execute()` directly with stray keys, because that is the only place the filter is the last line of defence. A transport test proves the whole stack and cannot tell which layer did the work. Keep the tool's filter anyway: it holds if the framework's parsing changes, or if another caller reaches `execute()`. Mutate the call site to find out which test actually bites.
