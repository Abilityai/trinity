## 2026-11-05 — pitfall — a client-side resolver whose only input is "did the server send key K" is dead when nothing sends K
**Context**: ent#1102. `src/mcp-server/src/tools/chat.ts::resolveWake` decided the receipt's `wake` field from `policyEnabled`, fed by `"wake_on_ending" in answer` — a key no backend path emitted. 27 TypeScript tests passed because every one of them handed `policyEnabled` in directly, so the resolver's live input was never exercised. Meanwhile the delegation contract shipped to every agent said *"the receipt's `wake` field says who brings you the ending"* and the unconditional `set_reminder` guidance had been removed, so the half-wired feature actively mis-taught: the backend wake fired, unannounced.
**Lesson**: When a pure helper's real input is a server field, the PR must include the emitter AND one test that drives the live call path — a resolver test that supplies the field by hand proves the branch table, never the wiring (the #2619/#3120 class). Two greps settle it before review: the key's name across the server tree, and the helper's own parameter across non-test callers. Second trap in the same class: `Boolean(answer.wake_on_ending)` over an object payload — `{effective: false}` is truthy, so an opt-out would have read as a promised wake. Read the inner field, never the container's truthiness.
