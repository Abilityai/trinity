## 2026-10-13 — pitfall — Refusing a key on the generic settings catch-all re-prices every scripted writer of that key, and they live outside the backend tree
**Context**: trinity-enterprise#862 PR1. The AAuth switches + issuer gained a dedicated `PUT /api/settings/aauth` and the generic `PUT/DELETE /api/settings/{key}` learned to refuse those keys (the #506 / ent#14 / ent#435 shape). Every backend test was green. `scripts/dev/aauth_prototype/demo.sh` — the two-instance harness the live acceptance step depends on — still wrote `aauth_issuer` and `aauth_prototype_enabled` through the catch-all, so it would have 422'd on first run; and because the flag it wrote had been narrowed to Flows 5–6 in the same diff, even a successful write would have turned nothing on. Found only by grepping the key names across the whole tree during `/review`.
**Lesson**: (1) Blocking a key on the catch-all is a contract change for every writer of that key, and the writers that matter are the ones the test suite never runs: `scripts/**/*.sh`, ops runbooks, the trinity-ops agent, docs that quote a `curl`. Before adding a `SETTINGS_ROUTE_KEYS`-style refusal, `grep -rn '<key>' --include='*.sh' --include='*.md' --include='*.py' .` and move each hit to the dedicated route in the same PR. (2) Narrowing what a flag governs is the same class one step removed: a writer that still flips the old flag "succeeds" and gets nothing, which is worse than a 422 — grep the flag name with the same sweep.
