## 2026-10-19 — pitfall — A read added to NavBar's mount goes out BEFORE the page's own first read, and reorders the requests every page's e2e specs pin
**Context**: #3302. NavBar gained a mount-time read of the operator-queue counts so the Ops badge is true on every page. NavBar is rendered INSIDE each view, and Vue runs a child's `onMounted` before its parent's — so on `/operations` the two count reads left before the page's `startPolling` list read. `e2e/background-refresh-invisible.spec.js` serves only the FIRST matching `/api/operator-queue` request and holds or aborts the rest, so three `@smoke` tests would have held or aborted the list read itself. The plan's "existing specs stay green" premise had been checked before the NavBar read was added; an independent review caught it from the mount order, not a run.
**Lesson**: A request added to a component that every page mounts (NavBar) is ordered ahead of that page's own mount-time requests. Defer it a tick (`nextTick` runs after the parent's `onMounted`) and skip it when the page already covers it (here: `operatorQueueStore.listLive`, set by the page's `startPolling`). Re-check request-order premises against the e2e helpers (`routeFirstThenHold` / `routeFirstThenAbort`) after any change that adds a request on mount, and pin the order with a unit mount of a parent that renders the real NavBar.
