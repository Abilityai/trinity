## 2026-10-19 — pitfall — Coalescing reads ("one at a time, plus one trailing") turns one request that never settles into a frozen surface; it is only safe over a bounded transport
**Context**: #3302 review. The Operations store's `fetchItems` became single-flight with one trailing rerun (so a WebSocket trigger every 5 s on every tab could not stack multi-request reads). Its reads went through the raw global `axios`, which carries no timeout (`utils/boundedHttp.js` says so: #2446). One request that never settled would have held `running` forever: the 10 s poll, every WS refresh, Retry, the refetch after a 409 and the bulk-cancel refetch all chained onto it, `loading` stayed true (Refresh spinning and disabled) and Clear All's `clearing` never reset — where the old uncoalesced code simply recovered on the next poll. The fleet grid's new "join the read in flight" had the same shape. Every unit test was green, because a mocked `axios.get` always settles.
**Lesson**: Adding single-flight, a join, or any "wait for the read in flight" to a reader moves the cost of a hung request from ONE call to EVERY later call. Before coalescing, make each request bounded — `utils/boundedHttp.js::http` (30 s, same global interceptor) or the `api.js` instance — and pin it with a test that the config reaching the transport carries the timeout (a mock cannot hang, so assert the bound, not the hang). Same class as #2446's per-control in-flight guards: a guard is only as live as the request it waits on.
