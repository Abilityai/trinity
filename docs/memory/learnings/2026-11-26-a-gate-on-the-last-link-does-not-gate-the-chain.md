## 2026-11-26 — pitfall — A visibility check on the last link does not gate a value computed over the whole chain
**Context**: trinity-enterprise#1367, `client_portal/asks/service.py::_project`. A re-raised alert carries `first_raised_at` and `raise_count`, both computed over every copy in its `replaces` chain. The first draft showed them to a Workspace viewer only when the ask it directly replaced was visible to that viewer, reusing the #3247 link rule. That hid the history on the first copy a new addressee received and showed all of it on the next repeat, because by then the direct predecessor was theirs. One unit test covered one hop and passed; an independent review found the second hop.
**Lesson**: Before reusing a per-row visibility rule, ask what the guarded value is computed over. A count, a first date or any other aggregate over a chain or a set needs a rule stated over the same chain or set: either the value is safe for everyone the row reaches (decide that and say it), or it is recomputed per viewer. Test the rule at two hops, with the audience changing in the middle; a single-hop test cannot tell the two apart.
