## 2026-10-27 — pitfall — A claim taken before its row exists must hand its id to the row insert
**Context**: #3989 (PR #4004). `/chat` admission minted a uuid and acquired the Redis capacity slot under it; `prepare_chat_execution` then let `create_task_execution` mint a second id for the `schedule_executions` row. Canary S-01 flagged every running chat turn and slot views named an id that resolved to nothing. Every path that finds a slot by the row id missed the chat slot: terminate's per-execution release, the watchdog's release after its CAS, #2433's slot renewal for a parked agent call, and the slot-TTL reaper. The boot-time orphan-slot sweep (`_reconcile_orphaned_slots`, run only from startup recovery) found no row for a live chat slot held by another process and reclaimed it. A unit test asserted the two ids differ (ent#752) and stayed green throughout.
**Lesson**: When any claim (slot, lease, idempotency key, gate record) is taken before the durable row exists, mint the id once and pass it to the row insert (`create_task_execution(execution_id=...)` exists for this). Two ids for one unit of work break every reconciler that joins the stores: canary invariants, orphan sweeps, and audit trails. Before writing a test that pins two ids as different, find a consumer that needs them different; if there is none, the test is pinning the bug.
