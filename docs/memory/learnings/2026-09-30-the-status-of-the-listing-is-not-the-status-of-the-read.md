## 2026-09-30 — pitfall — A status field that describes the first step of a two-step read says "read" when every second step failed
**Context**: trinity-enterprise#676, `client_portal/role_card.py::objectives_error`. The objective join lists `<canon>/objectives/` and then reads each file. `source.objectives_dir` records the LISTING (`read` / `absent` / `unreadable` / `timeout`); a file that fails to read becomes an `objective_unreadable` finding and the read carries on. The first draft of the card's "why are there no objectives" mapping looked only at `objectives_dir`, so a directory that listed fine and whose every file then failed mapped to "nothing wrong" and the card rendered the same empty block as an agent with no objectives. The user had ruled that a failed read must say so. Both plan reviewers caught it; the author, who had read the join end to end, did not.
**Lesson**: When a consumer turns a multi-step read into "empty vs failed", derive the verdict from the result of EVERY step, not from the field named after the first one. For a list-then-read fan-out that means: zero results plus any per-item failure finding (or items left unscanned by a bound) is a failed or incomplete read, never an empty. Write the mapping as a table test whose rows are produced by the reader's real failure modes (every file unreadable, every file invalid, names refused, beyond the scan bound), and keep one row for the true empty so the mapping cannot over-report either.
