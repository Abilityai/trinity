## 2026-10-02 — pitfall — A dispatch gate must read what the executor receives, not a field the caller chose to describe it
**Context**: trinity-enterprise#751 (the skill gate). The first build read a narrowed "the requester's own words" (`request_text`) at each producer instead of the dispatched message. Review found four doors through it: `/task` scanned only `user_message`, a caller-supplied field, while the agent read `message`; the Workspace dropped the quoted reply that the turn puts in front of the agent; an operator resume read the free text but not the chosen answer, though a question with no options takes any text as its answer; and a loop read its template while the approval would have run the rendered iteration. Each passed its own test, because each test supplied the narrowed field it was written against. The security audit then found a fifth: the caller's `system_prompt` on `/task` and fan-out, which is appended to the executor's own system prompt.
**Lesson**: Make the scanned text a superset of everything a requester put in front of the executor. Exclude only text the platform itself composed (frames, transcript scaffolding, the agent's own question). A field the caller supplies to describe its request is not that field's ground truth, and fail-closed applies to the input as well as to errors: an invocation quoted from history is held, because the gate cannot tell a quote from a request. Test each producer through its real composition with the invocation placed in the part the narrowed field leaves out (`message` vs `user_message`, the quote, the option). A test that supplies only the field it already reads cannot fail. The gate's requester attribution had the same defect: tests passed `schedule_context.schedule_id`, which `/api/internal/execute-task` never sends. In production every schedule shared one budget and Run now read as "A caller". Build fixtures the way the real producer builds them (here, the scheduler's row).
