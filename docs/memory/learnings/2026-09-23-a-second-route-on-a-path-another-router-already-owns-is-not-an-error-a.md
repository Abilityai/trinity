## 2026-09-23 — pitfall — A second route on a path another router already owns is not an error, a warning or a log line: FastAPI serves the first and the new endpoint is simply dead
**Context**: trinity-enterprise#641. The seat-scoped autonomy read was declared `@router.get("/{agent_name}/autonomy")` in `routers/seat_decisions.py` — but `routers/agent_config.py` already owns `/api/agents/{name}/autonomy` (the agent-level `autonomy_enabled` toggle) and `main.py` includes it first. Both routers carry the same `prefix="/api/agents"`, so the paths are identical; FastAPI matches the first registration and the new handler is never reached. Nothing raised, nothing warned, `/docs` listed a plausible entry, every unit test passed (they called the service and read the router's source text), `tsc` was clean, and the MCP tool's own tests passed because they assert the client's outgoing URL rather than what answers it. The only thing that found it was calling the URL against the dev instance and getting the *toggle's* payload back — `{"autonomy_enabled": true, "total_schedules": 3}` where an ask-class list should have been.
**Lesson**: Invariant #4 is usually cited for static-vs-`/{param}` ordering *within* one router; the same mechanism silently eats a duplicate path *across* routers, and there it is worse, because the two declarations are in different files and no diff shows both. Before adding a route, grep the whole `routers/` tree for the path segment, not just the file being edited — and pin it with a test that walks `router.routes` for a shared `(path, method)` across the routers involved, because that is a property a source-text guard structurally cannot see. Corollary for any new endpoint: a test that reads the handler's source proves it was *written*; call it, or assert it is what the app resolves, to prove it *runs*.
