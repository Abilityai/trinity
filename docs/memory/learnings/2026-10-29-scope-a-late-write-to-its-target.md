## 2026-10-29 — pitfall — A write at the end of a long operation must be scoped to the target it was computed for
**Context**: trinity-enterprise#529 plan review. `skill_service._sync_sources_locked` admits sources on a snapshot, and `record_sync` wrote each outcome `WHERE id = ?` alone. Moving a source's ref (the new boot follow, or an admin PUT that already existed) resets `last_commit_sha` so the next sync is not compared against the old tag. A sync that was already fetching the old tag then wrote the old commit back onto the new ref, and every later sync was refused as `moved_tag`; only another retarget got the row out. Both independent plan reviewers found it, and the tests for the reset alone stayed green. The PR's `/review` then found the same shape in `update_source`, which decides "did the target change?" from a read and wrote by id: a save naming the ref it last saw, landing across the follow, put the old tag back while keeping the follow's marker and record.
**Lesson**: When one writer resets state that another writer fills in after slow work (a sync, a probe, a build), the late writer's UPDATE must also match the inputs it worked from (here `url`/`ref`/`ref_type`). When they no longer match, drop the write (a sync result) or re-read and re-decide (an edit). Test it by interleaving: run the reset inside the slow step (patch the clone's `sync` to retarget the row before it returns), then assert the next run still succeeds.
