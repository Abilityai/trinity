## 2026-09-21 — pitfall — A parameter named `trusted_*` is a CodeQL "secret" source, and a new flow into an EXISTING log line alerts on a file the PR never touched
**Context**: trinity#2936 (trinity-enterprise#549). CodeQL's sensitive-data heuristic matches identifiers containing `secret` **or `trusted`**. An unused slot parameter `trusted_execution_id` was handed to `idempotency_service.resolve_and_validate_execution`, whose two fail-open warnings print the execution id — so the PR's first push failed the `CodeQL` check with two HIGH `py/clear-text-logging-sensitive-data` alerts, both on lines of a file the diff did not contain. Nothing sensitive was logged; the alert followed the NAME through a new data flow into old code.
**Lesson**: (1) When a CodeQL alert lands in a file you did not change, look for a new FLOW into it, not a new line — and read the flagged COLUMNS: they name the variable, and that variable's new callers name the source. (2) Identifier names are inputs to the scanner. Keep `trusted`, `secret`, `password`, `token` and `credential` out of the names of values that are none of those, above all values that can reach a logger. Rename at the source rather than dismiss: a dismissal is per-alert, and the next flow re-raises it. (3) `gh api "repos/<owner>/<repo>/code-scanning/alerts?ref=refs/pull/<N>/merge&state=open"` lists a PR's alerts with rule, path, line and columns.
