## 2026-10-22 — pitfall — A one-line rule or a per-line neutraliser built on `"\n"` leaves eight other line breaks a model reads as new lines
**Context**: trinity-enterprise#419. The seat-decision grammar's "one line" rule was `"\n" in value`, so a field with `\r`, NEL (`\x85`) or U+2028 passed. The field renders inside one bullet of the prompt's decisions block, and the break started a top-level line of its own. The memory envelope's first draft margined lines with `split("\n")`, which has the same hole: `\r`, `\v`, `\f`, `\x1c`–`\x1e`, `\x85`, U+2028 and U+2029 all stay inside one "margined" line. Verified by execution in review.
**Lesson**: wherever untrusted text enters a prompt line by line (a margin, a one-line field, a per-line prefix), split with `str.splitlines()` and test the rule with each terminator, not only `\n`. A model (and `str.splitlines`) treats them all as line breaks, even though a `\n` check does not. Pair it with a property test asserting that no stored character can produce a line without the prefix, and run it on the rendered block, not the helper (2026-09-08 entry).
