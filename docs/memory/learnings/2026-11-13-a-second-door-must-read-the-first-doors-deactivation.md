## 2026-11-13 — pitfall — a door that identifies a person by something other than the account must read the account's deactivation itself
**Context**: trinity-enterprise#1258. `users.suspended_at` (#995) is enforced where a request resolves to a `users` row: `get_current_user`, the socket doors. The Workspace's email-code door mints a portal session, which carries a verified email and no account, and it decided admission on "is an agent shared with this address" and "would `/login` admit it". Neither reads the column. A suspended account whose email held a share got a code, a session and agent turns, while `/login` refused the same person; a session minted before the suspension also kept working.
**Lesson**: Deactivation is a property of the account, so it reaches only the doors that load the account. Any door keyed by another identifier (an email, a channel identity, a link token) has to look the account up and apply the rule, at mint AND on each request, because its token outlives the decision. When adding such a door, or a deactivation-like state, list every credential kind and ask where each one re-reads account state. Put the per-request check in the one function every consumer of that credential already calls, and pin the consumer set with a test so a new consumer cannot skip it.
