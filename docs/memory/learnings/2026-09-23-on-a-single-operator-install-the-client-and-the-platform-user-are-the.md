## 2026-09-23 — pitfall — On a single-operator install the "client" and the "platform user" are the same human, so a rating written under one prefix is invisible to a query keyed on the other
**Context**: trinity-enterprise#641's demotion input — a negative rating in the last 30 days. Ratings land in `evaluations` with the evaluator namespaced by surface: `workspace:<email>` from the client portal, `operator:<email>` from the platform UI. Keying the query on `workspace:` alone (the seat surface, the obviously correct one) means that on every install where the seat person is also a Trinity user — i.e. the common case in this product — their thumbs-down is filed under `operator:` and the class can never demote. Two adjacent shapes bit the same query: reading `created_at` misses a rating flipped from up to down (only `updated_at` moves, and that flip IS the demotion), and windowing on "since the oldest surviving record" instead of a fixed 30 days lets a blocking rating fall out of scope as records expire — promotion by the clock.
**Lesson**: When an identity is namespaced by *surface*, a query keyed on one prefix is a query about a surface, not about a person. Match every prefix the same human can arrive through, and say in the test which install shape each one represents. Two corollaries for any "recent negative signal" gate: order by `COALESCE(updated_at, created_at)` so a revision counts as an event, and define the window as a fixed span — a window derived from the data being gated lets the gate open by attrition.
