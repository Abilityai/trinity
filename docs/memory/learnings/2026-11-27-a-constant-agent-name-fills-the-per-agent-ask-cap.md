## 2026-11-27 — pitfall — A unit module that raises asks for one constant agent fills that agent's 25-pending cap in the per-process database, and fails only under a shuffled order
**Context**: #4620, `tests/unit/test_ent1109_credential_handover.py`; fixed once before in `tests/unit/test_ent1158_instance_destination.py::_end_pending_asks` (#4401). The unit database is one SQLite file per process and its rows outlive the test. `raise_ask` refuses an agent's 26th pending ask (`OPERATOR_QUEUE_MAX_PENDING_PER_AGENT`); a direct `create_operator_queue_item` insert is not refused but counts toward the cap. File order passed; two of the three nightly seeds failed four tests each, a different four on each.
**Lesson**: Over the real database, give each test its own agent name (a uuid suffix, as `test_ent747_748_ask_discuss_dismiss.py` does), or end that agent's rows in the fixture every test goes through. A per-agent cap is shared state even when every request id is unique. The per-PR seed (12345) did not show it: run a new or changed module on all three nightly seeds (12345, 67890, 99999) before merging.
