## 2026-11-06 — pattern — A restriction keyed on a run must not copy the liveness rule of a clearance keyed on the same run
**Context**: abilityai/trinity-enterprise#925, `POST /api/skill-gate/check`. The gate's clearance (`_cleared_skills`) honours a run only while its row is live (`running`/`queued`/`pending_retry`), and treats an unknown id, another agent's run and a finished run alike — right for an UNLOCK, since a finished run's id must not keep unlocking a skill. The first plan mirrored that for the peer rule, a RESTRICTION: "finished → no requester → allowed". That is the fail-open direction: a peer's turn that outlives its row (the reaper marked it failed while it still runs, a background child) would load the restricted skill. Caught by the independent engineering review, switched by the owner.
**Lesson**: Before copying a guard's row-selection rule to a new check on the same row, ask which way the new check fails. A clearance must expire with the run (stale = deny); a restriction must outlive it (stale = still restricted). Keep only the part of the rule that protects against enumeration — the row must be this agent's, and an unknown id and another agent's run answer alike — which costs nothing when only the agent itself can ask.
