## 2026-11-03 — pattern — A new control over existing enforcement stores the CHOICE beside the enforced fields, derives it for old rows, and says "not applied" instead of migrating
**Context**: trinity-enterprise#341 (tool-access profiles). The plan's first draft resolved the profile on read and expanded it into the container env: every agent already in read-only mode would have read as Strict read-only, gained the send block in its env, failed `check_guardrails_env_matches`, and been recreated at its next start — including a start of an already-running agent (the ensure-running path), which kills a live run. Both independent plan reviewers caught it. The shipped shape keeps `disallowed_tools` and the read-only columns as exactly what is enforced (so every env/drift reader is unchanged), records the owner's choice in a separate key, derives the choice for rows that have none, and reports `applied: false` when the enforced fields differ from the choice's bundle — with an Apply action.
**Lesson**: when a new UI concept sits on top of fields the runtime already enforces, (1) never change what an untouched row enforces — derive the new concept from it, and write nothing on upgrade; (2) store the enforced fields materialized, not computed at injection time, so a later change to the concept's definition (a bundle gaining a tool) also shows "not applied" rather than silently recreating every container on that definition; (3) when a derived reading and the enforced state cannot both be true (a legacy read-only agent is not "Strict" because it still sends), surface the gap with an explicit apply, never by labelling it the stronger thing.
