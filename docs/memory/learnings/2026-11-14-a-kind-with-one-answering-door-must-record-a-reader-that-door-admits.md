## 2026-11-14 — pitfall — a kind with ONE answering door must record a reader that door admits, checked with the door's own rule
**Context**: #4579, the second occurrence of the #4501 class three days later. A `credential` ask can be answered only through the Workspace secret field (`ask_service.answer` refuses everything else), and that field opens for the ask's single reader only when the agent is on their Workspace roster. The raise resolved `primary` with no reach check, so a seated primary the agent was not shared with became the only reader of an ask nobody could fill, with `201 resolved: true` and no expiry. #4501 had fixed the same shape for `approver` and left this one out as "not fenced" — true of the answer fence, false of the kind: one door is a fence. Reusing #4501's predicate would have been wrong too: `can_open_agent` counts an admin's access to any agent because an approval can be decided in Operations, and a credential cannot, so an admin seated as primary would still have been recorded.
**Lesson**: When an ask kind restricts HOW it can be answered, the raise must restrict WHO is recorded to the people that one door admits, and must ask the door's own rule (here `agent_on_roster`, shared or owned), not a wider "can reach the agent" predicate written for a kind with more doors. Put the rule in the shared resolver so a re-address inherits it, and test it on the real door with real rows: a roster stub that answers for every arm hides a rule that refuses every owner. When fixing one instance of "a recorded reader who cannot act", list every kind with a restricted ending and check each, instead of scoping the fix by the mechanism that restricted the first one.
