## 2026-09-25 — pitfall — A thread-barrier race test can pass without the lock it guards: hold one worker inside the critical section

**Context**: trinity-enterprise#611 PR B, `db/operator_queue.py::create_native_item`, which runs the replay check, the depth count and the insert under a per-agent lock. The first race test released 6–8 threads through a `threading.Barrier` at the cap. With PostgreSQL's `pg_advisory_xact_lock` removed, it still passed 3 runs out of 3: each thread opened a pool connection first, and connection setup serialized the threads before any of them reached the count. With SQLite's `BEGIN IMMEDIATE` removed, it failed only 1 run in 3. The test could not reliably lose the race it existed to catch.
**Lesson**: A concurrency test has to hold one worker INSIDE the critical section — after the read the decision depends on, before the write — so the other workers are sure to arrive while it holds. Here that meant wrapping the module-level `make_insert` in a 0.15 s sleep. With the lock, the others wait and then read the committed state; without it, they all read the same stale state on every run. Prove it with a mutation (remove the lock) and require a red result on every repeat, on every backend the lock has a branch for. The `requires_postgres` marker with the `db_backend` harness puts the PostgreSQL branch into CI.
