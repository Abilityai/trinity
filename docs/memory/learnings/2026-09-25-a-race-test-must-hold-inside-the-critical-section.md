## 2026-09-25 — pitfall — A thread-barrier race test can pass without the lock it guards: hold one worker inside the critical section

**Context**: trinity-enterprise#611 PR B, `db/operator_queue.py::create_native_item`, which runs the replay check, the depth count and the insert under a per-agent lock. The first race test released 6–8 threads through a `threading.Barrier` at the cap. With PostgreSQL's `pg_advisory_xact_lock` removed, it still passed 3 runs out of 3: each thread opened a pool connection first, and connection setup serialized the threads before any of them reached the count. With SQLite's `BEGIN IMMEDIATE` removed, it failed only 1 run in 3. The test could not reliably lose the race it existed to catch.
**Lesson**: A concurrency test has to hold one worker INSIDE the critical section — after the read the decision depends on, before the write — so the other workers are sure to arrive while it holds. Here that meant wrapping the module-level `make_insert` in a 0.15 s sleep. With the lock, the others wait and then read the committed state; without it, they all read the same stale state on every run. Prove it with a mutation (remove the lock) and require a red result on every repeat, on every backend the lock has a branch for. The `requires_postgres` marker with the `db_backend` harness puts the PostgreSQL branch into CI.

**The same class, staged by hand (2026-09-28, review round).** A test for "a file entry re-using the id lands between the native replay check and the insert" first inserted the competing row from a hook on the per-agent LOCK. The lock is taken before the replay check, so the check saw the row, answered `replayed`, and the test passed without the fix it existed for. The competing write has to land AFTER the read it races: here it lands where the insert statement is built (`make_insert`), on the transaction's own connection, which reproduces the interleaving on both backends. The mutation still decides it: a staged race is only a test once removing the fix turns it red.

**And where the hold is installed (2026-09-28).** The hold was installed with `monkeypatch.setattr(dbq, "make_insert", …)` after `import db.operator_queue as dbq`. In a full-suite run a sibling test can leave a stand-in in `sys.modules["db.operator_queue"]` (and on the `db` package) that re-exports the real class. The patch then lands on the stand-in, while the real method keeps reading its own module dict, so the hold silently does not hold. The race test passed with the lock removed, and the staged-race test returned `created` on one nightly seed. Install the hold in the dict the running method reads, `Cls.method.__globals__` (the module-identity gotcha that test_1632's `_patch_engine` documents), and prove it with a stand-in installed: a pytest plugin that swaps both spellings at `pytest_collection_finish`.
