## 2026-11-25 — pitfall — A new keyword on a DB mixin method does not reach callers through the `database.py` facade
**Context**: trinity-enterprise#978. `visitor_shell_allowed` began calling `db.get_guardrails_config(agent, strict=True)` and failing closed on any exception. The mixin (`db/agent_settings/security.py`) gained `strict`; the facade method (`database.DatabaseManager.get_guardrails_config(self, agent_name)`) did not, so in production every call would have raised `TypeError`, and fail-closed would have taken the shell from every channel visitor on every agent. Every unit test was green: they passed a `MagicMock`, a test fake, or the mixin itself, none of which is the object callers hand in.
**Lesson**: Changing a DB method's signature means changing its facade delegation too, and a caller that turns an exception into a safe default must be tested through `database.DatabaseManager` (constructed with `__new__` and its `_*_ops` set), because that path is the only one where a dropped argument shows. A fail-closed `except Exception` makes a signature mismatch look like the safe state, so it hides exactly this bug.
