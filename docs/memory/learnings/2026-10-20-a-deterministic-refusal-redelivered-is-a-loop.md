## 2026-10-20 — pitfall — A consumer that re-delivers its input after a failure turns a deterministic refusal of that input into a loop
**Context**: trinity#3402, `shared_sessions/service.py::_wake_agent_locked`. A room wake moves its read cursor only on a reply, so a failed turn re-delivers its delta — right for a crash. The skill gate's hold was treated the same way: every later wake re-read the held post, raised a fresh approval for it (the occurrence key is the new wake's execution id), and once the per-requester cap filled, refused it on every wake. The agent never answered anything else in that room. A cold wake re-reads the last 30 messages whatever the cursor says, so moving the cursor alone could not fix it. The first plan ("advance the cursor on any gate verdict") would also have silently dropped whole deltas on a transient refusal (an unreadable gate map), and dropped an ordinary post that shared the held one's delta.
**Lesson**: Wherever a consumer retries by re-reading its input (a cursor, a delta, a queue claim), classify each failure: transient (re-deliver), or a verdict ON THAT INPUT (record it). Record the verdict next to the input it is about (here `room_gate_holds`: room, agent, seq), not by moving a shared cursor, which also governs input that was not the problem. Filter on the record from both the shown text and the scanned text, so nothing is shown that the gate did not read. Keep transient refusals OUT of the record by an explicit allowlist of standing codes (`STANDING_REFUSALS`), so a new refusal code re-delivers by default. Test the second and third wake, not just the first: the first is always correct.
