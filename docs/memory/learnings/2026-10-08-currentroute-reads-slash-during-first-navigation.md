## 2026-10-08 — pitfall — `router.currentRoute` reads `/` until the first navigation settles, so a boot-time "which page am I on" check judges the dashboard
**Context**: #3406. `main.js`'s 401 handler passed `router.currentRoute.value?.path || window.location.pathname` to the verdict. Until the first navigation completes, `currentRoute` is vue-router's `START_LOCATION`, whose path is `'/'`, which is truthy, so the fallback never ran. The guard holds that navigation open across `checkSetupStatus()`'s fetch, while `initializeAuth` has already fired `fetchUserProfile` and `App.vue` the ws-ticket POST. A dead token's 401 therefore landed in the window and was judged as `/`. That pushed `/chat/` and `/canvas/s/` visitors to `/login`, and silently voided #2791's Workspace veto on first load. Probed with the real router: during a pending initial push, `currentRoute.value === START_LOCATION`.
**Lesson**:
- Any decision taken outside a component about where the person is (an interceptor, an early listener, a boot hook) must treat `currentRoute.value === START_LOCATION` as "not known yet" and fall back to `window.location.pathname` (`platformSession.js::pathForVerdict`).
- A plain `||` fallback never fires, because START_LOCATION's path is `'/'`, not empty.
- Test it against a real `createMemoryHistory` router with a `beforeEach` held open, not a fake route object.
- Fixing the path re-routes every first-load 401, so audit the pages that leaned on the misjudgement. Here `/m`'s dead sessions were only ever ended because the 401 was judged as `/`; judged correctly, the auth-route `ignore` left the PWA with a dead token and a 5-second ws-ticket loop, and `/m` needed an arm of its own (#3406 review).
