## 2026-10-21 — pitfall — A "<= last id" watermark is not dedup when the sender delivers in parallel, and a per-request debounce is not a debounce under two workers
**Context**: abilityai/trinity-enterprise#934 (Telegram albums as one turn). The issue proposed an in-process asyncio timer in `TelegramWebhookTransport` to collect an album's items. Production runs `uvicorn --workers 2` (`docker-compose.prod.yml`, `docker-compose.hosted.yml`) and each album item is its own webhook POST, so an in-process buffer would split albums about half the time — invisible to single-process tests and to the local stack, which runs one `--reload` worker. Separately, `handle_webhook` deduplicated with `if update_id <= binding["last_update_id"]: skip`, read and written in two non-atomic steps. Telegram delivers over up to 40 parallel connections (`setWebhook.max_connections` default) and documents that updates "get out of order", so a slower request for update 101 read a row already saying 102 and was dropped at DEBUG — exactly the burst an album produces. Both independent plan reviewers found the dedup; the issue and the primary plan did not.
**Lesson**: (1) Before buffering, debouncing or ordering anything that arrives over HTTP, grep the deploy command for `--workers` (the #1813 rule) — the local stack is not the deployment. Cross-worker state goes in Redis, and "exactly one worker acts" can be had without a leader lease: every arrival bumps a per-group sequence and arms a timer on its own worker, and only the timer still holding the latest sequence drains (WATCH + MULTI) — see `adapters/transports/inbound_coalescer.py`. (2) A monotonic watermark is only a dedup when delivery is serial. With a parallel or out-of-order sender, claim each id (`SET key NX EX`) and keep the watermark as a fallback whose write only moves forward (`WHERE last < :id`). (3) When a feature makes a sender emit bursts, re-read the code that sits in front of it — the dedup, the rate limits — for assumptions that only held while traffic was sparse.
