## 2026-10-05 — pattern — An alert is a condition, not a message: dedup on the subject, not the id
**Context**: #3246. Every platform emitter minted a `request_id` per reading (a timestamp, a reset day, a tier) and relied on `UNIQUE(agent_name, request_id)` ON CONFLICT DO NOTHING for dedup. That made the id the state machine: a persisting condition filed a new row whenever the id rolled over, the same condition read by two workers became two rows, and a condition that cleared left its rows pending until a person acknowledged them — no emitter knew which row was "its" row to end.
**Lesson**: Key an alert on the thing it is ABOUT (`<kind>:<key>`), enforce "at most one pending per subject" in the database (a partial unique index that every terminal transition releases), update that row in place on each reading (`last_seen_at`, a seen count), and give the emitter a `clear` it calls where the code knows the condition ended — recorded as the platform's ending, never a person's answer or a timeout. Pair it with a lifetime (no hook is perfect) and a snooze (a person's dismissal must hold). When migrating emitters in batches, a ratchet listing the not-yet-migrated prefixes keeps "the rest follow" honest.
