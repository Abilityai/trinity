## 2026-09-28 — pitfall — Under `set -e`, `probe && echo OK` is a print, not a gate

**Context**: trinity#2995. `deploy-dev.yml`'s `=== Health ===` section ran `curl -sf http://localhost:8000/health && echo "Backend: OK"` under `set -e`. A failing probe skipped the `echo` and the script carried on, so the run went green and the #2204 `notify-failure` incident was never filed. The same shape was carried into #2986's `deploy-prod-nightly.yml`.
**Lesson**: `set -e` never aborts on a command on the left of `&&`/`||`, in an `if`/`while` condition, or (without `pipefail`) in a non-final pipeline stage — so a check has to end in an explicit `echo "::error::…"; exit 1`, written as a bounded poll with a per-probe `--max-time` (`/health` can stall past 10 s under GIL contention, #1230). Do NOT reach for script-wide `pipefail` instead: in a script that does `printf '%s\n' "$BIG" | grep -q …`, `grep -q` exits on its first match and the writer takes SIGPIPE, so past the 64 KB pipe buffer the pipeline returns 141 and a passing check reads red (0/20 at 30 KB, 20/20 at 70 KB); in bash, `grep -q … <<<"$VAR"` is the pipefail-safe form (`<<<` is bash-only, not POSIX sh). And before writing triage text, know which layer actually catches the failure: `docker compose up -d` already blocks on `depends_on: condition: service_healthy`, so a never-healthy backend fails at `Restart`, and the post-deploy probe only catches "Docker-healthy, then not answering on the host port".
