## 2026-10-12 — pitfall — a native `<select>` behind a confirm keeps the value the model never took
**Context**: trinity-enterprise#837 PR 2, `AccessPanel.vue`'s platform-role select (`BaseSelect` renders `<select :value="modelValue">`). The admin picks a role, a ConfirmDialog opens, they press Cancel or Esc — or the PUT is refused. The model (`op.role`) never changed, so Vue never re-patches `el.value`, and the row goes on showing a role the person does not have. On Windows a focused closed select also fires `change` on every arrow key, so an unconfirmed select is one keystroke from a write.
**Lesson**: bind a confirm-before-change select to a draft (`pending?.key === row.key ? pending.value : row.value`), set the draft on change, and clear it on cancel, Esc and refusal — the binding then CHANGES back and Vue resets the DOM. Confirm every change on a select whose write is a grant (the dialog taking focus also ends the keyboard cascade), and assert the select's `element.value` after a cancel and after a refused write in a mounted spec — a test of the model alone passes the bug.
