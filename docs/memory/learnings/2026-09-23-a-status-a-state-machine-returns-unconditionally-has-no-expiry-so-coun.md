## 2026-09-23 — pitfall — A status a state machine returns UNCONDITIONALLY has no expiry, so counting it over "all history" turns a dial into a one-way ratchet
**Context**: trinity-enterprise#641, building the autonomy dial on #638's decision records. `effective_status` computes `expired` on read from `review_by` — but only for rows still `active`; a `reversed` row returns `reversed` forever by design (it is a terminal flip, and #638 deliberately deletes nothing). The promotion rule reads "no reversals", and the obvious implementation counts `stats().reversals`, which #638 ships as exactly this issue's input. Counted that way a single reversal in a seat's entire history blocks its ask class permanently: every other input expires and renews, this one never does, so `on_request` is the only steady state the machine can reach and the "dial" can only ever go down. Two of the rule's own tests caught it precisely because they were written as a table over time rather than over a fixture.
**Lesson**: Before feeding a status into a windowed rule, ask which of its values the producer can *leave*. A terminal status is a fact about a row, not about the window — so a window predicate must retire it on the row's own clock (`review_by` here, via `_has_lapsed`), not inherit the producer's "this never changes". The general shape: **any monotone input in a rule meant to be reversible makes the whole rule monotone**, and the symptom is not a wrong answer on day one but a system that silently stops being able to say yes months later, with every test green.
