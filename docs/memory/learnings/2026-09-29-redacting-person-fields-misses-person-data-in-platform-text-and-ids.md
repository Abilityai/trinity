## 2026-09-29 — pitfall — Withholding a row's person FIELDS misses the person data a platform alarm carries in its free text and in its id
**Context**: trinity-enterprise#715. The plan withheld `responded_by_*`, `addressed_to_email`, `disposed_by_email` and `resolved_to` from machine keys on the operator-queue reads, and its test scanned each row for `@example.com`. Independent review found two platform emitters that put a person in the TEXT of an ordinary row: the ent#499 problem report (`question` = the client's email plus their verbatim comment, which ent#366 deliberately withholds from the rated agent) and the ent#308 inbox-collision alert (`question` lists client addresses, and its `request_id` is built from an email slug). Every field-level rule, and the test's own fixture rows, passed straight over them. The collision id was also unreserved, so the file write-back, the resume wake and the Execution Context "Ended asks" line could each hand it to the agent.
**Lesson**: When a principal class must not learn who a person is, the census is the emitters, not the columns. List every writer of the table (the #1677 `_ALLOWED_CALLERS` inventory is that list for the operator queue) and ask of each: does its free text or its id carry a person? A row about a person is withheld whole, since per-field redaction cannot remove an email from prose or from an id. Its id prefix goes into `_RESERVED_ID_PREFIXES`, because that tuple is what every agent-facing sink (write-back, resume, sync exclusions, the ended-asks line) reads as "platform alarm". Drive the real emitters in the test, so a renamed id or type turns it red.
