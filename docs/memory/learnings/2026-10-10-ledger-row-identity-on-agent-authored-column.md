## 2026-10-10 — pitfall — A platform row on the shared operator_queue ledger must be identified by its reserved id prefix, never by `type`
**Context**: PR #3517 (trinity-enterprise#631, person tags). The tag door read rows by `type = 'mention'`, and the operator door hid rows by the same test, with an exception for "a caller who names the type". `type` is agent-authored: the queue file's ingest only bounds its length (#3385), and `addressed_to_email` accepts any roster email. So an agent could write `{"type": "mention", "addressed_to_email": <sharee>}` and it appeared in that person's Inbox as "Alice mentioned you", and it was also hidden from the operator. Separately, `type` is a query parameter of `GET /api/operator-queue`, so the "names the type" exception let any sharee list who tagged whom with `?type=mention`.
**Lesson**: On a table that agents write to, a row's platform identity is the half an agent cannot write. That is the `_RESERVED_ID_PREFIXES` id prefix (rejected case-insensitively at both ingest seams), combined with the type when you need it (`queue_mentions.is_tag_clause` / `is_person_tag`). A visibility exclusion has no "unless the caller asks for it" branch when the asking is a request parameter. Hide the rows unconditionally, and give the rightful reader a separate query.
