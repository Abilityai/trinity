## 2026-09-23 — pitfall — Override the dependency the route captured, not the one you just imported
**Context**: `tests/unit/test_2915_operator_queue_sync_honesty.py::TestRefusal` (PR #2989) — green in isolation and in the author's full run, red under CI seed 12345 with `401 Not authenticated` from a TestClient app whose override table carried `get_current_user`.
**Lesson**: `app.dependency_overrides` is keyed by object identity. A route holds the callable it captured when its module was imported; `from dependencies import get_current_user` in a test returns whatever that name is bound to *now*. Under a seeded full-suite order an earlier module can stub or re-import `dependencies` (the `sys.modules` class the pollution lint exists for), so the two are different objects, the override is silently ignored, and the real auth runs. A harness that reaches a dependency through a fresh import is a test of import order, not of the route. Key the override off the callables found by walking the router's dependant tree (`route.dependant.dependencies[*].call`, recursively) and assert the walk found one, so a route-shape change fails loudly instead of answering 401.
