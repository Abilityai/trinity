## 2026-11-01 — pitfall — Trimming a tool description to fit the cap can drop the sentence that was doing the work
**Context**: #4121 (PR #4155). Adding two refusal codes pushed `write_user_memory`'s description past Claude Code's 2,048-character cap, and the trim took the clause saying shared memory "would leak one user's data to everyone else". The budget test went green and no test pinned that text. The eyeball on that build then saw an agent say "Saved" and write to shared auto-memory (#4156). Whether the trim played a part is unknown, and nothing would have told us: a `/review` of the author's own diff read the cut as tidying until it was held against that failure.
**Lesson**: Treat a tool description under budget pressure as safety text, not prose. Before cutting, name the sentence that exists to stop a known failure, take the cut from examples and phrasing instead, and pin that sentence with a test so a later trim fails loudly. When an eyeball shows a behaviour bug on a build, check what the branch changed in the text the model reads before writing "this change did not cause it".
