## 2026-10-13 — pitfall — an agent-supplied timestamp is bounded on BOTH ends at the write

**Context**: #3629 (the #3589 fix) threaded the producer's terminal instant — the agent-authored `retained_at`, or the #1083 callback's `completed_at` — into the `completed_at` column. `terminal_completed_at` clamped only the future; a past value was written verbatim. Retention hard-DELETEs executions on `completed_at < cutoff`, so a backdated value let an agent age its own row into the next sweep — a self-erasing audit trail. Found by independent validation of #3629; fixed by the trinity-enterprise#882 floor.

**Lesson**: when a write accepts a producer-controlled instant, clamp it to the full trusted window at the WRITE — `[server-written start, now]` — not just the end that breaks billing. Ask what every *reader* of the column does with an out-of-window value: retention reads `completed_at` directly, so guarding only the derived `duration_ms` (the #1832 `max(0, …)`) protects analytics while leaving the deletion predicate exposed. The bound lives in the shared helper as a REQUIRED keyword-only parameter (`floor=`), so a future third writer must decide rather than silently skip — the `_apply_git_env_from_db` per-call-site-gate pattern.
