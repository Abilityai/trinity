## 2026-10-26 — pitfall — A canary grace counted from `started_at` starts before the event it waits for
**Context**: S-01 `in_sql_only` false positives on healthy cron runs (#3952). The scheduler writes the row `running` before `/api/internal/execute-task` runs the skill-gate backstop and admission, so the ZADD (push) or RUNNING→QUEUED (pull) lands seconds after `started_at` — 7.4 s observed against a 3 s grace.
**Lesson**: Before choosing a grace, find what writes the timestamp it counts from and what has to happen after it. When the timestamp is stamped before a network call, the window is that call's latency and has no fixed bound. Give the slow side its own grace, derive the value, and pin it below the canary cycle (300 s). Do not exempt a whole row class to cover the gap: on a pull pilot, an exemption keyed on `pull_owns_dispatch` also hid the enqueue-failed stuck row from S-01 until E-01 fired, about 65 min later.
