## 2026-10-05 — pitfall — An alarm must not count toward the limit it reports on
**Context**: trinity#3130, `services/operator_queue_service.py::_maybe_emit_flood_alert`. The #1632 flood alarm was a platform row filed against the agent whose pending depth tripped it, and `count_pending_for_agent` counted every pending row. Each alarm raised the number it warned about, so once an agent reached the cap the condition could not clear, and the cooldown re-armed a fresh `queue-flood-{agent}-{timestamp}` row every 300 s: 386 of one agent's 435 rows were the alarm. The native `ask_operator` cap read the same predicate, so the alarm backlog also refused the agent's real asks with `queue_full`. Same growth shape as #2744 (timestamped id + a branch that repeats every cycle).
**Lesson**: (1) When a guard emits into the store it measures, exclude its own output from the measurement — by a marker the producer cannot forge (here the reserved id prefixes, the SQL twin of `is_platform_minted`), applied in ONE shared predicate every reader of that budget uses (`db/operator_queue.py::_own_pending_conds`). (2) "One alert per episode" needs an episode END condition in code; a cooldown alone is "one alert per window, forever". Test it by running the condition across many windows (advance the clock past the cooldown every cycle) and asserting one alert. (3) Routing through `create_bounded_alert` bounds the alarm's own rows, but its at-budget `alert-budget-` episode alert is itself cooldown-windowed — the budget is a backstop, not the edge trigger.
