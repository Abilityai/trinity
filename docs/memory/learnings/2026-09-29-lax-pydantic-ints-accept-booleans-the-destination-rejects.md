## 2026-09-29 — pitfall — A write-through model in pydantic's lax mode accepts values the destination's validator rejects: `true` becomes `1`

**Context**: the trinity-enterprise#671 review. A managed endpoint validated `metrics_daily_point_cap: Optional[int] = Field(None, ge=0, le=10_000_000)` and wrote the value through to the ops setting that OSS `config.validate_ops_setting` guards. Pydantic v2's lax mode parses a JSON `true` as `1` and `false` as `0`. For this key, which is never clamped, that meant a one-point-a-day quota or an unlimited one, while the OSS validator for the same key rejects both. The bounds parity test (model `ge`/`le` equal to the OSS table) was green, because the bounds matched and the *type* rule did not. The other window fields got away with it only because the floor clamp turns `1` into `5`.
**Lesson**: When a model writes through to a store whose own validator is the contract, bounds parity is not enough. Pin the type rule too: set `strict=True` on the fields (JSON integers still pass), and test a boolean and a numeric string at the model and through the real route. The instance of the 2026-07-31 "a cross-store write-through must honor the DESTINATION store's data contract" class to look for is a coercion the source allows and the destination refuses, not only a range.
