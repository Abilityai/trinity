## 2026-11-04 — pitfall — Rich parses `[...]` in every plain-string cell, so server text in a CLI table can crash the command
**Context**: trinity-enterprise#736, `src/cli/trinity_cli/output.py`. `_print_table` / `_print_dict` passed `str(value)` to `Table.add_row`, and Rich treats a plain string as console markup. A library author's `description` or `superseded-by` containing `[/]` raised `MarkupError: closing tag '[/]' at position 0 has nothing to close`, so `trinity skills list` failed for every user of that library. `[red]x[/red]` restyled the cell and `[link=…]` emitted a terminal hyperlink. Found while adding the `deprecated` column, the second author-text cell; the description column had the same exposure since the CLI shipped. The CLI's tests never caught it: the backend unit job installs neither `click` nor `rich`, so the only executable tests skip there.
**Lesson**: Any string a Rich renderer receives from the server (names, descriptions, author text, error messages) goes in as `rich.text.Text(...)`, never as a plain `str`, unless the code wrote the markup itself. Fix it once in the shared printer, not per column. A Rich test needs `importorskip("click")` / `importorskip("rich")`, and that skip is silent in CI, so also move the decidable rule (which rows, which cells) into a stdlib-only module that the unit job can load by path (`trinity_cli/skill_rows.py`, the #3007 / #837 precedent).
