## 2026-10-05 — pitfall — A PR that reverses a UI rule leaves the old rule's source-text pin red
**Context**: trinity#3242, `src/frontend/tests/unit/workspaceAsks.spec.js`. #2375 pinned PortalAsks' Send button by its source text (`:disabled="… || !picks[ask.id]"`) to prove "no pick, no send". #3242 deliberately reversed that rule ("Something else" plus a typed instruction is sendable with no pick), changed the predicate to `!approvalSendable(ask)`, and ran only the new targeted specs — the old pin, outside that set, turned the full `npm run test:unit` red. The same pin had also kept a now-dead `optionsOf` import alive because it matched the exact import specifier list. Same class as trinity#2829 / #2918.
**Lesson**: (1) When a change reverses a rule, grep the WHOLE test tree (vitest, pytest, mcp-server) for the old predicate's source text before calling the branch green, and run the full unit suite, not only the specs you wrote. (2) A `.vue` predicate that gates a store write is proven by a mounted behaviour spec, not by a regex over its source; when you meet such a pin, replace it with the behaviour test rather than re-pointing it. (3) Pin the module a component imports from, never its exact specifier list — a list pin forces dead imports to stay.
