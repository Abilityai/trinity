## 2026-09-25 — pitfall — Moving a guarded call site behind a helper can blind the discovery guard while it stays green

**Context**: trinity-enterprise#611. The new ask sink (`services/ask_service.py`) built each `/ws` trigger where the ending was decided (`answer` / `cancel` / `bulk_cancel`) and broadcast it from one helper, `_announce(audit_rows, trigger)`. The ent#467 guard (`tests/unit/test_ent467_ws_agent_scope.py::_broadcast_payloads`) discovers a payload by following `*broadcast*(json.dumps(x))` back to a dict literal using only the assignments of the function the call sits in. Inside `_announce`, `trigger` is a parameter, so the resolver returned nothing and skipped the call: all three new payloads — one of them fleet-level and needing an allowlist decision — were invisible, and `test_every_ws_payload_is_agent_keyed_or_explicitly_fleet_level` passed without having looked at them.
**Lesson**: After moving a guarded call site behind a helper, check the guard's DISCOVERY output (print what it found), not just its verdict — a guard that finds nothing new passes. Build the guarded value through a named constructor at the decision site (`_broadcast_payload({...})`) so the resolver reads a literal there, and prove it bites with a mutation: remove the new allowlist entry and watch the guard name the site.
