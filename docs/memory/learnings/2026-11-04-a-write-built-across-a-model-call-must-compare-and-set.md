## 2026-11-04 — pitfall — A write built from a value read before a model call must compare-and-set, or it lands over every change made during the call
**Context**: trinity-enterprise#962. The MEM-001 summarizer reads the stored summary, awaits the model for up to 30 s, then writes the new summary. Once the owner could undo a summary write, an undo made during that wait was overwritten by a summary built from the undone text, while the history row still read "undone". A row lock or "one transaction" around the write does not help: the read happened in an earlier transaction, before the await.
**Lesson**: When a write is derived from a value read before an `await` (a model call, an HTTP round-trip, a queue hop), pass the value it was built from to the writer and make the writer compare-and-set under the row lock (`expected_previous=`). A mismatch drops the write. Do not let it merge or retry, because the derivation itself is stale. A lock only serialises writers that read inside it. Pin it with a test whose stub for the awaited call performs the competing change, driven through the real caller rather than the db function.
