## 2026-10-08 — pitfall — A response field declared on the model is still dropped by every route that builds the model field by field
**Context**: trinity-enterprise#753 added `approval` to the library contract and declared it on `SkillInfo`. `GET /skills/library` constructs `SkillInfo(name=…, …)` explicitly and never named it, so it was null over REST for every skill. trinity-enterprise#754's "author recommends approval" line on a Shared card then had no source; the review found it only by asking what fed the line. This is the third shape of the allowlist class: #2580 (`message_id`) and ent#2320 (`last_turn_outcome`) were fields a service returned that the `response_model` did not declare. Here the model declared the field, the service returned it, and the constructor between them dropped it.
**Lesson**: Adding a field to a response model is three edits, not one: the producer returns it, the model declares it, and every explicit constructor of that model names it (`grep -n "ModelName("` across `routers/` and `services/`). Prove it at the REST boundary: call the route function, not the service, and assert the field on what it returns. A model-only or service-only test passes while the route still sends null.
