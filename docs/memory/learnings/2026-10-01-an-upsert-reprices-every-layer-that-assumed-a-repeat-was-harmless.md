## 2026-10-01 — pitfall — Turning `ON CONFLICT DO NOTHING` into `DO UPDATE` changes what a repeat means in every layer above the store
**Context**: trinity-enterprise#729, `db/metric_points.py::insert_points`. A metric correction at an existing identity had to update the row instead of deduplicating. The SQL change is a few lines. The surrounding system had been built on "a repeat is harmless", and four things broke. Two independent plan reviewers found them; the tests on the old shape stayed green.
**Lesson**: Before swapping a dedup for an upsert, check each assumption the old no-op was covering.
- **Batch replay drops changes.** A batch-level idempotency key that replays the first result now swallows a revert. `A → B → A` under one key or one turn ends on `B` with `replayed: true`. Either fold the current state into the key, or state the limit and pin it with a route test.
- **Lock order matters.** `DO UPDATE` row-locks every conflicting row, even one its `WHERE` skips. Two overlapping batches can now deadlock on PostgreSQL, where `DO NOTHING` never locked a committed row. Sort the payload by the conflict key.
- **The dialects split on duplicate keys.** Two rows with one key in one statement raise a cardinality violation on PostgreSQL. SQLite applies both and reports the second as an update. Refuse that input in the store itself, not only in the validator above it.
- **The counting idiom changes.** `RETURNING` replaces `rowcount` as the count: a counter column that is 0 on insert and +1 on update gives inserted, updated and skipped in one portable statement.
- **The change predicate is easy to mistest.** A null-safe change predicate (`IS DISTINCT FROM`) over two complementary nullable columns behaves exactly like `!=` for same-type input, because the non-NULL column decides the `OR`. The test that proves null-safety must move the value from one column to the other. A mutation to `!=` survived every "status label" test until one did.
