## 2026-09-25 — pitfall — A "who may do this" rule placed on the routes you are editing misses the entry point that authenticates through a different dependency

**Context**: trinity-enterprise#611 PR A, `/cso --diff`. The ask sink (`services/ask_service.py`) became the one writer of every ending. The person-only rule went onto the three operator routes as `reject_non_person_principal`. The fourth caller, the Workspace answer (`client_portal/asks/router.py`), authenticates through `get_portal_principal`. Its #2198 policy rejects agent keys but deliberately keeps a system key's breadth. So a system key reached the sink, and the ledger recorded a machine's answer as `disposed_by='person'`. The same PR had moved the #2376 offered-option check INTO the sink precisely so that "no entry point can skip it", yet it left "who may end an ask" at the routes. This is the 4.14 "defence on one of two branches" class again.
**Lesson**: When a service becomes the one writer, list its callers (grep for the sink's entry points). For each caller, name the auth dependency it runs under and that dependency's scope policy. A different dependency means a different principal model: a `PortalPrincipal` is not a `User`. Then either pass the rule's input into the sink (the actor states whether it is a person), or pin every caller with a test that drives it with a non-person principal. A rule enforced on N−1 doors reads to an attacker as optional.
