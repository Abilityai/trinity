## 2026-10-13 — pitfall — A recovery-side close keyed on the applier's return conflates won and lost; derive terminal side effects from the persisted row
**Context**: trinity#3588 (fifth occurrence of the #1804 class after #45, #767, #1804, #3589). The watchdog claim (`cleanup_service._claim_retained_result`) needed to close the execution's companion activities after `apply_result`, and the obvious gate — "non-RECONCILED means my CAS won" — is false: only `apply_result`'s SUCCESS branch reports a lost CAS (`error_code=RECONCILED`); the FAILED/CANCELLED branch gates its own side effects on the CAS bool internally but returns the same `TaskExecutionResult` either way, and its own comment says so. A close keyed on that return would have stamped companions FAILED + the claim's `retained_at` under a row whose standing terminal was CANCELLED — and the #1804 close lattice (correctly) refuses to let the real canceller fix it afterwards, making the wrong state permanent. Both independent plan reviewers found the same flaw; neither the caller's comment nor the return type made the asymmetry visible at the call site.
**Lesson**: (1) When a recovery path adds side effects after calling a shared applier, do not infer "I won" from the applier's return unless the return carries the CAS outcome on EVERY branch — audit each branch, not the happy one. (2) The robust shape is to derive the side effect from the PERSISTED row: re-read it, act only when it is terminal NOW (the same guard as `_close_queued_activities`' re-queue safety), and take state (`activity_state_for_terminal(row.status)`), instant (`row.completed_at`) and details from the row. A row-derived write cannot disagree with the row, is winner-agnostic (a lost claim closes in the terminal that actually stands), and keeps timestamp agreement by construction even when the producer stamp was unreadable. (3) If a caller genuinely needs the winner bit, put `cas_won` on the result type for ALL branches — a signal only one branch reports is a trap for the next caller.
