## 2026-09-30 — pitfall — An unpinned install in the agent image ships upstream releases unreviewed

**Context**: trinity#3106 (and #3012 before it). `startup.sh` ran `pip install --upgrade` with no versions on every container start, so each boot took PyPI's latest; FastAPI 0.142 then read the standard `OTEL_*` env Trinity injects *for Claude Code*, refused the `grpc` protocol, and every OTEL-enabled agent server exited on its next restart — no Trinity commit involved, and rolling back the image did not help. #3012 was the same class one layer up (`claude-code@latest` frozen by Docker's layer cache).

**Lesson**: (1) Anything the agent image installs — at build or at boot — is pinned to an exact version in a checked-in file, and a bump is a deliberate change with a rebuild; "repair at boot" reinstalls the pins, never `--upgrade`. (2) A pin file needs a bump channel (Dependabot or equivalent), or exact pins rot silently past security fixes. (3) Environment variables with *standard* names (`OTEL_*`, `HTTP_PROXY`, `PYTHON*`) are read by every library in the container, not only the program they were set for — when injecting one for a single consumer, check what else honors it, and opt the others out explicitly. (4) A platform env var added at create does not reach existing agents: recreate replays the old `Config.Env`, so a fix that only adds env covers new and DB-recovered agents, not restarts.
