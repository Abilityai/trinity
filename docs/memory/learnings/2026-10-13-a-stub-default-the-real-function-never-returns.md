## 2026-10-13 — pitfall — A stub's default return value has to be one the real function can produce
**Context**: trinity#3545. `crud.py` decided "is this a shared catalog template?" from `bool(get_github_template(...))`. The real function builds a template for every `github:` id, so the answer was always yes and every create with a personal GitHub token came out pull-only. `tests/unit/test_1484_create_agent_characterization.py` stubbed the function to return `None` for an unlisted repo, a value production never returns for a `github:` id, so the own-repository tests granted a working branch against a state that does not exist. Two branches in `crud.py` that handle that `None` are unreachable for the same reason.
**Lesson**: (1) Before stubbing a collaborator's return value, read its return statements; a stub may only return what one of them returns. A `# dynamic` comment beside `return_value = None` is a claim about the real function and needs the same check. (2) When a caller reads truthiness as a category ("found" as "listed"), look for a fall-through that makes the value always truthy. Ask the category question with its own predicate. (3) A `MagicMock()` module makes every new name a truthy callable, so a predicate added to a mocked module needs an explicit default in the fixture, and one test that pins the argument it is called with.
