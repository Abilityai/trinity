## 2026-10-20 — pitfall — A coalesced read must settle its callers when its chain DRAINS: a trailing read queued behind an awaited one clears state the caller writes after the await
**Context**: #3302, second review of PR #3817. The Operations store's reads became "one at a time, plus one trailing rerun". `respondToItem`'s 409 path does `await fetchItems()` and then writes `error = QUEUE_RESPONSE_NOT_RECORDED`, and every read clears `error` in its prologue. A 409 means someone else just ended the ask, and that ending broadcasts, so a queue WebSocket event usually lands while the refetch is out and queues the trailing read. The awaited promise was the caller's OWN run: the caller resumed and wrote the notice, the trailing read started a microtask later, and its prologue erased the notice before anything rendered. The old uncoalesced code started that read at once, so its prologue ran BEFORE the notice was written. Every test was green, because none fired a trigger during the refetch, and the source pin on `await fetchItems()` → `error = …` still matched.
**Lesson**: When a reader starts coalescing, decide what an awaited promise means. If a caller awaits a read in order to write state the read's prologue resets (`error`, a selection, a notice), the promise must settle when the whole chain drains — the run plus every rerun queued while it ran — not when the caller's own run ends; cap the chain so a trigger storm cannot stall the caller. Pin it with a test that fires a trigger DURING the awaited read, for both shapes: the caller that starts the chain and the caller that joins one already running (a mutant on the join path survived the first test alone). The durable fix for the class is still #2377's: a verb outcome does not belong in the field a read clears.
