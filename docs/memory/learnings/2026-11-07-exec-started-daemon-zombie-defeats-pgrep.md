## 2026-11-07 — pitfall — a daemon started by `docker exec` and later killed stays a zombie, and `pgrep -x <name>` matches it

**Context**: trinity-enterprise#1168 — the SSH grant starts sshd on demand (`pgrep -x sshd || /usr/sbin/sshd`, root exec) and the boot sweep stops idle listeners (`pkill -x sshd`). Verified live in `trinity-agent-base`: after the kill, `[sshd] <defunct>` stays in the process table because the container's PID 1 (`bash startup.sh` blocked on `tail -f /dev/null`, and equally a bare `sleep`) never reaps a child it adopted from a finished exec. The next grant's `pgrep -x sshd` matched the zombie, skipped the start, and the response advertised a port nothing listened on. `services/ssh_service.py::SSHD_START_CMD`.

**Lesson**: inside an agent container, "is <daemon> running?" must exclude zombies — `pgrep -x --runstates RSD <name>` (procps-ng ≥ 3.3.16; bookworm ships 4.0.2), or test the resource the daemon owns (the listening socket, a fresh pid-file whose pid is not `Z`), never a bare `pgrep`/`pidof`. Any idempotent "start if not running" exec that pairs with a "stop" exec on the same process has this shape, and a test double (`SimpleNamespace(exit_code=0)`) cannot show it — it needs the real image. Pin the flag in the unit test so a simplification does not quietly drop it.
