## 2026-10-09 — pitfall — A rate limit that counts side-effect rows becomes an oracle once the side effect is suppressed for some callers
**Context**: `routers/public.py` `/verify/request` (abilityai/trinity-enterprise#849). The per-address 429 counts `public_link_verifications` rows. When the login policy stopped minting codes for members, members never produced rows, so the 4th request returned 429 for an outsider and 200 for a member. The same review found the Slack `require_email` flow outside an AST caller guard because it rolled its own code instead of calling the named helpers.
**Lesson**: When a change suppresses a side effect for a subset of callers to hide which subset they are in, every counter derived from that side effect must count the request instead (`rate_limiter.check` keyed on the input), or the limit leaks the subset. A caller guard keyed on helper names also needs the delivery call (`send_verification_code`) in its set, so hand-rolled variants of the flow are caught.
