## 2026-10-07 — pitfall — A permanent artifact classified by a row that retention deletes reverts once the row is pruned
**Context**: trinity#2372, `operator_queue_service._sync_agent` reserved-prefix guard. Agent files written before ent#499 still carry platform alerts as `responded` entries, and nothing ever removes them. The obvious way to stop the #1631 impersonation WARNING was "skip quietly when the platform holds a row with this id for this agent". That works until the retention sweep deletes the row. From then on the same leftover entry is "unknown" again and the WARNING returns on every boot, permanently.
**Lesson**: When an artifact outlives the DB (a file entry in an agent workspace, a cached copy, a webhook replay), classify it by fields it carries itself. Do not classify it by whether a row that some retention policy can delete still exists. Here the entry's own `status` is enough: only a `pending` entry can pre-create a row, so only a `pending` reserved-prefix entry is impersonation. Test the classifier with the row absent. A fixture that has the row cannot show the regression.
