## 2026-10-29 — pattern — A heavy lazy singleton is warmed in the background, never built on a request
**Context**: trinity-enterprise#1022 retrieval memory. The embedding model (≈590 MB RSS, ~1 s to load) was built lazily by `memory_embeddings.availability()`, and the Settings status route called that inside an `async def` handler — so the first flip of the platform switch would have frozen a uvicorn worker for the whole load, on the request the operator was watching. Same class as #1927's "loading means no data yet": the heavy work was reachable from the request path because the accessor that *reports* on the resource also *constructed* it.
**Lesson**: separate "is it ready / why not" from "make it ready". A status read returns `is_loaded()` / `last_error()` and, when the feature is on and nothing is loaded, kicks a daemon-thread `warm()` and says "loading"; the only callers that may block on the build run on a worker thread (`asyncio.to_thread`) and are never a request handler. Boot warms it only when the feature is on, so an install that never turns it on pays nothing. Pin it with a test that patches the synchronous builder to raise and asserts the status call still answers.
