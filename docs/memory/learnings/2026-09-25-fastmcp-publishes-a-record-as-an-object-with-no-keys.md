## 2026-09-25 — pitfall — FastMCP publishes a `z.record` parameter as an object that accepts no keys

**Context**: trinity-enterprise#611 PR B, the `ask_operator` MCP tool. Its `context` and `proposal` were `z.record(z.string(), z.unknown())`, and the live `tools/list` published them as `{"type":"object","propertyNames":…,"additionalProperties":false}`: an object that may hold no keys at all. The cause is `fastmcp`, which passes every tool's schema through xsschema's `strictJsonSchema`. That walker stamps `additionalProperties: false` on each property whose schema has `type: "object"`, a record included; it does not descend into `anyOf`. The converter itself (`toJsonSchema`) was correct. The same shape already ships as `emit_event.payload` and `deploy_local_agent.files`. Claude Code sends the arguments anyway, but a model may obey the schema and send `{}`, and a client that validates the schema rejects real arguments.
**Lesson**: Check a tool's PUBLISHED schema, not its zod: read `client.listTools()` over the real transport and assert on the property schema. For a free-form object parameter, declare `z.union([z.record(z.string(), z.unknown()), z.null()])` — the walker leaves an `anyOf` alone, so the record keeps `additionalProperties: {}`, and the backend treats `null` as absent — until the platform stops the walker from treating records as closed objects.
