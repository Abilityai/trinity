## 2026-09-30 — pitfall — `download-artifact` with a `pattern` flattens a lone match, so per-artifact paths vanish when one PR is open
**Context**: #3103 / PR #3111. Both nightly comment jobs moved from `merge-multiple: true` into the workspace root to `path: <dir>` with per-artifact subdirectories, so a forged artifact could not overwrite the trusted verdict module. `actions/download-artifact` (`src/download-artifact.ts`) picks the destination as `isSingleArtifactDownload || mergeMultiple || artifacts.length === 1 ? resolvedPath : path.join(resolvedPath, artifact.name)`. With one open PR (or a scoped dispatch) the integration nightly has exactly one artifact, the named directory never exists, and a reader built on `<dir>/<artifact-name>/` finds nothing and posts nothing, with no error.
**Lesson**: A `pattern` download's layout depends on how many artifacts matched at run time. Code that reads `<path>/<artifact-name>/…` must fall back to `<path>` when that directory is absent (safe: the root holds files only when a single artifact matched), or download each artifact by `name`. Test the reader against both layouts; a test run with three or more PRs or seeds never produces the flat one.
