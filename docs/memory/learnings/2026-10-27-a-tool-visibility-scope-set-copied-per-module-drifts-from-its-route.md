## 2026-10-27 — pitfall — A tool-visibility scope set copied into each tool module stops matching its route when the route's rule changes
**Context**: trinity-enterprise#719, which lists each human-only MCP tool to the keys its route admits. #3435 gave three credential tools a `canAccess` of `{user, system}` written in `tools/agents.ts`; ent#966 copied the same set into `tools/nevermined.ts`, where `revoke_agent_delegation`'s `require_person` route already refused the system key the tool was listed to. Two other tools that front person-only routes, `respond_to_operator_queue` (since trinity-enterprise#611) and `close_room` (once its moderator rule asks for a person), had no `canAccess` at all, so they took their group's default: every operator key, agent and system included. No test could catch either: the harness issued only `user` and `agent` keys, and nothing crossed the person-gated routes with the tools that call them. The mirrored-constant class of 2026-07-16, inside one package.
**Lesson**: derive a human-only tool's `canAccess` from the backend rule its route takes, through the one predicate in `access.ts` (`humanOnlyToolAccess(rule)`), never from a scope set written in the tool module, and give its description the rule's keys sentence (`HUMAN_ONLY_KEYS_NOT_SHOWN`, inside `HUMAN_ONLY_WHO_MAY_CALL` for an agent-owner tool). Find the tools by route, not by name: cross every person and signed-in-session gate in the backend with the MCP client's request paths, because a tool with no `canAccess` inherits its whole group. Pin the listing over the real transport for every key scope, `system` included.
