## 2026-10-30 — pitfall — An agent door that also admits human principals hands every shared-with user the agent's own reach
**Context**: trinity-enterprise#1028 (PR #4114). The memory search agent door (`POST …/retrieval-memory/search`) derives its scope from the execution the caller names — the served person's scope on a person turn — and gated on `assert_own_agent` + `assert_agent_access`. The self-fence is right for an agent key, but `assert_agent_access` also admits any human the agent is shared with, so such a user could name another person's run and read that person's facts: exactly the read the owner door (`GET …`, `OwnedAgentByName` + `require_person`) refuses them. It mirrored the MEM-001 `write_user_memory` door, which has the same shape.
**Lesson**: A route that resolves its scope *from a resource the caller names* (an execution id, a session id) is built for the principal that owns that resource at run time — the agent. Gate it on the agent's own key (`if not current_user.agent_name: 403 agent_only`, the `aauth_agent_only` shape) and send humans to the door that takes the scope explicitly and carries the owner line. "Same gate as the sibling door" is not a safety argument when the sibling is a write: a write creates something the owner can see and undo, a read discloses. Check the reverse of ent#629 too — not only what an agent key reaches through human gates, but what a human reaches through an agent door.
