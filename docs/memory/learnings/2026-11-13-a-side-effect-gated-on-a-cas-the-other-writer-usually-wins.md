## 2026-11-13 — pitfall — A side effect gated on winning a status CAS is lost whenever the other writer is usually faster

**Context**: trinity#4475. The `execution_terminate` audit row (#3180) fired only when the terminate request won the CANCELLED compare-and-swap. The agent's terminate route waits up to 7 s for the process to exit before it answers, and the synchronous `/task` / `/chat` caller that started the turn sees the exit first and writes the terminal row. So on a real instance the terminate lost the CAS nearly every time and wrote no audit row, although its kill ended the work. Unit tests passed because the fake agent answered instantly and nothing else wrote the row. The parked arm had the same shape: the dispatcher reads the cancel key and writes CANCELLED itself.

**Lesson**: A CAS decides which writer's *status* stands. It does not say which request *caused* the outcome. Before gating a side effect (an audit row, a notification) on `cas_won`, check which writer reaches the CAS first in production, not in the unit harness. If the cause can lose the race, gate the side effect on the cause's own evidence (here: the agent answered `terminated` for this request), and dedupe repeats with a first-claim keyed on an id the cause verified. Do not key the claim on a caller-supplied id. Add a test that runs the competing writer before the CAS (wrap the CAS writer), because a harness where nothing else writes the row cannot see this class.
