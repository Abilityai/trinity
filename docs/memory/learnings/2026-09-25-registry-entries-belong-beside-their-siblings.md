## 2026-09-25 — pitfall — `tests/registry.json` conflicts at its tail on every merge, and splicing the conflict hunk can split an entry

**Context**: trinity-enterprise#611 PR A (#3023) conflicted with `dev` three times in one day, each time only at the end of `tests/registry.json`, because every PR appends its entries after the last one. On the third conflict, dev had also rewritten the description of the last entry both sides shared. Git's hunk therefore began in the middle of that entry, and keeping our side of the hunk carried the old description line along as a bogus `{"description": …}` entry. The JSON still parsed, and only a check that every entry has a `file` key caught it.
**Lesson**: Nothing orders the registry (no test sorts it or requires appending), so put a new entry next to its siblings — the same feature or the same area — rather than at the tail; dev's appends then merge without a conflict. When a conflict does happen, rebuild the file from `git show origin/dev:tests/registry.json`, then apply the PR's changes as whole entry blocks: new entries inserted, edited entries replaced only if dev left them alone. Assert that every entry has a `file` key and that the diff against dev is additive, apart from the edits you intended. Never re-serialise the JSON.
