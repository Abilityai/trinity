## 2026-09-25 — pitfall — `cleared_at` is the operator's list hygiene; a reader of terminal queue rows for anyone else must opt out of it

**Context**: trinity-enterprise#611 review. The Workspace ask list (`client_portal/asks/service.py::list_asks`) began carrying asks that ENDED in the last 7 days through `db.list_operator_queue_items`, whose default `include_cleared=False` was harmless while the list held pending rows only (Clear All never stamps a pending row). Once it held terminal rows, an operator's Clear All on the Resolved tab made a client's cancelled ask vanish from the Workspace inside the window — the exact "an ask that simply vanishes reads as answered" defect PortalAsks' own comment forbids. The same PR had already exempted the agent's readback (`get_item_for_agent_by_request_id` ignores `cleared_at`) and missed its second non-operator reader.
**Lesson**: When a query that used to return only open rows starts returning terminal ones, re-read every default filter it inherits and ask whose view each one encodes. `cleared_at` hides a row from the OPERATOR's list and nothing else: any reader serving the filer, the addressee, an inbox or a ledger passes `include_cleared=True` (and pins it with a Clear-All-then-read test). The Inbox (#610) and PR B's receipts are the next readers of these rows.
