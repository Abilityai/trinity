## 2026-10-20 — pattern — Keep rows out of every prompt by making exclusion the shared read's default, and mark the row rather than joining to the verdict's table
**Context**: trinity#3402. A held gated request had to stay out of every prompt builder on five stores, with about a dozen readers between them. First draft: each prompt builder filters (opt-in), and the Workspace joins `skill_gate_requests` on every read. Review found three problems. A forgotten opt-in is a silent replay. The join's `NOT IN` was UNKNOWN once any gate record had a NULL origin (the common case), which would have wiped a cursor. And the join broke the six existing test files whose partial schema had no gate table.
**Lesson**: When a security filter must cover every prompt read of a store, put it in the store's read function as the DEFAULT (`include_held=False`), and have the readers a PERSON sees opt in. A forgotten opt-in is a visible UI bug; a forgotten exclusion is a silent leak, and a future prompt builder gets the safe answer without knowing the rule exists. Classify the row by a column it carries itself, written when the verdict is known, and backfill existing rows ONCE in the migration from the exact record (a join on the turn id, never a guess from the text). Then the read is `col IS NULL`: no per-read subquery, no NULL trap, no cross-table dependency for every harness that builds a partial schema. Before relying on a predicate over a nullable column, ask what `NOT IN` does when the set holds a NULL.
