## 2026-10-10 — pitfall — A `system_settings` row that a human-only route writes is also writable and deletable through `/api/settings/{key}`
**Context**: PR #3516 (trinity-enterprise#709). Only the human-only, re-authenticated `PUT /api/users/me/password` writes `admin_password_source = ui`, and that row stops boot from re-syncing the admin hash to `ADMIN_PASSWORD`. The generic `DELETE /api/settings/{key}` is admin-gated but not human-only, so an admin's user-scoped MCP key could delete the row. The next restart then reverted the rotated password to the `.env` value. This is the #2380 install-provenance shape again, and the seventh time the catch-all has been a way around a gated write path (#506, #1609, ent#12, #1644, ent#14, ent#346).
**Lesson**: When a new settings key is written by a gated or human-only route, block it on the generic `PUT` and the generic `DELETE` in `routers/settings/generic.py` in the same PR. Block the DELETE too whenever removing the row loosens a rule, rather than re-arming a guard. Add a test that calls the generic handlers on the new key.
