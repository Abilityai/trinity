## 2026-10-02 — pitfall — The agent page's chat is the Workspace turn, not `/chat` or `/task`
**Context**: trinity-enterprise#751. The plan, the tests and the eyeball guide all treated a person's chat as `/chat` or `/task`, where the requester is proven, so an approver runs their own gated request. On localhost the agent page's chat ran through `client_portal.service.portal_chat`. That turn stamps `source_channel=portal` and `triggered_by=public` and reaches the agent through the `execute_task` backstop, so the gate classed the owner as an anonymous channel user. The Workspace then rendered the waiting request as a Failed turn, and the approved run's reply was skipped as "answered inline". 1,900 green unit tests missed this; the first manual eyeball step found it.
**Lesson**: Before gating or changing a dispatch path, trace which route each UI surface actually calls today. The Workspace (`/api/enterprise/client-portal/agents/{name}/chat[/stream]`) is the main chat, and `/task` is now mostly API, MCP and agent traffic. A Workspace turn carries a verified person (`PortalPrincipal.is_person`). It renders every non-retryable error as Failed, so a "not yet" state must be a reply, not an error. And `public` is an inline trigger for the completion report, so anything that runs later under that trigger must say so.
