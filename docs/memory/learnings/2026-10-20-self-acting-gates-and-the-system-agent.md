## 2026-10-20 — pitfall — A self-acting gate written as `scope == "agent"` locks out the system agent, and enabling a flag for it fails silently
**Context**: #3814. `heartbeat_service.authorize_heartbeat` (the gate for the heartbeat, the #1083 callback and both pull seams) required `scope == "agent"`. `trinity-system`'s key is `scope == "system"` and bound to its own name, so listing it in `PULL_MODE_PILOT_AGENTS` started a worker pool whose every poll got 403, while the backend routed its turns to the queue. The only signal was canary B-08 `workers_silent`. This is the backend twin of #2975 (MCP self-acting tools), found a second time.
**Lesson**: (1) For any "an agent may act only on itself" gate, test with the system agent's key as well as an agent key. The rule is "the credential's bound name equals the target", with the scope allowlisted (`agent`, and `system` for the system agent's own name only). Take the name from the key row, never from a parameter. (2) A per-agent feature flag that the system agent can be given also needs the system agent's env exceptions revisited. Here #1816 deliberately withheld `TRINITY_BACKEND_URL`, and the pull worker cannot start without it. Check every `is_system_agent_name` carve-out on the env path when a flag can name the system agent. (3) A running system agent is never recreated (#1816 AC2), so any flag that changes its container env needs a boot-time report for the state where the flag is on and the running container predates it.
