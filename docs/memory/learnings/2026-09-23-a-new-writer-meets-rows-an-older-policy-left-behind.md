## 2026-09-23 — pitfall — A new state writer meets data an older policy left behind, and flip-flops on it every cycle
**Context**: trinity#2915, `_write_responses_to_agent`. The new delivery tracking classified any `responded` row whose entry was present in the agent's file as `delivered`, and every platform-minted row as `not_applicable`. Both were right on their own; together they oscillated: files written before ent#499 still carry platform alarms as `responded` entries (the old write-back reconstructed them), so the same row matched both rules and flipped `delivered ↔ not_applicable` every 5 s, minting a `written_back` audit row each time on the immutable, 365-day-floored audit table. It was caught only because the first live cycle was watched; every unit test used fresh fixtures that no older policy had touched.
**Lesson**: (1) When a loop gains a classifier, its inputs include everything an OLDER policy wrote — entries, rows, files — not just what the current policy produces; build one fixture from real historical data (here: a pre-ent#499 file carrying a platform alarm) before calling the classifier complete. (2) Two classification rules that can both match one row need an explicit precedence written as code, not an ordering accident in a loop; the exclusion (`is_platform_minted` rows take no part in delivery) belongs where the maps are built. (3) An audit row per transition is only safe when the transition is monotone or rare — test "run the cycle twice on the same input and assert zero new writes" for every new edge-triggered writer.
