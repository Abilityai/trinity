## 2026-11-18 — pitfall — A module first imported inside `patch.dict(sys.modules, {"database": stub})` keeps the stub as its `db` for the rest of the session
**Context**: #4635, `tests/unit/test_4257_queue_stall_monitor.py`. `_run` stubbed `sys.modules["database"]`, then `patch("services.settings_service.…")` imported `settings_service` for the first time inside that block, so its module-level `from database import db` bound the stub. A later test that patched `settings_service.db` patched the stale stub, while the function under test read the real `database.db` at call time — green alone, red whenever the stub test ran first. Same family as 2026-10-05 (a re-import inside `patch.dict` rebinds the parent package attribute).
**Lesson**: a test that stubs `database` in `sys.modules` imports every module it will patch or call BEFORE entering the stub (one `_import_real_modules()` helper at the top of the driver). A test that patches the facade patches `database.db` — the object production code reads at call time — never a module's alias of it.
