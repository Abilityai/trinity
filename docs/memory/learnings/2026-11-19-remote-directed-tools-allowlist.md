## 2026-11-19 — pitfall — a gate over tool names that lists the dangerous ones is a denylist, and tool results are an outbound channel
**Context**: review of `feature/pro-assistant` (abilityai/trinity-enterprise#1283). A module that runs tools at a remote service's direction gated "needs the person's click" on a list of destructive-sounding prefixes (`delete_`, `remove_`, …) over the caller's full MCP reach. Every write not on the list ran unconfirmed, and a new tool would too. Separately, redaction was applied to what the person typed but not to what tools returned, so a file read or a log left the instance verbatim.
**Lesson**: the same shape as #848 (tool visibility) and #2323 (admin gate scopes): enumerate what MAY run unattended (reads), default everything else to the stricter path, and treat an unknown name as the stricter case. When output is consumed by a model, every tool result is both an exfiltration channel and an injection channel: scrub results on the way out with the same rule as input, and refuse credential files by path rather than hoping redaction catches their contents. Also from this review: a `get_or_create_*` accessor reached from a GET mints identity as a side effect of looking; `test_2669_minting_accessor_callers.py` catches it only if the pinned guards are run, which a per-file test run does not do.
