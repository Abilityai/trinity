## 2026-10-29 — pitfall — Every path that consumes a "did it change?" signal must run the effect gated on it
**Context**: PR #4091 review (trinity-enterprise#529). The fleet re-inject runs only when a sync reports `commit_changed`, judged against the source's recorded `last_commit_sha`. `POST /api/skills/library/sync` and the scheduled cycle spawned the re-inject; the per-source `POST /api/skills/sources/{id}/sync` recorded the new commit but did not. Its sync spent the signal, so the next full or scheduled sync compared against the new commit, saw no change, and running agents kept the old tag's skills until they restarted. A user doc even told admins to avoid that button, and the new boot follow made it the most likely click.
**Lesson**: When an effect is gated on "did X change since we last recorded it", list every writer of the recorded value (`grep record_skill_source_sync`), not only the path the feature was built on. Each one either runs the effect or does not advance the record. Put the effect in one helper all of them call (`_start_fleet_reinject_if_moved`), and test it through each route. A warning in the docs is not a fix.
