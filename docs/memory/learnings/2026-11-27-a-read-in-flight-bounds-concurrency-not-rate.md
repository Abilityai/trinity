## 2026-11-27 — pitfall — "One read in flight, one queued" bounds how many reads run at once, not how often
**Context**: #4813, found in the pre-landing review. The Executions store was changed to refetch on every `chat_start` activity instead of two event types nothing sent. Its existing guard queues one refresh behind the read in flight, and both the PR and its security report read that as "a burst cannot multiply requests". It only serialises: under a steady stream the queued refresh starts the moment the last one lands, so the rate is one refresh per round trip. Each refresh also calls `GET /api/executions/stats`, a single scan over the whole `schedule_executions` table (90-day default retention) that the list guard does not cover, so those calls could overlap. Every run sends two such events and an admin's socket carries the whole fleet's. The sibling stores (`portalWork.js`, `portalRailFeeds.js`) already pace push-driven refreshes with `PUSH_DEBOUNCE_MS`; this store had no pacing because its old trigger never fired.
**Lesson**: When a socket event becomes a refetch trigger, or an existing trigger starts matching a far more frequent event, answer three things from the code before shipping: how many events one unit of work sends and who receives them; what every request in the refresh costs on the backend (read the query, not the route name); and what bounds the rate, as distinct from the concurrency. Give a push-driven refresh a time bound (a throttle or the store family's debounce) and test it with fake timers: a burst, the edge of the window, and a refresh still owed when the surface closes.
