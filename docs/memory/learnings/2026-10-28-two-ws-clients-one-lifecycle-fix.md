## 2026-10-28 — pitfall — The SPA holds two `/ws` connections; a socket-lifecycle fix applied to one leaves the other
**Context**: #3445 (PR #4069). The first cut made the app-wide socket (`utils/websocket.js`, opened from `App.vue`) follow `authStore.token`: it closes when the session ends and reopens with a fresh ticket for a new one, because the server fixes a socket's scope at connect (ent#467). The Dashboard opens a second, separate socket (`stores/network.js::connectWebSocket`, `Dashboard.vue` mount → unmount). It read the token only when it connected or reconnected. A Dashboard left mounted across a session that ended in another tab therefore kept the earlier principal's scope, including after someone else signed in. The /review of the PR caught it, and the same PR now makes both sockets follow the session through one rule (`utils/socketSession.js::socketActionFor`).
**Lesson**: Any change to how a `/ws` connection is opened, scoped, closed or re-ticketed must name both clients (`utils/websocket.js` and `stores/network.js`), and either cover both or say why one is exempt. Before planning, grep `new WebSocket(` under `src/frontend/src`: the other hits are the voice and terminal sockets, which are separate endpoints. Retiring the Dashboard's second socket would remove the class.
