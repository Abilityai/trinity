## 2026-10-28 — pitfall — A refusal's remedy is an instruction to the calling model; never offer to widen a permission when a heuristic triggered it
**Context**: #3949 (PR #4070). The abilityai/trinity-enterprise#662 peer check reuses the skill gate's match-anywhere matcher, so a peer that only *mentions* `/<library-skill>` is refused 403 `skill_not_granted`. The refusal ended "An instance admin can grant it in `<caller>`'s Permissions panel". MCP `chat_with_agent` / `fan_out` hand `message` to the caller model as the tool result, and the delegation contract published into those tools says "On `retryable: false`, do what it says". So the remedy for a string match in prose was to widen a standing permission. Admins get the same wrong remedy from the drift report (`peer_skill_policy._recent_uses`). It runs the same matcher over `recent_peer_messages`, which has no status filter, so a mention counts as a "use", including a fan-out row the peer check itself refused. Each such mention gets a **Grant** button in Settings → Agents.
**Lesson**: Treat every refusal string that reaches a model as an instruction, not a log line. When a refusal can be triggered by a heuristic (a text matcher, a classifier) rather than by the caller's real action, its remedy must cover the false-positive case first (how to rephrase or resend) and must not point at granting or widening authority. Keep grant advice for refusals of a real action, such as calling a capability endpoint. Pin the text with an exact-match test (singular and plural), plus no slashed skill names in anything echoed into rows or replies.
