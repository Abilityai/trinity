## 2026-11-01 — pitfall — A liveness gate on an id the model types turns a stale copy into a lost write
**Context**: #4121. `write_user_memory` and `search_memory` gained "the named run must be `running`" (the ent#926 rule), and both still sent the model-typed `execution_id`, while the effect-guarded tools (`send_message`, `share_file`, `send_voice_reply`) go through `resolveExecutionId`, where the platform's `X-Trinity-Execution-Id` header wins. A resumed session cites ids from its own history (`turn_audience.py` records one 22 minutes old, seen live), and that used to be harmless on the write door: a stale id of the same person resolved to the same notes. The gate made it a refusal, so the fix for a security hole would have lost real notes on a live turn. Every test passed, because every test named the right id. An independent plan review found it; the code review would not have, since nothing in the diff looked wrong.
**Lesson**: When a door starts refusing on the STATE of a row the caller names, follow the id back to where it was typed before writing the check. A typed id that was merely imprecise before the gate becomes a wrong-answer path after it. The fix belongs at the edge that knows the real value, and the test must send a stale typed id beside a live header. It also closed an accident the rule alone leaves open: an interactive Claude Code or Gemini session's header is `manual`, so a web terminal can no longer write through whoever's turn happens to be live with this tool. Sibling of the "a read census must follow every exit of the row" class: a rule on a row is only as good as the path that picks the row.
