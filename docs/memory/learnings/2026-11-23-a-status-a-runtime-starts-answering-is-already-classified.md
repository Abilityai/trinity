## 2026-11-23 — pitfall — A status code a runtime starts answering is already classified by every caller under its old meaning
**Context**: trinity-enterprise#1176. Claude Code agents began refusing restricted turns before the CLI starts, as Gemini and Codex already did: 403 with a typed `turn_refused` body, and a 503 for "the platform could not be asked". Both statuses already meant something on every caller. `execution_classification.classify_switch_failure` mapped ANY 403 to `auth`, so both push paths (`task_execution_service`, `chat_execution_service`) would have walked the agent's subscriptions over a refusal, recording an auth refusal against every seat and re-sending the refused turn on each; a 503 was `auth` on the sync path, in `result_callback._STATUS_MAP` and in `pull_worker._PULL_STATUS_MAP`; and the public status read matched refusals by their WORDING (`public_chat_service._TURN_REFUSED_MARKERS`), so a new sentence read as a generic failure. None of it showed on the existing runtimes, because a subscription-less runtime walks nothing.
**Lesson**: Before a new producer answers an existing status, grep every consumer of that status on every path (sync, async callback, pull, the public reads) and read what each one does with it today; a classifier keyed on the status alone will apply the old meaning to the new producer. Give the new answer a typed body and make the classifier read the type first, keep a "could not ask" answer off any status a consumer treats as a credential failure (here 502, not 503), and pin every new sentence against any text matcher (`is_auth_failure`, refusal markers) with a test that drives the real push path with a subscription in the pool.
