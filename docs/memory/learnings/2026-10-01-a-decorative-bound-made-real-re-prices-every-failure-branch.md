## 2026-10-01 — pitfall — A decorative bound made real re-prices every caller's failure branch
**Context**: trinity#2969. `docker_service.execute_command_in_container` accepted `timeout` and forwarded it nowhere (docker-py's `exec_run` has none), so one hung exec pinned a thread of the 4-thread `_docker_executor` fleet-wide; three callers had each grown their own `timeout N` prefix + `asyncio.wait_for` workaround and three docs described the hole. Enforcing it inside the primitive (in-container `timeout -k 5 N` + `asyncio.wait_for(N+10)`, explicit `timed_out` flag) then surfaced a second defect the decorative bound had been hiding: `initialize_git_in_container`'s 60s per-step bound was never real, so a slow `git fetch origin` of a large existing remote now got killed, `rev-parse origin/main` failed, and init fell into the empty-remote branch — `git push -u origin main --force` over the remote's history.
**Lesson**: (1) A parameter the primitive accepts and ignores is a hole every caller works around separately and every doc describes; fix the primitive, then delete the workarounds and grep the docs for the claim (`not forwarded`, `decorative`), because the stale sentence outlives the code. (2) When a bound that was decorative becomes enforced, audit every call site's failure branch: timeouts that never fired now fire, and a caller that cannot tell "timed out" from "legitimately failed" may take a destructive branch (empty-remote force-push, retire-on-absence). Give the result an explicit `timed_out` flag, make the destructive paths check it first, and re-size the limits for the real work (60s → `GIT_INIT_STEP_TIMEOUT_S = 600` for a first fetch / `add .` / push of a whole workspace). (3) Refuse `timeout <= 0` at the primitive — GNU `timeout 0` means "no timeout", so a zero would silently reinstate the unbounded exec.
