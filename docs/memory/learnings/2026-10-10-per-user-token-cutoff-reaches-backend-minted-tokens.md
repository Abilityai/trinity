## 2026-10-10 — pitfall — A per-user token cutoff also reaches every backend-minted token that carries that user's `sub`
**Context**: PR #3516 (trinity-enterprise#709). The password change wrote `auth:sessions_revoked_before:{username}` and `is_user_session_revoked` treats a token with no `iat` as "issued before the cutoff". The EVT-001 event-loopback token (`event_dispatch_service._get_internal_token`) is minted per dispatch with `sub` = the provisioned admin and no `iat`, so after any admin password change every event-subscription dispatch got a 401 for the cutoff's whole TTL (7 days). All 35 of the PR's tests were green, because none of them minted a token the backend makes for itself.
**Lesson**: Before you add a rule keyed on `sub` to `get_current_user` or `decode_token`, list every `jwt.encode` / `create_access_token` caller (`grep -rn "jwt.encode(\|create_access_token(" src/backend`). Decide for each one whether the rule applies to it. Write a test that mints the token the real way and passes it through the rule. "Fail closed on a missing claim" is right for sessions, but it silently kills machine tokens that never carried the claim.
