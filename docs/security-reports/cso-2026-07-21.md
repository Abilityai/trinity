## Verification — 7 axes, all REFUTED with proof lines

A fresh-context adversarial auditor tried to break each and could not:

1. **Default-safe posture** — flag off ⇒ backend router 404s before any handler (`mcp_auth.py:76`); mcp-server mints no anon sentinel (`server.ts:258`), connector tools stay `connectorOnly`, auth group empty. No account, email, or session reachable.
2. **Internal-secret authz** — `assert_email_may_reach_agent` runs before the idempotency claim and before dispatch on `/chat`; agent/email used identically in gate, scope and dispatch (no normalization split). Holding the secret grants nothing beyond what all of `/api/internal/*` already grants.
3. **Cross-user replay** — `make_inline_auth_scope(agent, email)` folds the normalized email in; gate precedes the replay return, so a caller who lost access can't replay even their own snapshot.
4. **Enumeration / relay** — request path does only normalize → global cap → `add_task`; all branch-dependent work runs in a Starlette BackgroundTask after the 202 flushes. Constant body, no audit row, `_email_is_known` fail-closed, code only ever mailed to an already-known address.
5. **Anonymous → operator tools** — allow-list gate over `{user,agent,system}`; `canAccess` is enforced at **`tools/call`** in `fastmcp@4.4.0` (`MethodNotFound` for filtered-out tools), not just advertisement. The prior fail-open (#846 dynamic tools on the deny-check) is closed (`operatorOnly`).
6. **`verify_login` disclosure** — one uniform `INVALID_CODE_RESPONSE`; upstream status codes / env-var names / stack traces swallowed. Wrong-code, unknown-email and upstream-error indistinguishable.
7. **Audit integrity** — `actor_email` is a resolver fallback (`resolved_email or actor_email`); forging it needs the internal secret, which already permits arbitrary audit writes.

## Accepted-risk notes (not findings)

**N1 — `INTERNAL_API_SECRET` widened to act as any verified email.** The mechanism option A requires. Grants no privilege beyond internal-secret compromise (already backend god-mode over `/api/internal/*`), gated behind the flag (default off) and the secret (network-internal). *Recommendation:* set `INTERNAL_API_SECRET` explicitly in production rather than relying on the pre-existing `→ SECRET_KEY` fallback, now that this surface exists.

**N2 — inline `/verify` shares the per-account login bucket.** Pre-existing property; 5 bad inline codes can 429 a known email's web login for 15 min. DoS-class, hard-excluded. No new capability.
