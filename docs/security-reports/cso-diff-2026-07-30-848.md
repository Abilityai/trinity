## Why this second pass exists

The 2026-07-21 audit covered the same auth path and found nothing above gate. This
re-run is **not** a formality, because the review since then changed the security
question in a specific way:

> The prior report's "axis-1 default-safe posture" was **unconditional rather than
> opt-in** — not by design, but because `MCP_INLINE_AUTH_ENABLED` was wired into
> **zero** compose services and therefore could never be turned on.

That blocker is fixed in this branch (all four wirings, verified through compose's
own resolution). So every gate the prior audit assessed as "correct but unreachable"
is now **actually reachable on a deploy where the operator opts in**. Re-auditing the
now-live surface is the whole point of this pass.

### The library assumption is now tested, not asserted

The prior report's finding 5 justified the allow-list by citing `fastmcp@4.4.0`
internals. That citation was wrong twice over — wrong **version** (the lock resolved
4.8.0 at review time, 4.12.1 now; 4.4.0 was a stale local `node_modules`) and wrong
**mechanism** (`canAccess` is never re-invoked per call; enforcement is by absence
from the `toolsMap` built from the filtered list). Both load-bearing behaviours were
re-verified on the installed 4.12.1 and **the conclusion is unchanged** — the
falsy-auth filter-skip is still present, so the hardening is warranted.

The durable change is that the assumption is now pinned by a **behavioural** test
that boots a real FastMCP server and drives it with a real MCP client, asserting a
filtered-out tool is rejected on call **and that its body never executes**. That
survives chunk renames; a prose citation does not, which is exactly how it rotted
twice. The dated report was corrected in place with a post-audit note rather than
silently edited.

## Informational

**N1 — `INTERNAL_API_SECRET` can act as any verified email.** Carried forward from
the prior audit, unchanged and still accepted: it is the mechanism the
session-not-a-minted-key design requires, and it grants nothing beyond what
internal-secret compromise already grants (backend god-mode over `/api/internal/*`).
Now that the surface is genuinely reachable, the operational recommendation is no
longer theoretical — it has been carried into `.env.example` (where an operator
looks when enabling the flag) and requirements §7.6: **set `INTERNAL_API_SECRET`
explicitly in production rather than relying on the `→ SECRET_KEY` fallback**, so it
gets its own rotation lifecycle instead of inheriting `SECRET_KEY`'s.

**N2 — stale docstring pointed a maintainer at a known landmine (fixed this pass).**
`routers/mcp_auth.py:98` claimed the branch-dependent work "runs off the request path
**in a worker thread**". It does not, and must not: `mcp_auth_service` documents that
an earlier `asyncio.to_thread` revision silently stopped every code send (SQLite
connections are thread-affine → `_email_is_known` raises in the worker → its own
fail-closed handler swallows it into "unknown address"), a total feature outage that
still answers 202. The router is the file a maintainer opens first, so the natural
"make these consistent" edit was to reintroduce the outage. **Not a security finding**
— the invited failure is availability, not a bypass — but it is a real defect on the
enumeration-safety contract, so it was corrected to name `BackgroundTasks` explicitly
and state why a thread is wrong.

**Out of scope, noted for completeness:** `npm audit` in `src/mcp-server` reports 4
vulnerabilities (1 high `fast-uri`, 2 moderate, 1 low), **all transitive**
(`isDirect: false`). This PR changes no dependency file, so they are pre-existing on
`dev` and belong to the repo-wide dependabot backlog (12 open alerts), not to this
branch. Noted rather than dropped because `package.json` already carries `overrides`
pinning `fast-uri` and `@hono/node-server` — the override is evidently not fully
resolving the advisory, which is worth its own look outside this PR.
